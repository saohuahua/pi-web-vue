# 验证方案与源码索引：刷新、断线和并发操作怎样排查

用户看到的故障通常是“回答少了一截”“一直显示运行中”“切回来之后草稿变了”。本篇从这些现象进入，沿调用链定位，解释具体判断分支，再给能稳定制造问题的测试步骤。测试覆盖与浏览器待验收项分别列在对应场景下。

## 1 SSE 断了，刷新还能接上吗

### 主问：用一条完整时序讲清楚恢复

> 浏览器刷新和服务端重启影响的数据不同。刷新丢的是页面内存，Node 里的会话如果还在，任务可以继续运行。重新打开页面时，先根据会话 ID 读取已保存的历史，再订阅事件流。服务端安装监听后发送业务握手，告诉前端当前是否流式运行，并在存在当前助手消息时补发快照，前端再接后续增量。因此恢复依赖三部分：会话身份、持久历史和仍存活的运行实例。它能恢复已有记录及当前消息，但不是逐条重播断线期间的事件，也不能保证 Node 重启后接着原来的工具调用继续执行。

```text
页面刷新       浏览器内存清空               服务端任务可能继续
打开原会话     查询历史并写入列表           已落盘消息恢复
订阅 SSE       安装监听并发送握手           前端获知是否正在流式运行
补发快照       替换当前助手草稿             恢复仍存在的当前消息
接收 delta     在快照基础上继续组装         后续实时输出恢复
```

**为什么不是绝对无损：** 历史查询与事件订阅不是同一个原子快照。历史读完后、监听安装前，任务可能结束；此时详情里没有最终消息，连接又没有运行快照。当前打开流程没有统一的“订阅就绪后再对账”协议，不能保证这个窗口里也自动补齐。

### 核心处理：恢复消息内容和恢复运行状态分开

浏览器重新打开会话时，历史查询写入 `messages` 和 `entryIds`；服务端事件流则读取当前会话的 `streamingMessage`，把它作为 `message_start` 发给浏览器。前端收到的是当前消息快照，而不是从头重新执行 prompt。

下面是事件流建立过程的顺序示意，省去缓冲过滤和资源清理细节：

```text
等待会话实例就绪
注册实例销毁监听
注册业务事件监听 并暂存握手前事件
读取当前 streamingMessage
发送 connected 和 isStreaming
转发未被快照覆盖的缓冲事件
存在快照时发送 message_start
切换为实时转发
```

先安装监听再读取快照，是为了让接入过程发生的新事件进入可处理范围；先发握手，是为了让浏览器先知道运行状态，再应用后续消息。服务端还会过滤它判断已包含在快照里的部分事件，避免重复应用。但当前过滤依赖消息对象与事件形态，没有持久序号，不能代替跨断线的通用回放协议。

前端先检查当前是否仍处于运行阶段；已经落定时，忽略迟到的流式消息。仍在运行且收到的是助手快照，就标记 Agent 活跃，并用这份快照替换正在显示的助手草稿，随后再应用新来的增量。

运行阶段检查阻止任务已落定后迟到的消息重新唤起气泡。快照替换当前流式消息，不在旧草稿后面追加整份文本；否则断线前已显示“正在检查”，重连快照又带“正在检查接口”，页面可能出现重复前缀。

### 追问：不刷新，只自动重连，任务已经结束怎么办

> 恢复处理由握手状态和旧页面保存的状态共同决定。当前工作区在握手明确表示未流式运行、且页面之前确认 Agent 活跃时，会清空流式草稿，进入落定路径，清除活跃工具和重试状态，并重读历史。这覆盖了断线期间结束、重连后不再有新事件的一个关键场景，已有 store 测试。但这个分支依赖旧页面的活跃标记，不是每次握手都对账；仍在运行时也不会补齐断线期间所有已完成消息。因此准确回答是补了终态恢复的一条路径，还没有完整事件回放和一致快照协议。

握手分两条路径处理：服务端明确表示仍在生成，就恢复运行标记并查询运行态；服务端明确表示不再生成，而且旧页面之前确认过 Agent 活跃，就清掉流式草稿，进入统一的任务落定流程。握手缺少运行字段时，不把“未知”直接当作“已经结束”。

为什么不能只把运行标记关掉就结束？界面还有活跃工具、自动重试、压缩标记和旧草稿，落定路径会统一清理这些状态，并触发历史和运行态回读。只改一个总开关，工具卡片仍可能残留执行中。

为什么必须等服务端明确返回已经结束？字段缺失表示没有拿到明确状态，不能把缺失直接解释为已经结束。第二个条件要求页面先前确认 Agent 活跃，这也解释了新页面恢复为什么不能完全复用这条终态路径。

**复现与断言：**

1. 发 `agent_start` 和工具开始事件，让页面确认运行中。
2. 模拟断线期间完成，把历史接口设为返回最终回答。
3. 只发 `connected` 且 `isStreaming: false`，不再发结束事件。
4. 断言运行标记关闭、活跃工具为空、历史含最终回答及记录 ID。

已有 [chat-races.test.ts](../../tests/app/stores/chat-races.test.ts) 覆盖此 store 路径。刷新查询与订阅之间的窗口、运行中漏掉完整消息、真实网络恢复需额外验证。

## 2 为什么不靠 Last-Event-ID 保证不丢

### 主问：SSE 重连不就能自动续传吗

> 重新建连只恢复传输通道，续传还需要事件身份和服务端补发。先检查当前服务端是否给事件编号、是否保留可重放日志、是否按客户端游标补发。本项目编码输出只有 data，没有事件 id，也没有按 Last-Event-ID 查询的应用逻辑，所以当前走历史加快照恢复，不能宣称协议已经保证补发。如果要实现，必须给会话事件分配可比较的序号，保存一段日志，重连时按最后应用的序号补齐，并在前端去重。日志过期或服务重启后还要有完整快照回退，而不是拿到一个旧序号就假设仍能恢复。

### 追问：补发时收到重复事件，怎样避免文字翻倍

> 可以在应用事件前做序号判断，而不是追加以后再比较文字。假设快照包含到序号 120 的状态，那么补发 119、120 都应忽略，从 121 开始应用。若恢复查询期间实时事件已经到达，就要缓存它们，安装带游标的快照后再按序衔接，避免快照覆盖新内容。工具开始和结束也需要同样规则，不能只给文本去重。这里的序号是服务端协议能力，当前项目还没有实现；现有会话代次主要隔离旧页面操作，不能替代同一任务内的事件序号。

### 后续方案具体怎样设计

先定义恢复需要达到的目标，再决定是否保存全部事件。如果只要求最终历史完整，任务落定后重读权威历史较直接；如果要求工具进度和流式中间状态也按顺序接续，就需要更强的事件协议。

一种可实现的协议是：

1. 服务端每次改变会话可观察状态时分配单调序号，生成事件并保留在有容量或时间上限的日志中。
2. 恢复响应把历史、当前消息和运行状态对应到同一个游标，不能分别读取后拼出不同时刻的状态。
3. 前端进入恢复状态时暂存实时事件，装入快照后，只应用游标之后的事件。
4. 已应用的序号重复到达时忽略；发现序号缺口时补拉或重新取快照。
5. 日志已过期或服务端实例换代时，明确返回需要快照恢复，避免旧游标错误地指向新实例。

例如恢复快照停在 120，实时队列是 `[119, 120, 121, 121, 122]`，只应用 121、122；若只收到 124，则不能直接认定 123 不重要。浏览器刷新后持久化旧游标但没有对应的本地快照，也不能单独拿游标继续追加，需要先恢复其依附的状态。

这套方案会增加日志容量、快照一致性、去重与过期处理成本，适合在恢复要求明确之后实施。当前项目采用历史与当前快照，还没有上述事件日志。

证据：[事件流编码](../../server/utils/event-stream.ts)、[连接管理](../../shared/lib/agent-event-connection.ts)。

## 3 心跳、握手和重试有什么区别

### 主问：服务端一直发心跳，为什么用户看不到输出

> 需要分别检查网络通道、订阅关系和任务状态。心跳只说明流还在写数据，不能证明这个流仍监听着当前执行实例。例如旧实例已销毁，但流仍定时发注释，浏览器会觉得连接活着，新的命令却可能进入另一个实例，输出自然收不到。当前服务端在实例销毁时通知事件流关闭，清理监听与心跳，让前端重新连接；发送则等待业务握手，确认会话监听已安装。定位时需要对照会话 ID、实例生命周期和事件到达顺序，而不是只看到 HTTP 200 就断言连接正常。

### 追问：重试策略具体是什么，为什么不是一直立即重试

> 当前应用层配置是握手等待 30 秒、断开后按固定 3 秒延迟重新创建连接；实际调度没有倍增算法，属于固定延迟重连。启动错误会停止自动重试，因为配置或初始化失败未必靠重连能解决。固定延迟对本机少量连接比较直接，若以后远程部署有大量客户端同时恢复，可以考虑带上限的指数退避与抖动，减少同时重试的压力。这个调整要定义恢复后的重置条件和用户主动重试入口，不能只改一个时间常量就叫完善容错。

### 核心处理：关闭旧连接与旧定时器

连接管理器先确认回调是否来自仍在使用的连接，旧连接即使迟到一个事件，也不再送进当前 store。错误回调会丢弃并关闭当前源，按配置延迟重新创建；同会话已有重试定时器时不会再安排第二个。

`shouldMaintain` 要求连接仍属于当前会话，切走后不会继续为旧会话重试。关闭时还会递增重试代次，使旧的失败回调无法再次启动重试。这些判断共同防止“切到 B 后 A 还在后台不断重连”。

服务端关闭流时清心跳定时器、解除业务事件监听、解除销毁监听和 abort 监听。资源清理与关闭控制器是配套动作，否则浏览器不再需要连接后，服务端仍可能保留订阅者或定时任务。

**已有断言：** [event-stream.test.ts](../../tests/server/utils/event-stream.test.ts) 检查实例销毁后流结束；[rpc-manager.test.ts](../../tests/server/utils/rpc-manager.test.ts) 检查订阅者在场时推迟回收。心跳间隔为 30 秒，不意味着客户端有同样时长的静默检测截止时间。

## 4 点击发送报错，为什么不能自动再发一次

### 主问：怎样区分拒绝和结果未知

> 错误处理取决于失败阶段。业务握手失败时，还没有提交 prompt，可以撤回乐观消息并保留输入；服务端明确拒绝时，按返回错误处理；但请求已经发出以后网络断开，只能说明浏览器没拿到确认。当前普通发送会提示提交结果未确认并重读历史，运行中追加也会刷新队列快照，不自动重试。这有助于核对实际状态，但没有稳定命令 ID，仍不能可靠判断某一次提交是否被接受。对可能修改文件的任务，自动重试会带来重复副作用，所以可以优先补接受状态查询与幂等契约。

### 怎样定位错误发生在哪一段

| 可观察到的事实 | 能得出的判断 | 处理方式 |
| --- | --- | --- |
| 业务握手失败，prompt 尚未发出 | 本次输入没有通过此发送路径提交 | 回滚本地气泡并保留输入 |
| prompt 返回明确的业务拒绝 | 本次命令被拒绝 | 展示原因，用户修正后再提交 |
| prompt 已发出，但浏览器收到网络错误 | 接受结果未知 | 保留输入，查询历史或运行态，不自动重发 |
| HTTP 已确认，后续出现运行错误事件 | 接纳成功后执行失败 | 展示运行失败及已有结果，不回溯成“从未发送” |

当前代码以命令异常类型区分部分业务错误和传输错误，但异常类型本身不是一份跨网络的执行证明。若要支持安全重试，命令 ID 应覆盖“客户端发起 → 服务端接纳 → 状态查询”，还应定义相同 ID 携带不同参数时拒绝、已完成请求返回什么、幂等记录保留多久。只给气泡加一个 ID，无法约束工具是否重复执行。

**现有验证：** [chat.test.ts](../../tests/app/stores/chat.test.ts) 覆盖握手失败撤回、提交失败保留附件、连接结果不明提示。模拟错误验证前端分支，服务端幂等仍是后续协议能力。

**补充反例：** 服务端接受后丢掉 HTTP 响应，继续发送运行事件；观察页面是否错误允许重复提交，以及历史回读能否反映结果。即使最终补出了回答，也不代表中间没有重复执行风险。

## 5 A 切 B 再回 A，为什么 session ID 不够

### 主问：旧请求怎么识别

> 看两次打开 A 的时序：第一次 A 发出请求，切到 B 后又重新进入 A，第二次 A 已开始新操作；这时第一次 A 的失败才回来，ID 仍然匹配，但它已没有资格修改新页面。当前发送和多条异步命令保存会话代次，返回时同时检查 ID 与代次；历史重载还检查请求序号，防止同一代里旧查询覆盖新查询。成功、失败和 finally 都要检查，因为旧 finally 清 loading 或释放提交保护，也可能破坏新操作。可以用受控 Promise 固定返回顺序，而不是靠快速点击碰运气。

```text
t0  A 第一轮提交挂起          保存 ID A 和代次 1
t1  关闭 A 打开 B            代次递增
t2  再打开 A 并提交新内容    当前属于新的代次
t3  第一轮提交失败返回       ID 相同但代次不同 丢弃旧结果
```

### 怎样把偶发问题变成稳定测试

用可控 Promise 让第一条命令保持 pending，切换会话并启动新操作，再主动让旧请求失败。现有测试按以下顺序制造这个交错。

测试先让 A 会话的第一条请求一直等待，确保它已经发出；然后关闭 A、切到 B，再重新打开 A 并让新提交成功。最后主动使最早那条请求失败。预期旧操作被判为失效，新会话仍显示运行中、只保留新消息，也不弹出旧错误。这种安排能稳定复现仅比较会话 ID 时的漏洞。

关键不是“发了两个请求”，而是精确固定旧请求最后返回，并同时检查消息、运行标记和错误提示。只检查 `sessionId` 最终等于 A，发现不了旧错误已经把新任务状态清空。

**已有验证：** [chat.test.ts](../../tests/app/stores/chat.test.ts) 覆盖旧失败、旧握手等待者；[chat-races.test.ts](../../tests/app/stores/chat-races.test.ts) 覆盖旧提交不能解除新提交的草稿保护，旧模型设置与压缩失败不能写入新会话。

**仍须细查：** `openSession` 部分加载收尾和编辑目标恢复仍只检查 ID，不应推广为所有异步路径完全覆盖。历史查询与同一代内新 SSE 消息交错也是独立问题，请求序号不能自动解决事件版本问题。

## 6 点击停止后 3 秒一定结束吗

### 主问：停止卡住时怎么定位

> 先定位停止流程卡在哪个 await。当前先撤回队列，再发送 abort，只有两步确认返回后才安装 3 秒界面对账定时器。因此撤回或 abort 请求一直挂起时，定时器根本没有开始，不能说点击后 3 秒必定结束。即使定时器触发并清掉本地运行标记，也不证明服务端工具已经停止。合理的后续设计是给请求等待设置截止时间，超时后显示停止结果未确认并查询运行状态；真正允许启动冲突任务，应依据服务端状态，而不是依据本地计时到了。

| 输入安排 | 要检查什么 | 当前证据 |
| --- | --- | --- |
| 撤回返回错误 | 不调用 abort，保留运行态并提示 | `chat-queue.test.ts` |
| abort 返回错误 | 不误称停止成功 | `chat-queue.test.ts` |
| 清队列成功但 abort 仍挂起 | 本页不能追加任务 | `chat-races.test.ts` |
| 撤回或 abort 永远不返回 | 超时提示、状态查询和冲突操作限制 | 超时闭环待实现 |

不能把“Promise reject 有 catch”当成“Promise 永远 pending 也有处理”。

## 7 编辑分支失败了，怎么知道停在哪里

### 主问：接口失败就把 UI 切回去够不够

> 关键是确认服务端是否已经改变叶节点。请求可能在服务端导航成功后才丢响应，如果只把前端选中态改回原分支，界面和下一次模型上下文就不一致。当前导航先预览目标，然后发命令、重读权威详情；异常时再读取位置，必要时请求回退，回退后仍要读取确认。若这些步骤也失败，就记录位置未确认并禁止发送，保留用户输入等待重新加载。它牺牲了一点连续操作体验，但避免在未知上下文上继续产生副作用。测试不能只检查按钮选中态，还要检查发送资格和实际叶节点。

**已有断言：** [chat.test.ts](../../tests/app/stores/chat.test.ts) 覆盖预览后导航、拒绝后保留原分支、回退后无法读取则锁住发送；[chat-races.test.ts](../../tests/app/stores/chat-races.test.ts) 检查恢复期间切会话不能回退旧会话或锁住新会话。

## 8 队列明明更新了，为什么又变回旧内容

### 主问：同一会话的返回结果也要丢弃吗

> 要，因为会话相同不意味着数据版本相同。比如发起运行态查询时队列为空，查询返回前 SSE 已告诉页面队列里有一条新指令，如果直接应用旧快照，就会把新指令从界面抹掉。当前队列每次事件更新都会递增本地版本，请求发出时记录版本，回来时只有版本仍一致才覆盖。撤回也有类似检查，撤回期间后来加入的队列内容不能被旧的空数组覆盖。这个版本只是本地交错保护，不是服务端全局序号；如果事件本身丢失或跨窗口发生变化，还需要重新查询和更强的恢复契约。

**受控时序：** 挂起撤回响应 → 发新队列事件 → 返回实际撤回文字 → 检查新队列仍在、撤回文字回到草稿。已有 [chat-races.test.ts](../../tests/app/stores/chat-races.test.ts) 覆盖。

## 9 怎么证明优化有效，而不是感觉快了

### 主问：事件裁剪和 Markdown 优化分别测什么

> 传输与渲染需要分别测量。事件裁剪已去掉重复 partial，可以对固定事件样本比较序列化字节数，并验证工具 ID、名称和最终消息仍能正确组装。Markdown 缓存和按帧合并目前是候选方案，验证时应固定内容与到达节奏，记录解析调用次数、解析耗时、长任务以及最终 HTML 一致性。不能拿两次真实模型生成的总耗时直接比较，因为网络和模型输出节奏都变了。优化还要验证最后一段及时出现，结束后旧回调不会复活气泡，切会话后不会提交旧帧，这些正确性要求与性能指标同样重要。

**建议样本：** 短文本、多代码块长文本、文本与工具交错三类；固定同一份 delta 序列，记录浏览器、机器、样本大小及重复次数。分别报告首个可见输出、完成展示、解析总耗时和内存变化。当前没有这套性能基线，不填写提升比例。

## 10 为什么不能全部靠端到端测试

### 主问：mock 这么多，测试还有意义吗

> 不同测试层负责验证不同问题。纯函数测试快速检查内容块、参数片段和快照替换；store 测试使用真实 Vue 和 Pinia，把网络替换为可控对象，专门控制旧响应、握手失败和队列事件顺序；服务端测试检查预检确认、导航互斥和计数清理。最后再用浏览器验证刷新、断网、输入和滚动，用实际 SDK 验证事件契约。mock 的价值在于稳定制造反例，限制在于不能证明真实网络和 SDK 一定按模拟方式工作。因此需要明确每个测试的输入和断言，再补跨层验收，既不全靠 mock，也不让每个字符串拼接用例都等待真实模型。
