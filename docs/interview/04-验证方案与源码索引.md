# 验证方案与源码索引

面试官问“怎么证明”，关注的是结论能否落到可复现条件，而不是背出测试工具名称。应先说要证明什么，再说明怎样控制输入和时序，最后给出判定结果。本文把项目中常见结论与验证位置对应起来；测试本身的原理见 [测试体系](../learning/11-测试体系与验证边界.md)。

## 1 把方案变成可验证的判断

例如要证明“预检通过后不必等完整生成”，就不能只断言最终有回复。需要让执行保持未完成，但预检先成功，再观察命令已经返回且运行状态仍保留。这个条件会直接暴露等待了错误 Promise 的实现。其他结论同样应安排能够推翻它的输入，而不只验证正常路径。

| 面试中的结论 | 需要安排的条件 | 必须观察的结果 |
| --- | --- | --- |
| 预检后即可确认 | 预检先通过，完整 prompt 保持未完成 | 命令已返回，运行计数仍保留 |
| 旧响应不串会话 | 先打开 A，再打开 B，让 A 最后返回 | 最终消息与统计属于 B |
| 失败能撤回乐观消息 | 让握手或 POST 失败，经真实 Vue 响应式 store 读取列表 | 仅本次临时消息被移除，新输入保留 |
| 重连能恢复完成结果 | 断线期间任务完成，重连后不再发新事件 | 最终历史补齐，旧运行标记消失 |
| 停止有超时路径 | abort 请求始终不完成 | 用户能看到确认状态，界面不会被无限挂起 |
| 缓存减少解析开销 | 同样文本与 delta 节奏分别执行前后版本 | 输出一致，重复解析次数或耗时降低 |

前两项有相关既有单元测试。乐观消息撤回、完成后重连和停止超时是待补验证项；缓存属于改进方案，不能列成已验收成果。

实际回答可以围绕三个要素展开：

- **控制条件：** 使用延迟响应、可控 Promise 或固定事件序列，让问题稳定出现。
- **观察对象：** 同时检查内容、身份和运行状态，而不是仅看请求成功。
- **证据范围：** 说明它证明的是纯函数、store 还是浏览器行为，避免跨层推导。

## 3 面试官要求证明时的表达

**面试官：这些单元测试通过，就能说整个系统可靠了吗？**

> 只能说明被测条件下的行为。比如包装器测试用 mock 控制预检和执行结束，能证明应用处理这两个时点的方式，但还需要确认实际 SDK 的事件顺序与适配一致。浏览器重连、页面渲染和真实工具执行要另外验证。
>
> 验证记录应说清输入、环境和检查结果。如果当前只有源码分析，我就说明它是待验证假设，不会把测试计划写成已通过结果。

**面试官：为什么不全部交给端到端测试？**

> 因为关键反例需要控制时序。让真实模型恰好在断线期间完成不容易稳定复现，用可控事件可以准确验证对账逻辑；再用真实连接检查模块接通和交互。两层各有作用，不能只靠模拟，也不必用真实模型反复验证字符串拼接。

**面试官：没有性能数字，能讲什么结果？**

> 可以讲已证明的行为，例如命令确认早于完整生成、特定旧响应被丢弃，以及消息块按事件正确组装。性能提升则需要同输入的基线比较。结构性结果和测量结果分开，证据才对得上结论。

```text
输入与发送      chat.sendPrompt
连接就绪        AgentEventConnection.ensureConnected
命令接受        AgentSessionWrapper.sendPrompt
事件传输        createAgentEventStream 与 toClientAgentEvent
数据变换        chat.applyEvent 与 streamReducer
页面展示        MessageItem
```
