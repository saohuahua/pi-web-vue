# 验证方案与源码索引：刷新、断线和并发操作怎样排查

用户看到的故障通常是“回答少了一截”“一直显示运行中”“切回来之后草稿变了”。本篇从这些现象进入，沿调用链定位，解释具体判断分支，再给能稳定制造问题的测试步骤。测试覆盖与浏览器待验收项分别列在对应场景下。

## 1 SSE 断了，刷新还能接上吗

### 主问：用一条完整时序讲清楚恢复

> 浏览器刷新和服务端重启影响的数据不同。刷新丢的是页面内存，Node 里的会话如果还在，任务可以继续运行。重新打开页面时，先根据会话 ID 读取已保存的历史，再订阅事件流。服务端安装监听后发送业务握手，告诉前端当前是否流式运行，并在存在当前助手消息时补发快照，前端再接后续增量。因此恢复依赖三部分：会话身份、持久历史和仍存活的运行实例。它能恢复已有记录及当前消息，但不是逐条重播断线期间的事件，也不能保证 Node 重启后接着原来的工具调用继续执行。

```text
页面刷新       浏览器内存清空               服务端任务可能继续
打开原会话     查询历史并写入列表           已落盘消息恢复
订阅 SSE       安装监听并发送握手           前端获知是否正在流式运行
补发快照       替换当前助手草稿             恢复仍存在的当前消息
接收 delta     在快照基础上继续组装         后续实时输出恢复
```

**为什么不是绝对无损：** 历史查询与事件订阅不是同一个原子快照。历史读完后、监听安装前，任务可能结束；此时详情里没有最终消息，连接又没有运行快照。当前打开流程没有统一的“订阅就绪后再对账”协议，不能保证这个窗口里也自动补齐。

### 追问：刷新、断线、进程重启，这三种恢复各能恢复什么

> 三种恢复不是同一件事，先分清哪一层内存还在。刷新丢掉的是整个页面内存，服务端实例还在，所以靠“历史 + 当前消息快照 + 重新订阅”三件东西接上；断线重连时旧页面内存还在，`EventSource` 自动重连，靠握手补回运行态、靠快照替换掉旧草稿；服务端进程重启最严重，落盘的历史文件仍然可读，但内存里的会话实例、运行态和当前消息快照全部消失，不能宣称任务接着跑。

| 恢复方式 | 哪些状态还在 | 哪些必须重新取 | 覆盖不到的部分 |
| --- | --- | --- | --- |
| 刷新页面 | 服务端实例、已落盘历史、SDK 内存里的当前流式消息、草稿（`localStorage`） | 历史与 `entryIds`、`tree` 与 `activeLeafId`、模型与思考等级、`contextUsage` 与 `stats`、运行态（握手 `isStreaming`） | 页面内存里的乐观消息、活跃工具卡片、重试提示全部归零；历史查询与订阅之间的窗口不补齐 |
| 断线重连 | 旧页面的消息列表、运行标记、活跃工具、草稿，全部留在内存 | 运行态与当前助手消息快照；服务端已在断线期间结束时走终态清理分支，由它触发历史重读 | 断线期间发生的消息只在终态分支或 `agent_end` 触发的重读里补齐；事件本身不重放，重连后也不会主动把所有已完成消息重拉一遍 |
| 服务端进程重启 | 会话文件里的历史、图片与文件预览、草稿 | 全部内存态：新建 wrapper、重跑 `get_state` 拿运行态、重查历史与 `entryIds` | 原任务不会继续执行；`/api/cwd/validate` 的目录授权集合也在内存里，重启即清；进行中的工具调用状态不可恢复 |

三者的共同上限是同一句话：**能恢复的只有“文件里有的”和“当前实例内存里还在的”，没有事件日志，就没有断线期间的逐条补发。**

源码依据：[会话实例注册表](../../server/utils/rpc-manager.ts)、[文件访问授权集合](../../server/utils/file-access.ts)、[事件流握手与快照](../../server/utils/event-stream.ts)、[前端事件分发](../../app/stores/chat.ts)。

服务端重建实例的入口在 [rpc-manager.ts](../../server/utils/rpc-manager.ts) 的两级复用里，值得记住的是**它只防并发、不防重启**：

```ts
// 两级复用 先查已完成的实例 再查正在创建的 Promise
// 只保存完成后实例填不上初始化空档 两个请求会建出两个执行对象
const existing = registry.get(sessionId);
if (existing?.isAlive()) return { session: existing, realSessionId: sessionId };

const inflight = locks.get(sessionId);
if (inflight) return inflight;
```

`registry` 和 `locks` 都是模块级 `Map`，进程一退就空。所以重启后的第一次请求一定是重建而不是复用，历史从会话文件读，运行态与快照只能重新算。

**仍须细查：** 进程重启后的自动恢复只覆盖“历史能读、实例重建”这一段；任务是否要提示用户重新发起、授权目录要不要持久化，当前都没有实现，属于 P0 事件序号方案的同一批问题。

### 核心处理：恢复消息内容和恢复运行状态分开

浏览器重新打开会话时，历史查询写入 `messages` 和 `entryIds`；服务端事件流则读取当前会话的 `streamingMessage`，把它作为 `message_start` 发给浏览器。前端收到的是当前消息快照，而不是从头重新执行 prompt。

下面是事件流建立过程的顺序示意，省去缓冲过滤和资源清理细节：

```text
等待会话实例就绪
注册实例销毁监听
注册业务事件监听 并暂存握手前事件
读取当前 streamingMessage
发送 connected 和 isStreaming
转发未被快照覆盖的缓冲事件
存在快照时发送 message_start
切换为实时转发
```

先安装监听再读取快照，是为了让接入过程发生的新事件进入可处理范围；先发握手，是为了让浏览器先知道运行状态，再应用后续消息。服务端还会过滤它判断已包含在快照里的部分事件，避免重复应用。但当前过滤依赖消息对象与事件形态，没有持久序号，不能代替跨断线的通用回放协议。

前端先检查当前是否仍处于运行阶段；已经落定时，忽略迟到的流式消息。仍在运行且收到的是助手快照，就标记 Agent 活跃，并用这份快照替换正在显示的助手草稿，随后再应用新来的增量。

运行阶段检查阻止任务已落定后迟到的消息重新唤起气泡。快照替换当前流式消息，不在旧草稿后面追加整份文本；否则断线前已显示“正在检查”，重连快照又带“正在检查接口”，页面可能出现重复前缀。

### 追问：不刷新，只自动重连，任务已经结束怎么办

> 恢复处理由握手状态和旧页面保存的状态共同决定。当前工作区在握手明确表示未流式运行、且页面之前确认 Agent 活跃时，会清空流式草稿，进入落定路径，清除活跃工具和重试状态，并重读历史。这覆盖了断线期间结束、重连后不再有新事件的一个关键场景，已有 store 测试。但这个分支依赖旧页面的活跃标记，不是每次握手都对账；仍在运行时也不会补齐断线期间所有已完成消息。因此准确回答是补了终态恢复的一条路径，还没有完整事件回放和一致快照协议。

握手分两条路径处理：服务端明确表示仍在生成，就恢复运行标记并查询运行态；服务端明确表示不再生成，而且旧页面之前确认过 Agent 活跃，就清掉流式草稿，进入统一的任务落定流程。握手缺少运行字段时，不把“未知”直接当作“已经结束”。

为什么不能只把运行标记关掉就结束？界面还有活跃工具、自动重试、压缩标记和旧草稿，落定路径会统一清理这些状态，并触发历史和运行态回读。只改一个总开关，工具卡片仍可能残留执行中。

为什么必须等服务端明确返回已经结束？字段缺失表示没有拿到明确状态，不能把缺失直接解释为已经结束。第二个条件要求页面先前确认 Agent 活跃，这也解释了新页面恢复为什么不能完全复用这条终态路径。

**复现与断言：**

1. 发 `agent_start` 和工具开始事件，让页面确认运行中。
2. 模拟断线期间完成，把历史接口设为返回最终回答。
3. 只发 `connected` 且 `isStreaming: false`，不再发结束事件。
4. 断言运行标记关闭、活跃工具为空、历史含最终回答及记录 ID。

已有 [chat-races.test.ts](../../tests/app/stores/chat-races.test.ts) 覆盖此 store 路径。刷新查询与订阅之间的窗口、运行中漏掉完整消息、真实网络恢复需额外验证。

## 2 为什么不靠 Last-Event-ID 保证不丢

### 主问：SSE 重连不就能自动续传吗

> 重新建连只恢复传输通道，续传还需要事件身份和服务端补发。先检查当前服务端是否给事件编号、是否保留可重放日志、是否按客户端游标补发。本项目编码输出只有 data，没有事件 id，也没有按 Last-Event-ID 查询的应用逻辑，所以当前走历史加快照恢复，不能宣称协议已经保证补发。如果要实现，必须给会话事件分配可比较的序号，保存一段日志，重连时按最后应用的序号补齐，并在前端去重。日志过期或服务重启后还要有完整快照回退，而不是拿到一个旧序号就假设仍能恢复。

### 追问：补发时收到重复事件，怎样避免文字翻倍

> 可以在应用事件前做序号判断，而不是追加以后再比较文字。假设快照包含到序号 120 的状态，那么补发 119、120 都应忽略，从 121 开始应用。若恢复查询期间实时事件已经到达，就要缓存它们，安装带游标的快照后再按序衔接，避免快照覆盖新内容。工具开始和结束也需要同样规则，不能只给文本去重。这里的序号是服务端协议能力，当前项目还没有实现；现有会话代次主要隔离旧页面操作，不能替代同一任务内的事件序号。

### 后续方案具体怎样设计

先定义恢复需要达到的目标，再决定是否保存全部事件。如果只要求最终历史完整，任务落定后重读权威历史较直接；如果要求工具进度和流式中间状态也按顺序接续，就需要更强的事件协议。

一种可实现的协议是：

1. 服务端每次改变会话可观察状态时分配单调序号，生成事件并保留在有容量或时间上限的日志中。
2. 恢复响应把历史、当前消息和运行状态对应到同一个游标，不能分别读取后拼出不同时刻的状态。
3. 前端进入恢复状态时暂存实时事件，装入快照后，只应用游标之后的事件。
4. 已应用的序号重复到达时忽略；发现序号缺口时补拉或重新取快照。
5. 日志已过期或服务端实例换代时，明确返回需要快照恢复，避免旧游标错误地指向新实例。

例如恢复快照停在 120，实时队列是 `[119, 120, 121, 121, 122]`，只应用 121、122；若只收到 124，则不能直接认定 123 不重要。浏览器刷新后持久化旧游标但没有对应的本地快照，也不能单独拿游标继续追加，需要先恢复其依附的状态。

这套方案会增加日志容量、快照一致性、去重与过期处理成本，适合在恢复要求明确之后实施。当前项目采用历史与当前快照，还没有上述事件日志。

证据：[事件流编码](../../server/utils/event-stream.ts)、[连接管理](../../shared/lib/agent-event-connection.ts)。

## 3 心跳、握手和重试有什么区别

### 主问：服务端一直发心跳，为什么用户看不到输出

> 需要分别检查网络通道、订阅关系和任务状态。心跳只说明流还在写数据，不能证明这个流仍监听着当前执行实例。例如旧实例已销毁，但流仍定时发注释，浏览器会觉得连接活着，新的命令却可能进入另一个实例，输出自然收不到。当前服务端在实例销毁时通知事件流关闭，清理监听与心跳，让前端重新连接；发送则等待业务握手，确认会话监听已安装。定位时需要对照会话 ID、实例生命周期和事件到达顺序，而不是只看到 HTTP 200 就断言连接正常。

### 追问：为什么发送要等业务握手，而不是等 HTTP 200

> 差别在“命令通道”和“事件通道”是两条独立的连接。`POST /api/agent/:id` 返回 200 只说明命令被接纳，事件从 `GET /api/agent/:id/events` 这条长连接回来。如果先发 prompt 再装监听，极短回复可能在订阅建立之前就生成完，服务端这时还没有监听者，那些 `message_start` 与 `message_update` 没有任何人接，前端就会整段丢失这一次输出，而气泡停在“正在思考”。所以发送链路等的是业务 `connected`，不是 HTTP 200。

这就是 [chat.ts](../../app/stores/chat.ts) 里发送前那一行的作用，等的是连接管理器解析到 `connected`，而不是一个 HTTP 状态码：

```ts
// 先等 SSE 握手完成再发 prompt 短回复的事件才不会丢
await connection.ensureConnected(id)
if (sessionId.value !== id || generation !== sessionGeneration) return null
```

握手只有服务端装好监听、发完 `connected`（以及存在快照时补发 `message_start`）才完成；[连接管理](../../shared/lib/agent-event-connection.ts) 收到 `connected` 才把这次尝试标记为就绪并停掉重试，等待上限 30 秒。**补充反例：** 把 `ensureConnected` 注释掉直接发命令，用一句“只回复一个字”的 prompt 反复试，就能看到气泡空转或输出整段缺失，而握手失败那一侧反而有回滚测试覆盖。

**已有验证：** [chat.test.ts](../../tests/app/stores/chat.test.ts) 覆盖握手失败撤回乐观消息；服务端的握手前缓冲在 [event-stream.ts](../../server/utils/event-stream.ts) 里实现（`snapshotPublished` 之前的事件只进 `bufferedEvents`，`connected` 之后按序补发）。**仍须细查：** [event-stream.test.ts](../../tests/server/utils/event-stream.test.ts) 目前只覆盖销毁关流，缓冲与补发顺序还没有直接用例，需要作者核实或补测。

### 追问：重试策略具体是什么，为什么不是一直立即重试

> 当前应用层配置是握手等待 30 秒、断开后按固定 3 秒延迟重新创建连接；实际调度没有倍增算法，属于固定延迟重连。启动错误会停止自动重试，因为配置或初始化失败未必靠重连能解决。固定延迟对本机少量连接比较直接，若以后远程部署有大量客户端同时恢复，可以考虑带上限的指数退避与抖动，减少同时重试的压力。这个调整要定义恢复后的重置条件和用户主动重试入口，不能只改一个时间常量就叫完善容错。

### 核心处理：关闭旧连接与旧定时器

连接管理器先确认回调是否来自仍在使用的连接，旧连接即使迟到一个事件，也不再送进当前 store。错误回调会丢弃并关闭当前源，按配置延迟重新创建；同会话已有重试定时器时不会再安排第二个。

`shouldMaintain` 要求连接仍属于当前会话，切走后不会继续为旧会话重试。关闭时还会递增重试代次，使旧的失败回调无法再次启动重试。这些判断共同防止“切到 B 后 A 还在后台不断重连”。

服务端关闭流时清心跳定时器、解除业务事件监听、解除销毁监听和 abort 监听。资源清理与关闭控制器是配套动作，否则浏览器不再需要连接后，服务端仍可能保留订阅者或定时任务。

**已有断言：** [event-stream.test.ts](../../tests/server/utils/event-stream.test.ts) 检查实例销毁后流结束；[rpc-manager.test.ts](../../tests/server/utils/rpc-manager.test.ts) 检查订阅者在场时推迟回收。心跳间隔为 30 秒，不意味着客户端有同样时长的静默检测截止时间。

## 4 点击发送报错，为什么不能自动再发一次

### 主问：怎样区分拒绝和结果未知

> 错误处理取决于失败阶段。业务握手失败时，还没有提交 prompt，可以撤回乐观消息并保留输入；服务端明确拒绝时，按返回错误处理；但请求已经发出以后网络断开，只能说明浏览器没拿到确认。当前普通发送会提示提交结果未确认并重读历史，运行中追加也会刷新队列快照，不自动重试。这有助于核对实际状态，但没有稳定命令 ID，仍不能可靠判断某一次提交是否被接受。对可能修改文件的任务，自动重试会带来重复副作用，所以可以优先补接受状态查询与幂等契约。

### 怎样定位错误发生在哪一段

| 可观察到的事实 | 能得出的判断 | 处理方式 |
| --- | --- | --- |
| 业务握手失败，prompt 尚未发出 | 本次输入没有通过此发送路径提交 | 回滚本地气泡并保留输入 |
| prompt 返回明确的业务拒绝 | 本次命令被拒绝 | 展示原因，用户修正后再提交 |
| prompt 已发出，但浏览器收到网络错误 | 接受结果未知 | 保留输入，查询历史或运行态，不自动重发 |
| HTTP 已确认，后续出现运行错误事件 | 接纳成功后执行失败 | 展示运行失败及已有结果，不回溯成“从未发送” |

当前代码以命令异常类型区分部分业务错误和传输错误，但异常类型本身不是一份跨网络的执行证明。若要支持安全重试，命令 ID 应覆盖“客户端发起 → 服务端接纳 → 状态查询”，还应定义相同 ID 携带不同参数时拒绝、已完成请求返回什么、幂等记录保留多久。只给气泡加一个 ID，无法约束工具是否重复执行。

### 追问：一张表里到底有几个“完成”

> 有两个，而且不是同一层的意思。第一个是**接纳完成**：SDK 的同步校验与扩展预检通过，wrapper 立刻让 HTTP 返回，此时任务还在后台跑。第二个是**整轮执行完成**：SDK 的 `prompt()` Promise 落定，wrapper 递减 `pendingPromptCount` 并补一条 `prompt_done`。关键区别是——**“接受”这个语义是 wrapper 加出来的，SDK 原本那个 `prompt()` Promise 表示的是整轮执行完成。** 前端看到 POST 返回就认为任务结束，等于把这两个时点混成一个。

| 时点 | 谁完成的 | 前端此刻可以做什么 | 不能做什么 |
| --- | --- | --- | --- |
| 接纳完成（HTTP 返回） | wrapper 的 `preflight` Promise，由 SDK 的 `preflightResult(true)` 兑现 | 收起乐观提交保护、更新草稿与队列快照、允许继续输入；短回复的事件已经在流里排队 | 不能宣布任务结束：不能清运行标记、不能清活跃工具、不能认为回答已经完整，也不能据此判断服务端一定不会再改文件 |
| 整轮执行完成（`prompt()` 落定） | SDK 的 `prompt()` Promise，wrapper 在它的 `then` 里递减计数并 emit `prompt_done` | 可以按 `prompt_done` 收尾；真正清状态走 `agent_settled` 那条统一落定路径，并重读历史与运行态 | 不能把它当成“HTTP 还没返回所以没被接受”，也不能用它的到达时间推断 HTTP 是否成功 |

两个时点之间隔着的正是 `pendingPromptCount`：它只在整轮结束后递减，所以“HTTP 已返回、任务仍在运行”这段区间里 `isRunning()` 仍为真，实例也不会被空闲回收。这就是为什么 `get_state` 返回的 `isStreaming` 不能单独当运行口径。

```ts
// prompt 命令的 RPC 契约 prompt 返回的 Promise 在整轮 run 结束才 resolve
// 而 preflightResult true 在同步校验与扩展预检通过时回调
// HTTP 响应在 preflight 通过后就返回 先 ack 剩余进度全部走 SSE
await preflight;
return null;
```

**已有验证：** [rpc-manager.test.ts](../../tests/server/utils/rpc-manager.test.ts) 里有一条正是“让预检先通过、完整 prompt 保持未完成”的用例：`send({type:'prompt'})` 已经 resolve，`isRunning()` 仍为真，直到手动结束那条未完成的 Promise 才收到 `prompt_done`。**仍须细查：** `agent_settled` 在前端是本地合成的落定事件，不是服务端事件；服务端只发 `agent_end` 与 `prompt_done`，两者与落定路径的对应关系需要作者核实。**补充反例：** [chat.ts](../../app/stores/chat.ts) 在 `message_start` 与 `message_update` 分支上先查 `isRunning` 再应用（“迟到事件守卫”），这条守卫目前没有直接用例，可以构造“任务落定后再补发 `agent_start` 与增量”验证气泡会不会复活。

**现有验证：** [chat.test.ts](../../tests/app/stores/chat.test.ts) 覆盖握手失败撤回、提交失败保留附件、连接结果不明提示。模拟错误验证前端分支，服务端幂等仍是后续协议能力。

**补充反例：** 服务端接受后丢掉 HTTP 响应，继续发送运行事件；观察页面是否错误允许重复提交，以及历史回读能否反映结果。即使最终补出了回答，也不代表中间没有重复执行风险。

## 5 A 切 B 再回 A，为什么 session ID 不够

### 主问：旧请求怎么识别

> 看两次打开 A 的时序：第一次 A 发出请求，切到 B 后又重新进入 A，第二次 A 已开始新操作；这时第一次 A 的失败才回来，ID 仍然匹配，但它已没有资格修改新页面。当前发送和多条异步命令保存会话代次，返回时同时检查 ID 与代次；历史重载还检查请求序号，防止同一代里旧查询覆盖新查询。成功、失败和 finally 都要检查，因为旧 finally 清 loading 或释放提交保护，也可能破坏新操作。可以用受控 Promise 固定返回顺序，而不是靠快速点击碰运气。

```text
t0  A 第一轮提交挂起          保存 ID A 和代次 1
t1  关闭 A 打开 B            代次递增
t2  再打开 A 并提交新内容    当前属于新的代次
t3  第一轮提交失败返回       ID 相同但代次不同 丢弃旧结果
```

### 怎样把偶发问题变成稳定测试

用可控 Promise 让第一条命令保持 pending，切换会话并启动新操作，再主动让旧请求失败。现有测试按以下顺序制造这个交错。

测试先让 A 会话的第一条请求一直等待，确保它已经发出；然后关闭 A、切到 B，再重新打开 A 并让新提交成功。最后主动使最早那条请求失败。预期旧操作被判为失效，新会话仍显示运行中、只保留新消息，也不弹出旧错误。这种安排能稳定复现仅比较会话 ID 时的漏洞。

关键不是“发了两个请求”，而是精确固定旧请求最后返回，并同时检查消息、运行标记和错误提示。只检查 `sessionId` 最终等于 A，发现不了旧错误已经把新任务状态清空。

**已有验证：** [chat.test.ts](../../tests/app/stores/chat.test.ts) 覆盖旧失败、旧握手等待者；[chat-races.test.ts](../../tests/app/stores/chat-races.test.ts) 覆盖旧提交不能解除新提交的草稿保护，旧模型设置与压缩失败不能写入新会话。

**仍须细查：** `openSession` 部分加载收尾和编辑目标恢复仍只检查 ID，不应推广为所有异步路径完全覆盖。历史查询与同一代内新 SSE 消息交错也是独立问题，请求序号不能自动解决事件版本问题。

## 6 点击停止后 3 秒一定结束吗

### 主问：停止卡住时怎么定位

> 先定位停止流程卡在哪个 await。当前先撤回队列，再发送 abort，只有两步确认返回后才安装 3 秒界面对账定时器。因此撤回或 abort 请求一直挂起时，定时器根本没有开始，不能说点击后 3 秒必定结束。即使定时器触发并清掉本地运行标记，也不证明服务端工具已经停止。合理的后续设计是给请求等待设置截止时间，超时后显示停止结果未确认并查询运行状态；真正允许启动冲突任务，应依据服务端状态，而不是依据本地计时到了。

| 输入安排 | 要检查什么 | 当前证据 |
| --- | --- | --- |
| 撤回返回错误 | 不调用 abort，保留运行态并提示 | [chat-queue.test.ts](../../tests/app/stores/chat-queue.test.ts) |
| abort 返回错误 | 不误称停止成功 | [chat-queue.test.ts](../../tests/app/stores/chat-queue.test.ts) |
| 清队列成功但 abort 仍挂起 | 本页不能追加任务 | [chat-races.test.ts](../../tests/app/stores/chat-races.test.ts) |
| 撤回或 abort 永远不返回 | 超时提示、状态查询和冲突操作限制 | 超时闭环待实现 |

不能把“Promise reject 有 catch”当成“Promise 永远 pending 也有处理”。

## 7 编辑分支失败了，怎么知道停在哪里

### 主问：接口失败就把 UI 切回去够不够

> 关键是确认服务端是否已经改变叶节点。请求可能在服务端导航成功后才丢响应，如果只把前端选中态改回原分支，界面和下一次模型上下文就不一致。当前导航先预览目标，然后发命令、重读权威详情；异常时再读取位置，必要时请求回退，回退后仍要读取确认。若这些步骤也失败，就记录位置未确认并禁止发送，保留用户输入等待重新加载。它牺牲了一点连续操作体验，但避免在未知上下文上继续产生副作用。测试不能只检查按钮选中态，还要检查发送资格和实际叶节点。

**已有断言：** [chat.test.ts](../../tests/app/stores/chat.test.ts) 覆盖预览后导航、拒绝后保留原分支、回退后无法读取则锁住发送；[chat-races.test.ts](../../tests/app/stores/chat-races.test.ts) 检查恢复期间切会话不能回退旧会话或锁住新会话。

## 8 队列明明更新了，为什么又变回旧内容

### 主问：同一会话的返回结果也要丢弃吗

> 要，因为会话相同不意味着数据版本相同。比如发起运行态查询时队列为空，查询返回前 SSE 已告诉页面队列里有一条新指令，如果直接应用旧快照，就会把新指令从界面抹掉。当前队列每次事件更新都会递增本地版本，请求发出时记录版本，回来时只有版本仍一致才覆盖。撤回也有类似检查，撤回期间后来加入的队列内容不能被旧的空数组覆盖。这个版本只是本地交错保护，不是服务端全局序号；如果事件本身丢失或跨窗口发生变化，还需要重新查询和更强的恢复契约。

**受控时序：** 挂起撤回响应 → 发新队列事件 → 返回实际撤回文字 → 检查新队列仍在、撤回文字回到草稿。已有 [chat-races.test.ts](../../tests/app/stores/chat-races.test.ts) 覆盖。

## 9 怎么证明优化有效，而不是感觉快了

### 主问：事件裁剪和 Markdown 优化分别测什么

> 传输与渲染需要分别测量。事件裁剪已去掉重复 partial，可以对固定事件样本比较序列化字节数，并验证工具 ID、名称和最终消息仍能正确组装。Markdown 缓存和按帧合并目前是候选方案，验证时应固定内容与到达节奏，记录解析调用次数、解析耗时、长任务以及最终 HTML 一致性。不能拿两次真实模型生成的总耗时直接比较，因为网络和模型输出节奏都变了。优化还要验证最后一段及时出现，结束后旧回调不会复活气泡，切会话后不会提交旧帧，这些正确性要求与性能指标同样重要。

**建议样本：** 短文本、多代码块长文本、文本与工具交错三类；固定同一份 delta 序列，记录浏览器、机器、样本大小及重复次数。分别报告首个可见输出、完成展示、解析总耗时和内存变化。当前没有这套性能基线，不填写提升比例。

### 追问：长回复开始卡，按什么顺序定位

> 按数据流动的方向走一层再走一层，不要一上来就猜。顺序是**事件处理 → Markdown 解析与高亮 → DOM 提交与布局 → 滚动跟随**。每一层都有对应的观察手段，前三层用固定内容 + 固定 delta 时间表就能分离，最后一层必须看浏览器。定位结论要说清“主要成本落在第几层”，在拿到基线之前不能说“优化了百分之多少”。

| 顺序 | 这一层在做什么 | 怎么观察 | 观察到什么才算这层有问题 |
| --- | --- | --- | --- |
| 1 事件处理 | `applyEvent` 分发与 `streamReducer` 组装内容块，每来一个 delta 就跑一次 | 在 [applyEvent](../../app/stores/chat.ts) 入口计数，配合 Performance 面板的 long task 与主线程占用 | 事件本身很密但每次很短 → 问题是频率而非单次成本；单次就很长 → 先看 reducer 是否在复制大数组或长字符串 |
| 2 Markdown 解析与高亮 | `renderMarkdown` 对活动文本块重复解析，Highlight.js 参与代码块 | 统计 [renderMarkdown](../../app/utils/markdown.ts) 调用次数与每次耗时，看调用次数是否随 delta 数增长 | 调用次数远多于“稳定块数量 + 1 个活动块” → 稳定内容被重复解析，属于可缓存的那一类 |
| 3 DOM 提交与布局 | Vue 把新 HTML 写进 `v-html`，浏览器重排重绘 | Performance 面板的 Recalculate Style / Layout 时长，配合固定内容与固定 delta 节奏 | 解析耗时不高但 Layout 很长 → 瓶颈在节点规模或整块替换，不在 Markdown |
| 4 滚动跟随 | 布局变化后测距底部距离，决定是否滚动 | [useAutoScroll](../../app/composables/useAutoScroll.ts) 的 rAF 回调与滚动事件时间戳 | 前三层都正常但掉帧 → 跟随逻辑在被高频触发，属于调度问题而不是解析问题 |

三点纪律：**固定样本**（同一份内容与同一份 delta 时间表，才能比较两次改动），**分层归因**（不要把总耗时当成某一层的结论），**同时看正确性**（最后一段是否及时出现、结束后旧回调是否复活气泡）。

详细的分层依据、缓存边界与按帧合并的代价见 [05 前端流式对话实现与优化](05-前端流式对话实现与优化.md) 第 5 节，这里不重复。

**已有验证：** [agent-event-wire.test.ts](../../tests/shared/lib/agent-event-wire.test.ts) 覆盖裁剪后的字段结构，[markdown.test.ts](../../tests/app/utils/markdown.test.ts) 覆盖解析正确性。**仍须细查：** 四层的时间数据当前一条都没有，本页只能给顺序和方法，不能给占比结论。

## 10 为什么不能全部靠端到端测试

### 主问：mock 这么多，测试还有意义吗

> 不同测试层负责验证不同问题。纯函数测试快速检查内容块、参数片段和快照替换；store 测试使用真实 Vue 和 Pinia，把网络替换为可控对象，专门控制旧响应、握手失败和队列事件顺序；服务端测试检查预检确认、导航互斥和计数清理。最后再用浏览器验证刷新、断网、输入和滚动，用实际 SDK 验证事件契约。mock 的价值在于稳定制造反例，限制在于不能证明真实网络和 SDK 一定按模拟方式工作。因此需要明确每个测试的输入和断言，再补跨层验收，既不全靠 mock，也不让每个字符串拼接用例都等待真实模型。

### 追问：这四层各去哪看

几条容易踩的对照关系，先说清楚再去看代码：

- **路径安全是两层，不是一层。** [path-security.ts](../../server/utils/path-security.ts) 只做“目标是否在根里”的判断，词法比较在 resolve 之后进行，根必须以分隔符收尾，否则同前缀目录会绕过；[file-access.ts](../../server/utils/file-access.ts) 负责“根是哪些”，来自已有会话的 `cwd` 与项目根，加上 `/api/cwd/validate` 显式授权的目录，授权集合在内存里、**服务进程重启即清**。前者管判断，后者管范围，两者都不管 Agent 自己执行命令的行为。
- **压缩有两种触发。** 手动压缩走 [rpc-manager.ts](../../server/utils/rpc-manager.ts) 的 `compact` 分支（异常不吞，`finally` 里让会话列表缓存失效），自动压缩由 SDK 自己发起，前端只认 `compaction_start` / `compaction_end` 与 `auto_compaction_start` / `auto_compaction_end` 两组事件名。压缩后累计统计不会归零：[session-stats.ts](../../shared/lib/session-stats.ts) 对 `compaction` entry 只累计 usage 不计数，所以 token 与成本是单调增长的，“压缩后用量看起来被重置”通常是读错了指标——文件累计看 `stats`，当前窗口占用看 `contextUsage`。
- **插件包的测试分两处。** 远端版本比较这类纯逻辑在 [plugin-updates.test.ts](../../tests/server/utils/plugin-updates.test.ts)；包列表读取与安装/移除动作的状态流转在 [plugins.test.ts](../../tests/app/stores/plugins.test.ts)。**需要作者核实：** `tests/server/utils/` 下没有 `plugins.test.ts`，服务端 [plugins.ts](../../server/utils/plugins.ts) 的 `readPlugins` 与 `runPluginAction` 目前只有 store 侧 mock 覆盖。

从仓库测试入口运行本页列出的相关测试文件即可。阅读测试时重点看怎样控制返回顺序，以及最后检查了哪些业务状态。

**浏览器验收待补项：** 真正离线再上线、刷新时恰好完成、多窗口提交与停止、服务进程重启、Markdown 与滚动性能。测试通过不替代这些验收。

### 这些待补项的产品化排序

> 上述待补项不是同一优先级。排序口径是**解决根因 → 收窄竞态 → 建立事实**，不按功能热度排。完整表述与“怎么算做完”的判定在 [01 项目介绍与架构表达](01-项目介绍与架构表达.md) 第 7 节“如果继续做，第一优先级是什么”那张表里，那里是唯一维护处，这里只做与本页场景的对应，顺序完全一致。

| 顺序 | 对应的待补项与本页场景 | 为什么排在这里 |
| --- | --- | --- |
| P0 事件序号与游标 | 本页 §1 的刷新窗口、§2 的 `Last-Event-ID`、服务进程重启 | 断线、刷新、切会话三类现象的根因都是“不知道丢到哪了” |
| P1 命令 ID 与接纳状态查询 | 本页 §4 的“接受结果未知”与自动重试 | 现在只能提示用户核对历史，重复提交没有幂等约束 |
| P2 停止流程超时与状态回执 | 本页 §6 的撤回或 abort 永久挂起 | 停止是唯一会改变服务端行为的前端操作，卡住时无路可走 |
| P3 前端性能基线 | 本页 §9 的四层定位顺序与固定 delta 时间表 | 没有基线就只能猜瓶颈，优化成果无法诚实陈述 |
| P4 鉴权与执行隔离 | 本页 §11 的路径安全边界说明 | 产品化的前置条件，不是当前原型的缺陷 |

一句话记法：**先让“哪条事件生效了”可判定，再让“哪次提交生效了”可查询，然后才是停止、性能与安全。** 前两项没做完之前，浏览器验收清单里剩下的多窗口与刷新场景都只能记录现象，不能收敛成结论。
