# 项目介绍与架构表达

这篇文档按真实面试中的连续追问组织。每组从一个具体结论出发，再讨论反例、取舍和验证。技术判断以当前源码为依据，个人贡献按实际经历补充，参考来源见 [项目亮点与贡献说明](03-项目亮点与贡献说明.md)。

先读 [从最小 Agent 到 Web 工作台](../learning/00-从最小Agent到Web工作台.md)，讲清 SDK 用法、一句话的完整路径、工具执行与前端展示，再进入本篇的具体追问。

- **表达顺序**：当前实现 → 设计理由 → 条件变化 → 验证方式。
- **使用方式**：引用块是可参考的回答，不要求整段背诵；每次回答到能支撑结论的位置即可，等待下一次追问。

## 1 开场介绍

> 这是一个基于 Vue 3 和 Nuxt 4 的本地编程工作台。Node 服务集成 pi agent SDK，浏览器通过 HTTP 提交任务，通过 SSE 接收文本、思考和工具执行事件。项目支持会话创建恢复、文件预览和能力配置。
>
> SDK 负责模型调用和工具循环，应用层负责将持续运行的 Agent 接入浏览器。比较值得展开的是异步状态：命令接受、消息生成、工具执行和任务结束发生在不同时间，前端需要分别处理，并在刷新、切会话或请求失败时对账。

开场先说清系统和主线。个人负责范围紧接在这段后面，不用把所有功能和内部函数一次讲完。

## 2 架构追问：选型是否符合运行场景

**面试官：Nuxt 关闭了 SSR，那使用 Nuxt 的价值是什么？**

> 当前用的是 Nuxt 的工程组织、页面路由和 Nitro 服务端接口。浏览器承担动态会话展示，SDK 留在 Node 侧访问文件和执行工具。关闭 SSR 只改变页面渲染方式，不会关闭后端 API。
>
> 对本机工作台来说，重点是进入会话后的持续交互，搜索引擎收录并不是主要需求。客户端渲染简化了 EventSource、本地偏好和初始状态衔接。这个取舍适用于当前产品，并不是认为 SSR 没有价值。

**面试官：独立 Vue 加 Node 服务也能做。你怎么比较，而不是给当前选型找理由？**

> 先比较运行约束。当前页面和服务在本机共同启动、共同迭代，一个工程维护接口和共享类型比较方便。如果两部分需要独立发布或由不同团队维护，拆开可能更合适。
>
> 真正决定是否拆服务的，是生命周期和部署需求。比如要在远程机器托管多个 Agent，就不只是换个接口地址：当前会话注册表在单进程内存里，必须解决会话归属、任务路由和执行隔离。当前没有这类需求证据，所以我不会为了展示架构复杂度先拆服务。

**面试官：SDK 已经实现了 Agent，应用还做了什么？**

> 应用负责把 SDK 能力组织成工作台。例如命令接口和事件接口要取得同一个会话实例，浏览器要区分完整历史与生成中的内容，工具结果要配回对应调用，离开页面要解除订阅。SDK 提供的事件不会自动变成正确的 Vue 状态。
>
> 这里也要讲清来源。项目部分协议和 reducer 来自 pi-web 移植，不能全部说成原创。可以展示的个人工作应落到实际适配、组件实现或修复记录上，解释自己改了什么、为什么改，以及验证了什么。

## 3 发送追问：命令到底有没有被接受

这一组的重点是区分请求、任务和界面状态。先给正常链路，再用“响应丢失”和“回滚条件不成立”检查原结论，不能从存在 catch 分支直接推断所有失败都已处理。

**面试官：你说使用 HTTP 加 SSE，依据是什么？**

> 用户上行主要是提交、停止和切配置，属于离散命令；下行则是持续的文本和工具事件。HTTP 负责命令确认，SSE 负责订阅会话状态，符合当前交互方式。WebSocket 也能实现，但目前没有高频双向通信需求，换协议不会自动解决命令确认和状态恢复。

**面试官：两条连接独立，模型很快返回时会不会丢首批事件？**

> 所以发送前等待的是业务 connected，而不只是网络连接打开。服务端取得 SDK 会话、安装监听后才发送握手，前端等待完成再提交 prompt。这个顺序约束解决的是“开始运行时还没有订阅者”的窗口；之后发生断线仍要靠恢复机制处理。

**面试官：HTTP 什么时候返回？如果马上返回，预检失败怎么办？**

> 包装器等待 SDK 的成功预检回调后返回。这样既不需要等完整生成结束，也不会在校验之前无条件报告接受。预检前失败走 HTTP 错误，接受后的运行失败走事件通知。
>
> 这里需要分别测试两个 Promise 的完成时点：预检已经通过，但 SDK 的完整 prompt Promise 仍未完成时，命令应能返回，服务端运行计数仍应保留。仓库已有控制这两个时点的测试。

**面试官：服务端接受了，HTTP 响应丢了，前端看到异常。你能判断没执行吗？**

> 不能。网络错误只能证明浏览器没拿到确认，不能证明任务被拒绝。当前代码走请求异常处理，尝试回滚界面，但没有完整的接受状态查询或请求去重。因此“失败后直接重发”可能造成重复执行，尤其是任务已经开始改文件时。
>
> 改进时应先让命令有稳定请求 ID，并能查询其接受状态，再决定是否重试。仅禁用发送按钮只能防止当前页面连点，不能处理响应丢失后的重试，也不能处理其他窗口。

**面试官：你又说“回滚界面”。现有代码真的能撤回那条气泡吗？**

> 要看撤回条件，不能只看 catch 里写了 pop。当前代码把原始对象放进 Vue 的 ref 数组，失败后用取出的末尾元素与原始对象做引用比较。深响应式读取会得到代理对象，这个比较可能不成立。
>
> 本次审查用同样的 ref 入栈和读取方式得到不相等的结果，所以我会收窄结论：代码有回滚意图，但撤回条件存在问题。完整修复还需要验证真实 store 的失败路径，不能把这个最小验证说成修复已完成。

**面试官：直接加 toRaw 就行了，为什么还谈请求 ID？**

> 这是两个层次。toRaw 可以针对代理与原始对象比较做局部修正；客户端消息 ID 更适合在数组被替换、消息不在末尾时定位临时消息。服务端请求 ID 则用于命令去重和接受状态对账。
>
> 如果任务只要求修复代理比较，就应做最小改动并验证，不必顺手引入整套协议。但要声称网络重试可靠，才需要继续完成服务端那一层。把两个问题分开，可以避免为了修一个气泡问题做过大的改造。

## 4 恢复追问：成功建连以后缺了什么

这里改变的是任务结束与断线的先后关系。判断恢复能力时，必须说明断线期间发生了什么，以及重连后还会收到哪些信息。

**面试官：页面刷新后，正在输出的消息怎么恢复？**

> 页面重新打开时先读取历史，再连接 SSE。服务端实例还活着并保留当前助手消息时，会把这条消息作为快照补发，前端恢复草稿后继续接收 delta。历史负责已完成记录，快照负责当前生成内容。

**面试官：这和网络断了一下后自动重连，是同一条恢复路径吗？**

> 不是完全相同。重新打开会话会调用历史查询，而当前自动重连的 connected 分支不会立即补查历史，它主要在握手标记为流式中时设置运行状态。所以不能把“刷新能读到历史”直接推广成“每次重连都会完成历史对账”。

**面试官：任务恰好在断线期间完成，重连时没有流式快照呢？**

> 这就是当前恢复缺口。最终消息和结束事件都可能漏掉，重连后又没有快照；connected 为 false 时也不会主动清除旧运行标记。因此界面可能缺少最后一条消息，或仍显示运行中。
>
> 我会把原来的“重连恢复”准确拆成：已经有重新订阅和当前快照恢复，但断线期间完成后的对账还不完整。这个反例能直接验证，而不是继续用快照机制解释所有情况。

**面试官：那 connected 之后补一次 reload 就好了？**

> 对已经结束的任务，这是一个较小的补强方向。但运行中的情况还要处理查询和增量的重叠：请求发出后又收到新消息，旧查询返回时不能覆盖新内容。还要检查响应是否属于当前会话和当前连接代次。
>
> 完整方案可以让恢复响应包含一致的历史、当前运行状态和流式快照，再明确与后续事件的衔接。持久事件序号是更强的方案，但也增加日志保存和失效管理成本。对当前单机项目，我会先验证最小对账方案能覆盖哪些场景，再决定是否需要更重的协议。

**面试官：你文档里还有“停止后 3 秒兜底”，这能解决卡住吗？**

> 当前计时是在 await abort 请求结束后才开始。如果请求本身一直挂起，定时器还没启动。所以它只处理部分残留运行状态，不能说点击停止后一定在 3 秒内恢复。
>
> 进一步修改时，要区分请求超时、工具已停止和界面允许继续操作。请求超时不等于服务端停止，直接显示“已停止”会误导用户；更合理的是保留停止状态的确认与后续查询，并让超时提示表达结果尚未确认。

**面试官：你如何证明这次对账修复有效？**

> 用可控事件构造两条路径：一条断线时仍在生成，重连后检查快照和后续增量；另一条在断线期间完成，重连时不再发任何新事件，检查历史和运行状态是否最终正确。还要增加恢复请求未返回就切换会话的情况，检查旧响应不会覆盖新会话。
>
> 这里验证的是最终状态和事件衔接，不是只看 EventSource 有没有重新连接。服务进程重启属于另一个范围，当前快照在内存里，不能用这些测试推导出任务可跨进程继续执行。

## 5 渲染追问：机制是否真的对应性能收益

**面试官：你使用 reducer 做流式渲染，比直接拼字符串好在哪里？**

> 主要价值是管理结构化内容和明确变换规则。助手输出不仅有文本，还可能有思考和工具参数；reducer 按类型和索引更新内容块，store 再把结果写入 Vue 状态。它可以脱离组件测试，但仍有数组复制和字符串追加成本，不能仅凭纯函数就说性能更高。

**面试官：那长回复每次还会重新解析 Markdown 吗？**

> 当前消息组件直接调用 Markdown 渲染函数，没有已完成块缓存。增量状态组装和增量 Markdown 解析是两个环节，前者已经存在，后者不能声称完成。
>
> 性能分析需要分开看事件字节数、状态更新、解析和 DOM。若卡顿来自代码高亮，单纯换状态管理方式可能没有帮助；若来自大量历史节点，缓存活动文本解析也不一定解决主要问题。

**面试官：给你一天，怎么确定先改哪里？**

> 先用固定长文本和固定 delta 节奏复现，记录解析次数、解析耗时与页面更新情况，定位主要开销。确认 Markdown 是瓶颈后，优先复用已完成内容块的渲染结果，活动块仍完整解析。这样比立刻实现语法级增量解析更容易验证。
>
> 缓存需要绑定消息身份和内容，不能只按块索引，因为下一条消息会复用索引；渲染选项变化也要失效。当天的交付标准应是固定输入下结果一致、重复解析减少，并记录耗时，而不是承诺未经测量的提升比例。

**面试官：为什么不把每个 delta 渲染完直接追加 HTML？**

> 因为 Markdown 结构会受后续字符影响。例如代码围栏尚未闭合、列表继续增长时，前面的解释还可能变化。delta 也不一定落在完整语法边界上。直接追加片段 HTML 容易得到不同于完整文本的结果。
>
> 可以先复用稳定块、控制活动块刷新频率，再检查最终一帧是否及时完整展示。只有这些措施仍不足时，才值得引入更复杂的解析器；每增加一层复杂度，都应对应已测到的瓶颈。

## 6 回答中的思考落点

| 面试官改变的条件 | 回答需要改变的判断 |
| --- | --- |
| 单进程变成远程多实例 | 重新考虑会话归属与执行隔离，不只是拆目录 |
| 服务端接受但响应丢失 | 从“失败”改为“接受状态未知”，不能直接重试 |
| 任务在断线期间结束 | 仅快照不足，需要历史与运行态对账 |
| 发现 Vue 代理引用差异 | 承认局部实现缺口，区分最小修复与协议改造 |
| 发现实际卡顿在 Markdown | 将性能讨论落到解析成本，而不是继续强调 reducer |
