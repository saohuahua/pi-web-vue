# 项目介绍与架构表达：开场回答与项目全貌

用户打开本地项目，输入“检查接口报错的原因”，页面开始显示思考、读取文件、工具输出和最终回答；期间可以切会话、刷新页面、补充指令或停止任务。本篇沿这条路径给出**开场问题的可直接口述版本**，以及从业务到源码的完整链路。

**本篇只负责三件事：** 项目是什么、为什么这样设计、链路怎么走。机制原理见 [学习篇](../learning/README.md)，异常复现与验证见 [04 验证方案](04-验证方案与源码索引.md)，前端渲染与性能见 [05 前端流式对话](05-前端流式对话实现与优化.md)。

**优先级标记：** `[P0]` 必须能独立回答，`[P1]` 常见深入追问，篇末「**深入参考（P2）**」的内容查到即可，**不作为默认复习任务**。

**一条要练成的主线：** 为什么做 Web 工作台 → 为什么复用 Pi SDK 与 Nuxt/Nitro → 用户输入怎样变成 Agent 执行 → SDK 事件怎样经 SSE 投影成界面 → 为什么这些边界和取舍合理 → 当前不足与下一步。

## 1 项目介绍：是什么、为什么做、为什么做成 Web [P0]

### 面试官：介绍一下你的项目 [P0]

> 这是一个用 Vue 3 和 Nuxt 搭建的本地 Web 编程工作台。用户选择工程目录后，可以创建会话，让 Agent 读取项目、调用工具并持续输出结果。浏览器提供流式消息、工具卡片、文件预览、历史分支和能力配置，Node 服务托管实际运行的 SDK 会话。
>
> 主要工程问题是让一个持续执行的任务正确映射到页面。用户提交成功、模型开始输出、工具执行完成和整个任务结束是不同时间点；页面刷新、切会话和网络异常又会让这些状态交错。因此项目把命令提交、事件订阅、历史读取和输入草稿分别管理，再通过业务握手、输入快照、会话代次和历史对账把它们接起来。

个人职责接在产品介绍后，选择本人实际完成的模块展开。具体方案演进见 [发送、草稿、分支与队列案例](03-项目亮点与贡献说明.md)。

### 面试官：你为什么做这个项目，解决了什么具体痛点 [P0]

**核心结论：** Pi 在终端里已经能完成“读代码、改文件、跑命令”的闭环，但这个闭环留下的痕迹很难回看和导航；这个项目把同一套执行能力搬到浏览器，补上观察、回看和配置这三件事。

从真实使用场景倒推，终端里最别扭的是这几处：

| 场景 | 终端里的实际体验 | Web 工作台补的是什么 |
| --- | --- | --- |
| 一次长回复读了一半想找前面某段工具输出 | 输出线性滚动，翻回去就找不到边界 | 消息按内容块结构化，思考、文本、工具卡片分开 |
| 让 Agent 改完文件想确认改了什么 | 要另外开编辑器对照 | 文件 Inspector 直接预览，工具卡片显示参数与结果 |
| 同时跟进两个任务的思路 | 一个终端一次只跟一个会话交互 | 会话列表并行观察，切换不丢运行态 |
| 想接着上一次的思路继续 | 会话要靠命令回捞 | 历史树与分支导航，可从旧问题重新展开 |
| 输入里带一张报错截图 | 终端表达图片输入很受限 | 图片随消息提交，压缩后传给模型 |
| 换模型、看技能与扩展 | 分散在配置文件里 | 能力中心集中管理并即时生效 |

**目标用户是明确收窄的：** 就是在本机使用 Pi 的个人开发者，也就是作者自己。这不是一个准备服务多人的产品判断，而是当前实现的真实边界 —— 工具要访问本地工程、执行本地命令，所以它天然贴着“本机单用户”这个形态。

> 个人起因按你的真实情况替换：是因为终端里回看工具输出太麻烦，还是因为想练 Nuxt 全栈与 Agent 接入，两种说法都成立，但必须与你的实际经历一致。上面这张表可以用来说明“需求从哪里来”，不要直接当成项目立项文档。

### 面试官：既然 Pi 已经有 CLI 和 TUI，为什么还要做成 Web [P0]

**核心结论：** CLI 缺的不是执行能力，而是“观察能力”。执行内核复用现成的，产品价值全部落在浏览器擅长的部分。

先把两边已经做对的事分清楚，避免答成“Web 比终端好”这种空话：

- **CLI/TUI 已经解决：** 模型请求、工具循环、上下文压缩、会话持久化、终端内的交互渲染。
- **Web 额外要做的：** 事件协议、连接生命周期、状态归属、刷新恢复、竞态守卫。
- **Web 换回来的：** 结构化展示、可回看的历史与分支、文件与代码预览、多会话观察、浏览器侧输入能力、刷新后接续。

从工程成本看，这个交换并不便宜。多出来的部分主要是三类：

1. **多了一层协议。** 命令走 HTTP，事件走 SSE，两条通道各有自己的完成时点，必须解决先后顺序。
2. **多了一份状态。** 服务端有 SDK 会话与运行实例，浏览器有消息列表与运行标记，两边要靠快照、代次和重读对账。
3. **多了一套界面契约。** 工具执行进度、压缩状态、重试提示都要有对应的展示位。

**什么时候命令行更合适：** 一次性的短任务、远程 SSH 环境、只需要看最终 diff 的场景。这些场景下多一层 Web 只是负担。判断依据不是“哪个更先进”，而是这次任务需不需要回看、导航和并排观察。

### 面试官：这个项目最重要的核心链路是什么，为什么不能让 Vue 页面直接持有 SDK [P0]

**核心结论：** 因为执行的生命周期比页面的生命周期长。任务属于服务端会话，页面只是一次观察。

链路可以按三层记：

```text
浏览器 app/            输入、展示、交互状态（Vue + Pinia + 纯函数 reducer）
        ↓ HTTP 命令 / ↑ SSE 事件
Nitro 服务端 server/   会话实例注册、SDK 调用、事件转发、文件访问
        ↓ 进程内调用
Pi SDK（node_modules） 模型请求、工具循环、上下文管理、JSONL 持久化
```

**为什么这四件事必须在 Node 侧发生：**

- **工具要碰本机。** 读写工程文件、执行 shell 命令，浏览器没有这个能力。
- **凭证不能下发。** 模型配置与密钥在本机文件里，浏览器只应该拿到模型名与用量这类结果。
- **任务要比页面活得久。** 刷新页面只应该断开观察连接，不应该中断正在跑的任务。
- **SDK 进不了浏览器产物。** 这是一个纯 ESM 且内嵌 WASM 的 Node 包。

最后一条在代码里有两条直接证据。第一条是打包配置：

```ts
// nuxt.config.ts
nitro: {
  // pi SDK 是纯 ESM 且内嵌 WASM 的重包
  // 必须排除出 Nitro 打包 运行时从 node_modules 原样加载
  externals: {
    external: [
      "@earendil-works/pi-coding-agent",
      "@earendil-works/pi-agent-core",
      "@earendil-works/pi-ai",
      "@earendil-works/pi-tui",
      "undici",
    ],
  },
},
```

第二条是共享层的约束：`shared/lib/agent-event-wire.ts` 的文件头注明「shared 层不允许 import pi 包，这是打进浏览器产物的前提」，所以它在服务端把 SDK 事件先转成**手写的最小结构**再发出去。这两条合起来说明同一个判断 —— **SDK 只存在于 Node 侧，浏览器拿到的永远是投影。**

**这条链路的代价：** 页面拿到的永远是投影，不是 SDK 的原始对象。工具参数、消息内容和运行状态都要靠适配层搬运，SDK 一旦调整事件结构，改动点集中在 `shared/lib/agent-event-wire.ts` 这一个文件里。

### 面试官：用户发送一句话后，完整链路是什么 [P0]

以“检查接口报错的原因”为例：

1. **输入组件保存本次输入。** 读取文字和图片快照，交给 store，不在等待请求时重新读取一份可能已经变化的输入。
2. **store 建立提交状态。** 保留待确认文字，清空可编辑输入，追加用户气泡并显示运行反馈。
3. **等待业务握手。** SSE 服务端取得会话实例并安装监听后发送 `connected`。前端等到它再提交命令，避免极短回复发生在监听之前。
4. **HTTP 提交 prompt。** 服务端取得同一会话实例，调用 SDK；预检通过后确认接受，完整生成继续在后台运行。
5. **SSE 接收过程。** 文本、思考、工具执行等事件进入 store；reducer 组装当前助手消息，工具结果按调用 ID 关联。
6. **消息定稿与任务落定。** 完整消息进入历史列表；任务落定后清理运行状态，重读历史取得记录 ID、当前分支与统计信息。

```text
Composer 保存输入
        ↓
chat store 建立提交状态
        ↓
等待 connected ────── SSE 服务端已安装会话监听
        ↓
HTTP prompt → 会话包装器 → SDK 预检与持续执行
        ↑                         ↓
     接受确认                文本与工具事件
                                  ↓
                         SSE → store → reducer
                                  ↓
                         消息与工具组件展示
                                  ↓
                       落定后读取权威历史与统计
```

这里有两种“草稿”：输入框草稿是用户还没确认提交的内容；流式草稿是助手正在生成、尚未定稿的消息。二者生命周期不同，不能共用一个字段。

源码：[输入组件](../../app/components/ChatComposer.vue)、[chat store](../../app/stores/chat.ts)、[会话包装器](../../server/utils/rpc-manager.ts)。

## 2 通信方式：为什么拆成 HTTP 命令和 SSE 事件 [P0]

### 面试官：为什么选 SSE，不用 WebSocket [P0]

**核心结论：** 上行是离散命令、下行是持续事件，两者生命周期不同，所以命令走 HTTP、观察走 SSE。换成 WebSocket 仍要实现接受确认、恢复和去重，收益不抵成本。

> 用户上行主要是发送、停止、修改配置等离散操作，下行则持续输出文本与工具状态，因此当前用 HTTP 提交命令、SSE 订阅会话。一个任务可能在页面关闭后继续执行，重新打开页面需要重新订阅同一个运行实例，这使观察通道和任务本身有了独立生命周期。
>
> WebSocket 也能承载这套业务，而且适合更密集的双向交互，但换成一条连接仍要设计接受确认、任务结束、重连恢复和请求去重。当前选择的收益是命令接口清晰、事件订阅独立，代价是必须处理两条通道的先后顺序。若以后增加多人实时协作或高频双向控制，再重新比较协议与部署成本。

| 方案 | 在这个功能里的用法 | 主要代价 | 适合重新考虑的条件 |
| --- | --- | --- | --- |
| HTTP + SSE | 命令提交与会话事件订阅分开 | 握手、接受确认和恢复需要协调 | 当前的离散命令与持续下行输出 |
| WebSocket | 命令与事件共用双向通道 | 应用仍要实现确认、恢复和连接管理 | 高频双向协作成为主要交互 |
| 轮询 | 周期读取任务状态或增量结果 | 低频有延迟，高频有重复查询成本 | 只需低频完成状态，或用作恢复兜底 |
| fetch 响应流 | 自行读取响应分片并解析消息 | 需要管理消息边界、取消和重新订阅 | 需要更灵活的请求控制 |

### 追问：为什么不用一次 POST 直接返回流 [P1]

> 一次输入对应一次回答时，POST 返回流很直接。但这里任务属于服务端会话，过程中还有工具、压缩和追加指令，用户可以切走再回来。如果把观察完全绑定到最初的 POST，刷新后仍需要另一个入口查任务、恢复历史和接收后续事件。因此当前把提交与订阅分开，刷新只重建观察关系，不重复提交原命令。
>
> 用 fetch 消费独立事件接口同样可以保持这个架构，只是浏览器要自行处理流读取。两个问题要分别考虑：服务端任务是否独立于页面连接，以及浏览器用 EventSource 还是 fetch 接收输出。任务生命周期的设计比具体读取 API 更先决定恢复方式。

### 追问：HTTP 和 SSE 分开，第一批消息会不会丢 [P1]

发送处的关键顺序是先等待业务连接，再判断原操作是否仍有效，最后提交命令。

连接等待结束后，先比较当前会话与发送时保存的会话身份，再比较这一次打开会话的代次。两者都一致才继续提交；任一项变化，说明用户已经离开原来的操作上下文，本次等待结果作废。

通过检查后，才把本次输入提交给服务端。

`ensureConnected` 等待的是消息里的业务 `connected`，不是看到 HTTP 200 就通过。服务端可能已经打开流、发出了保持连接的注释行，但 SDK 还在初始化，此时发 prompt 仍可能早于监听安装。业务握手把“网络通了”和“会话订阅准备好了”分成两个时点。

中间的代次检查也有作用：等待握手期间用户可能已经切换会话。连接就绪仅表示可以收事件，不能证明原输入还应该发送到当前页面；检查不通过就丢弃旧操作。

### 追问：什么时候算提交成功，HTTP 要等整轮回答结束吗 [P0]

服务端有两个异步完成点：

| 完成点 | 说明什么 | 前端可以做什么 |
| --- | --- | --- |
| 预检接受 | SDK 已接纳本次调用 | 释放本次待确认输入，继续展示运行态 |
| 完整 prompt 结束 | 本轮调用完成或失败 | 结合事件清理状态、读取结果 |

包装器为接受阶段单独创建 Promise，SDK 成功预检时完成它；HTTP 等这个 Promise，完整执行的 Promise 则通过后续回调维护计数、错误和结束通知。如果预检前失败，HTTP 返回错误；如果已接受后才出错，通过事件报告。

这样短请求确认和长任务执行可以分开。HTTP 返回成功后立刻把 `isRunning` 设为 false，会把“已接受”误当成“已结束”。已有 [包装器测试](../../tests/server/utils/rpc-manager.test.ts) 特意让预检先通过、完整 prompt 保持未完成，检查命令已返回而运行计数仍保留。

## 3 刷新与恢复：三种数据各自补什么 [P0]

### 面试官：刷新后页面内存都没了，怎么接着显示 [P0]

**核心结论：** 页面只保存展示状态，任务由 Node 里的会话实例执行。刷新后按**历史 → 快照 → 事件**三层恢复：历史补已落盘内容，快照补当前未定稿消息，事件提供订阅之后的变化。

> 页面只保存展示状态，实际任务由 Node 里的会话实例执行。刷新之后先根据会话 ID 查询已保存的历史，再建立 SSE；服务端安装监听并发送当前运行标记，存在正在生成的助手消息时再补一份快照。前端用快照恢复流式草稿，后续 delta 继续追加，所以不需要把原问题再发送一遍。
>
> 这里要求服务端实例仍可提供运行态；服务进程也重启时，文件历史仍可读取，但内存里的执行过程和当前快照不能直接恢复。

### 追问：断线、刷新、进程重启分别能恢复什么 [P1]

三者的差别在于**哪些状态还在内存里**：

| 恢复方式 | 内存里还剩什么 | 能补回什么 | 补不回什么 |
| --- | --- | --- | --- |
| 刷新 | 全丢 | 历史、当前消息快照、重新订阅 | 断线期间已经定稿的其他消息 |
| 断线重连 | 旧页面的消息、运行标记、活跃工具 | 握手恢复运行态，快照替换流式草稿 | 同上，且终态判断依赖旧页面的活跃标记 |
| 服务端进程重启 | 实例、运行态、快照全丢 | 只能重读持久历史 | 中断的任务不能续接 |

**一个尚未覆盖的窗口：** 刷新后历史读完、订阅建立之前任务刚好结束，可能既没有最终历史，也没有流式快照。要补这个窗口，需要给快照和事件建立共同版本。

**现在没有事件日志回放。** `Last-Event-ID` 不是客户端带一个值就能补齐，服务端必须保存事件并实现补发。完整时序、反例与复现方法见 [04 §1](04-验证方案与源码索引.md)。

## 4 技术选型：为什么复用 Pi SDK [P0]

### 面试官：SDK 已经有 Agent 了，这个项目的技术工作在哪里 [P0]

**核心结论：** SDK 负责模型请求、工具循环与上下文；应用负责把这些过程组织成能操作、能恢复、能对账的工作台。真正的工程量在**执行系统与浏览器之间的状态契约**上。

> SDK 负责模型请求、工具循环、上下文与会话资源。应用负责把这些过程组织成用户能操作的工作台。例如同一会话的命令接口和事件接口要取得同一个实例；文本、思考与工具参数要被正确组装；两次同名工具调用要按调用 ID 配对；页面离开要清订阅，回来要恢复历史和运行态。编辑旧问题还要改变服务端上下文位置，运行中追加则要处理队列与停止的关系。
>
> 因此核心工作落在执行系统与浏览器之间的状态和交互契约上。工具循环能够产生结果，但不会直接提供适合 Vue 组件的状态，也不会替应用处理输入恢复、旧响应写回和文件 Inspector 的联动。

### 追问：为什么不自己写模型请求和 while 循环 [P0]

> 最小循环需要向模型发送上下文、识别工具调用、执行工具、把结果放回上下文并继续请求。对于验证一个工具流程，这样做已经足够。工作台还需要长期会话、取消、压缩、模型配置和扩展生命周期，复用 SDK 可以把应用工作集中到交互与一致性上。
>
> 代价是应用依赖 SDK 事件结构和运行语义。当前通过服务端包装器和事件适配层承接差异，并为预检、文本、工具元数据与结束处理保留测试。若项目目标转为研究任务调度或工具循环本身，自研更有价值；当前目标是交付工作台，维护完整运行时会扩大开发范围。

### 追问：为什么不是直接启动 Pi CLI 或走 RPC 子进程 [P0]

**核心结论：** 当前项目用的是**进程内 SDK**，不是子进程。项目文件名里的 `rpc-manager` 指的是“命令分发器”，不是与外部进程通信的 RPC。

先把三种形态分清楚，这三个词在面试里很容易被混着问：

| 形态 | 是什么 | 谁在用 | 事件怎么出来 |
| --- | --- | --- | --- |
| Pi CLI / TUI | 终端里的完整应用，自带交互渲染 | 直接使用 Pi 的用户 | 渲染在终端里，不对外暴露 |
| 进程内 SDK | 在 Node 里 `import` 库，自己创建会话对象 | **本项目** | `subscribe` 回调拿到事件 |
| RPC 子进程 | 宿主进程 spawn 一个 agent 进程，用协议通信 | 需要进程隔离的宿主 | 跨进程序列化后再解析 |

**本项目是第二种**，证据在 `server/utils/agent-services.ts`：它直接 `import { createAgentSessionServices } from "@earendil-works/pi-coding-agent"` 并在当前进程内 await 调用。项目里所有 `node:child_process` 的用法都指向 `git`（`server/utils/worktree.ts`、`server/api/file-index.get.ts`）和插件包管理（`server/utils/plugin-updates.ts`），没有一处是用来启动 Agent 的。

**为什么不在这个项目里选子进程：**

- **事件要跨边界。** 子进程方案要把 SDK 事件先序列化再过管道，等于在应用协议之外再加一层协议；进程内可以直接复用 SDK 的事件形状。
- **会话生命周期要自己管。** 实例注册、空闲回收、启动合并这些逻辑现在写在 wrapper 里；换成子进程后还要多管一层进程存活与重启。
- **共享配置是常态。** 代码注释里明确写了「pi CLI 与 pi-web 共享同一份配置是常态」，两边都直接读 `~/.pi/agent`，进程内接入不需要额外的配置同步。

**子进程真正的优势，以及什么时候会改选：** 隔离。当前所有工具都在 Node 进程权限下执行，一个失控命令影响的是整个服务进程。如果要做执行隔离、资源限制或多人服务，进程或容器边界是更自然的选择，那时这层 wrapper 会退化成客户端。

> 面试里被问「你这个 RPC 是怎么实现的」时，先纠正这个前提：它是进程内的会话包装器，不是跨进程 RPC。主动说清这一点，比顺着问题答下去安全得多。

### 追问：为什么必须有 Node，SDK 不能放浏览器吗 [P1]

**第 1 节已经从链路分层角度给过结论**（工具要碰本机、凭证不能下发、任务比页面活得久、SDK 进不了浏览器产物），这里补充这个选择带来的**部署边界**。

本项目的工具要访问本地工程、读取会话文件并可能执行本地命令，依赖的是服务端运行环境。浏览器负责命令和展示，Node 持有会话实例与文件访问能力。这样刷新页面只断开观察连接，不会主动销毁任务。

这个部署也限定了产品边界：当前是本机工作台。远程多用户化需要增加身份、目录归属、执行隔离和资源限制；仅把服务监听地址开放出去，仍会共享本地权限与进程资源。完整的边界清单与下一步优先级见本篇第 7 节。

## 5 工程选型：为什么是 Nuxt + Pinia [P1]

### 面试官：既然关闭 SSR，为什么还用 Nuxt [P1]

**核心结论：** 用 Nuxt 是因为页面路由、工程组织、共享代码和 Nitro 服务端 API 在同一个工程里；关闭 SSR 只是放弃服务端渲染，**不等于放弃服务端能力**。

> 当前使用 Nuxt 的页面路由、工程组织、共享代码和 Nitro 服务端 API。关闭 SSR 后，页面由浏览器渲染，但本地 SDK 仍由 Node 服务执行。产品重点是用户进入工作台后的持续操作，公开页面搜索收录不是主要需求，所以没有把 SSR 作为当前收益。
>
> Vite 加独立 Node 服务也能实现。差别是要分别维护页面与服务启动、路由、接口集成及部署约定。当前两部分在本机一起启动和迭代，一体化工程比较直接；如果以后 Agent 跑在远程执行机、需要独立扩缩容或单独发布，则应抽离执行服务。拆分时还要重新设计会话归属和路由，当前内存注册表无法直接跨实例共享。

### 追问：为什么用 Pinia，provide/inject 不也能共享数据 [P1]

输入框要看运行状态决定发送模式，消息区要展示当前草稿，工具区要读活跃调用，切会话又要统一清理这些状态。它们属于同一个业务生命周期，所以由 chat store 提供状态和动作，避免组件各自维护一份运行标记。

| 方式 | 在项目里的适用位置 | 要自己解决的事情 |
| --- | --- | --- |
| 组件局部状态 | 补全弹层、局部展开、输入框尺寸 | 组件卸载后是否需要保留 |
| provide/inject | 明确组件子树内的共享依赖 | 提供者的生命周期与更新约定 |
| Pinia store | 会话、工作区等跨组件领域状态 | 异步时序、状态归属和切换清理 |
| 纯函数 reducer | 内容块的确定性变换 | 由调用方执行网络与其他副作用 |

Pinia 与 reducer 没有重复：前者承接谁在什么时候执行什么动作，后者承接收到一个事件后内容怎样变化。具体块更新过程见 [05 前端流式对话](05-前端流式对话实现与优化.md)。

源码：[Nuxt 配置](../../nuxt.config.ts)、[chat store](../../app/stores/chat.ts)、[reducer](../../shared/lib/streaming-message.ts)。

## 6 项目的边界、不足与下一步 [P0]

### 面试官：这个项目最大的不足是什么 [P0]

**核心结论：** 功能面已经比较完整，缺的是**恢复协议**。断线期间发生了什么，服务端没有留下可补发的记录。

把这句结论展开成一张边界表，面试时按被问到的方向取用：

| 边界 | 当前真实状态 | 根因 |
| --- | --- | --- |
| 断线恢复 | 只能恢复当前正在生成的那一条消息 | 没有事件日志、事件序号和补发协议 |
| 多标签并发改同一会话 | 本页有序，跨窗口不保证 | 服务端只有单实例内的互斥与串行 |
| 服务进程重启 | 历史可读，任务不能续接 | 执行状态与快照都在内存里 |
| 会话分支 | 能读、能切换、能改旧问题重发 | 没有独立的 fork 创建流程 |
| 重复提交 | 传输失败会提示核对历史 | 没有命令 ID 与幂等接纳记录 |
| 自定义业务工具 | 能管理资源，没有注册工具 | 只做静态扫描与包管理 |
| MCP | 能力中心显示未接入 | 没有 Bridge，也没有服务注册表 |
| 长回复性能 | 有定位顺序，没有测量基线 | 没有可复现的性能数据，不填提升比例 |
| 停止任务 | 有撤回队列与 abort | 没有请求超时闭环 |

**这张表本身就是回答质量的一部分。** 能把“哪些做了、哪些只是 SDK 提供但项目没接、哪些是下一步”分清楚，比声称全都做完更可信。项目里每条边界的写法都可以在 [04 验证方案与源码索引](04-验证方案与源码索引.md) 找到对应的复现路径。

### 面试官：这套东西现在能放到服务器上给别人用吗 [P0]

**核心结论：** 不能。它现在是一个本机工作台，不是一个多租户服务。

三件事必须同时说清：

1. **接口没有鉴权。** `server/api` 下的路由任何人都能直接调用，只要能访问到这个端口。
2. **工具继承进程权限。** Agent 可以执行 shell 命令、读写文件，它的权限边界就是启动这个 Node 进程的用户的权限，**没有额外沙箱**。
3. **文件接口的路径校验不是执行隔离。** 预览接口会做路径规范化与目录边界检查，防止读取工作区之外的文件，但那只约束“预览”这一条读路径，管不了 Agent 自己执行命令时的行为。

同理，Pi 的 **project trust 也不是工具沙箱**。它决定的是项目级资源（`.pi/` 下的扩展、技能、插件）是否允许加载，回答的是“要不要信任这个仓库带来的代码”，不是“运行这个命令安不安全”。信任之后，扩展与命令同样继承进程权限。

> **一条硬边界：** 不要把它暴露到公网或做内网穿透。启动参数固定绑在 `127.0.0.1`，这是有意为之，不是没来得及配。要产品化，先做身份、目录归属、执行隔离和资源限制，再谈开放监听。

### 面试官：如果继续做，第一优先级是什么 [P0]

按“解决根因 → 收窄竞态 → 建立事实”排序，不按功能热度排：

| 优先级 | 要做什么 | 为什么排在这里 | 怎么算做完 |
| --- | --- | --- | --- |
| P0 | 给服务端事件加序号与游标，恢复时返回带游标的历史 + 当前消息，再衔接游标之后的事件 | 断线、刷新、切会话三类问题的根因都是“不知道丢到哪了” | 用可控测试构造“查询与订阅之间任务结束”，能补齐终态 |
| P1 | 客户端生成命令 ID，服务端记录接纳状态，同 ID 重试返回原状态 | 现在“接受态未知”只能靠提示用户核对历史来兜底 | 重复提交同一 ID 不产生第二次执行 |
| P2 | 停止流程加超时与状态回执 | 停止是唯一会改变服务端行为的前端操作，卡住时用户无路可走 | 超时后界面能区分“已停”与“未知” |
| P3 | 建立前端性能基线：固定内容、固定 delta 时间表，分别记录事件处理、解析、DOM 与布局 | 没有基线就只能猜瓶颈，也就没法诚实地写优化成果 | 能指出占比最大的那一段，而不是只能说“感觉更顺” |
| P4 | 加鉴权与执行隔离 | 这是产品化的前置条件，不是当前原型的缺陷 | 未评估前不宣称可以多人使用 |

**为什么把事件序号排第一而不是先把功能做多：** 后面每一项都会依赖“现在到底哪一条事件生效了”这个判断。恢复协议不补，编辑重发、队列、压缩这些功能每加一个，就要多写一套代次与版本守卫；补上之后，这些守卫才有统一的判据。

## 深入参考（P2）

这一区的内容**查得到就行，不需要背**：低频框架比较、与学习篇重复的原理，以及尚未落地的优化方向。

### 为什么选 Vue 而不是 React

**结论：** 两个框架都能实现这条链路，选择 Vue 是因为熟悉度与组件组织方式，**没有同功能性能基准证明换 React 会有收益**。

> 这个工作台需要持续把事件转成页面状态。Vue 的响应式数据、模板和 composable 能组织这条链路，React 的 state、reducer 和 hook 也能实现。选择 Vue 后，具体落地是 Pinia 持有会话业务状态，纯 reducer 处理结构化消息，组件展示文本、工具和输入交互。

真正有区别的是**框架适配细节**，这些才是继续用当前栈的理由：

- Vue 深响应式读取会产生代理对象，原始对象引用比较要单独处理。
- reducer 返回的新状态必须整体写回 reactive 容器，不能就地改属性。
- `EventSource` 这类代理敏感对象放在闭包，生命周期由业务管理。

### 长回复为什么会卡（原理与测量详见 05）

**结论：** 流式只表示结果逐步到达，不保证每一步处理都便宜。当前 reducer 按块追加增量，但消息组件仍可能对累计文本重新执行 Markdown 解析与代码高亮，文本越长重复扫描越多。

**定位顺序（测不出数字就不写优化收益）：**

1. 用相同内容加固定 delta 时间表跑一遍。
2. 分别记录事件处理、解析高亮、DOM 提交与布局的耗时。
3. 按占比决定先动哪一层 —— 解析占主要时间就先减少稳定块的重复计算，DOM 多再评估虚拟列表，主线程长时间被占再考虑 Worker。

**为什么不只解析新增字符：** Markdown 后续字符会改变之前内容的结构（代码围栏要闭合、列表要延续），每个 delta 不一定是完整语法单位，分别解析再拼 HTML 可能与全文解析结果不同。

**当前已经实施的**只有事件裁剪、内容块组装与展示职责分离。块级渲染缓存、虚拟列表、Worker、按帧合并都属于**候选优化，尚未实现**。完整的性能追问、判据表与测量边界见 [05 §5](05-前端流式对话实现与优化.md)。
