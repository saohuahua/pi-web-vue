## 六、事实边界

**已实现且有代码依据**

- SDK 在 Node 服务端承载，浏览器只通过 HTTP 命令 + SSE 事件交互
- 会话实例跨请求复用与并发合并（`registry` + `locks`）
- 命令接纳与整轮完成两个时点的区分（`preflight` / `prompt`）
- SDK 事件到 wire 事件的裁剪适配（`toClientAgentEvent`）
- 纯函数 reducer 组装流式消息（`streamReducer`）
- 三层判据 + 队列版本守卫异步结果
- 编辑历史消息后从父节点开分支（`navigate_tree`）
- 停止前先撤回队列（`clear_queue` 等接纳链）
- 图片三层防护（客户端压缩 / 前端校验 / 服务端再验）

**SDK 提供、项目只是消费**

- Agent 执行循环、工具调用与执行、模型调用
- 会话文件（JSONL）读写与 entry 树
- **上下文压缩算法**（手动 `compact()` 与自动阈值触发都在 SDK 内）
- `agent_settled` 事件（`agent-session.d.ts:47`）
- 分支导航 `navigateTree`

**尚未实现**

| 未实现 | 说明 |
| --- | --- |
| **事件重放 / 断点续传** | SSE 重连只补订阅之后的增量，无事件序号和游标 |
| **任务级恢复** | 服务端进程重启后执行无法恢复 |
| **任务持久化** | 无独立任务队列、无执行状态落库 |
| **`fork`** | `rpc-manager.ts:365` 是抛错占位，分支能力走 `navigate_tree` |
| **结果验证层** | 界面展示的是执行过程，不判断任务是否真的成功 |
| **MCP 接入** | `McpPanel.vue` 是纯占位，只有空状态文案，无连接逻辑 |
| **RAG / 多用户 / 多 Worker** | 均未实现 |
| **请求取消 = 任务停止** | 不等价，`abort` 不保证在固定时间内结束 |
| **单条撤回队列** | Pi 只支持清空全部队列 |

> 涉及**未实现能力**的题（RAG 设计、MCP 完整接入、多用户/多 Worker 部署、Workflow 选型、Agent 评估）**不在本文档范围内**——它们在面试中只能作为「扩展设计」讨论，且必须先声明未实现。需要时单独准备。

**待核实**

- `isEventIncludedInSnapshot` 用引用相等（`event.message === snapshot`），SDK 是否稳定复用同一对象引用**未在真实链路验证**
- `tool_execution_end` 到 `message_end` 之间卡片显示「完成」的窗口是**代码路径推导**，未做真机验证
- `chat.ts:562` 的 `syncFromSessionCwd` 缺 sessionId 守卫是**代码推导**，未做真机验证
- 长回复渲染性能无实测数据，文档中不出现任何性能提升比例

## 七、最容易说错的五条

1. **把 SDK 能力说成自研**——压缩算法、工具执行、模型调用都是 SDK 的
2. **把界面恢复说成任务恢复**——刷新能恢复界面，服务端重启任务就没了
3. **把请求返回说成任务结束**——落定要等 `agent_settled`
4. **把「有工具调用但没有结果」说成完成**——当前实现会显示成「完成」，是真实误导
5. **说「做了结果验证」**——项目没有验证层，展示的是执行过程而非结果可信度

详细的纠错说明在 02 篇小结与 03 场景 F。
