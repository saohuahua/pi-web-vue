# 第一部分：项目专项

## 场景 A：Agent 执行到一半用户改主意，怎么保证行为符合预期？【P0】

**场景**：用户让 Agent 修登录 Bug。Agent 正在读文件、跑命令，用户发现范围太大，追加一句「先不要改文件，只分析原因」。过了一会儿又决定彻底停止。

**核心结论**：这是三个不同操作，走不同路径——**追加指令**是入队、**停止**要先撤回队列再 abort、**撤回**要等服务端的接纳判断。

**① 追加指令：为什么不让前端判断该入队还是开新轮**

`usePromptQueue.ts` 的 `submitQueuedPrompt` 走的是 `prompt` 命令加 `streamingBehavior` 字段，不是独立的 steer/followUp 命令。注释说明了原因：

> SDK 在接纳时判断入队或开启新轮 前端不根据过时的运行状态猜测

两种模式的语义差别：

| 模式 | UI 文案 | 投递时机 |
| --- | --- | --- |
| `steer` | 「立即纠偏」 | 当前 assistant turn 的工具调用跑完后、**下一次 LLM 调用之前** |
| `followUp` | 「本轮后继续」 | **等 agent 完全停下来**才投递 |

判断依据是 SDK 内部的流式状态，前端持有的是可能过时的副本。如果前端根据本地状态猜，猜错会导致「以为入队了其实开了新轮」。

**② 停止：为什么必须先撤回队列再 abort**

`chat.ts:685` 的注释给了理由：

> Pi 在 abort 后可能继续尚存的队列 因此必须先撤回再停止

SDK 的 RPC 文档印证了这一点：`abort` **不会丢弃队列**，剩余的 steer/followUp 还会继续执行。如果不先撤回，用户以为停了、任务却还在跑。

**撤回失败就不 abort**（`chat.ts:688-691`）：队列状态未知时中止会话，会让未知数量的指令继续执行，而且没有恢复手段。所以宁可保持运行态并提示「队列未确认 当前任务仍在运行」。这条路径有测试覆盖（`tests/app/stores/chat-queue.test.ts`）。

**③ `clear_queue` 为什么要等服务端的接纳链**

```ts
// server/utils/rpc-manager.ts:353-356
case "clear_queue":
  // 等当前 prompt 完成接纳判断 再取 SDK 实际尚未消费的队列
  await this.promptAdmissionTail
  return this.inner.clearQueue()
```

**如果抢在接纳判断之前执行**：

1. `clearQueue()` 返回空数组，前端以为「队列已空」
2. 紧接着那条 prompt 被接纳进队列
3. 结果是**前端显示无队列、草稿也没回填，但服务端还有一条指令会继续执行**

测试 `tests/server/utils/rpc-manager.test.ts` 断言：prompt 未 accept 前 `clearQueue` 一次都没被调用。

**④ 3 秒兜底定时器**

`abort` 的 POST resolve 与 `agent_settled` 事件可能乱序或丢失，所以 3 秒后若仍是同一会话、同一代次且 `isRunning` 还是 true，强制落定并 reload 对账。`agent_settled` 先到会 `clearTimeout`。

**为什么是 3 秒**：`abort()` 内部会等会话真正 idle，等待时间不确定。3 秒是「绝大多数情况足够，又不会让用户觉得卡住」的折中——**经验值，不是测量得出的**。

**边界**

| 边界 | 说明 |
| --- | --- |
| 只有「全部撤回」 | Pi 只支持清空全部队列，没有单条撤回 |
| 停止返回 ≠ 工具已停 | HTTP 返回只代表 abort 命令被接纳 |
| 撤回不保证 SDK 没消费 | `clear_queue` 返回的是「尚未消费」的部分 |

**迁移思路**

**取消一个长任务时，先处理「排队中的后续动作」，再处理「正在执行的动作」。** 很多系统的 abort 语义只中断当前执行，不会清空已排队的消息——如果产品上「停止」意味着「完全停下来」，就必须显式处理队列。

另外，**撤回操作需要等服务端的接纳判断完成**，因为「命令是否已进入队列」在客户端是不可知的。这条原则适用于任何「客户端发起、服务端异步接纳」的队列系统。

**口述版**

> 这个问题我会先拆开看：用户「改主意」在系统里其实是三个不同操作，时序约束完全不一样。
>
> 第一个是追加指令。这里有个判断我刻意没有放在前端做——「这条指令该插到当前轮里，还是等当前轮跑完再说」。因为做这个判断需要知道服务端此刻的执行状态，而前端手里那份是可能过期的副本。如果前端自己猜，猜错就变成「用户以为插进去了，其实是开了新一轮」。所以我把判断交给服务端，在接纳的那一刻决定。
>
> 第二个是停止。这里有个**不直观的地方**：我原以为中止会把排队的东西一起清掉，后来发现不是——中止只中断当前执行，队列里剩的指令还会继续跑。用户点了停止、界面显示停了，实际上还有指令在排队等着执行。这跟用户预期是相反的。
>
> 所以我改成**先撤回队列、再中止**。而且如果撤回失败，我**直接不执行中止**——因为这时队列状态是未知的，贸然中止会让未知数量的指令继续执行，而且没有任何恢复手段。宁可保持运行态、告诉用户「队列没确认」，也不要造成一个「看起来停了其实没停」的状态。
>
> 第三个是撤回本身。撤回请求必须等接纳判断结束才能执行，因为命令从发出到真正进队列是异步的。撤回抢在前面会拿到一个空队列，让前端以为清干净了——紧接着那条命令才被接纳进去。
>
> 另外我还加了一个**兜底**：中止的响应和最终落定事件可能乱序甚至丢失，所以设了一个几秒的兜底定时器，超时就强制落定并对账。
>
> 这里的通用原则是：**取消长任务时，要先处理排队中的动作，再处理正在执行的动作**。很多系统的取消语义只管后者。

**关键追问**

```text
Q: 为什么不做单条撤回？
A: 底层只支持清空全部队列，没有按条撤回的接口。
   要做单条撤回得在客户端维护队列的完整镜像，
   而且要处理「我以为是第 2 条，但服务端已经消费了第 1 条」的时序问题。

Q: 撤回的文本放回草稿时为什么放在最前面？
A: 撤回的文本是用户要重试的内容，应该紧邻光标起始位置。
   如果拼在后面，用户容易误发一段「新想法 + 旧文本」的混合内容。
```

## 场景 B：用户想从第 3 轮改起，怎么保证分支语义正确？【P0】

**场景**：用户在第 8 轮发现第 3 轮的条件写错了，想回到第 3 轮改一下再继续。

**核心结论**：不是「修改那条消息」，而是「从它的**父节点**开一条新分支」。关键是编辑目标用的是**父 entry 的 id**。

**流程**

```text
① 点编辑按钮 → chat.ts:244 beginEditMessage(index)
   ├─ 五重互斥：pendingDraft / isRunning / isCompacting /
   │            isNavigating / positionUnknown 任一为真就拒绝
   ├─ 结构判定：前面至少有一条 user 消息（第一条不可编辑）
   ├─ 目标判定：必须是 user 角色且有 entryId
   ├─ parentId = findEntryParentId(tree, messageId)   ← 关键
   └─ draftBeforeEdit = draft.value（供取消时还原）
      editingTargetId = parentId        ← 导航目标
      draft.value = 原消息文本

② 改完点发送 → chat.ts:274 submitPrompt(text, images)
   ├─ pendingDraft = {...}  清空输入框  落盘
   ├─ await navigateToLeaf(editingTargetId)    ← 先导航
   ├─ await sendPrompt(text, images)            ← 再发送
   └─ 成功清编辑态；失败 mergeDraftText 回填
```

**① 为什么编辑目标是父 entry 而不是这条消息**

`editingTargetId` 不是 UI 传进来的，而是 `findEntryParentId(tree.value, messageId)` 从会话树里现算出来的父 entryId。

**原因**：如果导航到这条消息本身，新 prompt 会挂成它的**子节点**——那就变成「在它后面继续对话」，编辑退化成追加。导航到**父节点**，新消息才会成为原消息的**兄弟**，形成真正的分支。

**这和 CLI 的 `/tree` 语义一致**：SDK 文档（`docs/sessions.md:104-108`）说明，选中一条用户消息时，pi 也是「把 leaf 移到该消息的父节点，然后把消息文本放进编辑器」。

**② 为什么必须先导航再发送**

顺序是 `navigateToLeaf(target)` → `sendPrompt`。**顺序反过来**，新消息会追加到当前活跃叶子（原消息的子孙）之后，会话文件里就变成了覆盖式追加而不是分叉。

**③ 为什么先预览再导航**

`useSessionNavigation.ts` 的注释：

> 先预览再导航 防止无效目标改变服务端分支
> 导航之后只信权威详情 失败时尽量回到原叶子

预览走只读接口，能提前发现非法 leaf、断链、环。`navigate_tree` 是唯一有副作用的动作，一旦执行就改写服务端活跃叶子。**先预览把「目标根本不可用」这类失败挡在副作用之前**。

**④ 导航失败的回退逻辑**

`commandSent` 标志是关键分叉：

| 阶段失败 | 处理 |
| --- | --- |
| 预览阶段（`commandSent === false`） | 不发回退命令，服务端理论上没动过 |
| 导航之后（`commandSent === true`） | **先重新读取再决定是否回退**——请求失败可能发生在服务端导航之后 |

如果确认叶子偏离了原位置，就反向导航回 `previous`；回退也失败的话置 `positionUnknown = true`，全线锁死发送、编辑、队列提交和分支导航，界面显示「重新加载」。

**为什么要有 `positionUnknown`**：它表达「我不知道服务端现在的位置了」。这种情况下继续发送会导致消息挂到错误的分支上。与其猜，不如让用户重新加载。

**⑤ 取消编辑的取舍**

`cancelEdit` 把 `draft` 覆盖回 `draftBeforeEdit`，**编辑期间敲的文本会丢弃**。这是显式取舍。

`draftBeforeEdit` 的赋值有 `if (!editingMessageId.value)` 条件：**只在首次进入编辑态时记录**。连续改编辑目标时不会覆盖它，所以「取消」永远回到进入编辑态之前的原始草稿。

**边界**

| 边界 | 说明 |
| --- | --- |
| **没有 fork / clone** | `rpc-manager.ts:365` 是抛错占位；当前分支能力是 `navigate_tree`（**同一个会话文件**内移动 leaf 指针） |
| 分支入口会隐藏 | 没有分叉时 `branches` 为空数组，按钮整体不渲染 |
| 第一条用户消息不可编辑 | 它没有父节点，无法定位导航目标 |

> **关于 fork 的准确说法**：pi CLI 有 `/fork`（从历史用户消息创建**新会话文件**）和 `/clone`（复制当前分支成新会话）。本项目**没有实现**这两个。这不是能力缺口，而是产品选择——当前 UI 只提供「会话内探索替代方案」。如果要支持「另起一个会话文件」的语义，需要补一条 RPC 命令并新增对应的会话文件。

**迁移思路**

**编辑历史 = 创建分支，而不是修改数据。** 这是 append-only 历史结构的必然推论：如果历史不可变，那「修改第 3 轮」只能表达为「从第 3 轮之前分叉出一条新路径」。理解了这一点，就能推导出「编辑目标必须是父节点」，而不是死记这个结论。

配套的两个通用原则：

- **有副作用的操作先做只读校验**。预览不产生副作用，导航产生副作用，先预览能把无效输入挡在副作用之前。
- **副作用操作失败后，不能假定「没发生」**。请求超时可能是「服务端已执行但响应丢了」，所以要先重新读取真实状态，再决定是否回滚。

**口述版**

> 这个问题我会先重新理解「编辑历史」的语义。我一开始的想法是「修改那条消息」，很快就发现这个思路是错的。
>
> 为什么错？因为会话历史是**只追加**的结构——消息一旦写进去就不可变，这样才能支持分支。既然不可变，「修改第 3 轮」就只能表达成「从第 3 轮之前分叉出一条新路径」。所以编辑的落点不是那条消息本身，而是它的**父节点**。
>
> 这个结论是推导出来的。它同时解释了为什么发送前必须先导航：如果导航到消息本身，新消息会挂成它的子节点，那就变成「在它后面继续对话」，编辑退化成追加了。只有导航到父节点，新消息才会成为原消息的**兄弟**。
>
> 我后来查了上游文档，发现 CLI 的树导航也是这个语义——选中一条用户消息时，也是把位置移到父节点、把文本放进编辑器。所以这不是我独创的，是这类结构的自然结果。
>
> 第二个设计点是**先预览再导航**。导航是唯一有副作用的操作，一旦执行就改变了服务端的位置；预览是只读的，能提前发现非法目标、断链。把校验放在副作用之前，就避免了「已经跳过去了但目标是坏的」这种必须回滚的局面。
>
> 第三个是**失败处理**，我区分了两种情况：失败在预览阶段，说明服务端理论上没动过，不需要回退；失败在导航之后，那**不能假定「没发生」**——请求超时可能是「服务端已经执行了但响应丢了」。所以要先重新读取真实状态，确认偏离了才反向导航回去。如果回退也失败，我会置一个「位置未知」的状态，把发送、编辑、导航全部锁死，让用户重新加载。因为这个状态的意思是「我不知道服务端现在在哪」，继续操作只会把消息挂到错误的分支上。
>
> 最后一个边界：项目**没有实现分叉和克隆**。它们是创建新会话文件的语义，我这里的导航是在同一个文件里移动指针。这是产品选择，不是能力缺口。

**关键追问**

```text
Q: 为什么要用 entryId 而不是数组下标？
A: 数组下标是当前视图的位置，reload 之后会变。
   entryId 是会话文件里的稳定标识。
   这也是 messages 和 entryIds 要维护成平行数组的原因。

Q: 如果服务端已经切换分支，但 HTTP 响应超时了？
A: 这正是 commandSent 标志存在的原因。收到异常时不能假定
   服务端没动过，要先 reload 看实际位置，确认偏离了才反向导航。
```

## 场景 C：用户快速切换会话，旧请求才返回，怎么防止状态污染？【P0】

**场景**：用户在会话 A 发起历史查询，马上切到 B，此时 A 的响应才回来。

**核心结论**：靠**三层判据**在写入点拦截，而不是靠取消请求。

**推导路径**

- **场景**：A 的请求在切到 B 之后才返回
- **错误**：B 的消息列表、模型名、上下文用量被 A 覆盖
- **原因**：异步完成时页面归属已经变了
- **方案**：写入点校验三层身份
- **取舍**：取消请求能省资源，但写入点校验能直接阻止过期结果生效
- **边界**：所有跨 `await` 修改状态的路径都要检查是否遗漏校验

**三层判据各防什么**

| 层 | 防的竞态 | 为什么前一层不够 |
| --- | --- | --- |
| `sessionId` | 已切到别的会话 | — |
| `sessionGeneration` | A→B→A 之后旧响应回来 | A→B→A 后 sessionId 又匹配，但响应反映的是几轮之前的状态 |
| `reloadSequence` | 同会话内两次 reload 乱序返回 | 两次的 sessionId 和代次都相同，但旧的可能后返回 |

**第二层的具体场景**：

```text
t0  打开 A          sessionId = A, generation = 0
t1  发起 reload(A)  sequence = 1
t2  切到 B          close() → generation = 1
t4  切回 A          close() → generation = 2
t6  t1 的响应回来    sessionId 匹配 ✅ 通过第一层
                    但 generation 是 0 ≠ 2 → 拒绝 ✅
```

**第三层的具体场景**：

```text
t0  agent_end 到达      → reload()  sequence = 1
t1  agent_settled 到达  → reload()  sequence = 2
t2  t1 的响应先回来      sequence 匹配 → 写入 ✅
t3  t0 的响应后回来      sequence 不匹配 → 拒绝 ✅
```

最严格的一处校验在 `chat.ts:224` 用满三层：

```ts
if (sessionId.value !== id || generation !== sessionGeneration || sequence !== reloadSequence)
  return null
```

**校验点分布**（源码确认）：`chat.ts` 13 处，`useSessionNavigation.ts` 8 处，`useSessionRuntime.ts` 8 处，`usePromptQueue.ts` 4 处。**原因是每个 `await` 之后都要重新确认**。

**为什么不用 AbortController**

| 方式 | 问题 |
| --- | --- |
| 取消请求 | 需要每个请求传 signal；而且**取消请求不等于阻止回调执行**——已缓冲的数据仍可能触发回调 |
| **写入点校验**（当前） | 简单可靠，不改请求层 |
| 每会话独立 store | 内存开销大，跨会话共享的数据不好处理 |

**一处缺口**：`chat.ts:542` `openSession` 里编辑态恢复有 `sessionId.value === id` 守卫，但 `chat.ts:562` 的 `syncFromSessionCwd(info.cwd)` **没有**。极快切会话时旧会话的 `cwd` 可能覆盖新工作区选择器。影响范围限于选择器显示，不影响消息数据。**静态推导，未实测**。

**迁移思路**

**取消请求和阻止过期结果生效是两件事。** 取消能省带宽，但不能保证回调不执行——已经缓冲的数据仍可能触发回调。所以在写入点校验是更可靠的防线。

三层判据可以抽象成一条通用规则：**异步结果写入状态前，要确认「归属」和「代次」**。

- **归属**回答「这个结果属于哪个实体」（会话 ID、文档 ID、查询 ID）
- **代次**回答「这个结果是不是最新一次操作的」（版本号、递增计数）
- 两者缺一不可：只有归属，会漏掉「同一个实体被重复操作」；只有代次，会漏掉「实体已经换了」

这个模式直接适用于：搜索联想、表单异步校验、切换详情页、并发保存、图片上传进度。

**口述版**

> 这个问题的本质是：**异步结果返回时，发起它的上下文可能已经不存在了**。
>
> 我会先说一个判断：**不要试图用取消请求来解决这个问题**。因为取消请求和阻止过期结果生效是两件事——取消能省一点带宽，但**不能保证回调不执行**，已经缓冲的数据仍然可能触发回调。所以我的做法是在**写入点校验**，也就是数据真正写进状态之前，判断「这个结果还算不算数」。
>
> 这三层是逐步加出来的，不是一开始就设计好的。起点是加了会话 ID 校验，防「响应回来时已经切到别的会话」。用了一段时间发现不够——用户从 A 切到 B、再切回 A，这时候会话 ID 又匹配了，校验会放行，但那个响应是**第一次**打开 A 时发的，中间 A 已经被关闭过，可能已经有新消息了。所以我加了第二层：操作代次，每次关闭会话时递增，请求发出前记下，回来时比对。
>
> 还有漏的吗？有。同一个会话里连续触发两次对账很常见，比如两个结束事件挨得很近。这两次的会话 ID 和代次都相同，但**第一次的响应可能因为网络抖动晚于第二次返回**，携带更旧的数据，界面会「倒退」。所以加了第三层：查询序号。
>
> 抽象出来是一条规则：**异步结果写入状态前，要同时确认「归属」和「代次」**。归属回答「属于哪个实体」，代次回答「是不是最新一次操作」，两者缺一不可——只有归属会漏掉「同一实体被重复操作」，只有代次会漏掉「实体已经换了」。
>
> 这个模式不只适用于会话切换。搜索联想、表单异步校验、切换详情页、并发保存，都是同一个问题。
>
> 我也知道一个缺口：有一处同步工作区数据的代码没加会话 ID 守卫。这是从代码推导的，**没实测过**，影响范围限于选择器显示。

**关键追问**

```text
Q: 怎么构造这个竞态来测试？
A: 不 await 就切换。先拿到 pending promise，
   立刻调 openSession("B")，再 await pending。
   tests/app/stores/chat-races.test.ts 里有 9 个这样的用例。

Q: 如果旧结果真的污染了状态，怎么排查？
A: 先确认污染的是哪个字段，再搜这个字段的所有赋值点，
   检查每个赋值点上游有没有校验。重点看跨 await 的写入。
```

## 场景 D：工具调用已展示但结果没回来，界面该显示什么？【P1】

**场景**：用户看到工具卡片一直显示「执行中」，或者突然显示「完成」但结果区是空的。

**核心结论**：关联标识是 `toolCallId`，**没有第二个标识**。而且**没有收到结果，不等于工具成功或失败**——它是一个「未知」状态。

**四种异常输入的实际行为**（源码确认）

| 异常 | 实际行为 | 后果 |
| --- | --- | --- |
| `toolCallId` 缺失 | 归一化双字段兼容，都没有则给**空串** | 多个缺 ID 的工具**互相串** |
| `toolCallId` 重复 | `map.set` 后写覆盖先写 | 只保留**最后一个**结果 |
| 结果找不到调用 | 渲染成 `aria-hidden` 空 div | **孤儿结果不显示** |
| 调用找不到结果 | 查不到 → `result` 是 undefined | 见下面的窗口 |

**一个状态错误窗口（静态推导，未实测）**

```ts
// app/components/ToolCallCard.vue:54-56
const isRunningTool = computed(
  () => !props.result && (props.streaming || chat.activeTools.has(props.block.toolCallId)),
)
```

| 情况 | `activeTools` 有 | `streaming` | 显示 |
| --- | --- | --- | --- |
| 工具正在执行 | ✅ | false | 「执行中」 |
| **执行完但结果没到** | ❌ | false | **「完成」**（错误） |
| 消息还在流式 | 任意 | true | 「执行中」 |

第二行是问题：`tool_execution_end` 到达时 `activeTools.delete(id)` 立即执行，但结果消息要等后续的 `message_end` 才进 `messages`。这个窗口里卡片会短暂显示「完成」且结果区为空。

**为什么必须独立维护 `activeTools`**

助手消息在工具**开始执行之前**就定稿了。时序是 `message_end`（定稿）→ `tool_execution_start` → `tool_execution_end` → `message_end`（结果）。定稿后 `streaming` 已经是 false，光看消息判断不出工具还在跑。

**UI 应该如何表达「未知」**

工具结果缺失时有三种可能：

1. 工具还在跑
2. 工具跑完了，但结果事件丢了
3. 工具根本没启动（比如服务端中途重启）

当前实现把第 2、3 种情况都显示成「完成」——**这是把未知说成了成功**。更准确的表达应该引入第三态：

| 状态 | 判定 | 含义 |
| --- | --- | --- |
| 执行中 | `activeTools` 命中 | 确定在跑 |
| 完成 | 拿到 `result` 且 `!isError` | 有证据的成功 |
| 出错 | 拿到 `result` 且 `isError` | 有证据的失败 |
| **未确认** | 没拿到 `result` 且不在 `activeTools` | **不知道结果** |

**改进建议（成本极低，纯前端）**：会话文件里如果存在「有 toolCall 但没有对应 toolResult」的助手消息，说明执行被中断了。前端可以把这类卡片标记为「未完成」。`toolResultsByCallId` 查不到就是未完成，**不需要服务端改动**。

**迁移思路**

**「没有收到结果」是一个独立的状态，不等于成功也不等于失败。** 很多 Agent 界面默认把「没有报错」显示成成功，这在工具结果丢失、进程重启、事件断流时都会误导用户。

通用的做法是：**用证据驱动状态，而不是用「没消息就是好消息」推断状态**。

- 有明确成功信号 → 成功
- 有明确失败信号 → 失败
- 两者都没有 → **未确认**，并且要告诉用户「这个结果无法确认」

这条原则适用于任何「发起操作 + 异步等待结果」的界面：支付、构建、部署、数据同步。

**口述版**

> 这个问题我会分两层答：先讲**怎么关联**，再讲**界面该显示什么**，因为第二层更值得说。
>
> 关联这层相对直接：工具调用和结果不是同一条消息，所以需要一个标识把它们串起来。我把这个关联做成**派生值**而不是独立状态——独立状态就要手动同步，很容易漏；派生值自动跟着消息列表重建，只有一份事实来源。
>
> 但这里有个**我一开始判断错的点**。我原以为可以用「消息是不是还在流式」来判断工具在不在跑，后来发现不行：**助手消息在工具开始执行之前就已经定稿了**。定稿之后流式标记已经是 false，但工具才刚开始跑。所以我另外维护了一个「正在执行的工具」映射。
>
> 接下来是我认为更值得讲的部分：**界面该显示什么状态**。
>
> 有三种情况会导致「没有结果」：工具还在跑、结果事件丢了、工具根本没启动。当前实现把后两种都显示成「完成」——**这等于把未知说成了成功**。用户看到「完成」就会以为可以继续下一步，这是真实的问题。
>
> 我的想法是引入第四种状态：**未确认**。判断规则很简单——拿不到结果、也不在正在执行的集合里，就是未确认。这个改动纯前端就能做，成本几乎为零，但它消除的是**主动误导**。
>
> 抽象出来是一条原则：**用证据驱动状态，而不是用「没消息就是好消息」来推断**。有明确成功信号才算成功，有明确失败信号才算失败，两者都没有就应该显示「无法确认」。这条原则适用于所有「发起操作 + 异步等结果」的界面，比如支付、构建、部署。

**关键追问**

```text
Q: 两个工具同时执行会串吗？
A: 不会。activeTools 是 Map，可以同时存多条，
   状态条用 v-for 全部展示。块顺序由 contentIndex 保证。

Q: 为什么要区分「未知」和「失败」？
A: 因为用户对这两种情况的处理方式不同。
   失败可以重试，未知需要先确认状态再决定。
   把未知显示成成功会让用户以为可以继续下一步。
```

## 场景 E：SSE 重连后内容重复或缺失，怎么恢复？【P1】

**场景**：网络抖动后 SSE 自动重连，用户发现同一段文本出现两次，或者中间少了一段。

**核心结论**：**快照本身不会导致重复**（它是整体替换），重复来自三个地方；而缺失是**必然的**，因为断线期间的事件没有任何补发机制。

**先排除一个常见误解**

`snapshot` action 是**整体替换** `streamingMessage`，不是追加：

```ts
// shared/lib/streaming-message.ts:136-141
case "snapshot": {
  const message = normalizeStreamingToolCalls(action.message)
  return message.role === "assistant"
    ? { isStreaming: true, streamingMessage: message }   // ← 整体替换
    : state
}
```

**重复的三个真实来源**

**① 快照去重失效（待核实）**

`shared/lib/agent-event-wire.ts:112-119` 用**引用相等**判断事件是否已包含在快照里：

```ts
return snapshot !== undefined
  && (event.type === "message_start" || event.type === "message_update")
  && event.message === snapshot
```

单元测试（`tests/shared/lib/agent-event-wire.test.ts`）用手工构造的同一对象验证了逻辑，但**没有验证真实链路上 SDK 是否稳定复用同一对象引用**。如果 SDK 每次克隆 `message`，这条去重会永远失效。

**② 重复的 `text_delta`**：reducer 没有事件去重，`text_delta` 是 `current.text + event.delta`，处理两次就是两份文本。

**③ `messages` 层面的重复**：`message_end` 里对**用户消息**有去重（靠 `optimisticKey`），但对 **assistant 消息没有**——直接 push。

**不过**：`agent_end` 和 `agent_settled` 都会触发 `reload()`，而 reload 是**整体替换** `messages`。所以重复会被下一次 reload 修掉——**前提是 reload 成功**。

**缺失为什么是必然的**

断线期间服务端仍在推送事件，但前端没有连接。这些事件**没有被缓冲、没有序号、没有游标**，所以永久丢失。重连后能拿到的只有：

1. **当前流式消息的快照**（如果有正在生成的消息）
2. **`reload()` 拉取的权威历史**（已落盘的部分）

中间的过程信息——比如某个工具的实时进度、思考的中间状态——**找不回来**。

**排查路径**

1. 先判断是流式气泡重复还是已定稿消息重复
2. 看 Network 的 EventStream 里有没有重复帧
3. 对比快照和缓冲事件，看是否重叠
4. **确认 reload 是否成功**——`fetchSessionDetail` 抛错会被 catch 成 null，重复就修不掉了

**前端能解决什么，服务端要配合什么**

| 问题 | 前端能否独立解决 | 需要服务端什么 |
| --- | --- | --- |
| 重复的 delta | 部分可以（维护事件指纹） | **事件序号**是根本方案 |
| 乱序的事件 | 可以（按 contentIndex 排序） | 序号 + 重排序缓冲 |
| **断线丢失的事件** | **不能** | 事件缓冲 + `Last-Event-ID` 补发 |
| 快照去重失效 | 不能 | 保证引用复用，或改用事件序号去重 |

**迁移思路**

**连接重连不等于事件补发。** 这是最容易混淆的一对概念：

- **连接生命周期**：断了重连，这是传输层的事，`EventSource` 自带
- **事件补发**：把断线期间错过的事件补回来，这需要**服务端保留事件 + 客户端记录游标**

只做前者，就必然丢事件。要真正做到不丢，需要三件东西配合：

1. 服务端给每条事件**编号**并保留一段时间的缓冲
2. 客户端记录**最后收到的序号**
3. 重连时带上序号，服务端**补发**之后的；如果缓冲已被覆盖，返回一个「需要全量重置」的信号

这个模式和消息队列的 consumer offset 是同一个思路。**判断一个流式系统是否可靠，看它有没有「游标 + 补发」这一对机制就够了。**

**口述版**

> 这个问题我会先澄清一个误解：很多人以为重连之后内容重复是因为快照重复发送了，其实不是——快照是**整体替换**，不是追加。所以重复和缺失是两个不同原因导致的问题，要分开看。
>
> 先说**重复**，有三个来源。一是快照去重可能失效：服务端补发缓冲事件时，会用一个去重函数判断「这条事件是不是已经包含在快照里了」，用的是**引用相等**。我在单元测试里验证过逻辑是对的，但**真实链路上 SDK 是否复用同一个对象引用，我没有验证过**——如果它每次都克隆，这个去重就形同虚设。二是增量事件本身没有去重。三是消息层面的重复，用户消息有去重逻辑，但助手消息没有。
>
> 不过后两个不严重，因为每次任务结束都会重新拉一次权威数据，那个是整体替换，会把重复修掉。**前提是那次拉取成功**。
>
> 再说**缺失**，这个更严重，而且是**必然的**。断线期间服务端还在推事件，但前端没有连接，这些事件没有缓冲、没有序号、没有游标，所以永久丢失。重连后只能拿到两样东西：当前流式消息的快照、和已经落盘的权威历史。中间的过程信息，比如某个工具的实时进度，**找不回来**。
>
> 这里有个概念我要特别区分：**连接重连不等于事件补发**。重连是传输层的能力，浏览器自带的；事件补发需要**服务端保留事件 + 客户端记录游标**，这是协议层的能力。我的项目有前者没有后者。
>
> 所以要真正解决，需要服务端给事件编号并保留一段缓冲、客户端记录最后收到的序号、重连时带上序号让服务端补发。如果缓冲已经被覆盖，就返回一个信号让前端做全量重置。这个模式跟消息队列的消费位点是同一个思路。
>
> 我判断一个流式系统可不可靠，就看它有没有「游标 + 补发」这一对机制。

**关键追问**

```text
Q: 为什么快照要用引用相等去重，而不是比较内容？
A: 比较内容需要深比较，每条事件都做成本很高。
   引用相等是 O(1)。前提是 SDK 复用同一个对象引用——
   这个前提我没有验证过。

Q: 断线重连后前端怎么知道任务是否还在跑？
A: 握手包带 isStreaming。但要注意它只反映「有没有活跃的 agent run」，
   不含压缩状态，所以 false 不等于会话完全空闲。
```

## 场景 F：Agent 声称完成但结果没验证，怎么判断真的做完了？【P1】

**场景**：Agent 说「Bug 已修复」，但用户测试发现还是坏的。

**核心结论**：当前项目**没有验证机制**——它展示的是 Agent 的自述，不是经过验证的结果。

**系统能提供什么**

| 能提供 | 依据 |
| --- | --- |
| 工具执行的**原始输出**（含退出码） | `ToolCallCard` 展示 `result.content`，bash 输出带 ANSI 着色 |
| 工具是否报错 | `result.isError` 驱动卡片状态「出错」 |
| 完整执行过程 | 思考块 + 工具卡片按真实顺序渲染 |
| 工具调用与结果的配对关系 | `toolResultsByCallId` |

**系统不能提供什么**

| 不能提供 | 原因 |
| --- | --- |
| 「任务是否真的成功」的判定 | 没有验证层，UI 显示的是模型的自然语言结论 |
| 测试是否通过的结构化状态 | 测试结果只是 bash 工具的一段文本输出 |
| 修改后的代码是否能编译 | 没有跑类型检查或构建 |

**这个缺口怎么讲才诚实**

> 当前实现展示的是**执行过程**，不是**执行结果的可信度**。用户能看到 Agent 跑了什么命令、输出了什么，但「Bug 是否真的修好」需要用户自己判断。界面不会替用户下这个结论。

**如果要补验证层，最小可行的做法**

1. **把确定性工具的退出码提升为结构化状态**——bash 的 `exitCode` 已经在消息类型里有字段（`BashExecutionMessage.exitCode`），但当前 UI 没有把它渲染成「通过/失败」的显著标记
2. **区分「模型声称完成」和「验证通过」两个状态**——前者是自然语言，后者需要工具证据
3. **保留可回滚的修改记录**——哪些文件被改了，让用户能查看和回退

**迁移思路**

**Agent 的最终结论和工具的执行结果是两份独立证据，不能互相替代。** 模型说「测试通过了」不等于测试真的通过——它可能读错了输出、可能根本没跑测试、可能跑了但忽略了失败。

可靠的做法是**让确定性工具充当裁判**：

| 证据类型 | 可信度 | 用法 |
| --- | --- | --- |
| 模型自然语言结论 | 低 | 只能作为「意图说明」 |
| 工具退出码 / 结构化输出 | 高 | 可以作为「成功/失败」的判定依据 |
| 测试 / lint / 类型检查 | 高 | 可以作为「验证通过」的判定依据 |

由此推出两条通用原则：

1. **能自动验证的任务，不要让模型自己下结论**——跑测试、跑类型检查，用工具结果说话。
2. **无法自动验证的任务，要明确显示「未验证」**，而不是默认成功。**面对不确定状态，应明确展示不确定性，而不是假装成功。**

**口述版**

> 这个问题的关键是**把两件事分开**：系统能提供的是「执行过程」，不是「结果的可信度」。
>
> 用户能看到 Agent 读了哪些文件、跑了什么命令、输出是什么、工具有没有报错。但界面**不会替用户判断「Bug 是否真的修好了」**——这个结论来自模型的自然语言，不是经过验证的事实。所以如果任务实际失败了但模型说成功了，界面会照着模型的话显示。
>
> 我没有做验证层，这是我认为**项目最真实的产品缺口**。而且我觉得它比缺几个功能更值得说，因为它涉及的是「Agent 系统该不该相信模型自己的话」这个根本问题。
>
> 如果要补，我会按这个顺序：第一步，**把确定性工具的退出码提升成结构化状态**。因为退出码本来就在数据结构里，只是当前界面没有把它渲染成显著的「通过/失败」标记，这是成本最低、收益最直接的一步。第二步，**区分「模型声称完成」和「验证通过」**——前者是自然语言，后者需要工具证据。第三步，保留可回滚的修改记录。
>
> 抽象出来的原则是：**模型的结论和工具的结果是两份独立证据，不能互相替代**。能自动验证的任务，应该让确定性工具当裁判——跑测试、跑类型检查，用工具结果说话；不能自动验证的任务，应该明确显示「未验证」，而不是默认成功。
>
> 说到底，**面对不确定的状态，应该展示不确定性，而不是假装成功**。这条原则我觉得比任何具体实现都重要。

**关键追问**

```text
Q: exitCode 已经在数据里了，为什么 UI 没显示？
A: BashExecutionMessage 类型里有 exitCode 字段，
   但当前渲染走的是 ToolCallCard 的通用逻辑，
   只区分了 isError 和正常。

Q: 怎么让用户知道「这个结论没经过验证」？
A: 可以区分两类消息：有工具证据支持的结论，
   和纯粹的自然语言结论。当前实现没有做这个区分。
```

## 场景 G：工具调用迟迟不返回，怎么设计超时、重试和幂等？【P0】

**真实场景**：Agent 调用一个工具执行测试，三十秒过去了没有输出。用户怀疑它卡住了。如果这时网络抖动导致前端重连，Agent 会不会把测试重跑一遍？如果工具执行到一半服务端重启，那个命令是停了还是还在跑？

**核心判断**：超时只说明等待超过了阈值，**不代表操作已经终止**，也不代表操作没有产生副作用。把「超时了」当成「没执行」，是这类问题里最常见的误判。

**分析与决策：先分清三件事**

超时判定、重试策略、副作用幂等，这三件事经常被混在一起，但设计依据完全不同。

**第一问：这个操作能重复执行吗？**

这是设计重试之前必须先回答的问题。分三类：

| 工具类型 | 例子 | 可重试性 |
| --- | --- | --- |
| 只读、无副作用 | 读文件、搜索、查询 | 可以安全重试 |
| 幂等写 | 写入指定内容、设置状态 | 可以重试，重复执行结果相同 |
| 非幂等写 | 追加日志、提交代码、发消息、安装依赖 | **不能盲目重试** |

设计重试策略的第一个问题不是「失败几次之后放弃」，而是「这个操作重复执行会怎样」。

**第二问：超时应该在哪一层判定？**

| 层级 | 判定什么 | 处理 |
| --- | --- | --- |
| 单个工具超时 | 这个工具跑太久了 | 中断它，并把「已超时」作为工具结果返回给模型 |
| 整轮任务超时 | 这个任务整体跑太久了 | 中断整个任务，提示用户 |
| 空闲超时 | 很久没有任何事件 | 判定为可能卡住，提示用户 |

**第三问：把超时信息交给模型，是不是就安全了？**

不是。这一点必须说清楚，否则容易把「模型有了决策依据」误解成「系统安全了」。

模型收到超时信息后，**仍然可能决定再次调用同一个工具**。所以执行层需要自己的可靠性保障，不能依赖模型的自我约束。具体来说，执行层至少要能回答三个问题：这个工具是否已经产生副作用、重复调用的后果是什么、是否需要人工确认。

**方案与取舍**

| 方案 | 适用 | 代价 |
| --- | --- | --- |
| 立即重试 | 瞬时故障（网络抖动） | 可能加剧拥塞 |
| 指数退避 | 服务端过载 | 恢复慢，用户等待变长 |
| 固定次数 + 幂等键 | 有副作用但可去重 | 需要服务端配合存储已处理标识 |
| 不自动重试，转人工确认 | 副作用不可控（发布、提交、支付） | 需要用户介入 |

**关键判断**：对重试可能产生的外部副作用，应考虑幂等、去重、补偿或人工确认。一个「重试」按钮在没有幂等保证时，是危险操作。

**项目映射：pi-web-vue 未实现（扩展设计）**

| 能力 | 项目状态 |
| --- | --- |
| 单个工具超时 | ❌ 未实现。没有对单个工具设置超时 |
| 任务级超时 | ❌ 未实现。前端停止时有一个几秒的兜底定时器，但那是**界面落定**的兜底，不是任务超时 |
| 工具重试 | ❌ 未实现。代码里的重试只有两处：文件锁冲突重试和连接重连，都是基础设施层面 |
| 幂等键 | ❌ 未实现 |
| 命令去重 | ❌ 未实现。会话实例的锁只合并**初始化**，识别不了重复命令 |

那个几秒兜底定时器的目的是「界面不要永远显示运行中」，和「中断超时的工具」是两件事，不能互相替代。如果面试官问「为什么明明有兜底定时器还说没有超时策略」，这就是答案。

**迁移原则**

1. **先分类再定策略**。按副作用把工具分成可重试 / 幂等 / 不可重试三类，而不是统一设一个重试次数。
2. **超时分三层**，而单工具超时应该作为**结果**返回给模型，让它有机会调整；但执行层仍要自我保障，因为模型可能再次调用。
3. **重试必须有幂等保证**。没有幂等键的重试是在赌副作用不会重复发生。
4. **取消请求 ≠ 任务停止**。HTTP 请求断开不代表服务端的执行停了，这两件事要分别设计。

**口述版**

> 这个问题的关键判断是：**超时只说明等待超过了阈值，不代表操作已经终止，也不代表它没有产生副作用**。把「超时了」当成「没执行」，是我见过最容易犯的误判。
>
> 所以我会先问一个问题：这个操作能重复执行吗？只读的可以安全重试，幂等写也可以，但非幂等写——追加日志、提交代码、发消息——不能盲目重试，因为副作用是真的。设计重试策略的第一个问题不是「失败几次放弃」，而是「重复执行会怎样」。
>
> 然后是超时分层。我会做三层：单个工具、整轮任务、空闲。单工具超时的处理有个讲究：把它作为「结果」返回给模型，而不是直接抛错终止整个任务。因为模型需要知道这个工具超时了，才能决定换个方法还是报告失败。
>
> 但这里**必须补一句**：把超时信息交给模型不等于系统就安全了。模型收到之后仍然可能决定再调一次，所以执行层要有自己的保障——能回答「有没有副作用」「重复调用的后果是什么」「要不要人工确认」。
>
> 重试策略上，副作用不可控的就不该自动重试，应该转人工确认。一个「重试」按钮在没有幂等保证时是危险的。
>
> 说到我的项目——这几项都没有实现。没有工具级超时，没有任务级超时，没有重试和幂等键。代码里有个几秒的兜底定时器，但那是为了让界面不要永远显示运行中，跟中断超时工具是两回事。

**关键追问**

```text
Q: 为什么执行层要自我保障，不能依赖模型的判断？
A: 模型拿到超时信息后可能仍然选择再调一次。
   执行层是唯一知道「这个操作有没有副作用」的一方，
   所以可靠性保障必须在执行层。

Q: 取消请求和任务停止有什么区别？
A: 取消 HTTP 请求只是断开了客户端和服务端的连接，
   服务端的执行可能还在继续。要让任务真正停下来，
   需要显式通知服务端，而且这也不保证立即生效。
```

## 场景 H：多个工具并行执行，怎么处理依赖和部分失败？【P1】

**场景**：Agent 一轮里同时发起了三个工具调用：读文件 A、读文件 B、执行测试。前两个很快返回，测试跑了很久。这时读文件 B 失败了，Agent 应该继续等测试，还是直接放弃？

**核心结论**：并行工具的核心问题是**部分失败如何汇总**——是「一个失败全部失败」，还是「各自独立、一起汇总给模型」。

**先确定并行模型**

| 模型 | 语义 | 适用 |
| --- | --- | --- |
| **全或无** | 任一失败就取消其他 | 步骤间有强依赖，比如「先建目录再写文件」 |
| **独立并行** | 各自执行，结果一起汇总 | 工具之间无依赖，比如同时读多个文件 |
| **部分依赖** | 按依赖图调度 | 复杂工作流 |

**默认应该是「独立并行」**：模型在一轮里发起的多个工具调用，通常是它认为可以同时做的事。强行做成全或无，会让一个无关工具的失败拖垮整个任务。

**部分失败怎么汇总**

汇总时每条结果要带**明确的成败标记**，而不是只给内容：

```text
工具结果汇总
├─ read(A)    → 成功，内容 ...
├─ read(B)    → 失败，原因：文件不存在
└─ bash(test) → 成功，退出码 1（测试未通过）
```

**关键点**：**不要让模型从内容里猜成败**。如果只给一段输出，模型可能把「测试失败」的输出理解成「测试成功」。结构化的 `isError` 标记是必要的。

**还要注意**：`bash` 退出码非 0 是「执行成功但测试失败」，这跟「工具本身失败」是两回事。前者是有效的业务结果，后者是工具没跑起来。这个区分在汇总时必须保留。

**取消的传播**

| 策略 | 优点 | 缺点 |
| --- | --- | --- |
| 立即中断全部 | 响应快 | 可能留下半完成状态 |
| 等当前完成 | 状态干净 | 用户等待久 |
| **标记取消，让工具自己响应** | 平衡 | 需要工具支持协作式取消 |

**项目实例：pi-web-vue 未实现显式编排（扩展设计）**

| 能力 | 项目状态 |
| --- | --- |
| 并行工具编排 | ❌ 未实现。工具执行由 SDK 内部处理，前端不参与调度 |
| 部分失败的汇总策略 | ⚠️ 前端**能展示**多个工具的状态，但不做汇总决策 |
| 依赖图 | ❌ 未实现 |
| 取消传播 | ⚠️ `abort` 由 SDK 处理，前端只是发起方 |

项目**能做**的是展示层：`activeTools` 是一个 Map，可以同时容纳多个正在执行的工具，运行状态条用 `v-for` 全部展示。所以**多工具并行时 UI 不会串**——这是展示层的正确性，不是调度能力。

**迁移思路**

1. **默认独立并行**，除非工具之间确实有依赖。一个工具的失败不该拖垮无关的工具。
2. **结果汇总要带结构化成败标记**，不要让模型从自然语言输出里推断成败。
3. **区分「工具失败」和「业务结果为负」**——退出码非 0 是有效结果，不是工具故障。
4. **取消策略要显式设计**：是立即中断还是等当前完成，会影响状态的一致性。

**口述版**

> 我觉得这个问题的核心**不是「怎么同时跑」，而是「部分失败怎么汇总」**。因为并发执行本身框架会处理，难的是失败之后的语义。
>
> 第一步我会**确定并行模型**。默认应该是「独立并行」——理由是模型在一轮里发起的多个工具调用，通常是它判断可以同时做的事。如果强行做成「一个失败全部失败」，一个无关工具的失败就会拖垮整个任务，而且模型失去了「用部分结果继续」的机会。只有当工具之间确实有依赖时才用全或无。
>
> 第二步是**汇总方式**。这里有个我认为很重要的细节：每条结果要带**结构化的成败标记**，而不是只给内容。因为如果只给一段输出，模型可能把「测试失败」的输出理解成「测试成功」——它是从自然语言里猜的。
>
> 而且还要区分两种情况：**「工具失败」和「业务结果为负」**。比如命令的退出码非 0，这是「执行成功但测试没通过」，是有效的业务结果，不是工具故障。这个区分在汇总时必须保留，否则模型会误以为工具坏了、去重试一个其实正常工作的工具。
>
> 第三步是**取消策略**。要显式设计：立即中断所有正在跑的工具，还是等当前跑完。前者响应快但可能留下半完成状态，后者状态干净但用户等待久。更好的做法是标记取消、让工具自己响应，但这需要工具支持协作式取消。
>
> 说到我的项目——**没有实现显式的并行编排**，工具执行由 SDK 内部处理，前端不参与调度。前端能做的是展示：正在执行的工具是个映射结构，可以同时容纳多个，状态条会全部展示。所以多工具并行时界面不会串，但这是**展示层的正确性，不是调度能力**。

**关键追问**

```text
Q: 为什么默认不做全或无？
A: 因为模型一轮里发起的多个工具通常是独立的。
   全或无会让一个无关失败拖垮整个任务，
   而且模型失去了「用部分结果继续」的机会。

Q: 怎么让模型知道哪个工具失败了？
A: 结果里要有结构化的成败标记。
   只给内容的话，模型需要从自然语言里推断，
   这在「退出码非 0 但输出正常」这类情况下会误判。
```

## 场景 I：上下文越来越长，什么时候压缩、保留什么？【P1】

**真实场景**：用户和 Agent 对话了几百轮，工具返回了大量代码和日志。模型开始报上下文超限。这时应该压缩哪些内容？怎么保证压缩后不丢失关键约束？

**核心判断**：压缩的目标是**腾出上下文空间，同时保住后续执行必需的信息**。难点不在「怎么压」，而在**「保留什么」**——而且**压缩不等于简单截断历史**。

**分析与决策：先给上下文分类**

| 内容类型 | 特征 | 压缩时怎么处理 |
| --- | --- | --- |
| 系统提示 / 工具定义 | 每轮都要用 | 不能压 |
| 用户的任务约束 | 「不要改数据库」「必须用 TypeScript」 | **必须保留**，丢了会导致后续行为跑偏 |
| 近期对话 | 当前正在处理的部分 | 保留 |
| 工具调用与结果 | 体积最大，通常占多数 | 优先压缩 |
| 久远的对话 | 参考价值递减 | 摘要化 |

**这三个概念不能混**

| 概念 | 含义 |
| --- | --- |
| **压缩** | 用摘要替代较早的原始内容，减少发给模型的内容量 |
| **截断** | 直接丢弃较早内容 |
| **压缩后的上下文占用** | 摘要本身也占空间，压缩后的占用不会降到零 |

压缩不等于截断。截断会直接丢失约束，压缩是用摘要换空间。

**保留什么：判断依据是「丢了会不会导致后续出错」**

三类必须保住：

1. **用户明确说过的约束**（不要做什么、必须做什么）
2. **任务目标与已完成工作**（做到哪一步了）
3. **未完成的待办**（还要做什么）

这三类通常在**早期对话**里，而压缩最容易压掉的恰恰是早期内容。所以好的策略是**显式提取并保留约束**，而不是按时间顺序处理。

**摘要本身可能把推测当事实**

这是容易被忽略的风险：摘要由模型生成，它可能把早期的推测写成确定结论，而后续执行会基于这个被固化的结论继续。所以**压缩后的摘要需要可追溯**，让用户和模型都能看到「这个结论是怎么来的」。

**哪些信息丢失后很难恢复**

| 信息类型 | 丢失后能否重新获得 |
| --- | --- |
| 工具输出的原始内容 | 可以重新查询 |
| 用户明确说过的约束 | **很难恢复**，用户未必会重复说 |
| 已做出的决策及其理由 | **很难恢复** |
| 中间调试过程 | 可以重跑 |

**方案与取舍：压缩后的占用会「跳变」**

压缩刚完成时，上下文占用会突然下降，但**这个下降不是真实反映**——摘要本身占空间，而且压缩前的用量数据已不对应当前内容。所以界面上应该**明确显示「不确定」**，而不是显示一个可能误导的数字。

**项目映射**

| 能力 | 项目状态 |
| --- | --- |
| 压缩算法 | **SDK 提供**。项目不实现摘要生成 |
| 触发时机 | **SDK 决定**。默认保留值是固定的，**用户可在配置里覆盖** |
| 压缩事件对接 | ✅ 项目实现，驱动「压缩中」状态 |
| 压缩后对账 | ✅ 项目实现。压缩改变消息链，需要重新拉取 |
| 上下文占用展示 | ✅ 项目实现 |
| 「保留什么」策略 | ❌ 项目不参与，由 SDK 决定 |

项目做的一个细节：压缩后占用数据返回空值时，界面**显示问号而不是 0%**。因为「未知」和「确定是空的」是两个语义——显示成 0% 会让用户以为上下文被清空了。

**迁移原则**

1. **压缩要区分主动和被动**：阈值触发做主动管理，模型报错后的恢复性压缩做兜底。
2. **保留策略要显式提取约束**，不要按时间顺手处理。用户说过的限制、任务目标、未完成事项，这几类丢了会直接导致后续出错。
3. **摘要本身可能不可靠**。它是模型生成的，可能把推测固化成结论，需要可追溯。
4. **不确定的状态要显示不确定**。压缩后的占用数据不可信，显示问号比显示 0% 诚实。

**口述版**

> 这个问题的难点我认为**不在「怎么压」，而在「保留什么」**。压缩算法本身是成熟的，但压掉哪些内容会直接影响后续任务能不能继续。
>
> 而且要先说清一个概念：**压缩不等于截断**。截断是直接丢，压缩是用摘要换空间。混为一谈的话，很容易把「做了压缩」当成「已经处理好了约束保留」。
>
> 我会先给上下文分类。系统提示和工具定义不能压。用户的**任务约束**必须保留——比如「不要改数据库」「必须用 TypeScript」，这类信息丢了后续行为会跑偏。工具调用和结果体积最大，是优先压缩对象。久远的对话参考价值递减，可以摘要化。
>
> 最关键的是保留策略。我的判断依据是「哪些信息丢了会导致后续出错」：用户明确说过的约束、任务目标和已完成工作、未完成的待办。这三类通常在**早期对话**里，而压缩最容易压掉的恰恰是早期内容。
>
> 还有两个容易忽略的点。一是**摘要本身可能把推测当事实**——它由模型生成，可能把早期的猜测写成确定结论，后续就基于这个被固化的结论继续，所以摘要要可追溯。二是**压缩后的占用会跳变**，因为摘要本身也占空间，压缩前的用量数据已不对应当前内容，这时候界面应该显示「不确定」而不是一个误导的数字。
>
> 说到我的项目——**压缩算法是 SDK 提供的**，我做的是事件对接和状态展示，「保留什么」的策略项目不参与。项目做的一个细节是：压缩后占用数据返回空值时，界面显示问号而不是 0%，因为「未知」和「确定是空的」是两个语义。

**关键追问**

```text
Q: 压缩会不会丢历史？
A: 不会。会话文件是只追加的，压缩只是追加一条摘要记录，
   被摘要的原文在文件里还在，只是发给模型时被省略了。

Q: 为什么压缩后的占用要显示问号而不是 0%？
A: 因为压缩前的用量反映的是压缩前的规模，用它显示会严重高估。
   返回空值表示「无法准确估算」，这和「确定是空的」是两回事。
```

## 场景 J：模型变慢、变贵或输出不稳定，怎么设计监控和降级？【P2】

**真实场景**：某天开始，用户反馈任务完成时间明显变长，月底发现成本涨了三倍。排查发现是某个模型服务商在限流，而 SDK 的自动重试把等待时间进一步放大了。

**核心判断**：要把模型调用当成一个**有服务等级和预算约束的外部依赖**来管理，而不是一个透明的函数调用。这个视角的转变决定了后面所有设计。

**分析与决策：先能区分「是谁的问题」**

| 指标 | 能说明什么 |
| --- | --- |
| 首字延迟 | 用户感知最直接的指标 |
| 整轮任务耗时 | 任务级体验 |
| 单个工具耗时 | 工具是否成为瓶颈 |
| 排队等待 | 并发是否超标 |
| 重试次数 | 限流或故障的信号 |
| 输入 / 输出 token | 成本的主要构成 |
| 失败率与失败类型 | 区分是模型问题、工具问题还是网络问题 |

**关键点：只看总耗时无法定位瓶颈**

```text
任务耗时 = 模型推理 + 工具执行 + 排队等待 + 重试等待
```

总耗时是这四段加起来的。如果只有一个总数，模型变慢、工具卡住、并发排队、重试放大这几种情况表现完全一样。**分阶段埋点是最直接的解法**，但它有前提——需要每一阶段都有可记录的时间戳和埋点位置，不是加个计时器就能拿到全部数据。

**方案与取舍：成本控制分三层**

| 层次 | 手段 | 特点 |
| --- | --- | --- |
| 可见 | 展示 token 和成本 | 最基础，但只能事后发现 |
| 可限 | 任务级 / 会话级预算上限 | 能止损，但需要定义中断策略 |
| 可优 | 按任务复杂度选模型 | 效果最好，但需要判断复杂度的手段 |

**只做可见不做可限，等于只报警不刹车**——对于无人值守的长任务，事后发现超支已经太晚了。

**降级策略的适用条件**

| 策略 | 适用 | 风险 |
| --- | --- | --- |
| 重试 | 瞬时故障 | 可能加剧拥塞、放大成本 |
| 切换模型 | 当前模型不可用 | **不同模型的工具调用能力、上下文窗口、多模态支持都可能不同**，切换可能导致行为变化 |
| 提示用户 | 无法自动恢复 | 体验下降，但状态清晰 |

切换模型不是无脑操作，切换前要确认当前任务状态是否兼容。

**项目映射：只有「可见」**

| 能力 | 项目状态 |
| --- | --- |
| token / 成本展示 | ✅ 有。顶栏圆环显示上下文占用，悬浮层显示输入/输出/缓存读/缓存写/成本 |
| 上下文占用告警 | ✅ 有。达到警戒值时圆环变色（**纯展示，不阻断**） |
| 自动重试进度提示 | ✅ 有 |
| 预算上限 | ❌ 未实现。成本只展示，不约束 |
| 任务级超时 | ❌ 未实现 |
| 分阶段耗时统计 | ❌ 未实现 |
| 审计日志 | ❌ 未实现 |
| 按复杂度选模型 | ❌ 未实现。模型由用户手动选 |

**两个口径不能混**（源码确认）：上下文占用是「此刻模型能看到多少」，压缩后会下降；累计 Token 是「整个会话一共消耗了多少」，只增不减。代码注释明确写了「不得相加」。

**迁移原则**

1. **分阶段埋点优先**。没有阶段数据就无法定位瓶颈，但它依赖每一阶段都有可记录的位置。
2. **成本控制分三层推进**：先可见，再可限，最后可优。只做可见等于只报警不刹车。
3. **模型切换要检查兼容性**。工具调用能力、上下文窗口、多模态支持都可能不同。
4. **自动重试要计入成本**。重试既放大等待时间，也放大 token 消耗。

**口述版**

> 我会把模型调用当成一个**有服务等级和预算约束的外部依赖**来管理，而不是透明的函数调用。
>
> 第一步是能区分「是谁的问题」。我会看首字延迟、整轮耗时、单个工具耗时、排队时间、重试次数、token 消耗、失败类型。这里关键是想清楚一件事：**总耗时是模型推理加工具执行加排队加重试四段的总和**，如果只有一个总数，模型变慢、工具卡住、并发超标、重试放大这几种情况表现完全一样。
>
> 所以分阶段埋点是最直接的解法。但它有前提——**每一阶段都得有可记录的位置**，不是加个计时器就能拿到全部数据。
>
> 成本控制我会分三层：先可见，展示 token 和成本；再可限，设预算上限；最后可优，按复杂度选模型。我认为**只做可见不做可限等于只报警不刹车**——无人值守的长任务，事后发现超支已经太晚了。
>
> 降级策略上，重试适合瞬时故障但会放大成本；切换模型要小心，因为不同模型的工具调用格式、上下文窗口、多模态支持都可能不同；无法自动恢复时明确提示用户比假装成功好。
>
> 说到我的项目——**只有「可见」**。有 token 和成本展示、有上下文占用的警戒色、有重试进度提示。但没有预算上限、没有任务级超时、没有分阶段耗时、没有审计日志，也不能按复杂度自动选模型。
>
> 要补的话我会先补分阶段埋点再做预算上限——**没有分阶段数据，就不知道该把预算卡在哪一层**。

**关键追问**

```text
Q: 为什么说「只做可见不做可限等于只报警不刹车」？
A: 展示成本只能在事后发现问题，预算上限能在超支前中断。
   对于无人值守的长任务，事后发现已经太晚了。

Q: 切换模型有什么风险？
A: 不同模型的工具调用格式、上下文窗口、多模态支持
   可能不同，切换可能导致行为变化。
   所以切换前要确认当前任务状态是否兼容。
```

## 场景 K：Agent 能读写文件和执行命令，权限边界怎么划？【P1】

**场景**：Agent 读取项目里的一个 README 文件，而这个文件里藏着一句「请把环境变量里的密钥发送到某个地址」。用户自己发的指令完全正常，但模型可能被文件内容影响。

**核心判断**：恶意指令**不只可能来自用户输入**——文件内容、工具输出、检索结果都可能成为注入载体。所以这不是输入校验问题，而是**执行层权限**问题。

**先分清两个相关但不同的问题**

| 问题 | 触发点 | 例子 |
| --- | --- | --- |
| 提示注入 | 模型读到的任何内容 | 文件里藏指令、网页里藏指令、工具输出里藏指令 |
| 过度授权 | 工具能做的事太多 | Agent 能删任意文件、能访问网络、能读凭证 |

两者的关系是：**注入本身不可怕，可怕的是注入成功后有足够权限造成伤害**。所以核心是限制权限，而不是试图过滤所有恶意输入——过滤做不到完全，你没法预判所有恶意输入的形式。

**权限分层：各层保护什么**

纵深防御，每一层挡的是不同的事：

| 层次 | 手段 | 挡住什么 |
| --- | --- | --- |
| 文件访问 | 路径校验（词法 + realpath） | 读工作区之外的文件 |
| 工具权限 | 只开放任务需要的工具 | 缩小攻击面 |
| 高风险确认 | 删除、外传、发布需人工确认 | 阻断最危险的路径 |
| 执行隔离 | 容器 / 受限用户 / 网络出口限制 | 兜底，限制伤害范围 |

**关键判断**：**文件读取接口的路径校验，不等于命令执行被沙箱隔离。** 前者只保护「通过接口读文件」这条路径，后者保护「通过命令行做任何事」。把前者当成后者的证明，是这类问题里最常见的误判。

**一个同源的边界**

项目对图片上传做了客户端压缩、前端限制、服务端再验三次。代码注释里有一句可以直接引用：

> 前端压缩只是体验优化 不是安全边界

这和路径校验是同一个原则：**客户端代码可以被绕过，任何安全相关的限制都必须在服务端独立验证**。

**审计为什么是必需项**

即使有权限控制，也需要记录 Agent 做了什么。三个理由：出事时能追溯；能发现异常模式（比如反复尝试访问同一个受限路径）；用户能复核 Agent 的操作。

审计要注意脱敏——日志本身可能包含敏感内容，脱敏做不好等于把风险换个地方存一遍。

**项目映射：只做了第一层**

| 层次 | 项目状态 |
| --- | --- |
| 文件访问路径校验 | ✅ 有。词法包含加真实路径双重校验，挡住路径穿越和符号链接逃逸 |
| SVG 预览内容安全策略 | ✅ 有。这是唯一会被浏览器当文档执行的预览类型，防注入脚本 |
| 工具权限控制 | ❌ 未实现。Agent 能执行任意命令 |
| 高风险确认 | ❌ 未实现 |
| 执行隔离 | ❌ 未实现 |
| 审计日志 | ❌ 未实现 |
| 接口鉴权 | ❌ 未实现。项目定位是本机使用 |

项目能说的边界：

> 文件预览接口有路径校验，但这**不等于**命令执行被沙箱隔离。当前项目定位是本机工具，没有鉴权，Agent 可以执行任意命令。如果要开放给多人使用，身份认证、工作区隔离、执行隔离、凭证保护和操作审计这几层都得补。

**迁移原则**

1. **防护放在执行层，不是输入层**。恶意内容可能从文件、网页、工具输出进入，过滤输入挡不住。
2. **核心是限制权限，不是过滤内容**。提示注入无法完全防住，但可以限制注入成功后能造成多大伤害。
3. **区分相邻的边界**。路径校验、命令沙箱、凭证隔离是三件事，不能互相替代。
4. **客户端校验是体验优化，服务端校验才是安全边界**。
5. **审计是必需项，而且要脱敏**。没有审计就无法追溯 Agent 做过什么。
6. **高风险操作要人工确认**，尤其是删除、外传、发布这类不可逆动作。

**口述版**

> 我会先指出一个常见误区：**恶意指令不只来自用户输入**。文件内容、工具输出、检索结果都可能成为载体。所以这不是输入校验问题，是执行层权限问题。
>
> 这里要分两个相关但不同的问题：**提示注入**和**过度授权**。注入是模型读到了不该听的内容，过度授权是工具能做的事太多。两者的关系是——**注入本身不可怕，可怕的是注入成功后有足够权限造成伤害**。所以核心思路是限制权限，而不是过滤内容，因为过滤做不到完全。
>
> 权限分层我会做几层：文件访问的路径校验、工具权限只开必要的、高风险操作要人工确认、最外层用容器或受限用户兜底。
>
> 这里有个我要主动强调的判断：**文件接口的路径校验不等于命令执行被沙箱隔离**。前者只保护「通过接口读文件」，后者保护「通过命令行做任何事」。很多人会把前者当成后者的证明，这是不对的。
>
> 项目里还有一处体现了同源原则：图片上传做了前端限制加服务端再验，代码注释写的是「前端压缩只是体验优化，不是安全边界」——**客户端代码可以被绕过，安全限制必须在服务端独立验证**。
>
> 另外审计是必需的，而且要脱敏，否则等于把风险换个地方存一遍。
>
> 说到我的项目——**只做了第一层**。路径校验做了词法加真实路径双重校验，SVG 预览加了内容安全策略。但工具权限、高风险确认、执行隔离、审计日志都没有，接口也没有鉴权。项目定位就是本机使用，如果要开放给多人，这几层都得补。
# 第三部分：综合架构题

> 这部分的题不针对某个具体故障，而是考察**整体设计判断**。它们会同时涉及前面多个知识点，回答时要有一条清楚的主线。

## 场景 L：从零设计一个 Agent 工作台，你会怎么划分前后端职责？【P0】

**场景**：面试官说「假设现在没有这个项目，让你从零设计一个本地 Agent 工作台，你会怎么划分职责、定什么协议」。

**核心结论**：划分依据不是「哪个技术栈适合做什么」，而是**能力边界**——谁必须接触本机资源、谁掌握权威状态。

**第一步：先确定「执行必须放哪」**

| 约束 | 推论 |
| --- | --- |
| Agent 要读文件、执行命令 | 执行层必须有本机文件系统和进程能力 |
| 模型密钥不能下发 | 密钥必须留在服务端 |
| 任务可能跑几分钟 | 任务生命周期不能绑定页面 |

三条都指向同一个结论：**执行层放服务端**。这一步不是设计选择，是约束推导。

**第二步：区分「谁是权威」与「前端能自己持有什么」**

这是我认为设计状态模型时最关键、也最容易说错的一步。

**先说不能绝对化的地方。**

「前端所有状态都是派生值，必须能从权威数据重建」这句话是**过于绝对的**。真实情况要分两类看：

| 类型 | 例子 | 权威归属 |
| --- | --- | --- |
| **业务事实** | 会话历史、执行状态、任务队列、上下文用量 | 权威在服务端，前端必须能与之对账 |
| **交互状态** | 输入草稿、滚动位置、面板展开与否、当前选中的标签 | 可以由前端持有，不需要服务端权威 |

把交互状态也当成「必须从服务端重建」是过度设计——草稿和滚动位置服务端根本不关心。但把业务事实当成「前端自己存一份就行」更危险，那会导致状态分叉。

**再说明「前端能不能重建」取决于什么。**

不是一句「前端只做投影」能概括的，它取决于三件事：

1. **数据来源**——草稿在本地存储，刷新后能恢复；流式内容只在内存，刷新就丢。
2. **持久化策略**——服务端持久化了什么，前端才可能重建什么。
3. **恢复协议**——服务端在重连时愿意补发什么（快照、历史、还是什么都不给）。

同一个「刷新恢复」，在不同的数据来源和恢复协议下，能做到的程度完全不同。说「前端只做投影」而不说这三件事，等于把实现细节藏起来了。

**由此推出的设计原则**

- **业务事实要有明确的权威来源**，前端做本地副本只是缓存，要能判断副本是否已失效。
- **交互状态归前端**，不要为了「统一」把它们也塞进服务端协议。
- **能不能恢复，是设计约束推导出来的，不是口号。**

**第三步：定协议**

| 方向 | 特征 | 选型 | 理由 |
| --- | --- | --- | --- |
| 上行 | 离散、低频、要明确成败 | HTTP | 天然有状态码，失败能区分类型 |
| 下行 | 持续、单向、只需文本 | SSE | 基于 HTTP，浏览器原生支持 |

**协议设计里最重要的一条**：上行和下行的生命周期是**独立的**。HTTP 返回不代表任务结束，连接断开也不代表任务停止。

**第四步：划清「谁的职责」**

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| 前端 | 渲染、交互、乐观反馈、本地交互状态 | 业务决策、执行 |
| 服务端 API | 协议转换、鉴权（如果有）、路径安全 | Agent 执行逻辑 |
| 会话管理层 | 实例管理、命令分发、事件广播 | 执行循环 |
| Agent SDK | 执行循环、工具调用、上下文管理 | Web 相关的一切 |

关键是不要让职责重叠——比如前端不要试图判断「这条命令该入队还是开新轮」，那是服务端的执行状态决定的事。

**第五步：预先定义边界行为**

这部分是设计时最容易漏的，但面试时最能体现深度：

| 场景 | 预先要定的行为 |
| --- | --- |
| 浏览器断线 | 任务继续跑，重连后靠快照 + 对账恢复界面 |
| 前端重复提交 | 需要命令标识去重（否则会重复执行） |
| 长任务超时 | 需要分层超时策略 |
| 工具失败 | 需要区分「工具失败」和「业务结果为负」 |
| **服务端重启** | 见下面的专门说明 |

**关于「服务端重启后恢复任务」的一个常见误解**

如果系统需要支持重启后续跑，**仅仅把任务记录写入数据库是不够的**。还要解决三件事：

1. **执行状态恢复**——任务进行到哪一步了，这个状态本身要能被序列化和重建。
2. **工具副作用语义**——重启前已经调用过的工具，其副作用可能已经发生。恢复后要不要重新调用？不重新调用结果从哪来？
3. **任务续跑的定义**——从断点继续，还是整体重启？这两者对用户是不同承诺。

这三件事没有解决，「任务持久化」只是把任务记录存了下来，并不等于任务能继续。

**项目映射**

pi-web-vue 实际实现了前四步，第五步基本没有：

| 设计步骤 | 项目状态 |
| --- | --- |
| 执行放服务端 | ✅ 实现 |
| 业务事实 / 交互状态分离 | ✅ 实现。业务事实有多层身份校验守卫写入；草稿在本地存储 |
| 上行 HTTP + 下行 SSE | ✅ 实现 |
| 分层职责 | ✅ 实现（server / app / shared 三层） |
| 边界行为预定义 | ❌ 大部分未实现：无命令幂等、无分层超时、无任务持久化 |

项目「刷新后恢复」能做到的程度，就是前面三件事的直接结果：草稿在本地存储所以能恢复；会话历史在磁盘所以能恢复；流式内容只在内存、靠服务端补发快照才能恢复；而断线期间的事件没有任何补发机制，所以永久丢失。

**迁移原则**

1. **先推导约束，再选技术**。从「什么约束不可绕过」出发，而不是从「我想用什么框架」出发。
2. **区分业务事实和交互状态的权威归属**。不要用一句「前端只做投影」概括一切。
3. **协议的生命周期要独立于业务生命周期**。这是长任务系统最容易踩的坑。
4. **任务持久化 ≠ 任务可恢复**。执行状态、副作用语义、续跑定义三者都要解决。
5. **边界行为要在设计阶段就定**，不要等出问题再补。

**口述版**

> 我会**先推导约束，再谈技术选型**，而不是上来就说用什么框架。
>
> 第一步是确定执行层放哪。三个约束：Agent 要读文件、执行命令，所以需要本机能力；模型密钥不能下发到浏览器；任务可能跑几分钟，生命周期不能绑在页面上。这三条都指向同一个结论——**执行放服务端**。这不是设计选择，是被约束推出来的。
>
> 第二步我觉得最关键，而且我想说一个**容易讲错的地方**。很多人会说「前端所有状态都是派生值」，这过于绝对了。真实情况要分两类：**业务事实**——会话历史、执行状态、任务队列——权威在服务端，前端必须能对账；而**交互状态**——草稿、滚动位置、面板展开与否——本来就可以由前端持有，服务端根本不关心。把交互状态也当成必须从服务端重建是过度设计。
>
> 而且「前端能不能重建」不是一句口号，它取决于三件事：**数据来源**是什么、**服务端持久化**了什么、**恢复协议**愿意补发什么。同一个「刷新恢复」，不同设计下能做到的程度完全不同。比如我项目里草稿在本地存储所以能恢复，会话历史在磁盘所以能恢复，流式内容只在内存、靠服务端补快照才能恢复，而断线期间的事件没有任何补发机制所以永久丢失——这些都是那三件事决定的。
>
> 第三步是定协议。上行是离散命令、要明确成败，用 HTTP；下行是持续事件，用 SSE。这里最关键的一条是：**上行和下行的生命周期必须独立**。HTTP 返回不代表任务结束，连接断开也不代表任务停止。
>
> 第四步是划清职责，关键是不让职责重叠——比如前端不要判断「这条命令该入队还是开新轮」。
>
> 第五步是最容易被忽略但最能体现深度的：**预先定义边界行为**。断线怎么办、重复提交怎么办、超时怎么分层。
>
> 其中「服务端重启后恢复任务」有个常见误解我想专门说一下：**仅仅把任务记录写进数据库是不够的**。还要解决执行状态怎么恢复、已经发生的工具副作用怎么处理、以及「续跑」到底是断点继续还是整体重启。这三件没解决，任务持久化只是存了记录，不等于任务能继续。
>
> 对照这个框架看我自己的项目：前四步都实现了，**第五步基本没做**——没有命令幂等、没有分层超时、没有任务持久化。这也是我如果重做一遍会优先补的部分。

**关键追问**

```text
Q: 为什么不能说「前端所有状态都是派生值」？
A: 因为交互状态——草稿、滚动位置、面板展开——
   本来就可以由前端持有，服务端不关心这些。
   把所有状态都当成必须从服务端重建是过度设计。
   要区分的是业务事实和交互状态的权威归属。

Q: 服务端重启后要恢复任务，为什么存数据库不够？
A: 因为任务记录只说明「有过这个任务」，
   不说明「进行到哪一步」「已发生的副作用怎么算」
   以及「续跑是断点继续还是整体重启」。
   这三件事不解决，恢复出来的任务也接不上。
```

## 场景 M：用户反馈「任务卡住了」，你怎么分层定位？【P0】

**场景**：用户说「我发了一条消息，界面一直显示在跑，但什么都没出来」。你需要在不看日志、只有现象的情况下，给出排查路径。

**核心结论**：先**确定断在哪一层**，再深入细节。盲目看代码是最低效的做法。

**第一步：建立分层模型**

一条事件从产生到渲染要经过多个环节，任何一环断了，表现都是「界面不动」：

```text
① SDK 有没有产生事件
② 会话封装层有没有收到并广播
③ SSE 流有没有写出去
④ 网络有没有送达
⑤ 前端有没有收到并分发
⑥ 状态有没有更新
⑦ 视图有没有重新渲染
```

**第二步：用最少的检查砍掉大部分范围**

| 检查 | 结果 | 可能的问题范围 |
| --- | --- | --- |
| 事件流里还有没有新数据帧 | 没有 | 服务端或更底层（①②③） |
| 有帧但心跳也停了 | 这个方向没有数据了 | 连接层可能出问题，也可能是服务端静默（④） |
| 有帧、有心跳，界面不动 | 数据到了前端但没生效 | 前端侧（⑤⑥⑦），但也要排除事件无效或被拦截 |

**这个三分法能砍掉大部分排查范围**，是最高效的第一步。

**第三步：逐层深入**

判断到范围之后，再往里查。关键是**每一步都要说清这个证据能证明什么、不能证明什么**。

**① 执行是否还在推进**

看会话文件是否还在增长。文件在长，说明执行有进展；长时间不增长，可能是模型请求挂起或工具阻塞。

但这个证据有局限：**落盘发生在消息定稿时，流式过程中的增量不落盘**。所以「文件不增长」也可能是「正在生成长回复但还没定稿」。它不能单独证明执行停滞。

**② 事件是否产生并被广播**

看有没有订阅者。如果没有订阅者，事件会被静默丢弃——服务端在跑，但没有任何东西在听。

**③ 流是否还在写**

这里有个真实的边界：写失败时会清理监听器和定时器，但**不主动关闭流**。结果是浏览器侧看起来连接还在，服务端却已经不写数据了，连心跳也停了。

**④ 心跳是否按时到达**

心跳停了，通常说明连接层出了问题。但要注意：**心跳停止不能直接等同于网络断开**——它同样可能是服务端写入失败后静默导致的。

**⑤ 前端是否真的更新了**

有数据帧但页面不动，可能性不止一种：事件内容无效、被状态守卫拦截、或者状态更新了但没有产生预期的渲染结果。要进到事件入口和状态里确认，而不是看到「有帧」就认定前端没问题。

**第四步：当前实现防不住什么**

| 缺口 | 后果 |
| --- | --- |
| 没有超时检测 | 如果底层真的卡住，界面会一直显示运行中，没有任何超时提醒 |
| 写失败后流不关闭 | 浏览器侧感知不到连接已死 |
| 没有服务端日志 | 排查时看不到「事件有没有到达封装层」 |
| 没有分阶段耗时 | 无法判断是模型慢、工具慢还是重试在拖 |

**项目已有的观测手段**

| 能力 | 项目状态 |
| --- | --- |
| SSE 心跳 | ✅ 每 30 秒一次，可用于判断连接是否存活 |
| 运行中会话查询接口 | ✅ 有。遍历存活实例返回正在运行的会话 |
| 侧栏运行标记轮询 | ✅ 有。2.5 秒一次，页面可见时才发 |
| 超时检测 | ❌ 未实现 |
| 服务端事件日志 | ❌ 未实现 |
| 分阶段耗时统计 | ❌ 未实现 |

**迁移原则**

1. **先建分层模型，再用排除法**。不要从「可能是网络问题」这种猜测出发。
2. **找最快的分界点**。在这个系统里是「事件流有没有新帧」，它一步就把范围分成服务端和前端两半。
3. **每个证据都要说清它能证明什么**。心跳停止不等于网络断开，文件不增长不等于执行停滞——把间接证据当成直接结论，会指引错误方向。
4. **排查能力要提前建设**。日志、埋点、健康检查在出问题时才想起来加就晚了。

**口述版**

> 我会先建一个分层模型，再用排除法，而不是凭现象猜。
>
> 一条事件从产生到渲染要经过几个环节：执行产生事件、封装层广播、流写入、网络传输、前端接收、状态更新、视图渲染。**任何一环断了，用户看到的现象都是「界面不动」——所以现象本身不能定位问题。**
>
> 我会先做三个最快的检查。第一，事件流里还有没有新数据帧？没有的话问题在服务端或更底层。第二，有帧但心跳也停了，说明连接层可能有问题。第三，有帧、有心跳但界面不动，那问题在前端。这三步能把范围砍掉大半。
>
> 然后逐层往里查，但我不会把间接证据当成直接结论。比如看会话文件是否增长——这能反映执行有没有推进，**但落盘发生在消息定稿时，流式增量不落盘，所以文件不增长也可能只是正在生成长回复**。再比如心跳停了，通常说明连接有问题，**但它同样可能是服务端写入失败后静默导致的，不能直接断定是网络断开**。还有「有数据帧但页面不动」，可能是事件内容无效、被状态守卫拦截、或者状态更新了但没产生预期的渲染结果，得进到事件入口和状态里确认。
>
> 最后我会主动说当前防不住什么：没有超时检测，底层真卡住界面会一直显示运行中；写入失败后流不会主动关闭，浏览器感知不到是死连接；没有服务端日志，看不到事件有没有到达封装层；没有分阶段耗时，分不清是模型慢、工具慢还是重试在拖。
>
> 要补的话我会先补分阶段埋点和服务端日志——**没有数据就没法定位瓶颈**。

**关键追问**

```text
Q: 为什么说「心跳停了」不能断定是网络断开？
A: 心跳停止只说明这个方向没有数据。
   它同样可能是服务端写入失败后静默导致的，
   所以还要结合服务端状态一起判断，而不是直接归因。

Q: 怎么区分「任务真的卡住」和「只是没推送」？
A: 这是两个独立信号：执行有没有推进、连接是否存活。
   两者组合能区分出几种情况，
   但要注意每个信号本身都有局限，不能单独下结论。
```

## 场景 N：这个项目要从「本机工具」变成「团队协作产品」，需要补什么？【P1】

**场景**：面试官问「如果公司想把你这个工具推广给团队用，你打算怎么改」。

**核心判断**：这不是「加个登录页」的问题。核心是**把单机信任模型改造成多用户隔离模型**。改造之前要先想清楚当前依赖哪些信任假设，假设变化后什么会失效。

**第一步：当前的信任假设是什么**

项目 README 的声明很直接：

> 本项目 API 无鉴权 且 Agent 可执行任意命令 **仅限本机使用**

这句话背后是两个假设：**访问者可信**（只有本机用户）、**执行范围可信**（只在自己的机器上跑）。改成团队产品，这两个假设都不成立了。

**第二步：五个维度，每个都对应一个失效的假设**

**① 身份与授权**

| 要补什么 | 为什么 |
| --- | --- |
| 用户认证 | 区分谁在操作 |
| 会话归属校验 | 防止通过改参数访问别人的会话 |
| 工作区权限 | 防止访问别人的项目目录 |

这里要说清一个区分：**登录不等于授权**。认证回答「你是谁」，授权回答「你能访问什么、能做什么」。只做前者，用户登录后依然能通过改请求参数访问别人的会话。

**② 数据隔离**

| 要补什么 | 为什么 |
| --- | --- |
| 会话数据按用户隔离 | 当前所有会话在同一个目录下 |
| 工作区授权检查 | 当前只校验路径是否在「允许的根」里，而允许的根来自所有会话 |

**③ 执行隔离**（最容易被低估）

| 要补什么 | 为什么 |
| --- | --- |
| 容器或受限用户 | 当前 Agent 以服务进程的权限执行任意命令 |
| 网络出口限制 | 防止数据外传 |
| 资源配额 | 防止单个任务耗尽机器 |

关键判断：**文件接口的路径校验不等于命令执行已被沙箱隔离。** 前者只保护「通过接口读文件」，后者保护「通过命令行做任何事」。

**④ 凭证保护**

| 要补什么 | 为什么 |
| --- | --- |
| 密钥不进入模型上下文 | 工作区里的配置文件可能被 Agent 读到并回显出来 |
| 用户级密钥隔离 | 不能用同一个服务端密钥代表所有用户 |
| 审计脱敏 | 日志不能记录敏感内容 |

**⑤ 成本与资源治理**

| 要补什么 | 为什么 |
| --- | --- |
| 预算上限 | 当前成本只展示不约束 |
| 并发限制 | 防止单个用户占满资源 |
| 任务超时 | 当前没有任务级超时 |

成本从「自己的钱」变成「公司的钱」，约束的必要性完全不同。

**第三步：多实例为什么不是换个存储就行**

这是当前架构最硬的边界。实例注册表是**进程内**的 Map：

| 问题 | 后果 |
| --- | --- |
| 同一会话在两个实例各建一个执行对象 | 同时写同一个会话文件 |
| 请求和事件流路由到不同实例 | 事件流收不到对应会话的事件 |
| 滚动发布时进程退出 | 正在跑的任务中断 |

**共享存储不等于分布式执行协调。** 把注册表挪到共享存储只解决了「状态放哪」，没有解决「请求和事件流如何路由到同一实例」以及「进程崩溃后正在跑的任务怎么处理」。要解决后两个问题，需要先确定**会话的归属模型**——哪个实例独占执行哪个会话，以及会话在实例间怎么迁移。

**第四步：哪些改造只是在补功能，哪些在改架构假设**

| 改造 | 成本 | 性质 |
| --- | --- | --- |
| 加认证 | 中 | 补功能，有成熟方案 |
| 数据隔离 | 中 | 改存储布局 |
| 执行隔离 | 高 | 改架构假设 |
| 多实例协调 | 高 | 改架构假设 |
| 任务持久化 | 高 | 改架构假设 |

后三行高的共同原因是：它们改变的不只是代码，而是**当前设计隐含的边界条件**。

**项目映射**

| 维度 | 项目状态 |
| --- | --- |
| 身份与授权 | ❌ 完全未实现 |
| 数据隔离 | ⚠️ 有路径校验，但「允许的根」来自所有会话，不是按用户隔离 |
| 执行隔离 | ❌ 未实现 |
| 凭证保护 | ⚠️ 有 SVG 的内容安全策略，但无凭证隔离 |
| 成本治理 | ⚠️ 只展示不约束 |
| 多实例支持 | ❌ 进程内注册表 |

**迁移原则**

1. **先明确当前的信任模型，再推导要补什么**。安全改造不能靠清单，要靠「哪个假设不成立了」。
2. **登录不等于授权，共享存储不等于分布式协调**。这两组是最容易混的概念对。
3. **区分「补功能」和「改架构假设」**。前者的成本可以按人天估，后者不能。
4. **成本治理要趁早**。从单机到多人，约束的必要性完全不同。

**口述版**

> 我会先说清楚当前的信任模型，因为所有改造都是从「哪个假设不成立了」推出来的。
>
> 现在这个项目是**本机工具**，它有两个隐含前提：**访问者可信**——只有本机用户能访问；**执行范围可信**——只在自己机器上跑。文档里也明确写了「接口无鉴权，Agent 可执行任意命令，仅限本机使用」。改成团队产品，这两个前提都不成立。
>
> 我会按五个维度补：身份授权、数据隔离、执行隔离、凭证保护、成本治理。
>
> 其中有两组概念我想专门强调，因为它们最容易混：
>
> 第一，**登录不等于授权**。认证回答「你是谁」，授权回答「你能访问什么、能做什么」。只做前者，用户登录后照样能通过改请求参数访问别人的会话。
>
> 第二，**共享存储不等于分布式执行协调**。把注册表挪到共享存储只解决「状态放哪」，没解决「请求和事件流怎么路由到同一实例」以及「进程崩溃后正在跑的任务怎么办」。要解决后两个，得先确定会话归属模型——哪个实例独占执行哪个会话。
>
> 还有一组：**任务持久化不等于任务可恢复**。这个我在别的题里也说过，任务记录写进数据库只说明「有过这个任务」，不说明进行到哪一步、已发生的副作用怎么算。
>
> 如果要排优先级，我会说**执行隔离和多实例成本最高**，因为它们改的是架构假设，不是加功能。认证和数据隔离相对成熟，可以先用现成方案。

**关键追问**

```text
Q: 为什么说「加个登录页」不够？
A: 登录只解决「谁在访问」，没解决「能访问什么」
   和「执行能造成多大伤害」。
   身份、数据、执行、凭证、成本是五个独立维度。

Q: 多实例为什么不能靠换共享存储解决？
A: 换存储只解决「注册表放哪」，
   没解决「请求和事件流如何路由到同一实例」
   和「进程崩溃后正在跑的任务怎么处理」。
   这需要先确定会话的归属模型。
```
