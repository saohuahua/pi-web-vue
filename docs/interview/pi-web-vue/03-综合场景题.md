## 场景 A：Agent 执行到一半，用户改主意了【P0】

**场景**：用户让 Agent 修登录 Bug。Agent 正在读文件、跑命令，用户发现范围太大，追加一句「先不要改文件，只分析原因」。过了一会儿又决定彻底停止。

**结论**：这是三个不同操作，走不同路径——**追加指令**是入队、**停止**要先撤回队列再 abort、**撤回**有版本校验。

**① 追加指令：steer 还是 followUp**

`usePromptQueue.ts` 的 `submitQueuedPrompt` 走的是 `prompt` 命令 + `streamingBehavior` 字段，**不是**独立的 steer/followUp 命令。注释说明了设计：

> SDK 在接纳时判断入队或开启新轮 前端不根据过时的运行状态猜测

| 模式 | UI 文案 | 投递时机 |
| --- | --- | --- |
| `steer` | 「立即纠偏」 | 当前 assistant turn 的工具调用跑完后、**下一次 LLM 调用之前** |
| `followUp` | 「本轮后继续」 | **等 agent 完全停下来**才投递 |

**为什么前端不自己判断该用哪个**：判断依据是 SDK 内部的流式状态，前端持有的是一份可能过时的副本。如果前端根据本地状态猜，猜错会导致「以为入队了其实开了新轮」。

**② 停止：为什么必须先撤回队列再 abort**

`chat.ts` 的注释给了理由：

> Pi 在 abort 后可能继续尚存的队列 因此必须先撤回再停止

SDK 的 RPC 文档印证了这一点（`docs/rpc.md`）：`abort` **不会丢弃队列**，剩余的 steer/followUp 还会继续执行。如果不先撤回，用户以为停了、任务却还在跑。

**撤回失败就不 abort**：队列状态未知时中止会话，会让未知数量的指令继续执行，而且没有恢复手段。所以宁可保持运行态并提示「队列未确认 当前任务仍在运行」。这条路径有测试覆盖（`tests/app/stores/chat-queue.test.ts`）。

**③ `clear_queue` 为什么要等服务端的接纳链**

```ts
case "clear_queue":
  // 等当前 prompt 完成接纳判断 再取 SDK 实际尚未消费的队列
  await this.promptAdmissionTail
  return this.inner.clearQueue()
```

**如果抢在接纳判断之前执行会怎样**：

1. `clearQueue()` 返回空数组，前端以为「队列已空」
2. 紧接着那条 prompt 被接纳进队列
3. 结果是**前端显示无队列、草稿也没回填，但服务端还有一条指令会继续执行**

这正是「误称任务已停止」这类错误。测试 `tests/server/utils/rpc-manager.test.ts` 断言：prompt 未 accept 前 `clearQueue` 一次都没被调用。

**④ 3 秒兜底定时器**

`abort` 的 POST resolve 与 `agent_settled` 事件可能乱序或丢失，所以 3 秒后若仍是同一会话、同一代次且 `isRunning` 还是 true，强制落定并 reload 对账。`agent_settled` 先到会 `clearTimeout`。

**为什么是 3 秒**：`abort()` 内部会等会话真正 idle（`abortRetry → abortCompaction → agent.abort → waitForIdle`），这个等待时间不确定。3 秒是「绝大多数情况足够，又不会让用户觉得卡住」的折中——**经验值，不是测量得出的**。

**边界**

| 边界 | 说明 |
| --- | --- |
| 只有「全部撤回」 | Pi 只支持清空全部队列，没有单条撤回 |
| 停止返回 ≠ 工具已停 | HTTP 返回只代表 abort 命令被接纳 |
| 撤回不保证 SDK 没消费 | `clear_queue` 返回的是「尚未消费」的部分 |

**口述版（约 65 秒）**

> 用户改主意在系统里对应三个不同操作，路径完全不一样。
>
> 追加指令是入队。我用的是 `prompt` 命令加一个 `streamingBehavior` 字段，而不是独立的 steer 或 followUp 命令。原因是「入队还是开新轮」这个判断依赖 SDK 内部的流式状态，前端手里那份是可能过时的副本。如果前端自己猜，猜错会导致「以为入队了其实开了新轮」。所以让 SDK 在接纳时判断。两种模式的区别是投递时机——steer 在当前轮的工具调用跑完后、下一次模型调用之前投递；followUp 要等 agent 完全停下来。
>
> 停止这个操作有个不太直观的地方：**必须先撤回队列再 abort**。因为 Pi 在 abort 之后不会丢弃队列，剩余指令还会继续跑。而且如果撤回失败了，我就直接不 abort——队列状态未知时中止会话，会让未知数量的指令继续执行，而且没有任何恢复手段。
>
> 撤回还有一个服务端的细节：`clear_queue` 必须等接纳链。因为 SDK 的 prompt 接纳是异步的，在 `preflightResult` 回调之前，那条指令还没进队列。如果撤回抢在接纳判断之前执行，会返回空数组让前端以为队列空了，紧接着那条指令又被接纳进去——结果是前端显示无队列、草稿也没回填，但服务端还有一条指令会执行。
>
> 最后还有个 3 秒兜底。因为 abort 的 HTTP 响应和 `agent_settled` 事件可能乱序或丢失，所以 3 秒后如果还认为在运行，就强制落定并 reload 对账。

**追问**

```text
Q: 为什么不做单条撤回？
A: Pi 只支持 clearQueue 清空全部，没有按条撤回的 API。
   所以 UI 上只有一个「全部撤回」按钮。

Q: 撤回的文本去哪了？
A: 回填到草稿，放在当前输入之前。
   放在前面是有意的——撤回的文本是用户要重试的内容，
   应该紧邻光标起始位置。

Q: 撤回队列也要版本校验？
A: 要。clear_queue 飞行期间 SDK 可能又推来 queue_update，
   这时候返回的空队列是过期的，直接覆盖会擦掉新的排队消息。
```

## 场景 B：用户编辑历史消息，从第 3 轮重新开始【P0】

**场景**：用户在第 8 轮发现第 3 轮的条件写错了，想回到第 3 轮改一下再继续。

**结论**：不是「修改那条消息」，而是「从它的**父节点**开一条新分支」。关键是 `editingTargetId` 用的是**父 entry 的 id**。

**完整流程**

```text
① 用户点消息上的编辑按钮
   └─ chat.ts beginEditMessage(index)
      ├─ 五重互斥判定：pendingDraft / isRunning / isCompacting /
      │                 isNavigating / positionUnknown 任一为真就拒绝
      ├─ 结构判定：前面至少有一条 user 消息（第一条不可编辑）
      ├─ 目标判定：必须是 user 角色且有 entryId
      ├─ parentId = findEntryParentId(tree, messageId)   ← 关键
      └─ draftBeforeEdit = draft.value（记快照，供取消时还原）
         editingMessageId = messageId
         editingTargetId = parentId        ← 导航目标
         draft.value = 原消息文本

② 用户改完点发送
   └─ chat.ts submitPrompt(text, images)
      ├─ pendingDraft = {...}  清空输入框  落盘
      ├─ await navigateToLeaf(editingTargetId)    ← 先导航
      ├─ await sendPrompt(text, images)            ← 再发送
      └─ 成功则清编辑态；失败则 mergeDraftText 回填
```

**① 为什么编辑目标是「父 entry」而不是「这条消息」**

`editingTargetId` 不是 UI 传进来的，而是 `findEntryParentId(tree.value, messageId)` **从会话树里现算出来的父 entryId**。

**原因**：如果导航到这条消息本身，新 prompt 会挂成它的**子节点**——那就变成「在它后面继续对话」，编辑退化成追加。导航到**父节点**，新消息才会成为原消息的**兄弟**，形成真正的分支。

**这和 CLI 的 `/tree` 语义是一致的**：SDK 文档（`docs/sessions.md:104-108`）说明，选中一条用户消息时，pi 也是「把 leaf 移到该消息的父节点，然后把消息文本放进编辑器」。

**② 为什么必须先导航再发送**

顺序是 `navigateToLeaf(target)` → `sendPrompt`。**顺序反过来**，新消息会追加到当前活跃叶子（原消息的子孙）之后，`.jsonl` 里就变成了覆盖式追加而不是分叉。

**③ 为什么先预览再导航**

`useSessionNavigation.ts` 的注释：

> 先预览再导航 防止无效目标改变服务端分支
> 导航之后只信权威详情 失败时尽量回到原叶子

`previewSessionContext` 走的是只读接口，能提前发现非法 leaf、断链、环。`navigate_tree` 是唯一有副作用的动作，一旦执行就改写服务端活跃叶子。**先预览把「目标根本不可用」这类失败挡在副作用之前**。

**④ 导航失败的回退逻辑**

`commandSent` 标志是关键分叉：

| 阶段失败 | 处理 |
| --- | --- |
| 预览阶段（`commandSent === false`） | 不发回退命令，服务端理论上没动过 |
| 导航之后（`commandSent === true`） | **先重新读取再决定是否回退**——请求失败可能发生在服务端导航之后 |

如果确认叶子真的偏离了原位置，就反向导航回 `previous`；回退也失败的话置 `positionUnknown = true`。一旦为真就全线锁死：禁止发送、编辑、队列提交、分支导航，界面显示「重新加载」。

**为什么要有 `positionUnknown`**：它表达「我不知道服务端现在的位置了」。这种情况下继续发送会导致消息挂到错误的分支上。与其猜，不如让用户重新加载。

**⑤ 取消编辑的取舍**

`cancelEdit` 把 `draft` 覆盖回 `draftBeforeEdit`，**编辑期间敲的文本会丢弃**。这是显式取舍——「取消即放弃编辑改动」。

`draftBeforeEdit` 的赋值有 `if (!editingMessageId.value)` 条件：**只在首次进入编辑态时记录**。连续改编辑目标时不会覆盖它，所以「取消」永远回到进入编辑态之前的原始草稿。

**边界**

| 边界 | 说明 |
| --- | --- |
| **没有 fork** | 项目支持会话内分支导航和编辑后重提，但**独立的 fork 命令未实现**（`rpc-manager.ts` 里是抛错占位） |
| 分支入口会隐藏 | 没有分叉时 `branches` 为空数组，按钮整体不渲染 |
| 第一条用户消息不可编辑 | 它没有父节点，无法定位导航目标 |

> **关于 fork 的准确说法**：pi CLI 有 `/fork`（从历史用户消息创建**新会话文件**）和 `/clone`（复制当前分支成新会话）。本项目**没有实现**这两个。当前的分支能力是 `navigate_tree`——它在**同一个会话文件**内移动 leaf 指针，语义不同。这不是能力缺口，而是产品选择：当前 UI 只提供「会话内探索替代方案」。

**源码位置**：`app/stores/chat.ts`、`app/composables/useSessionNavigation.ts`、`shared/lib/session-branches.ts`（移植）

**口述版（约 70 秒）**

> 编辑历史消息的语义不是「修改那条消息」，而是「从它的**父节点**开一条新分支」。
>
> 这里最关键的设计是：编辑目标用的不是这条消息的 entryId，而是它**父节点**的 entryId。这个 id 不是 UI 传进来的，是从会话树里现算出来的。为什么用父节点？因为如果导航到这条消息本身，新消息会挂成它的子节点，那就变成了「在它后面继续对话」，编辑就退化成追加了。导航到父节点，新消息才会成为原消息的兄弟。
>
> 顺便说一句，这和 pi CLI 的 `/tree` 语义是一致的——SDK 文档里写，选中用户消息时也是把 leaf 移到父节点，然后把消息文本放进编辑器。
>
> 所以发送流程必须是先导航再发送。顺序反过来，新消息会追加到当前活跃叶子之后，会话文件里就变成了覆盖式追加而不是分叉。
>
> 导航之前还要先预览。预览走只读接口，能提前发现非法叶子、断链、环这些问题。而 `navigate_tree` 是唯一有副作用的动作，一旦执行就改写了服务端活跃叶子。先预览就是把「目标根本不可用」这类失败挡在副作用之前。
>
> 失败处理分两种情况。如果预览阶段就失败，说明服务端理论上没动过，不发回退命令。如果导航之后才失败，那就要**先重新读取再决定是否回退**——因为请求失败可能发生在服务端导航之后。如果回退也失败，就置一个「位置未知」标志，这时候发送、编辑、导航全部锁死，提示用户重新加载。
>
> 有一条边界要说清楚：项目**没有实现 fork**。pi CLI 有 `/fork` 和 `/clone`，它们会创建新的会话文件；我这里的 `navigate_tree` 是在同一个会话文件里移动指针，语义不同。这是产品选择，不是能力缺口。

**追问**

```text
Q: 为什么要用 entryId 而不是数组下标？
A: 数组下标是当前视图的位置，reload 之后会变。
   entryId 是会话文件里的稳定标识，分支操作必须用它定位。
   这也是 messages 和 entryIds 要维护成平行数组的原因。

Q: 如果服务端已经切换分支，但 HTTP 响应超时了？
A: 这正是 commandSent 标志存在的原因。收到异常时不能假定
   服务端没动过，要先 reload 看实际位置，确认偏离了才反向导航。

Q: 前端显示的分支和 SDK 实际分支不一致时怎么办？
A: 先尝试恢复（反向导航），恢复不了就置 positionUnknown
   并锁死操作，让用户重新加载。不猜、不硬撑。
```

## 场景 C：用户快速切换会话，旧请求才返回【P0】

**场景**：用户在会话 A 发起历史查询，马上切到 B，此时 A 的响应才回来。

**结论**：靠**三层判据**（会话 ID + 操作代次 + 查询序号）在写入点拦截，而不是靠取消请求。

**推导路径**

- **场景**：A 的请求在切到 B 之后才返回
- **错误**：B 的消息列表、模型名、上下文用量被 A 覆盖
- **原因**：异步完成时页面归属已经变了
- **方案**：写入点校验三层身份
- **取舍**：取消请求能省资源，但写入点校验能直接阻止过期结果生效
- **边界**：所有跨 `await` 修改状态的路径都要检查是否遗漏校验

**三层判据各防什么**（完整推导见 [02 篇 Q17](02-状态管理与会话恢复.md)）

| 层 | 防的竞态 | 为什么前一层不够 |
| --- | --- | --- |
| `sessionId` | 已切到别的会话 | — |
| `sessionGeneration` | A→B→A 之后旧响应回来 | A→B→A 后 sessionId 又匹配，但响应反映的是几轮之前的状态 |
| `reloadSequence` | 同会话内两次 reload 乱序返回 | 两次的 sessionId 和代次都相同，但旧的可能后返回 |

**为什么不用 AbortController**

| 方式 | 问题 |
| --- | --- |
| 取消请求 | 需要每个请求传 signal；而且**取消请求不等于阻止回调执行**——已缓冲的数据仍可能触发回调 |
| **写入点校验**（当前） | 简单可靠，不改请求层 |
| 每会话独立 store | 内存开销大，跨会话共享的数据不好处理 |

**这是本题最值得讲的判断**：取消请求和阻止过期结果生效是两件事。取消能省带宽，但不能保证回调不执行。**在写入点校验是更可靠的防线**。

**校验点为什么这么多**

`chat.ts` 内 13 处，其他 composable 里 20 处。**原因是每个 `await` 之后都要重新确认**。

**这个模式可以迁移**：搜索联想、表单异步校验、切换详情页、文件预览、并发保存——凡是「发起异步请求 + 用户在等待期间可能改变上下文」的场景，都是同一个问题。

**一处真实的缺口**

`openSession` 里 `sessionId.value === id` 守卫覆盖了编辑态恢复，但 `syncFromSessionCwd(info.cwd)` **没有**。极快切会话时，旧会话的 `cwd` 可能覆盖新工作区选择器。影响范围限于工作区选择器的显示，不影响消息数据。**静态推导，未做真机验证**。

**口述版（约 60 秒）**

> 这个场景的本质是：Promise 一旦创建就无法取消，`fetch` 发出后即使调用方不再关心结果，回调仍然会执行。
>
> 我的做法不是去取消请求，而是在**写入点校验**。因为取消请求和阻止过期结果生效是两件事——取消能省一点带宽，但已经缓冲的数据仍可能触发回调。在写入前判断「这个结果还算不算数」是更可靠的防线。
>
> 判据有三层，每层防一类不同的竞态。第一层是会话 ID，防已经切到别的会话。第二层是操作代次，防的是用户从 A 切到 B 再切回 A 的情况——这时候会话 ID 又匹配了，但那个响应是第一次打开 A 时发的。第三层是查询序号，防同一会话内两次 reload 乱序返回——这两次的会话 ID 和代次都相同，但旧的可能因为网络抖动后返回。
>
> 整个 store 里有 13 处校验点，其他 composable 里还有二十处。原则是每个 `await` 之后都要重新确认。
>
> 这个模式不只适用于会话切换。搜索联想、表单异步校验、切换详情页、并发保存，凡是「发起异步请求 + 用户在等待期间可能改变上下文」的场景，都是同一个问题——用身份加版本号在写入点拦截。
>
> 我也知道一个缺口：`openSession` 里同步工作区 cwd 那一行没有加会话 ID 守卫，而同一个 try 块里上面那行有。这是从代码推导的，没实测过。

**追问**

```text
Q: 怎么构造这个竞态来测试？
A: 不 await 就切换。先拿到 pending promise，
   立刻调 openSession("B")，再 await pending。
   tests/app/stores/chat-races.test.ts 里有 9 个这样的用例。

Q: 如果旧结果真的污染了状态，怎么排查？
A: 先确认污染的是哪个字段，再搜这个字段的所有赋值点，
   检查每个赋值点上游有没有校验。重点看跨 await 的写入。
```

## 场景 D：工具调用展示了，但结果没关联上【P1】

**场景**：用户看到工具卡片一直显示「执行中」，或者突然显示「完成」但结果区是空的。

**结论**：关联标识是 `toolCallId`，**没有第二个标识**。缺失会串、重复会覆盖、不匹配会静默不显示。

**四种异常输入的实际行为**

| 异常 | 实际行为 | 后果 |
| --- | --- | --- |
| `toolCallId` 缺失 | 归一化双字段兼容，都没有则给**空串** | 多个缺 ID 的工具**互相串** |
| `toolCallId` 重复 | `map.set` 后写覆盖先写 | 只保留**最后一个**结果 |
| 结果找不到调用 | 渲染成 `aria-hidden` 空 div | **孤儿结果不显示** |
| 调用找不到结果 | 查不到 → `result` 是 undefined | 见下面的窗口 |

**一个状态错误窗口（静态推导）**

| 情况 | `activeTools` 有 | `streaming` | 显示 |
| --- | --- | --- | --- |
| 工具正在执行 | ✅ | false | 「执行中」 |
| **执行完但结果没到** | ❌ | false | **「完成」**（错误） |
| 消息还在流式 | 任意 | true | 「执行中」 |

第二行是问题：`tool_execution_end` 到达时 `activeTools.delete(id)` 立即执行，但结果消息要等后续的 `message_end` 才进 `messages`。这个窗口里卡片会短暂显示「完成」且结果区为空。

> **静态推导，尚未实测**。没有真实链路测试覆盖。

**为什么必须独立维护 `activeTools`**

助手消息在工具**开始执行之前**就定稿了。时序是 `message_end`（定稿）→ `tool_execution_start` → `tool_execution_end` → `message_end`（结果）。定稿后 `streaming` 已经是 false，光看消息判断不出工具还在跑。

**排查路径**

1. 看 `activeTools` 里有没有这个 `toolCallId`
2. 看 `messages` 里有没有对应的 `toolResult`
3. 对比两边 ID——不一致说明问题在归一化或事件处理；一致但没配上说明问题在 computed 更新

**最值得主动提的改进**

> 会话文件里如果存在「有 toolCall 但没有对应 toolResult」的助手消息，说明执行被中断了。前端可以把这类卡片标记为「未完成」而不是「完成」。**`toolResultsByCallId` 查不到就是未完成，不需要服务端改动**。

这个改进成本几乎为零，但能消除一个真实的误导——服务端重启后这种半截数据是必然会出现的。

**口述版（约 55 秒）**

> 工具调用和工具结果只有一个关联标识：`toolCallId`。工具调用在助手消息的 content 数组里，执行结果是一条独立的 `toolResult` 消息。我用一个 computed 从 messages 里扫出所有结果，建一个 ID 到 result 的 Map，做成 computed 而不是独立 state 是为了保证只有一份事实来源。
>
> 「执行中」这个状态比较特殊。因为助手消息在工具**开始执行之前**就已经定稿了，定稿后消息上的 streaming 标记已经是 false。所以我单独维护一个 `activeTools` 的 Map，start 时写入、end 时删除、中间更新进度。
>
> 异常输入有几个已知边界。`toolCallId` 缺失时归一化会给空串，多个缺 ID 的工具会互相串。结果找不到对应调用时，它作为一条消息存在但渲染是 `aria-hidden` 的空 div，也就是不显示——用户看不到「有个结果没配上」。另外 `tool_execution_end` 到 `message_end` 之间有一个短窗口，卡片会短暂显示「完成」但结果区是空的，这是从代码路径推导的，没实测过。
>
> 还有个值得改进的点：如果会话文件里有「有工具调用但没有对应结果」的消息，说明执行被中断了。当前实现会显示成「完成」，这是真实的误导。前端能检测出来——查不到结果就是未完成，不需要服务端改动。

**追问**

```text
Q: 两个工具同时执行会串吗？
A: 不会。activeTools 是 Map，可以同时存多条。

Q: 工具执行失败怎么显示？
A: result.isError 为真时卡片加 is-error 类，状态「出错」。
   注意判定的是工具结果里的 isError，不是网络错误。
```

## 场景 E：SSE 断线重连后内容重复【P1】

**场景**：网络抖动后 SSE 自动重连，用户发现同一段文本出现两次。

**结论**：**快照本身不会导致重复**（它是整体替换），重复来自三个地方。

**先排除一个常见误解**

`snapshot` action 是**整体替换** `streamingMessage`，不是追加：

```ts
case "snapshot": {
  const message = normalizeStreamingToolCalls(action.message)
  return message.role === "assistant"
    ? { isStreaming: true, streamingMessage: message }   // ← 整体替换
    : state
}
```

**重复的三个真实来源**

**① 快照去重失效（待核实）**

去重函数用**引用相等**判断事件是否已包含在快照里：

```ts
return snapshot !== undefined
  && (event.type === "message_start" || event.type === "message_update")
  && event.message === snapshot
```

**如果 SDK 在每次事件里克隆 `message` 对象，这条去重会永远失效**。单元测试用手工构造的同一对象验证了逻辑，但**没有验证真实链路上 SDK 是否稳定复用同一对象引用**。

**② 重复的 `text_delta`**

reducer 没有事件去重，`text_delta` 是 `current.text + event.delta`，处理两次就是两份文本。

**③ `messages` 层面的重复**

`message_end` 里对**用户消息**有去重逻辑（靠 `optimisticKey` 比对），但对 **assistant 消息没有去重**——直接 push。

**不过**：`agent_end` 和 `agent_settled` 都会触发 `reload()`，而 reload 是**整体替换** `messages`。所以重复会被下一次 reload 修掉——**前提是 reload 成功**。

**排查路径**

1. 先判断是流式气泡重复还是已定稿消息重复
2. 看 Network 的 EventStream 里有没有重复帧
3. 对比快照和缓冲事件，看是否重叠
4. **确认 reload 是否成功**——`fetchSessionDetail` 抛错会被 catch 成 null，重复就修不掉了

**前端能解决什么，服务端要配合什么**

| 问题 | 前端能否独立解决 | 需要服务端什么 |
| --- | --- | --- |
| 重复的 delta | 部分可以（维护事件指纹） | **事件序号**是根本方案 |
| 乱序的事件 | 可以（按 contentIndex 排序） | 序号 + 重排序缓冲 |
| 断线丢失的事件 | **不能** | 事件缓冲 + `Last-Event-ID` 补发 |
| 快照去重失效 | 不能 | 保证引用复用，或改用事件序号去重 |

**口述版（约 55 秒）**

> 首先要排除一个误解：快照本身不会导致重复。前端收到快照走的是 `snapshot` action，它是**整体替换**流式消息，不是追加。
>
> 重复有三个可能来源。第一是快照去重失效——服务端补发缓冲事件时会和一个去重函数比对，判断事件是否已包含在快照里，这个函数用的是**引用相等**。我在单元测试里用手工构造的同一对象验证过逻辑，但真实链路上 SDK 是否复用同一对象引用，我**没有验证过**。如果它每次克隆，这条去重就会失效。
>
> 第二是重复的 delta，reducer 没有事件去重。第三是消息层面的重复，`message_end` 里对用户消息有去重，但对 assistant 消息没有，是直接 push 的。不过这个会被下一次 reload 修掉，因为 reload 整体替换消息列表——**前提是 reload 成功**。
>
> 排查顺序是：先判断是流式气泡重复还是已定稿消息重复，再看 Network 里有没有重复帧，最后确认 reload 是不是真的成功了。
>
> 根本的解决方案是服务端给事件编号，前端做去重和乱序检测。断线期间丢失的事件只能靠服务端事件缓冲加 `Last-Event-ID` 补发，前端单独解决不了。

**追问**

```text
Q: 为什么快照要用引用相等去重，而不是比较内容？
A: 比较内容需要深比较，每条事件都做成本很高。
   引用相等是 O(1)。前提是 SDK 复用同一个对象引用——
   这个前提我没有验证过。

Q: 重复会被永久保留吗？
A: 不会。agent_end 和 agent_settled 都会触发 reload，
   reload 整体替换 messages。但前提是 reload 成功。
```

## 场景 F：用户抱怨「看起来完成了，实际没修好」【P1】

**场景**：Agent 说「Bug 已修复」，但用户测试发现还是坏的。

**结论**：当前项目**没有验证机制**——它展示的是 Agent 的自述，不是经过验证的结果。这是产品层面的真实缺口。

**系统能提供什么**

| 能提供 | 依据 |
| --- | --- |
| 工具执行的**原始输出**（含退出码） | `ToolCallCard` 展示 `result.content`，bash 输出带 ANSI 着色 |
| 工具是否报错 | `result.isError` 驱动卡片状态「出错」 |
| 完整执行过程（读了哪些文件、跑了什么命令） | 思考块 + 工具卡片按真实顺序渲染 |
| 工具调用与结果的配对关系 | `toolResultsByCallId` |

**系统不能提供什么**

| 不能提供 | 原因 |
| --- | --- |
| 「任务是否真的成功」的判定 | 没有验证层，UI 显示的是模型的自然语言结论 |
| 测试是否通过的结构化状态 | 测试结果只是 bash 工具的一段文本输出 |
| 修改后的代码是否能编译 | 没有跑类型检查或构建 |

**这个缺口怎么讲才诚实**

> 当前实现展示的是**执行过程**，不是**执行结果的可信度**。用户能看到 Agent 跑了什么命令、输出了什么，但「Bug 是否真的修好」需要用户自己判断。界面不会替用户下这个结论。

**如果要补验证层，最小可行的做法**

1. **把确定性工具的退出码提升为结构化状态**——bash 的 `exitCode` 已经在消息类型里有字段（`BashExecutionMessage.exitCode`），但当前 UI 没有把它渲染成「通过/失败」的显著标记
2. **区分「模型声称完成」和「验证通过」两个状态**——前者是自然语言，后者需要工具证据
3. **保留可回滚的修改记录**——哪些文件被改了，让用户能查看和回退

**为什么不建议说「已经做了验证」**：代码里没有任何验证逻辑。面试官只要问「你怎么判断测试通过了」，就露馅了。**主动划清这个边界反而加分**。

**口述版（约 55 秒）**

> 这个问题要分开看：系统能提供的是**完整的执行过程**，不是**结果的可信度**。
>
> 用户能看到 Agent 读了哪些文件、跑了什么命令、命令的原始输出是什么、工具有没有报错。bash 的输出还做了 ANSI 着色，退出码也在消息结构里。但界面不会替用户判断「Bug 是否真的修好了」——这个结论来自模型的自然语言，而不是经过验证的事实。
>
> 所以如果一个任务实际上失败了、但模型说成功了，界面会照着模型的话显示。我没有做验证层，这是一个真实的产品缺口。
>
> 如果要补，最小可行的做法是把确定性工具的退出码提升成结构化状态。因为 bash 的 `exitCode` 本来就在消息类型里有字段，只是当前 UI 没有把它渲染成显著的「通过/失败」标记。第二步是区分「模型声称完成」和「验证通过」这两个状态。第三步是保留可回滚的修改记录。
>
> 我不会说「已经做了验证」，因为代码里确实没有。但我知道这个缺口在哪、以及最小的补法是什么。

**追问**

```text
Q: exitCode 已经在数据里了，为什么 UI 没显示？
A: BashExecutionMessage 类型里有 exitCode 字段，
   但当前渲染走的是 ToolCallCard 的通用逻辑，
   只区分了 isError 和正常。

Q: 怎么让用户知道「这个结论没经过验证」？
A: 可以区分两类消息：有工具证据支持的结论，
   和纯粹的自然语言结论。当前实现没有做这个区分。
```

## 场景 G：一次提交多张图，模型装不下【P2】

**场景**：用户粘贴了多张截图，希望 Agent 一起看。

**结论**：项目有**三层防护**——客户端压缩、前端数量与大小校验、服务端二次校验。

| 层 | 位置 | 规则 |
| --- | --- | --- |
| **客户端压缩** | `app/utils/image-compress.ts` | 超过 **1MB** 且不是 GIF 时压缩到最长边 **1024px**、JPEG 质量 **0.85**；压完反而更大时保留原图 |
| **前端校验** | `shared/lib/image-attachments.ts` | 最多 **10 张**，每张最大 **10MB** |
| **服务端校验** | `rpc-manager.ts` `validateAgentImages` | 同样的规则再验一次 |

**为什么三层都要**

`rpc-manager.ts` 的注释说明了服务端校验的必要性：

> 图片先过服务端边界校验 前端压缩只是体验优化 不是安全边界

**前端校验是体验，服务端校验才是边界**。前端代码可以被绕过（改 JS、直接调 API），所以服务端必须独立校验。

**为什么压缩阈值和上传上限差 10 倍**

| 值 | 用途 |
| --- | --- |
| 1MB | **压缩触发阈值**——超过就压，控制传输体积和上下文占用 |
| 10MB | **硬性上限**——超过就拒绝，防止内存爆掉 |

压缩后实际只有几百 KB，所以 10MB 是给「压缩失败的极端情况」兜底的（比如浏览器不支持 `createImageBitmap`）。

**为什么 GIF 不压缩**：GIF 是动图，用 canvas 压缩会**丢失动画**，只保留第一帧。宁可传大一点，也不破坏用户内容。

**为什么是 1024px 和 0.85 质量**：这两个值是「视觉上够用」和「体积可接受」的折中。**工程经验值，不是测量得出的最优解**。

**边界**

| 边界 | 说明 |
| --- | --- |
| 图片只传 `data` 和 `mimeType` | `previewUrl` 留在浏览器，不上传 |
| 服务端不单独存图片 | 图片进会话文件，随消息一起持久化 |
| 10 张是硬限制 | 超过返回明确的错误文案，不是静默丢弃 |

**口述版（约 50 秒）**

> 项目对图片有三层防护：客户端压缩、前端校验、服务端二次校验。
>
> 客户端压缩的规则是超过 1MB 且不是 GIF 时，压缩到最长边 1024px、JPEG 质量 0.85。GIF 不压缩，因为它是动图，用 canvas 压会丢掉动画只留第一帧。宁可传大一点，也不破坏用户内容。
>
> 前端校验是 10 张、每张 10MB。服务端还会再验一遍，代码注释里写得很清楚：**前端压缩只是体验优化，不是安全边界**。这句话是关键的——前端代码可以被绕过，改 JS 或者直接调 API 都行，所以服务端必须独立校验。
>
> 压缩阈值 1MB 和上传上限 10MB 差了 10 倍，因为它们解决不同问题。1MB 是压缩触发点，为了控制传输体积和上下文占用；10MB 是硬上限，为了防内存爆掉。压缩后实际只有几百 KB，所以 10MB 是给压缩失败的极端情况兜底的。
>
> 至于 1024px 和 0.85 这两个值，是「视觉够用」和「体积可接受」的折中，属于工程经验值，不是测量出来的最优解。

**追问**

```text

A: 存在会话文件里，随消息一起持久化。
   前端只传 base64 data 和 mimeType。

Q: 为什么不做服务端压缩？
A: 当前在客户端压，好处是不占服务端 CPU、少一次传输。
   坏处是依赖浏览器能力（createImageBitmap），
   不支持时会跳过压缩直接传原图。
```
