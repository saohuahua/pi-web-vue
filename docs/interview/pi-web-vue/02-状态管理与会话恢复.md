# 02 状态管理与会话恢复

> 对应简历：**「针对文本、思考和工具调用事件分段到达场景，基于纯函数 reducer 按内容索引组装消息块，并通过 toolCallId 关联工具调用与执行结果，实现流式内容和工具运行状态的分层展示」**；**「针对页面刷新后流式消息状态丢失的问题，结合会话历史查询、当前助手消息快照及 SSE 重连恢复界面；通过会话 ID、操作代次与查询序号校验异步结果，避免过期响应污染当前会话。对接 SDK 的手动及自动上下文压缩事件，展示压缩状态、当前上下文占用和会话 Token 用量。」**

## Q12 为什么不能直接在 SSE 回调里改消息？为什么要用纯函数 reducer？

**核心结论**：三个具体后果，不是「规范问题」——**结构会丢**（不知道增量属于哪一块）、**无法测试**（要 mock 网络和 DOM）、**更新点散落**（改状态的地方满文件都是）。

**Agent 一轮回复的真实结构**

```text
[0] thinking  "让我看看项目结构..."
[1] toolCall  { toolCallId: "call_1", toolName: "ls", input: { path: "." } }
[2] thinking  "目录里有个 src，我看看里面的文件"
[3] toolCall  { toolCallId: "call_2", toolName: "read", input: { path: "src/index.ts" } }
[4] text      "这个项目的入口在 src/index.ts，它做了三件事..."
```

**块是交替的，顺序就是真实发生顺序**。这就是为什么要用 `content: Block[]` 而不是字符串。`types.ts:52` 定义了四种块：`text` / `thinking` / `toolCall` / `image`。

**为什么「找最后一个块」会出错**

考虑这个结构：

```text
[0] text      "我先看看"              ← 这段已经定稿
[1] toolCall  ls
[2] text      "目录结构是这样的"       ← 这段的第一个增量到达时
```

在 `[2]` 的第一个增量到达时，`content` 里**还没有** `[2]` 这个块，找「最后一个 text 块」会命中 `[0]`——**文本被追加到了第一段后面**。`contentIndex` 存在的理由就是：事件明确说「我属于第几块」，不需要猜。

**为什么直接写在回调里就无法测试**

reducer 是纯函数，测试只需要构造 state 和事件：

```ts
// tests/shared/lib/streaming-message.test.ts:7-19
let state = streamReducer(INITIAL_STREAMING_STATE, { type: "start" })
state = streamReducer(state, { type: "snapshot", message: snapshot })   // ← 必须
state = streamReducer(state, { type: "delta", event: { type: "text_start", contentIndex: 0 } })
state = streamReducer(state, { type: "delta", event: { type: "text_delta", contentIndex: 0, delta: "你" } })
expect(state.streamingMessage?.content).toEqual([{ type: "text", text: "你" }])
```

如果逻辑写在 `onmessage` 里，测试就需要构造或 mock `EventSource`、模拟网络消息到达、等待异步回调。成本和脆弱度都高一个量级。

**为什么状态变更要收敛到一个入口**

```ts
// chat.ts:209-212
// reducer 返回新对象 必须整体覆盖 reactive 目标 直接改属性会丢不可变语义
function applyStream(action: Parameters<typeof streamReducer>[1]) {
  Object.assign(stream, streamReducer(stream, action))
}
```

`applyStream` 在全文件只有 **7 个调用点**（`:324`、`:332`、`:342`、`:350`、`:377`、`:625`、`:634`）。要查「哪些地方会改流式状态」，grep 一个函数名就够了。

**reducer 与 Pinia 的分工**

| | `streamReducer`（纯函数） | Pinia store |
| --- | --- | --- |
| 位置 | `shared/lib/` | `app/stores/` |
| 依赖 | 无框架依赖 | Vue 响应式、其他 store |
| 职责 | **怎么算**（给定事件算出新状态） | **什么时候算、算完放哪、算完还要做什么** |
| 可测试性 | 直接调用 | 需要建 Pinia 实例、mock fetch |

**store 决定「要不要处理这个事件」，reducer 决定「处理成什么样」**。最好的例子是 `chat.ts:335-352`：

```ts
case "message_start": {
  // 迟到事件守卫 run 已结束的流式事件会复活幽灵气泡
  if (!isRunning.value) break                      // ← store 的决策
  if (msg?.role === "assistant") {
    applyStream({ type: "snapshot", message: msg }) // ← 交给 reducer
  }
  break
}
```

`if (!isRunning.value) break` 是必要的守卫：SSE 事件可能迟到（断线重连后补发的缓冲事件），如果 run 已经结束，处理它会让已经消失的流式气泡「复活」——注释里叫它「幽灵气泡」。

**这个设计的通用性**：任何「增量事件流 → 结构化文档」的场景都是同一个模式——协同编辑、日志流聚合、实时协作文档。核心是**用不可变更新保证可推演性**。

**代价**

| 代价 | 说明 |
| --- | --- |
| 每次 delta 都创建新对象 | 数组浅拷贝 + 对象展开，长回复时有 GC 压力 |
| 没有去重和排序 | 假定事件按序到达且不重复 |
| `Object.assign` 是浅合并 | 如果 reducer 某次返回缺字段的对象，旧值会残留（当前 `StreamingState` 恒定两字段，不会触发） |

**口述版**

> 因为一条助手消息不是一个字符串，而是一份有序的块文档。
>
> Agent 的一轮回复结构是「先思考，然后调工具，拿到结果再输出文本」，这些内容块交替出现，顺序就是真实发生的顺序。如果按最简单的方式拼字符串，就没法把工具调用渲染成可折叠的卡片，也没法在卡片里展示参数和执行结果。
>
> 所以我把消息表示成 `content: Block[]`，每个块有自己的类型。流式事件里带一个 `contentIndex`，明确告诉我这个增量属于第几块。用索引而不是「找最后一个块」是有具体原因的：一轮里可能有多个同类型块，比如文本、工具、又一段文本。如果用「找最后一个 text 块」，第二段文本的第一个增量到达时，那个块还没建出来，就会被错误地追加到第一段后面。
>
> 组装逻辑写成纯函数 reducer，放在 `shared/lib` 里，不依赖 Vue 也不依赖 SDK。这样有两个好处：一是可以直接写单元测试，输入 state 和事件、断言输出，不需要 mock 网络和 DOM；二是所有流式状态变更收敛到一个入口，全文件只有 7 个调用点，grep 一下就能穷举。
>
> reducer 和 Pinia 不是二选一。reducer 负责「给定事件算出新状态」，Pinia 负责「什么时候处理这个事件、处理完还要做什么」。比如 `message_start` 事件来了，store 先判断当前是不是还在运行中——如果 run 已经结束，这个事件是迟到的，处理它会让已经消失的流式气泡复活，所以直接跳过；确认要处理了才交给 reducer。
>
> 代价也要说清楚：每次 delta 都创建新对象，长回复时有 GC 压力；而且 reducer 不做去重和排序，它假定事件按序到达且不重复。

**追问链**

```text
Q: reducer 为什么放在 shared 而不是 app？
A: 因为它是纯函数，没有 Vue 依赖。放 shared 让它天然可测、可复用，
   也避免了 app/ 目录下测试要 mock Vue 环境。
   shared 层还有一个约束：不能 import pi 包，因为 SDK 进不了浏览器 bundle。

Q: 每次 delta 都创建新对象，性能有问题吗？
A: 有 GC 压力，但当前没有实测数据。如果要做优化，
   可以考虑结构共享或者按帧合并。不过要权衡：
   不可变更新的可推演性是当前测试和排查的基础。

Q: 如果 state 里有十几个字段，Object.assign 会不会有问题？
A: 当前 StreamingState 只有两个字段，且 reducer 每个分支都返回完整对象，
   所以浅合并不会残留旧值。如果字段变多，应该改成整体替换。
```

## Q13 reducer 怎么按内容索引组装消息？

**核心结论**：核心是 `updateContentBlock` 一个函数，它把「定位块 → 计算新块 → 返回新状态」抽象出来，让 9 个事件分支只需要关心「怎么算这一块」。

```ts
// streaming-message.ts:32-48
function updateContentBlock(state, contentIndex, update) {
  const message = state.streamingMessage
  if (!message || !Number.isInteger(contentIndex) || contentIndex < 0) return state

  const content = [...message.content]           // ① 浅拷贝数组
  const nextBlock = update(content[contentIndex]) // ② 让调用方决定新块
  if (!nextBlock) return state                    // ③ null 表示放弃本次更新
  content[contentIndex] = nextBlock               // ④ 改拷贝，不改原数组
  return { isStreaming: true, streamingMessage: { ...message, content } }
}
```

**逐行去掉会怎样**

| 步骤 | 去掉会怎样 |
| --- | --- |
| ① `[...message.content]` | 直接改 `message.content[i]` 会改动上一次 state 里的数组，纯函数语义被破坏 |
| ② 传 `content[contentIndex]` | 调用方要自己索引，边界判断散落各处 |
| ③ `if (!nextBlock) return state` | 各分支要自己写「条件不满足就返回原 state」 |
| ⑤ `{...message, content}` | Vue 的 `Object.assign` 写回会失去不可变语义 |

边界保护（`:38`）挡住三种输入：`!message`（还没收到快照就来 delta）、`!Number.isInteger`（SDK 传了 `undefined`）、`contentIndex < 0`。**注意没有检查上界**——但各分支的 `update` 回调在越界时会看到 `undefined` 并返回 `null`，所以不会真的写入空洞。这是隐式保护，不是显式校验。

**九个分支按行为分三类**

| 事件 | 行为 | 失败时 |
| --- | --- | --- |
| `text_start` / `thinking_start` / `toolcall_start` | **幂等**：已有块就保留，没有就新建 | 无 `toolName` 时不建 toolCall 块 |
| `text_delta` / `thinking_delta` / `toolcall_delta` | **增量有损**：要求当前块类型匹配 | 不匹配返回 `null`，丢弃 |
| `text_end` / `thinking_end` / `toolcall_end` | **权威自愈**：不关心当前块，直接覆盖 | — |

**最重要的规律**：**`_delta` 是增量的、有损的；`_end` 是权威的、自愈的。**

`text_end`（`:65-70`）**不关心 current 是什么**，直接用事件里的完整内容覆盖。即使中间所有 delta 都丢了，只要它到了，这个块就会被写成正确的内容。而 `text_delta`（`:59-64`）要求 `current?.type === "text"`，否则返回 `null` 丢弃。

**推论（重要边界）**：如果 `text_start` 丢了，后续所有 `text_delta` 都会被丢弃，直到 `text_end` 到达才恢复。表现是**「一段时间没内容，然后整段突然出现」**。

**完整推演一：没有快照，所有事件都被丢弃**

```text
事件 1: text_start  { contentIndex: 0 }
  state.streamingMessage === null → 守卫拦截，return state

事件 2: text_delta  { contentIndex: 0, delta: "你好" }
  message === null → 同样被丢弃

事件 3: text_end    { contentIndex: 0, content: "你好" }
  message === null → 还是被丢弃
```

**结论**：如果没有先收到 `message_start` 快照，所有 delta 都会被丢弃。这是**正确的行为**——`message_start` 才是「这一轮开始了」的信号，它负责把 `streamingMessage` 从 null 变成真实对象。这个推演说明了为什么服务端的快照重放是必要的，不是可选的优化。

**完整推演二：正确顺序**

```text
① message_start → snapshot
   state = { isStreaming: true, streamingMessage: { role: "assistant", content: [] } }

② text_start { contentIndex: 0 }
   content = [] → update(undefined) → { type: "text", text: "" }
   content[0] = { type: "text", text: "" }

③ text_delta { contentIndex: 0, delta: "你好" }
   update(content[0]) → current.type === "text" → { ...current, text: "" + "你好" }
   content[0].text === "你好"

④ text_end { contentIndex: 0, content: "你好，有什么可以帮你？" }
   update(content[0]) → { ...current, type: "text", text: "你好，有什么可以帮你？" }
   ↑ 自愈：即使前面 delta 全丢，这里也会写对
```

**完整推演三：工具调用**

```text
① toolcall_start { contentIndex: 1, id: "call_abc", toolName: "read" }
   → content[1] = { type: "toolCall", toolCallId: "call_abc", toolName: "read", input: {}, rawInput: "" }

② toolcall_delta { contentIndex: 1, delta: '{"path":"' }
   → content[1].rawInput = '{"path":"'   → 卡片显示「参数流入中」

③ toolcall_delta { contentIndex: 1, delta: 'README.md"}' }
   → content[1].rawInput = '{"path":"README.md"}'

④ toolcall_end { contentIndex: 1, toolCall: { id: "call_abc", ... } }
   → content[1] = { type: "toolCall", toolCallId: "call_abc", toolName: "read",
                    input: { path: "README.md" } }
   → rawInput 消失，参数变成格式化 JSON
```

**`toolcall_start` 的两个防御**（`:87-105`）

① `event.id ?? current.toolCallId`——如果事件没带 id，保留已有的。因为 `toolcall_start` 可能被重发（比如快照恢复后）。

② `if (typeof event.toolName !== "string") return null`——**没有工具名就不建块**。因为块建出来也没法渲染，`toolPreview` 需要名字才能生成预览（`app/utils/tool-preview.ts:10-28` 按 `toolName` 分支）。

**一个值得主动讲的取舍**

`text_delta` 收到时如果发现块类型不匹配，**可以选择**直接建一个块然后追加。但当前实现选择丢弃。**为什么丢弃是对的**：因为「不是 text 块」意味着状态异常（收到了乱序事件，或者这一块其实是 toolCall）。这时候强行建块会**破坏块顺序**，让工具卡片和文本错位。

> 流式场景下，「少显示一点」比「显示错位」更容易接受，因为权威事件会兜底。

**口述版**

> 核心是一个叫 `updateContentBlock` 的函数，它把「定位块 → 计算新块 → 返回新状态」抽象出来，9 个事件分支只需要关心「怎么算这一块」。
>
> 它做四件事：浅拷贝 content 数组，把当前块交给调用方算新块，如果返回 null 就放弃更新，否则写回拷贝并返回新消息对象。用不可变更新是因为 reducer 是纯函数，直接改原数组会破坏可推演性。
>
> 九个分支分三类。`_start` 是幂等的，块已存在就保留，不存在就建空的。`_delta` 是有损的——它要求当前块类型匹配，不匹配就返回 null 丢弃。`_end` 是权威的，它不关心当前块是什么，直接用事件里的完整内容覆盖。
>
> 这个分类带来一个重要特性：**delta 丢了不会导致最终结果错误**。比如 `text_start` 丢了，后续所有 delta 都会被丢弃，表现是一段时间没内容然后整段突然出现；但只要 `text_end` 到了，这个块就会被写成正确的内容。
>
> 有一个推演能说明快照的必要性：如果没收到 `message_start` 快照，`streamingMessage` 是 null，那么守卫会直接返回原状态——所有 delta 包括 `text_end` 都会被丢弃。所以服务端在握手后补发快照不是可选的优化，而是必要的。
>
> 还有一个取舍值得说：`text_delta` 发现当前块类型不匹配时，我选择丢弃而不是强行建块。因为强行建块会破坏块顺序，让工具卡片和文本错位。流式场景下少显示一点比显示错位更容易接受——因为最终有权威事件兜底。

**追问链**

```text
Q: 如果事件乱序呢？比如 contentIndex 2 先于 1 到达？
A: 会错位。reducer 直接按下标写入，不校验是否连续。
   当前不处理乱序，依赖三层保证：SDK 串行 emit、
   SSE 单流保序、缓冲按序补发。

Q: 如果事件重复呢？
A: 会重复。reducer 没有事件 ID 概念，
   重复的 text_delta 会导致文本重复。这是已知局限。

Q: 为什么 toolcall_start 没名字就不建块？
A: 因为块建出来也没法渲染。toolPreview 按 toolName 分支生成预览，
   没有名字只能显示 "tool" 兜底。宁可等下一个事件带名字。
```

## Q14 工具调用和工具结果怎么关联？toolCallId 缺失会怎样？

**核心结论**：**唯一关联标识是 `toolCallId`**。工具调用在助手消息的 `content` 数组里，结果是一条独立的 `toolResult` 消息，靠 ID 配对。

```text
助手消息 content[]                      messages[]
┌────────────────────────┐            ┌──────────────────────────┐
│ { type: "toolCall",    │            │ { role: "toolResult",    │
│   toolCallId: "abc",   │◄──配对────►│   toolCallId: "abc",     │
│   toolName: "read" }   │            │   content: [...],        │
└────────────────────────┘            │   isError: false }       │
                                      └──────────────────────────┘
        ↓                                        ↓
   ToolCallCard :block                    toolResultsByCallId.get("abc")
```

**配对是派生的，不是独立状态**

```ts
// chat.ts:201-207
const toolResultsByCallId = computed(() => {
  const map = new Map<string, ToolResultMessage>()
  for (const m of messages.value) {
    if (m.role === "toolResult") map.set(m.toolCallId, m)
  }
  return map
})
```

**为什么做成 computed 而不是独立 state**：保证单一事实来源。如果做成独立 state，每次 `messages` 变化都要手动同步，容易出现两份数据不一致。computed 是派生值，自动跟随 reload。

**四种异常输入的处理**

**① `toolCallId` 缺失**：`normalize.ts:33` 做双字段兼容（`toolCallId` / `id`），两个都没有时给**空串**。**后果**：多个缺 ID 的工具会互相串——它们都用 `""` 作为 key。

**② `toolCallId` 重复**：`map.set` 是后写覆盖先写。**后果**：同一 ID 有多个结果时，只保留最后一个。

**③ 结果找不到调用（孤儿结果）**：结果仍作为一条消息存在于 `messages` 里，但 `MessageItem.vue:31-32` 对它的渲染是一个 `aria-hidden` 的空 div。**孤儿结果不会被显示**——用户看不到「有个结果没配上」，问题被静默。

**④ 调用找不到结果**：`ToolCallCard` 的 `result` 是 undefined，判定逻辑（`ToolCallCard.vue:54-56`）：

```ts
const isRunningTool = computed(
  () => !props.result && (props.streaming || chat.activeTools.has(props.block.toolCallId)),
)
```

| 情况 | `activeTools` 有 | `streaming` | 显示 |
| --- | --- | --- | --- |
| 工具正在执行 | ✅ | false | 「执行中」 |
| **工具执行完了但结果没到** | ❌ | false | **「完成」**（错误！） |
| 消息还在流式 | 任意 | true | 「执行中」 |

**第二行是一个真实的窗口**：`tool_execution_end` 到达时 `activeTools.delete(id)` 立即执行，但结果消息要等后续的 `message_end` 才进 `messages`。在这个窗口里卡片会短暂显示「完成」且结果区为空。

> 这是**代码路径推导**，未做真机验证。窗口长度取决于 `tool_execution_end` 和 `message_end` 之间的间隔。

**为什么必须独立维护 `activeTools`**

`ToolCallCard.vue:52-53` 的注释把因果说清楚了：

> assistant 消息在工具开始执行前就定稿了 streaming 已是 false
> 执行中状态必须查 activeTools 它覆盖 tool_execution_start 到 end 的真实区间

**关键时序**：`message_end`（assistant 定稿）→ `tool_execution_start` → `tool_execution_update` → `tool_execution_end` → `message_end`（toolResult）。

**助手消息在工具开始执行之前就定稿了**，所以定稿后消息上的 `streaming` 已经是 false，光看消息判断不出工具还在跑。`activeTools` 是个 `reactive(new Map())`，`tool_execution_start` 写入、`tool_execution_end` 删除、`tool_execution_update` 更新进度。

**参数显示的两阶段**

流式期间显示 `rawInput`（原始 JSON 片段，可能不合法不完整），定稿后显示格式化后的 `input`。`normalize.ts` 为此分了两个导出：

```ts
export function normalizeToolCalls(msg) { return normalizeAssistantToolCalls(msg) }                    // 不带 rawInput
export function normalizeStreamingToolCalls(msg) { return normalizeAssistantToolCalls(msg, { includeStreamingRawInput: true }) }
```

定稿路径（`message_end`）走前者，把临时的 `rawInput` 丢掉。类型定义里也标注了 `rawInput` **不持久化**（`types.ts:48`）。

**一个值得主动提的改进**

> 会话文件里如果存在「有 toolCall 但没有对应 toolResult」的助手消息，说明执行被中断了。前端可以把这类卡片标记为「未完成」，而不是「完成」。**这个不需要服务端改动**——`toolResultsByCallId` 查不到就是未完成。当前实现会把这种情况显示成「完成」，是一个真实的误导点。

**口述版**

> 工具卡片需要显示三种状态：参数流入中、执行中、完成或出错。这三个状态的数据来源不一样。
>
> 参数流入中读的是消息块里的 `rawInput`——流式期间参数还没解析完，只有原始 JSON 片段，所以先显示原文，等 `toolcall_end` 到了再换成格式化的 `input`。这里有个细节：`rawInput` 是临时态，定稿时会被 `normalizeToolCalls` 丢掉。
>
> 执行中这个状态比较特殊。因为助手消息在工具**开始执行之前**就已经定稿了——`message_end` 先到，`tool_execution_start` 后到。所以定稿之后消息上的 `streaming` 标记已经是 false，光看消息判断不出工具还在跑。我的做法是单独维护一个 `activeTools` 的响应式 Map。
>
> 结果的关联靠 `toolCallId`。工具调用在助手消息里，执行结果是一条独立的 `toolResult` 消息。我用一个 computed 从 `messages` 里扫出所有结果，建一个 `toolCallId → result` 的 Map。做成 computed 而不是独立 state 是为了保证只有一份事实来源——会话重载后 Map 自动重建。
>
> 异常输入方面有几个已知边界要诚实说。`toolCallId` 缺失时归一化会给空串，多个缺 ID 的工具会互相串。结果找不到对应调用时，它作为一条消息存在但渲染是一个 `aria-hidden` 的空 div，也就是不显示，用户看不到「有个结果没配上」。另外 `tool_execution_end` 到 `message_end` 之间有一个短窗口，卡片会短暂显示「完成」但结果区是空的。
>
> 还有一个我觉得值得改进的点：如果会话文件里有「有工具调用但没有对应结果」的消息，说明执行被中断了。当前实现会把这种情况显示成「完成」，这是一个真实的误导。前端其实能检测出来——查不到结果就是未完成，不需要服务端改动。

**追问链**

```text
Q: 如果两个工具同时执行呢？
A: activeTools 是 Map，可以同时存多条。
   run-strip 用 v-for 遍历全部展示。块顺序仍由 contentIndex 保证。

Q: 工具执行失败怎么显示？
A: result.isError 为真时卡片加 is-error 类，状态文字「出错」。
   注意这里判定的是工具结果里的 isError，不是网络错误。

Q: rawInput 一直不消失怎么办？
A: 说明 toolcall_end 没到，可能流中断了。
   reload 后从会话文件读到的消息走 normalizeToolCalls（不带 rawInput），
   会恢复成只有 input。
```

## Q15 流式内容、工具运行状态为什么要分层展示？

**核心结论**：因为**它们的生命周期和权威性都不同**。流式内容是临时的、可能丢的、没有 entryId；已定稿消息是持久的、权威的、有 entryId 的。

| 维度 | 流式内容 | 已定稿消息 |
| --- | --- | --- |
| **存储位置** | `stream.streamingMessage`（单个对象） | `messages[]`（数组） |
| **权威性** | 增量拼出来的，可能有损 | 来自会话文件，权威 |
| **entryId** | 没有 | 有（`entryIds[]` 平行数组） |
| **可编辑** | ❌ | ✅ |
| **key 策略** | 无 key（始终是最后一个节点） | `entryIds[i]` |
| **清理时机** | `message_end` 时清空 | reload 时整体替换 |

**为什么必须分开渲染**

**① 生命周期不同**——`messages` 是已定稿的持久数据，`streamingMessage` 是临时的。混在一个数组里要到处判断「这条是不是流式的」。

**② `key` 策略不同**——已定稿用 `entryIds[i]`（服务端权威 ID）；流式气泡**没有 `key`**，因为它始终是最后一个节点。`ChatPanel.vue:146` 有个回退：`:key="chat.entryIds[i] || \`local-${i}\`"`——乐观追加的用户消息 entryId 是空串（`chat.ts:623` 占位），所以回退到下标。reload 后 entryId 填上真实值，key 变化导致重建，**这是有意的**。

**③ 交接时机可控**——`chat.ts:376-377` 的注释：「先追加进 messages 再清流式气泡，顺序反了会闪一帧重复」。先清气泡再 push 中间会有一帧「消息不见了」；push 之后不清气泡会有一帧「消息出现两次」。

**属性差异也是分层的证据**

| 属性 | 列表项 | 流式气泡 |
| --- | --- | --- |
| `entry-id` | ✅ | ❌ |
| `editable` | ✅（多个条件） | ❌ |
| `streaming` | ❌ | ✅ |

**为什么流式气泡不能编辑**：它没有 entryId，无法定位到会话树里的节点，编辑后无法确定分支位置。

**第三层：运行状态条**

除了流式内容和工具卡片，还有一个独立的运行状态条，展示 `activeTools` 和 `retryInfo`。**为什么需要它**：工具卡片显示的是**已完成消息里的工具调用**，而运行状态条显示的是**此刻正在跑什么**。`chat.ts:441` 的注释说明了分工：

> 工具执行实时状态 卡片等 message_end 定稿后由历史渲染 状态条只负责此刻正在跑什么

还有「正在思考」占位，有**五个否定条件**——只在「等待模型首字」的真空期显示。任何一个其他状态出现，就用更具体的展示。

**思考块的分阶段展示**

流式期间显示「思考中… N 字」（实时计数），定稿后显示「思考了 N 秒」。**时长不是维护计时器算的**，而是用相邻两条消息的时间戳差（`MessageItem.vue:127-134`）。理由：reload 之后计时器就没了，但时间戳是从会话文件读出来的，永远能重算。

**分层的代价**

| 复杂度 | 说明 |
| --- | --- |
| 渲染两处 | 列表 + 独立的流式气泡 |
| 交接顺序 | `message_end` 里先 push 再清，顺序不能反 |
| 状态判断 | 「执行中」要同时看 `streaming` 和 `activeTools` |
| 展示优先级 | 运行状态条、「正在思考」占位、工具卡片三者显示条件要互斥 |

**为什么不合并**：合并的代价是每个状态判断都要区分「这条消息是不是流式的」，判断散落各处反而更复杂。当前的做法是**按生命周期分层，每层职责单一**。

**口述版**

> 因为流式内容和已定稿消息的**生命周期和权威性都不同**，混在一起会有三个问题。
>
> 一是 reload 时不知道该不该覆盖。已定稿消息来自会话文件，是权威的，reload 应该整体替换；流式消息是增量拼出来的，可能不完整，reload 不该碰它。
>
> 二是编辑功能无法判断。编辑历史消息需要 entryId 来定位会话树里的节点，而流式消息没有 entryId。所以我在模板里给列表项传 `entry-id` 和 `editable`，流式气泡不传。
>
> 三是 key 策略不同。列表用 entryId 做 key 保证复用正确，流式气泡没有 key 因为它始终是最后一个节点。
>
> 除了这两层，实际上还有第三层：运行状态条。它显示的是「此刻正在跑什么」，而工具卡片显示的是「已完成消息里的工具调用」。这两个是不同时间维度的信息。注释里写得很清楚——工具执行实时状态由状态条负责，卡片等 message_end 定稿后由历史渲染。
>
> 分层带来一个细节要注意：`message_end` 里必须先 push 到 messages 再清流式气泡，顺序反了会闪一帧重复或者一帧空白。
>
> 另外思考块的展示也是分阶段的：流式期间显示「思考中… N 字」的实时计数，定稿后显示「思考了 N 秒」。时长不是维护计时器算的，而是用相邻两条消息的时间戳差——因为 reload 之后计时器就没了，但时间戳是从会话文件读出来的，永远能重算。

**追问链**

```text
Q: 为什么流式气泡没有 key？
A: 因为它始终是列表的最后一个节点，不需要复用判断。

Q: 列表项的 key 为什么用 entryId 而不是下标？
A: entryId 是服务端权威 ID，能保证 Vue 正确复用 DOM。
   乐观消息还没 entryId，所以回退到下标，
   reload 后 entryId 填上，key 变化导致重建——这是有意的。

Q: 「正在思考」占位为什么要五个否定条件？
A: 它只在「等待模型首字」的真空期显示。有流式内容、有工具在跑、
   在压缩、在重试，任何一种情况都有更具体的展示方式。
```

## Q16 页面刷新后到底恢复了什么？没恢复什么？

**核心结论**：三种数据来源补三样东西，**但补的都是界面，不是任务**。任务一直在服务端进程里跑，浏览器只是重新订阅。如果服务端进程重启，任务就真的没了。

![自动重连边界](../../learning/assets/05-reconnect-boundary.svg)

| 数据来源 | 补什么 | 权威性 |
| --- | --- | --- |
| **会话历史查询**（HTTP） | 已落盘的消息、entryId、分支树、累计统计 | ✅ 权威，但**有延迟** |
| **助手消息快照**（SSE 握手包） | 未定稿的流式消息 | ✅ 权威，但是**瞬时的** |
| **SSE 增量事件** | 订阅之后发生的变化 | ⚠️ 有损，断线期间永久丢失 |

**完整的恢复流程**

```text
① 用户按 F5，SPA 重新加载，内存状态清空
② Router 挂载 /session/[id]
③ chat.ts:542 openSession(id)
   ├─ close()                        清空状态，generation +1
   ├─ draftStore.get(id) → draft     从 localStorage 恢复草稿
   └─ sessionLoading = true
④ chat.ts:216 reload()
   ├─ sequence = ++reloadSequence
   ├─ GET /api/sessions/:id
   │    ↓ openSessionForRead：有存活 wrapper 用内存态，否则读磁盘
   │    ↓ buildSessionContext：沿 parentId 从 leaf 上溯到根
   ├─ 三重校验
   └─ messages / entryIds / tree / stats 全部赋值
⑤ chat.ts:567 connection.maintain(id)   建立 SSE
⑥ event-stream.ts:122 const snapshot = session.streamingMessage
⑦ encode({ type: "connected", isStreaming })
⑧ chat.ts:314 case "connected"
   ├─ isStreaming === true → isRunning = true, refreshRuntimeState()
   └─ isStreaming === false && sdkAgentActive → 合成 agent_settled
⑨ event-stream.ts:129 if (snapshot) encode({ type: "message_start", message: snapshot })
⑩ chat.ts:335 → applyStream({ type: "snapshot", message })
⑪ 流式气泡显示完整内容，后续 delta 继续追加
```

**三种数据各自补了什么、补不上什么**

| 阶段 | 补上了什么 | 补不上什么 |
| --- | --- | --- |
| ④ HTTP 历史 | 已落盘消息、entryIds、分支树、累计统计 | 未定稿的流式消息、运行状态 |
| ⑦ `connected` | `isStreaming`（任务是否还在跑） | 流式内容本身 |
| ⑨ `message_start` | 未定稿消息的完整内容 | 快照之后到连接建立之间的事件 |
| 后续 SSE 增量 | 订阅之后的变化 | 断线期间丢失的事件 |

**为什么 `entryIds` 只能从 HTTP 来**：SSE 增量事件里只有消息内容，没有 entry ID。而分支操作（编辑历史消息、切换分支）需要 entry ID。所以每次 `agent_settled` 之后都要 reload 一次。

**`connected` 的补偿逻辑**（`chat.ts:314-327`）：如果断线期间任务结束了，`agent_settled` 是在没有连接的时候发出的，永久丢失。前端重新连上时，如果握手包说服务端没在跑但本地 `sdkAgentActive` 还是 true，就主动合成一次落定。

**为什么条件是 `sdkAgentActive`**：全新页面时它是 false，本来就没有残留状态需要清理。

**「界面恢复」与「任务恢复」的区别**

| | 界面（消息列表） | 任务（Agent 执行） |
| --- | --- | --- |
| 存储位置 | 会话文件（JSONL，持久化） | 服务端进程内存 |
| 能否重建 | ✅ 读文件就能重建 | ❌ 内存丢了就没了 |
| 刷新页面后 | 完全恢复 | **仍在跑**（因为进程没重启） |
| 服务端重启后 | 完全恢复 | **永久丢失** |

`/api/agent/running` 这个接口说明了边界（`running.get.ts:4-6`）：它遍历存活的 wrapper 返回 `isRunning()` 的会话。**它查的是服务端进程内存**，进程重启后返回空数组，而界面无从得知「原来有个任务被中断了」。

**局限**

| 局限 | 根因 |
| --- | --- |
| 断线期间事件永久丢失 | 无事件序号、无游标、无服务端缓冲 |
| 无法判断任务是否被中断 | 无任务状态持久化 |
| `reload` 是全量拉取 | 无分页/增量协议 |
| 快照去重依赖引用相等 | 未在真实链路验证 |
| `refreshRuntimeState` 静默失败 | `catch {}` 无提示 |

**口述版**

> 先区分两个概念：**界面恢复**和**任务恢复**，这两个完全不是一回事。
>
> 刷新页面时，我用了三种数据拼出界面。第一种是 HTTP 查会话历史，从会话文件里读出已落盘的消息、entryId、分支树和累计统计。第二种是 SSE 握手包里带的消息快照——如果刷新时 Agent 正在流式输出，新连接建立后服务端会补发一条 `message_start`，携带当前正在生成的那条消息的完整内容。这个快照不是优化，是必要的：因为 reducer 的守卫要求 `streamingMessage` 先存在，没有快照的话所有增量事件都会被丢弃，用户会看到一个空的流式气泡。第三种是握手之后的增量事件。
>
> 但这三种补的都是**界面**。任务本身一直跑在服务端进程里，浏览器只是重新订阅了一下。如果服务端进程重启了，那个任务就真的没了——前端没有任何办法恢复它，因为它连「曾经有个任务被中断了」都不知道，这个信息根本没有持久化。所以我的接口只能告诉前端「现在有没有会话在跑」，不能告诉前端「有个任务挂了」。
>
> 有一个细节值得一提：如果断线期间任务正好结束了，那个 `agent_settled` 事件是在没有连接的时候发的，永久丢了。所以我在处理 `connected` 事件时加了一个补偿——如果握手包说服务端没在跑，但本地还认为 SDK 是活跃的，就主动合成一次落定，把残留的「正在运行」状态清掉。条件里要判断 `sdkAgentActive`，因为全新页面本来就没有残留状态需要清理。
>
> 局限我也很清楚：断线期间的事件是永久丢失的，因为服务端没有事件缓冲也没有序号；而且如果服务端进程重启，界面只知道任务不在跑，不知道它曾经被中断过。

**追问链**

```text
Q: 断线期间的工具执行细节能恢复吗？
A: 不能。那些 tool_execution_* 事件永久丢了。
   但工具的执行结果在会话文件里，reload 之后能看到最终结果。

Q: 快照和增量会不会重复？
A: 有一个去重函数，用的是引用相等。我在单测里用手工构造的
   同一对象验证过，但真实链路上 SDK 是否复用同一对象引用，
   我没有验证。这是明确的待确认项。

Q: openSession 的顺序为什么是 close → 设 id → 恢复草稿 → await reload → 建连？
A: 三个顺序都有理由。先 close 是因为不关旧连接的话，
   旧事件还会流进新会话的视图。先恢复草稿再 await reload，
   是因为如果反过来，用户在加载期间打的字会被晚到结果覆盖。
   最后才建连，是先有数据再有连接。
```

## Q17 会话 ID 不够用吗？为什么要额外加操作代次和查询序号？

**核心结论**：**三层判据各防一类不同的竞态，不是冗余**。

**第一层：会话 ID**——防「响应回来时已经切到别的会话了」。最直观，但只靠它不够。

**第二层：操作代次 `sessionGeneration`**——防「A→B→A 之后旧响应回来」。

```text
t0  用户打开会话 A          sessionId = A, generation = 0
t1  发起 reload(A)          sequence = 1
t2  用户切到 B              close() → generation = 1
t4  用户切回 A              close() → generation = 2
t5  openSession(A)          sessionId = A
t6  t1 的响应回来了          sessionId.value === A ✅ 通过第一层
```

**只有 `sessionId` 判据会误判**：响应看起来是给 A 的，实际上它是 t1 时刻发的，反映的是 t2 之前的状态。加上 `generation` 后：t1 记下的 `generation = 0`，t6 时是 2，**不相等 → 正确拒绝**。生成位置在 `close()`（`chat.ts:498`）。

**第三层：查询序号 `reloadSequence`**——防「同一会话内两次 reload 乱序返回」。

```text
t0  agent_end 事件到达  → reload()  sequence = 1
t1  agent_settled 到达  → reload()  sequence = 2
t2  t1 的响应先回来      sequence 匹配 → 写入新数据 ✅
t3  t0 的响应后回来      sequence 不匹配（1 ≠ 2）→ 拒绝 ✅
```

**这两次的会话 ID 和代次都相同**，前两层都通过。如果不用序号，t0 的旧数据会覆盖 t1 的新数据，界面「倒退」。`reloadSequence` 在两处递增：每次 reload 开头（`chat.ts:219`），以及 `invalidateReload()`（`chat.ts:119`，导航前主动作废在途 reload）。

**四层判据的完整决策表**

| 场景 | sessionId | generation | sequence | 结果 |
| --- | --- | --- | --- | --- |
| 正常返回 | ✅ | ✅ | ✅ | 接受 |
| 切到别的会话后返回 | ❌ | — | — | 拒绝 |
| A→B→A 后第一次 A 的响应返回 | ✅ | ❌ | — | 拒绝 |
| 同会话内两次 reload，旧的后返回 | ✅ | ✅ | ❌ | 拒绝 |
| 导航期间返回 | 由 `invalidateReload()` 使 sequence 失配 | | | 拒绝 |

最严格的一处校验把三层都用上了，就在 `reload` 里（`chat.ts:224`）：

```ts
if (sessionId.value !== id || generation !== sessionGeneration || sequence !== reloadSequence)
  return null
```

**校验点的分布**

`chat.ts` 内共 **13 处**：`166`、`224`（三层）、`297`、`299`、`640`、`642`、`658`、`664`、`687`、`695`、`699`、`705`、`712`。

其他 composable：`useSessionNavigation.ts` **8 处**（`:50`、`:54`、`:57`、`:62`、`:67`、`:73`、`:76`、`:81`）；`usePromptQueue.ts` **4 处**（`:73`、`:83`、`:92`、`:115`）；`useSessionRuntime.ts` **8 处**（`:43`、`:65`、`:79`、`:85`、`:98`、`:103`、`:119`、`:132`）。

**校验点为什么这么多**：**每个 `await` 之后都要重新确认**。因为 `await` 期间用户可能切会话了。

**为什么不用 AbortController 取消请求**

| 方式 | 问题 |
| --- | --- |
| 取消请求 | 需要每个请求都传 signal；而且**取消请求不等于阻止回调执行**（回调仍可能收到已缓冲的数据） |
| **校验后忽略**（当前） | 简单、可靠、不需要改请求层 |
| 每会话独立 store | 内存开销大，且跨会话共享的数据不好处理 |

> **面试可以这样讲**：「取消请求和阻止过期结果生效是两件事。取消请求能省一点带宽，但不能保证回调不执行——已经缓冲的数据仍可能触发回调。所以我选择在写入点校验，这是更可靠的防线。」

**一处真实的缺口**（代码推导，非实测）：`chat.ts:552` 有 `sessionId.value === id` 守卫，但 `:562` 的 `syncFromSessionCwd(info.cwd)` **没有**。极快切会话时，旧会话的 `cwd` 可能覆盖新工作区选择器。影响范围限于选择器显示，不影响消息数据。

**口述版**

> 这三层是逐步加出来的，每一层防的是一类不同的竞态。
>
> 第一层是会话 ID，防「响应回来时已经切到别的会话了」。这个最直观，但只靠它不够。
>
> 第二层是操作代次。场景是用户从 A 切到 B 再切回 A，这时候会话 ID 又是 A 了，第一层判据会通过。但那个响应是第一次打开 A 时发的，中间 A 已经被关闭过一次，可能已经有新消息了。所以我在每次 `close()` 时递增一个 `sessionGeneration`，请求发出前记下当时的代次，响应回来时比对，不等就丢弃。
>
> 第三层是查询序号。同一个会话里连续触发两次 reload 很常见——`agent_end` 和 `agent_settled` 挨得很近，两个都会触发 reload。这两次的会话 ID 和代次都相同，但第一次的响应可能因为网络抖动晚于第二次返回，携带的是更旧的数据。所以每次 reload 开头递增一个 `reloadSequence`，响应回来时比对序号，不是最新的就丢弃。
>
> 代码里最严格的一处校验把三层都用上了，就在 `reload` 里。整个 store 里有 13 处校验点，原则是每个 `await` 之后都要重新确认，因为 await 期间用户可能切会话了。
>
> 还有一个设计选择值得说：我没有用 `AbortController` 去取消请求，而是选择在写入点校验。因为取消请求和阻止过期结果生效是两件事——取消请求能省带宽，但不能保证回调不执行，已经缓冲的数据仍可能触发回调。在写入点校验是更可靠的防线。
>
> 我也知道一个缺口：`openSession` 里同步工作区 cwd 那一行没有加 sessionId 守卫，而同一个 try 块里上面那行有。极快切会话时理论上存在旧会话 cwd 覆盖新工作区选择器的窗口。影响范围限于选择器显示，不影响消息数据。

**追问链**

```text
Q: close() 里为什么同时递增两个计数器？
A: sessionGeneration 让所有在途异步回调失效，
   reloadSequence 让在途的 reload 结果作废。
   粒度不同：代次是会话级的，序号是请求级的。

Q: 如果旧结果真的污染了状态，怎么排查？
A: 先看有没有漏掉校验的写入点。
   可以搜所有对 messages/stats/model 的赋值，
   检查每个赋值点上游有没有校验。

Q: 为什么 closeIfCurrent 需要存在？
A: Vue Router 切换路由时，新组件的 setup 可能先于旧组件的 unmount。
   如果旧组件在 unmount 时无条件 close()，
   会把新组件刚 openSession 打开的会话清掉。
```

## Q18 队列状态为什么需要版本号？同一个函数里 contextUsage 为什么不用？

**核心结论**：因为**写入源的数量不同**。队列状态有两个写入源（SSE 推送 + HTTP 拉取），拉取结果可能过期；`contextUsage` 只有一个写入源，不存在互相覆盖的问题。

**问题：拉取与推送的时序**

```text
t0  前端发 get_state 请求                      version = 5
t1  SSE 推来 queue_update（队列变成 3 条）      version = 6
t2  t0 的响应回来，携带「队列 2 条」（过期数据）
    如果直接覆盖 → 队列从 3 条变回 2 条  ❌ 数据倒退
```

**推送是实时的、增量的；拉取是延迟的、全量的**。两者同时存在时，必须给拉取结果加一个「是否已过期」的判据。

```ts
// usePromptQueue.ts:31-43
let version = 0

const applyUpdate = (messages: QueueMessages) => {
  version += 1                          // ← 每次写入都递增
  queuedMessages.value = { steering: [...messages.steering], followUp: [...messages.followUp] }
}

const applySnapshot = (messages: QueueMessages, requestedAtVersion: number) => {
  if (requestedAtVersion === version) applyUpdate(messages)   // ← 版本一致才写
}
```

调用方在 `useSessionRuntime.ts:30` 和 `:51`：发请求前记下 `version`，返回时版本一致才写入。

**为什么两个字段策略不同**

| | `contextUsage` | `queuedMessages` |
| --- | --- | --- |
| **写入源数量** | **1 个**（只有 HTTP 快照） | **2 个**（SSE `queue_update` + HTTP 快照） |
| **数据性质** | 服务端每次现算的派生值 | 服务端维护的队列状态 |
| **冲突可能** | 无 | **有** |
| **处理** | 无条件覆盖 | 版本守卫 |

`contextUsage` 可以无条件覆盖，因为 SSE 事件流里**不带** context 数据，不存在第二个写入源；而它的值本身就是服务端每次现算的，最新的就是最准的。

**版本守卫的复用：撤回队列**

`clear_queue` 请求飞行期间，SDK 可能又推来 `queue_update`（比如用户又发了一条排队消息）。这时候撤回响应返回的空队列就是过期的，直接覆盖会把新的排队消息擦掉。所以 `recallQueue` 复用同一个守卫（`usePromptQueue.ts:111`、`:119`）。

**这个模式的通用性**：「拉取 + 推送」双源状态的经典解法就是**版本号 + 条件写入**。数据库的乐观锁、前端缓存与服务端推送的合并，都是同一个思路。

**局限**：版本号是内存变量，刷新后归零（但刷新后队列本来就要重新拉）；`model`、`thinkingLevel`、`isCompacting` 是直接覆盖的，因为它们的写入源也比较少。

**口述版**

> 因为这两个字段的**写入源数量不同**。
>
> 队列状态有两个写入源：SSE 推来的 `queue_update` 事件，和 `get_state` 这个 HTTP 快照。推送是实时的，拉取是延迟的。如果快照在飞行期间，SSE 推来了新的队列状态，那快照返回时就是过期的，直接覆盖会把新状态冲掉，表现是队列里的消息数量倒退。
>
> 所以我在请求发出前记下版本号，返回时版本一致才写入。版本号在每次写入时递增，所以只要有推送更新落地，快照就整体作废。
>
> 同一个函数里 `contextUsage` 是直接覆盖的，因为它只有一个写入源，就是这条 HTTP 快照，SSE 事件流里不带上下文数据，不存在两个源互相覆盖的问题。而它的值本身就是服务端每次现算的，最新的就是最准的。
>
> 这个版本守卫不只用在快照上，撤回队列也复用了。因为 `clear_queue` 请求飞行期间 SDK 可能又推来 `queue_update`，这时候撤回响应返回的空队列就是过期的，直接覆盖会把新的排队消息擦掉。
>
> 这是「拉取 + 推送」双源状态的经典问题，解法就是版本号加条件写入，和数据库乐观锁是同一个思路。

**追问链**

```text
Q: 版本号为什么不用时间戳？
A: 时间戳会有精度和时钟问题（同一毫秒内的两次更新无法区分）。
   单调递增的计数器更可靠。

Q: 如果 SSE 断了，版本号还会递增吗？
A: 不会。断线期间没有 queue_update 事件，所以版本号不变，
   快照会被接受。这也是合理的——断线期间没有推送更新，
   快照就是最新的。
```

## Q19 上下文压缩是你实现的吗？手动和自动压缩有什么区别？

**核心结论**：**压缩算法是 SDK 的，我做的是接入和展示。**

| 能力 | 归属 |
| --- | --- |
| 手动压缩 `compact()` | **SDK**（`agent-session.js:1474`） |
| 自动阈值压缩 | **SDK**（`compaction.js:160-164` `shouldCompact()`） |
| 溢出恢复压缩 | **SDK**（`agent-session.js:1658-1695`） |
| 压缩算法（摘要生成） | **SDK**（`compaction.js`） |
| 压缩事件 | **SDK**（`compaction_start` / `compaction_end`） |
| **压缩入口按钮与状态展示** | **项目**（`useSessionRuntime.ts:111`、`chat.ts:427-438`） |

**SDK 的手动压缩**：`compact()` 第一步是 `await this.abort()`——**先中止当前 agent**。SDK 文档注释明确：

> Aborts the current agent operation first. Manual compaction never retries or continues the interrupted agent turn.

**自动压缩的触发条件**：

```js
// compaction.js:160-164
export function shouldCompact(contextTokens, contextWindow, settings) {
    if (!settings.enabled) return false;
    return contextTokens > contextWindow - settings.reserveTokens;
}
```

**注意：不是百分比阈值，是 token 差额。** 默认 `reserveTokens: 16384`、`keepRecentTokens: 20000`（`compaction.js:74-78`），项目仓库里**没有任何地方覆写**这三个值。

> **一个容易被问倒的点**：前端显示的 80% 只是**展示用的警戒色**，和自动压缩的触发点**没有对应关系**。是否触发取决于模型的 `contextWindow`——200k 窗口下约在 91.8% 触发，32k 窗口下约在 48.8% 触发。

**两种自动压缩原因**

| reason | 触发条件 | 是否重试被中断的轮 |
| --- | --- | --- |
| `"threshold"` | `contextTokens > contextWindow - reserveTokens` | ❌ |
| `"overflow"` | 模型返回上下文超限错误，且 `stopReason !== "stop"` | ✅ **重试一次**（`_overflowRecoveryAttempted` 防重入） |
| `"overflow"` | 同上但 `stopReason === "stop"` | ❌ 响应已完成，无法继续 |
| `"manual"` | 用户点按钮 | ❌ |

**压缩后会话文件怎么变**：**append-only，不删任何东西**。`session-manager.js:992` 的文件契约：

> The session is append-only: use appendXXX() to add entries, branch() to change the leaf pointer. **Entries cannot be modified or deleted.**

「删除」发生在**投影层**（`session-manager.js:198-226` `buildContextEntries`）：发给模型的上下文 = `[摘要] + [firstKeptEntryId 起保留的旧 entry] + [压缩之后的新 entry]`。被摘要掉的部分**只在发给模型时被省略，文件里还在**。这直接决定了 Q20 里两个 Token 口径的差异。

**项目侧的压缩代码**

事件处理（`chat.ts:427-438`）：`compaction_start` 时把 `isCompacting` 置 true 显示「压缩上下文中」，`compaction_end` 时清掉并 reload。

> **事实纠正**：当前 SDK 版本（0.85.1）**只有** `compaction_start` / `compaction_end`，用 `reason: "manual" | "threshold" | "overflow"` 区分。`auto_compaction_start` / `auto_compaction_end` 在 SDK 里**零匹配**，是历史遗留的兼容分支，**实际永不命中**。

手动压缩入口（`useSessionRuntime.ts:110-123`）：

```ts
// 压缩结果由事件落定 HTTP 接纳不代表压缩结束
dependencies.isCompacting.value = true      // ← 乐观置位
try {
  await sendAgentCommand(id, { type: "compact" })
} catch (error) {
  dependencies.isCompacting.value = false   // ← 只在失败时回滚
}
```

**注释就是设计意图**：HTTP 返回只代表命令被接纳，压缩真正结束要等 `compaction_end` 事件。所以成功路径**不回滚** `isCompacting`——这跟 Q5 的两个完成时点是一样的思路。

**为什么压缩必须由 SDK 做**

| 原因 | 说明 |
| --- | --- |
| 需要知道完整的上下文 | 哪些 entry 在活跃分支上、哪些被摘要过，只有 `SessionManager` 知道 |
| 需要调用模型生成摘要 | 摘要本身是一次 LLM 调用 |
| 需要原子地改写 agent 内存状态 | 压缩后 `agent.state.messages` 必须同步替换 |
| 需要与 entry 树保持一致 | `firstKeptEntryId` 必须是有效的 entry id |

**口述版**

> 首先要说明边界：**压缩算法是 SDK 提供的，我做的是接入和展示**。
>
> SDK 有两条压缩路径。手动的是用户点按钮触发，实现上它会先 abort 当前正在跑的 agent，而且压缩后不会继续那个被中断的对话轮。自动的分两种原因：一种是阈值触发，条件是当前上下文 token 数超过「窗口大小减去保留值」，默认保留 16384 个 token；另一种是溢出恢复，模型返回了上下文超限的错误，SDK 会压缩后重试一次，用一个标志位保证只试一次。
>
> 有个容易被问到的点：自动压缩的触发条件**不是百分比**，是 token 差额。前端显示的 80% 只是展示用的警戒色，和触发点没有对应关系。实际触发点取决于模型窗口——200k 窗口下大约在 91.8%，32k 窗口下大约在 48.8%，这是算出来的，不是猜的。
>
> 项目侧我做的是三件事。一是对接压缩事件，`compaction_start` 时把 `isCompacting` 置为 true 显示「压缩上下文中」，`compaction_end` 时清掉并 reload 一次，因为压缩改变了消息链。二是手动压缩入口，这里有个细节：HTTP 返回只代表命令被接纳，压缩真正结束要等事件，所以我在成功路径不回滚状态，只在失败时回滚——这跟 prompt 的接纳和完成是两个时点是一样的思路。
>
> 三是展示 Token 用量，这个下面单独说，因为有两种不同口径。
>
> 还有一点要说清楚：**压缩不会删历史**。会话文件是 append-only 的，压缩只追加一条摘要 entry，被摘要掉的内容在文件里还在，只是发给模型时被投影层省略了。这也是为什么压缩后页面仍然能展示完整历史。

**追问链**

```text
Q: 压缩会不会丢历史？
A: 不会。会话文件是 append-only 的，压缩只追加一条 compaction entry。
   被摘要掉的内容在文件里还在，只是发给模型时被投影时省略了。

Q: 压缩过程中能发新消息吗？
A: 不能。服务端的 sendPrompt 里有忙判定，
   导航中或压缩中直接返回 409 session_busy。

Q: 为什么会有 auto_compaction_start 这个分支？
A: 那是从 pi-web 移植时保留的兼容分支，
   当前 SDK 版本里没有这个事件名，所以永远不会命中。
```

## Q20 当前上下文占用和会话 Token 用量分别是什么？为什么不能相加？

**核心结论**：**两个完全不同的指标**。上下文占用是「此刻模型能看到多少」，压缩后会**下降**；会话累计 Token 是「整个会话一共烧了多少」，只增不减。

| | `contextUsage`（上下文占用） | `stats.tokens`（会话累计） |
| --- | --- | --- |
| **含义** | **当前**上下文占用了多少 | 整个会话**累计**消耗了多少 |
| **数据来源** | SDK `getContextUsage()` | `computeSessionStats(entries)` |
| **统计范围** | 活跃分支上的消息 | **整个会话文件**（含未激活分支 + 被压缩的历史） |
| **压缩后** | **下降** | **不下降** |
| **精度** | 估算（字符数÷4） | 真实 usage 累加 |
| **UI 位置** | 顶栏圆形徽标 | 悬浮层「会话累计」 |

`types.ts:419-421` 的注释把边界写死了：

> compaction 只追加摘要 entry 被汇总的历史仍留在文件里 因此累计值单调增长
> 与运行态的 context usage 是两项独立指标 **前端不得相加**

**`contextUsage` 的三种返回形态**

| 情形 | 返回 | 前端表现 |
| --- | --- | --- |
| 无模型或窗口为 0 | `undefined` | 不显示占用 |
| **刚压缩完，还没有新的 assistant 响应** | `{ tokens: null, contextWindow, percent: null }` | **显示问号图标**，不显示数字 |
| 正常 | `{ tokens, contextWindow, percent }` | 显示剩余百分比 |

**情形 2 为什么要返回 null**：压缩后的上一条 usage 反映的是**压缩前**的上下文规模，用它来显示会严重高估（`agent-session.js:2715-2717` 注释说明了这个理由）。前端对应做了降级——`percent === null` 时渲染 `CircleHelp` 图标而不是 0%。**null 和 0 的语义完全不同**：null 表示未知，0 表示确定是空的。

**估算口径是两段式的**

| 分支 | tokens 来源 | 是否含 system prompt / 工具定义 |
| --- | --- | --- |
| 有有效 usage | 最后一条 assistant 的 provider usage | **隐式包含** |
| 无有效 usage | 逐条消息 `estimateTokens` 累加 | **不包含** |
| usage 之后的新消息 | `estimateTokens` 累加 | 不包含 |

`estimateTokens` 的口径是**字符数 ÷ 4**（`compaction.js:188-226`），SDK 自述：

> Estimate token count for a message using chars/4 heuristic. This is **conservative (overestimates tokens)**.

**所以 `contextUsage` 是一个估算值，不是精确值**。面试时如果被追问精度，应该直接承认，并说明它在「有 usage 时」会锚定到真实值。

**`stats` 的统计范围**

`session-reader.ts:349-350` 的调用点注释：

> 统计按完整 entries 累计 含未激活分支与被压缩历史 与显示消息是两个口径

**注意传的是全量 `entries` 而不是活跃分支**。所以**切到另一个分支，累计 token 不会变**——它统计的是整个会话文件。

**前端展示**：`ChatPanel.vue:357-380` 做 clamp 到 `[0, 100]` 和取整（SDK 不做这两件事，`percent` 可能超过 100）。浮层里同时展示两个口径，**靠文案区分**：标题「会话累计」下面是累计值，第六行「当前上下文」是运行态值。

**一处口径偏差（要主动说）**

`session-stats.ts:56` 只累加 `compaction` 的 usage，而 SDK 的 `getSessionStats()`（`agent-session.js:2664`）累加的是**两者**：

```js
if ((entry.type === "branch_summary" || entry.type === "compaction") && entry.usage)
```

**本项目未启用分支摘要功能**，所以实际不会有偏差。但文件头注释声称「与 SDK 的 getSessionStats 同一套口径」，严格说是不准确的。

**另一个事实**：项目**从未调用** SDK 的 `getSessionStats()`。项目用自研的 `computeSessionStats` 从会话文件复刻了同一口径，因为要在服务端读文件时顺便算出来。

**口述版**

> 这是两个完全不同的指标，特别容易讲错。
>
> 一个是「当前上下文占用」，来自 SDK 的 `getContextUsage()`，表示**此刻模型能看到多少 token**。它的特点是**压缩后会下降**，因为压缩把旧消息换成了摘要，模型能看到的内容变少了。
>
> 另一个是「会话累计 Token」，我从会话文件的所有 entry 累加出来，表示**整个会话一共烧了多少**。它的特点是**只增不减**，因为会话文件是 append-only 的，压缩只追加一条摘要 entry，被摘要掉的历史还在文件里，仍然被累计。而且它统计的是整个文件，包括未激活的分支。所以切到另一个分支，累计 token 不会变。
>
> 代码注释里明确写了这两个是独立指标，前端不得相加。界面上我靠文案区分——顶栏的圆环是当前上下文，悬浮层标题是「会话累计」。
>
> 有几个精度和边界要诚实说。第一，上下文占用是**估算值**。SDK 的口径是字符数除以 4，它自己注释说是偏保守的。只有在能拿到 provider 返回的真实 usage 时才会锚定到准确值，之后新加的消息还是估算。
>
> 第二，刚压缩完的那一刻，SDK 会返回 `tokens: null`。因为压缩前的那条 usage 反映的是压缩前的规模，用它显示会严重高估。前端对应做了降级，显示一个问号图标而不是 0%——因为 null 表示未知，0 表示确定是空的，这两个语义完全不同。
>
> 第三，统计口径有一处偏差。我的 `computeSessionStats` 只累加 compaction 的 usage，而 SDK 的 `getSessionStats` 还累加 branch_summary。本项目没启用分支摘要，所以实际没有影响，但严格说文件头注释里「与 SDK 同一口径」的说法不准确。
>
> 还有一点：项目其实从未调用 SDK 的 `getSessionStats()`，而是自己从会话文件复刻了同一套口径，因为我要在服务端读文件的时候顺便算出来。

**追问链**

```text
Q: 为什么切到另一个分支，累计 token 不变？
A: 因为 computeSessionStats 传的是全量 entries 而不是活跃分支。
   代码注释明确写了「统计按完整 entries 累计 含未激活分支与被压缩历史」。
   这是有意的——累计统计应该反映真实计费。

Q: contextUsage 的 percent 会超过 100 吗？
A: SDK 侧不做裁剪，可能超过 100（估算偏保守）。
   前端 clamp 到 [0, 100]。

Q: 成本为什么显示「未提供」？
A: 因为不是所有模型都提供价格数据。
   formatCost 把「无价格数据」和「真实为 0」统一处理，不做估算。
```

## Q21 如果任务执行中服务端重启，会发生什么？

**核心结论**：**任务永久丢失，而且前端不知道它被中断了。** 因为执行状态全在进程内存里，没有任何持久化。

| 状态 | 存储位置 | 重启后 |
| --- | --- | --- |
| 会话消息（entry 树） | 磁盘 JSONL 文件 | ✅ 完整保留 |
| 会话元数据（名称、时间） | 磁盘 JSONL 文件 | ✅ 完整保留 |
| **Agent 执行实例** | **服务端进程内存**（`registry`） | ❌ **丢失** |
| **正在执行的工具** | **服务端进程内存**（SDK 内部） | ❌ **丢失** |
| **运行中队列** | **服务端进程内存**（SDK 内部） | ❌ **丢失** |
| **`pendingPromptCount`** | **服务端进程内存** | ❌ **丢失** |
| 前端界面状态 | 浏览器内存 | ❌ 刷新即丢 |

**为什么 Agent 执行不能跨进程恢复**

因为执行是一个「活的」过程，不是可以序列化的状态。执行到一半时进程里有：

1. **模型请求的流式响应**——可能正在接收一个长回复，接收了一半，连接断了就是断了
2. **正在执行的工具**——比如 `bash` 跑了一个 5 分钟的命令，子进程随父进程一起死
3. **SDK 内部的执行状态机**——它知道自己处于「第 3 轮、正在等工具结果」，但这个状态没有持久化

**能恢复的只有「结果」，不能恢复的是「过程」**。

**单纯恢复历史消息为什么不够**

因为**历史消息里没有「有一个任务被中断了」这个事实**。重启后 `registry` 是空的 → `/api/agent/running` 返回空数组 → 侧栏显示「没有会话在跑」。但如果中断发生在一次工具调用之后，会话文件里会留下「有 toolCall 但没有对应 toolResult」的半截数据。

**界面会怎么显示**？`ToolCallCard` 的 `result` 是 undefined，`activeTools` 是空的，`streaming` 是 false → 显示**「完成」**。

**这是一个真实的误导**：工具实际上没有执行完（甚至可能没执行），但界面显示「完成」。

**改进建议（按成本排序）**

**① 前端检测「未完成的工具调用」**（成本极低，**纯前端就能做**）

> 会话文件里如果存在「有 toolCall 但没有对应 toolResult」的助手消息，说明执行被中断了。前端可以把这类卡片标记为「未完成」，而不是「完成」。`toolResultsByCallId` 查不到就是未完成，**不需要服务端改动**。

**② 执行状态落盘**（成本中等）：记录 `{ sessionId, commandId, startedAt, status }`，启动时把所有 `running` 改成 `interrupted`。前端就能知道「上次的任务被中断了」。

**③ 命令幂等**（成本中等）：前端生成 `commandId`，服务端记录已处理的 ID。

**④ 完整方案**（成本很高）：把执行状态机也持久化，让任务能在新进程里从断点继续。这需要 SDK 层面支持序列化执行状态，**当前 SDK 不提供**。

**多实例部署是同一个根因**：`registry` 是进程内 Map，多实例部署时同一会话在两个进程里会各建一个 `AgentSession`，同时往同一个 JSONL 文件写。要支持需要把注册表移到共享存储 + 会话级分布式锁。

**口述版**

> 任务会永久丢失，而且前端不知道它被中断了。
>
> 原因是执行状态全在进程内存里。会话消息存在磁盘的 JSONL 文件里，重启后能完整读回来；但 Agent 执行实例、正在跑的工具、运行中的队列，全在进程内存，重启就没了。`registry` 是一个模块级的 Map，进程一重启就是空的。
>
> 而且这里有个更深的问题：**Agent 执行本身不能跨进程恢复**。因为它不是可以序列化的状态，而是一个活的进程——里面可能有正在接收的模型流式响应、正在跑的子进程、SDK 内部的执行状态机。能恢复的只有结果，不能恢复的是过程。
>
> 更糟的是，单纯恢复历史消息是不够的。因为历史消息里没有「有一个任务被中断了」这个事实。重启后 `/api/agent/running` 返回空数组，前端以为一切正常。但如果中断发生在一次工具调用之后，会话文件里会留下「有工具调用但没有对应结果」的半截数据，而界面会把这种情况显示成「完成」——这是一个真实的误导。
>
> 如果要改进，我按成本排了优先级。第一件事成本几乎为零，而且纯前端就能做：检测「有工具调用但没有结果」的情况，把它标记成「未完成」而不是「完成」。前端其实已经有这个信息了——查结果 Map 查不到就是未完成。
>
> 第二件是执行状态落盘，记录每个会话的当前任务状态，启动时把 running 的改成 interrupted，这样前端能知道「上次的任务被中断了」。第三件是命令幂等，加 commandId 防止重试导致重复执行。
>
> 至于完整的任务恢复——让任务在新进程里从断点继续——那需要 SDK 支持序列化执行状态，当前不提供，所以不在可行范围内。
>
> 多实例部署也是同样的根因：registry 是进程内 Map，同一会话在两个进程会各建一个执行实例，同时写同一个文件。要支持需要把注册表移到共享存储，再加会话级的分布式锁或者会话亲和性路由。

**追问链**

```text
Q: 优雅关闭时会发生什么？
A: nitro 的 close hook 会调 destroyAllRpcSessions，
   把所有 wrapper 的 dispose 掉。但正在执行的 Agent 任务本身
   不会完成，它会随进程一起消失。

Q: 为什么不做任务队列持久化？
A: 因为执行体本身不能序列化。即使把「有个任务待执行」记下来，
   重启后也无法从断点继续——工具已经跑了半截，模型请求已经断了。

Q: 那 SSE 断线呢？和进程重启有什么区别？
A: 完全不同。SSE 断线只是传输层断了，服务端的 Agent 还在跑，
   重连后能看到结果。进程重启是执行体没了，无法恢复。
```

## 本篇小结

| 决策 | 解决的问题 | 代价 |
| --- | --- | --- |
| **块数组 + contentIndex** | 文本/思考/工具交替出现时能定位到正确的块 | 每次 delta 创建新对象，有 GC 压力 |
| **纯函数 reducer** | 可测试、状态变更收敛、可推演 | 无去重、无排序，依赖事件按序到达 |
| **三层判据 + 队列版本** | 四类不同的异步竞态 | 13 处校验点靠人工维护，新增代码容易漏 |
| **压缩对接而不实现** | 边界清晰，不夸大能力 | 受 SDK 事件结构约束 |

**最关键的一个认知**：

> **增量事件（`_delta`）是有损的，权威事件（`_end`）是自愈的。**
>
> 这个分类决定了整个系统的容错特性：中间丢事件不会导致最终结果错误，只会导致过程中的显示不完整。

**最需要主动划清的边界**：

1. **界面恢复 ≠ 任务恢复**——刷新能恢复界面，服务端重启任务就没了
2. **压缩是 SDK 的**——项目只做事件对接和状态展示
3. **上下文占用 ≠ 累计 Token**——压缩后前者下降、后者不变，不能相加
4. **「有工具调用但没有结果」当前显示成「完成」**——真实的误导点，纯前端可修
