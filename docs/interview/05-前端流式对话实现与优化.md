# 前端流式对话实现与优化

用户发送“读一下配置文件，解释启动报错”，页面会依次展示文本、工具参数、工具结果和后续回答。本篇沿这个过程拆解消息如何组装、组件如何更新、滚动如何跟随，以及长回答为什么可能变慢。

## 1 从页面看流式对话的责任

在讲页面之前，先说明前端的起点：**前端拿到的永远是投影，不是 SDK 的原始对象。** 工具要访问本地文件与执行命令、模型凭证不能下发到浏览器、任务生命周期比页面长、SDK 是纯 ESM 且内嵌 WASM 的 Node 包 —— 这四件事决定了浏览器里既没有 SDK 实例，也没有模型请求。`nuxt.config.ts` 把四个 `@earendil-works/*` 包和 `undici` 放进 `nitro.externals.external`，`shared/lib/agent-event-wire.ts` 的文件头也写明 shared 层不允许 import Pi 包，这是能进浏览器产物的前提。

所以浏览器拿到的是经过裁剪的事件与消息投影。这也解释了本篇所有优化为什么只能在**投影之后**做：可以调 reducer、Markdown、组件与滚动，但改不了 SDK 发什么、发多细、什么时候发，那部分属于服务端与 SDK 的职责边界。核心链路的三层分工见 [01 项目介绍与架构表达](01-项目介绍与架构表达.md) 的核心链路一节。

用户看到的是输入框、消息、工具卡片和停止按钮，底层却同时发生请求确认、模型输出、工具执行与历史保存。页面不能只拼接文字，还要解释“输入是否发出”“任务是否接受”“当前在做什么”和“能否继续操作”。

项目用 Pinia 保存会话业务状态，纯 reducer 组装当前助手消息，Vue 组件展示结果。连接对象留在 store 闭包中，避免把网络对象当普通响应式数据；页面路由负责开始和结束当前会话的订阅。

```text
用户操作 → Composer → chat store → HTTP 命令 → SDK
SDK 事件 → SSE → 连接管理器 → store → reducer → 消息组件
历史查询 ────────────────────────→ messages 与记录 ID
```

理解这条链路时先区分几个对象：

- 输入框 draft 是用户尚未提交的文字，流式草稿是助手正在生成的消息。
- messages 主要保存完整消息，实时阶段也可能包含临时用户气泡。
- isRunning 表达整体界面运行状态，activeTools 保存正在执行的工具；没有新文字不代表任务结束。

> reducer 管理内容变换，store 管理业务时序，组件管理展示。每层都正确接起来，才形成完整的流式体验。

## 2 完整链路怎样落到前端

### 进入会话与提交输入

会话页取得 ID 后调用 openSession：关闭旧连接、读取目标历史，再维护 SSE，查询当前模型与工具信息。历史响应返回时检查会话身份，防止用户已经切到别处却显示旧内容。工作区同步是异步发起，不要求它完成才建立订阅。

Composer 处理输入法、补全弹层和发送快捷键。中文选字阶段先检查 isComposing，补全面板打开时优先消费 Enter，普通输入下才将 Enter 作为发送。这些是同一键盘事件的优先级问题，不能给每个功能分别绑定 Enter 而忽略冲突。

点击发送后，组件保存文本与附件快照，调用 store 的 submitPrompt；store 保留待确认文本、清空可编辑输入并保存草稿，再显示乐观消息、等待 connected 业务握手并提交 prompt。失败合并与会话隔离在 store 中处理。等待之前先建立一份可见的提交状态。

这里要强调反面后果：**如果先发 prompt 再装监听，极短回复可能在订阅建立之前就生成完**，那一段输出前端会整段丢失，而 HTTP 照样返回成功，界面看起来只是「没反应」。这正是发送链路要等待业务 `connected` 而不是等 HTTP 200 的原因 —— 200 只说明命令被送达，不说明事件已经有人在听。实现见 [chat store](../../app/stores/chat.ts) 里发送前的 `ensureConnected` 调用，就绪判定在 [连接管理](../../shared/lib/agent-event-connection.ts)：只有收到 `connected` 事件才把这次连接标记为 ready，超时或 `startup_error` 直接失败而不是继续发送。

先将本次用户文字作为临时消息加入列表，同时插入一个临时记录 ID；然后打开界面的运行标记，初始化助手流式状态。这样握手仍在等待时，用户已经能看到自己的提交和等待反馈。

临时 entry ID 为空，因为真实记录身份尚未从历史查询取得。start 只初始化流式阶段，此时没有助手消息。页面据此可以显示等待反馈，但不能把等待提示说成模型已经产生思考内容。

### 接受确认与持续事件

ensureConnected 等待服务端安装监听后发出的业务握手；它可以复用已有就绪连接，不是每条消息重新创建 SSE。随后发送 prompt，SDK 预检接受后 HTTP 可以返回，生成继续通过 SSE 展示。

EventSource 处理网络事件边界，应用 JSON.parse message.data，再按类型分发。项目没有手写 fetch 字节流拼包逻辑。一次内部 text_delta 也不等于一个 token，它可能包含多个字符或半个 Markdown 结构。

例如收到一条“文本增量”事件，指定第 0 个内容块，并携带文字“你好”。处理含义就是找到当前助手消息的第 0 个文本块，在已有文字后追加“你好”。它不是一份能够独立恢复整条消息的完整记录。

这条增量依赖之前的助手快照和块初始化。服务端会裁掉 SDK 增量中重复携带的 partial 全文，并提前提取工具元数据供前端使用。

#### 两个完成时点在前端长什么样

同一条 prompt 有两个不同的完成时点，前端必须把它们分开：

- **已接受。** HTTP 命令返回成功。服务端为接纳阶段单独建了一个 Promise，SDK 预检通过就完成它、让 HTTP 返回，而完整 prompt 继续在后台跑；运行口径由 `pendingPromptCount` 维持。
- **已结束。** 整轮生成真正收尾，由 `agent_settled` 这类结束信号决定。

如果在 HTTP 返回时立刻把 `isRunning` 置为 false，就是把「已接受」当成了「已结束」：停止按钮和运行标记会提前消失，而模型还在输出，用户既不知道任务还在跑，也失去了中断入口。所以前端只在开始提交时打开运行标记，等落定信号才关闭它。

```ts
// 服务端在预检通过时就确认 HTTP 完整生成继续在后台跑
// 前端也不能把 POST 成功当成任务结束 真正的落定只认结束信号
case "agent_settled":
  sdkAgentActive = false;
  isRunning.value = false;
  activeTools.clear();
  break;
```

> 一次提交有两个完成时点，HTTP 返回成功只代表**已接受**，不代表整轮生成**已结束**。如果在前端把 HTTP 200 直接当成结束，就会出现“界面说完成了，模型还在写”的错位。判断结束要看结束信号，而不是看提交请求的响应。

服务端侧的接纳逻辑与 `prompt_done` 事件在 [会话包装器](../../server/utils/rpc-manager.ts)，测试见 [rpc-manager.test.ts](../../tests/server/utils/rpc-manager.test.ts)：其中一条用例让 SDK 先回调预检通过，断言 `send` 已经 resolve、HTTP 可以返回，而 wrapper 的运行口径仍然是真，直到整轮结束才发出 `prompt_done` 并转为假；另一条断言同步抛错也会把运行计数回滚，否则实例会永久显示运行中。

### 状态组装、工具关联与展示

状态更新分成纯内容计算与响应式写回两个步骤。

每次事件进入时，reducer 根据旧状态计算下一份流式状态；store 再把返回字段写入原来的响应式容器。外层对象继续被组件订阅，内部的助手消息和内容块按本次变化更新。

reducer 根据内容索引更新文本、思考或工具参数，未变化块可复用引用。工具参数未完整时保存 rawInput，最终采用结构化 arguments；最终工具结果通过 toolCallId 配到卡片，不靠相邻位置或名称猜测。

ChatPanel 分别渲染历史列表和独立流式消息。MessageItem 按块类型选择 Markdown、思考或工具组件。文本仍调用累计全文的 renderMarkdown，Vue 调度合并不等于 Markdown 已经做增量解析。代码复制与文件链接在父容器委托处理，滚动行为由 composable 在 DOM 更新后调度。

### 用一组事件实际演算消息如何生成

以下用“先说明操作，再调用 read”展示状态变化。事件内容为讲解样例，处理规则对应当前 reducer：

| 顺序 | 到达的事件 | 内容块变化 |
| --- | --- | --- |
| 1 | 助手 `message_start`，内容为空 | 建立当前助手消息，`content = []` |
| 2 | `text_start`，索引 0 | 创建文本块，文字为空 |
| 3 | `text_delta`，内容“先检查” | 索引 0 变成“先检查” |
| 4 | `text_delta`，内容“配置文件” | 索引 0 变成“先检查配置文件” |
| 5 | `text_end`，完整文字 | 用事件中的完整文字收尾该块 |
| 6 | `toolcall_start`，索引 1，调用 ID 为 call-1 | 创建工具块，名称 read，参数暂为空 |
| 7 | `toolcall_delta`，参数片段 | 追加到 `rawInput`，此时未必是完整 JSON |
| 8 | `toolcall_end`，完整参数 | 写入最终结构化 `input` |

处理一条文本增量时，先定位，再校验类型，最后追加。

文本增量根据内容索引找到目标块，确认它确实是文本块，才将新片段接到已有文字后面。如果当前助手消息不存在、索引无效或块类型不符，就保留原状态，避免把片段拼到错误位置。

这也说明增量依赖初始化或快照；漏掉前置事件时，单靠后续片段无法完整恢复，需要重新取得当前消息状态。

`updateContentBlock` 复制内容数组与当前消息，再替换目标块；其他块保持原引用。store 用 `Object.assign` 把返回值写回既有 reactive 容器，保留组件已经订阅的外层代理。

这里有三层身份：消息对象、内容数组、具体块。数据层保留未变块引用，为后续精细复用提供条件；当前模板仍可能重新调用多个文本块的渲染函数，所以“引用没变”和“没有重复解析”还不是一件事。

### 工具参数为什么先保存字符串，再拿完整对象

假设参数分成两次到达：第一段是 `{"path":"src/`，第二段是 `api.ts"}`。第一段不是完整 JSON，立即 `JSON.parse` 会失败。当前 `toolcall_delta` 先拼接原始片段，`toolcall_end` 再使用 SDK 提供的完整参数对象。

工具参数完成时，使用结束事件携带的调用 ID、工具名称和完整参数对象，替换对应工具块。生成中的原始参数字符串到此完成职责，展示和后续查询以完整结构化参数为准。

前端展示参数不代表前端执行工具。工具由 SDK 在服务端运行，执行事件更新活跃工具，最终 `toolResult` 按调用 ID 回到对应卡片。这样可以区分“模型正在生成调用参数”和“工具已经开始读取文件”，避免只看到工具名称就显示成已完成。

进一步阅读：[消息状态与工具渲染](../learning/06-消息状态与工具渲染.md)。

### 定稿、结束与退出

message_end 将完整消息加入列表并清空草稿，后续历史查询补上记录 ID。工具调用消息结束后仍可能继续执行，任务的整体运行标记由 Agent 落定等分支处理。历史查询、当前快照和生命周期事件分别覆盖不同信息，不存在“收到任意 end 就清空全部状态”的通用规则。

离开页面关闭当前订阅，不自动停止 SDK；点击停止先撤回队列，再发送 abort，并在请求结束后安装延迟对账。自动重连可恢复当前快照；如果握手明确已非流式且旧页面确认过 Agent 活跃，还会落定并补查历史。没有事件序号回放，仍在运行时遗漏的完整消息、刷新查询与订阅间的窗口尚无统一对账保证。

### 三种恢复在前端的差别

恢复的差别不在服务端做了什么，而在于**页面内存里还剩什么**：

| 恢复方式 | 页面内存里还有什么 | 需要重新取什么 | 前端表现 |
| --- | --- | --- | --- |
| 刷新页面 | 全丢，草稿、运行标记、工具状态都不在了 | 历史消息、服务端当前消息快照、一次新的订阅 | 历史先回来，流式气泡由快照重建，增量从快照之后继续 |
| 断线自动重连 | 旧消息、运行标记、活跃工具都还在 | 握手给出的运行态、当前消息快照 | 运行标记由握手校正；快照替换旧草稿而不是追加；久未结束的任务会落定并补查历史 |
| 服务端进程重启 | 不可恢复，内存实例与快照随进程消失 | 只能重新读取文件历史 | 历史仍可读，但任务不能续接，界面不再有正在生成的气泡 |

三种恢复的复现步骤与断言见 [04 验证方案与源码索引](04-验证方案与源码索引.md) 第 1 节，这里不重复。

## 3 状态设计的连续追问

**面试官：为什么要把历史和流式草稿分开，放一个数组里不也能更新？**

> 一个数组也能实现，但每个元素都需要区分临时、生成中和完成状态，并处理替换、快照与历史查询的覆盖。当前采用独立草稿，让增量更新主要作用于当前消息，完成后再进入列表，状态转换比较直接。
>
> 代价是流式实例转成历史实例时要处理身份与局部交互延续，历史查询也可能与新事件重叠。所以这个拆分减少了一部分管理复杂度，却没有自动解决去重、key 稳定和恢复一致性。

**面试官：最终完整消息既然会回来，前面的 delta 还有必要保存吗？**

> delta 用于及时展示过程，最终消息用于收尾，两者服务不同时间点。网络正常时可以持续更新草稿，完整消息到达后用最终内容定稿。但不能因为有最终消息就任意丢掉中间 delta，否则生成期间的文本可能缺失；也不能因为一直有 delta 就忽略最终错误与结束状态。
>
> 如果未来按帧合并展示，要处理待提交 delta 与最终消息的先后，确保旧回调不会在定稿后把草稿重新写出来。因此合并队列必须与定稿、切会话和清理一起处理。

## 4 常见问题：定位依据、当前处理和修复方向

下表中的现象是分析场景，不表示每项都已由用户实际遇到。已有代码路径与尚未完成的修复分别列出。

| 场景 | 定位依据 | 当前处理与边界 | 修复或验证重点 |
| --- | --- | --- | --- |
| 首轮回复没有显示 | 检查 prompt 发出时监听是否就绪 | 已等待业务 connected，不只等待网络 open | 验证冷启动下极短回复；不要合并创建与首条发送 |
| 中文选字时误发送 | 检查键盘事件与弹层优先级 | 已先检查 `isComposing`，再处理补全，最后处理 Enter 发送 | 验证选字、补全确认、Shift+Enter 三类行为 |
| 用户消息显示两次 | 比较乐观消息与服务端用户消息的匹配 | 已有文本与时间戳相关的局部匹配，不是请求幂等 | 明确临时消息身份；网络重试另需服务端去重 |
| 提交失败后气泡未撤回 | 检查代理对象与原始对象引用比较 | 已通过 `toRaw(last) === optimistic` 修正，测试覆盖失败撤回 | 仍只删除末尾同一对象；稳定客户端 ID 是进一步方案 |
| 带图任务只发送了文字 | 检查清空附件与读取附件的先后 | 已传入附件快照，成功后只移除本批对象 | 已有新增附件不被清除的测试；图片不跨刷新持久化 |
| 切换会话后旧内容出现 | 检查请求、连接是否仍属于当前会话 | 发送检查 ID 与代次，reload 还检查请求序号 | 不推广为所有路径已覆盖；打开会话的部分收尾仍仅检查 ID |
| 重连后缺消息或仍运行 | 检查握手状态与旧页面活跃标记 | 已增加有条件的终态落定与历史回读 | 仍在运行及刷新窗口需要进一步一致性协议 |
| 点击停止后迟迟不恢复 | 检查定时器安装在 await 前还是后 | 撤回队列及 abort 确认后才开始 3 秒兜底 | 任一请求挂起都需反馈；超时和确认停止分开表达 |
| 复制反馈或折叠状态重置 | 检查 v-html 替换和组件 key 变化 | 流式消息独立渲染，历史 key 从临时索引变为 entry ID 时可能重挂载 | 用稳定 UI 身份，明确交互状态的保存位置 |

**面试官：你说比较 session ID 能防串会话，为什么还要代次？**

> A 请求发出后切到 B，再切回 A，最早那次 A 响应返回时，当前 ID 又是 A，仅比较 ID 就无法知道它属于旧的一次打开。ID 表示对象身份，代次表示这次操作的身份，两者不同。
>
> 当前 close 会递增 generation，发送和多条异步命令保存 ID 与代次，返回时同时检查；历史 reload 还检查同代内的请求序号。取消旧请求可以节省资源，但结果守卫仍有必要。现有测试已安排旧失败和旧握手最后返回，验证 A→B→A；这不代表未带代次的其他收尾路径也自动受保护。

**面试官：把每个失败都恢复输入框，会不会覆盖用户后来输入的内容？**

> 直接覆盖会丢掉新内容，只有输入为空才恢复又会漏掉旧内容。当前普通提交把待确认文字单独保留，失败时将旧提交与新输入合并，按会话持久化；附件则使用独立快照，成功后只清本批，失败保留。
>
> 比如先发“检查接口”，等待时又输入“顺便看测试”，失败后两个文本都会保留，而不是让后者消失。会话代次变化时，旧操作不回填到新页面。已有按会话文字草稿和合并测试，但图片不跨刷新保存，多窗口也没有草稿冲突合并；命令是否执行仍需服务端对账。

源码：[输入组件](../../app/components/ChatComposer.vue)、[chat store](../../app/stores/chat.ts)、[连接管理](../../shared/lib/agent-event-connection.ts)、[消息列表](../../app/components/ChatPanel.vue)。

## 5 Vue 渲染与 Markdown 的性能追问

### 5.1 当前代码已经做了什么

| 实现 | 直接作用 | 不代表什么 |
| --- | --- | --- |
| 服务端去除增量中的 partial 全量快照 | 减少重复传输字段 | 不是浏览器渲染缓存 |
| 历史列表与流式消息分开渲染 | 区分两类数据与生命周期 | 不保证历史组件从不更新 |
| reducer 替换目标块，保留其他块引用 | 控制状态变换范围 | 仍有数组复制和字符串追加 |
| Highlight.js 使用常用语言集合 | 限制引入的语言集合 | 未提供包体收益测量 |
| Markdown 交互在消息容器委托 | 新生成代码块可复用点击处理 | 不阻止 v-html 子树被替换 |
| 滚动使用 post watcher 和 rAF | DOM 更新后执行，合并滚动调度 | 没有合并消息 reducer 或 Markdown 解析 |

**面试官：流式消息独立了，是否每个 delta 就只更新一个块？**

> 数据层主要更新目标内容块，但渲染层要看组件边界。当前一条助手消息的所有文本块仍在同一个 MessageItem 模板里调用 renderMarkdown。这个组件更新时，多个文本块的渲染表达式可能重新执行。
>
> 已完成的历史消息是其他组件实例，Vue 是否更新它们取决于依赖和 props，不能反过来说每个 delta 一定重绘整个列表。正确结论是：当前没有明确的文本块解析缓存；需要记录实际调用范围，不能仅凭组件树推断所有重绘次数。

**面试官：Vue 已经批量更新了，还需要做节流吗？**

> Vue 会合并同一调度周期内的更新，但网络事件可能分散在多个周期，reducer 也仍按调用执行。是否还要限制展示频率，取决于事件频率和每次解析成本。
>
> 如果需要合并文本增量，应保留完整数据，只降低提交到展示层的频率。不能使用会丢弃中间输入的简单 throttle。更不能只用不断重置的 debounce，否则连续输出时用户可能长时间看不到内容。

### 5.2 一份有边界的优化顺序

**面试官：如果长回复开始卡顿，你先做什么？**

> 先分段测量：事件处理和 reducer、Markdown 解析与高亮、组件提交和布局、滚动。固定回复内容及 delta 节奏，避免把模型本身输出变慢误判成前端卡顿。首字时间也要拆开看，等待握手和模型首个事件不属于 Markdown 开销。
>
> 如果主要成本在反复解析活动文本，就先降低不必要的解析频率；如果稳定块也反复解析，再加稳定块复用。只有长历史节点数量成为主要瓶颈，才评估虚拟列表。优化顺序由测量决定，而不是把常见技术全部装进去。

建议按以下条件选择，当前均未作为完整优化落地：

| 瓶颈 | 可选改动 | 代价与必要约束 |
| --- | --- | --- |
| delta 很碎，展示更新过密 | 同一消息同一块内合并连续文本，按帧或有限间隔提交 | 不跨块乱拼；块结束、快照、消息完成前处理待提交内容 |
| 稳定文本重复解析 | 拆出内容块组件或缓存渲染结果 | 需要稳定消息身份、内容版本与渲染选项；缓存要可回收 |
| 活动长文本与代码反复解析 | 控制活动块渲染频率，按测量决定是否延迟高亮 | 最终完整渲染必须及时完成，不能遗漏最后一段 |
| 解析仍占用主线程过久 | 评估 Worker 承担纯文本解析 | 有传输成本；结果带版本，丢弃旧结果；DOM 操作留在主线程 |
| 历史 DOM 规模过大 | 分页或虚拟化 | 可变高度、折叠、搜索、选择复制与滚动锚点更复杂 |

判据表如下。四层按顺序往下走，每层都先确认「这一层是不是主要成本」，再决定要不要动它：

| 层级 | 怀疑对象 | 用什么观察 | 看到什么才继续往下走 |
| --- | --- | --- | --- |
| 1 reducer 与状态组装 | 事件分发、状态对象与消息复制 | Performance 面板录制整段流式过程，看 long task 归属；统计单次 `applyEvent` 到写回的时间，对照 delta 到达频率 | 单次事件到状态写回的时间远小于帧预算；连续 delta 下耗时随累计长度增长不明显 |
| 2 Markdown 解析与代码高亮 | `renderMarkdown` 重复扫描累计文本 | 在渲染函数入口加计数，记录一次流式更新里同一消息各文本块的调用次数与入参长度；固定内容对照固定 delta 时间表 | 解析调用次数与入参长度都在预期内，长文本也不产生显著 long task |
| 3 DOM 提交与布局 | 组件更新范围、`v-html` 替换引发的重排 | Performance 面板的 bottom-up 视图看 style、layout 与 `v-html` 提交的占比，对照内容块数量与消息数量 | 布局耗时与内容块数量基本同阶，替换后没有反复触发的强制同步布局 |
| 4 滚动跟随 | `scrollTo` 这类滚动操作触发布局 | 把滚动路径临时改成只记账不滚动，用同一份内容与 delta 时间表做对照 | 开关滚动前后耗时差异可以忽略；差异明显时先修滚动时机 |

三点使用说明：

- **首字时间要单独拆出来。** 从发送到第一个文字之间包含握手等待、HTTP 往返和模型首个事件，这段不属于渲染开销，不能和渲染耗时加在一起当作「前端变慢」。
- **固定内容加固定 delta 时间表做对照。** 同一份回复内容与同一套 delta 节奏下比较开关某项改动的两轮记录，才能排除模型本身输出变慢这个变量。
- **引用没变不等于没有重复解析。** `MessageItem` 里 `v-html="renderMarkdown(block.text)"` 是模板里的普通函数调用，一次流式更新会让同一条消息里的多个 Markdown 块重新调用渲染函数，当前**没有稳定的块级渲染缓存**；数据层保留未变块引用，只说明后续有做精细复用的条件。

**面试官：按帧合并时，message_end 已经到了，前一帧 delta 还在队列怎么办？**

> 最终完整消息应成为权威结果，待提交队列必须在定稿路径中处理：可以先提交有效增量再定稿，也可以丢弃已被完整消息覆盖的片段。关键是不能在定稿之后让旧 rAF 再次写回草稿，否则会出现结束后气泡复活。
>
> 切会话和快照替换也有同样问题，所以队列应绑定 session、消息和连接代次，并能取消。这个优化增加了时序状态，必须一起测试，不能只记录帧率改善。

**面试官：为什么不用每次只解析新增字符？**

> Markdown 语法不是字符片段彼此独立。例如围栏、表格和引用可能需要后续内容才能确定结构，新增片段解析成 HTML 后直接追加，可能与完整文本解析不同。
>
> 更可控的第一步是复用已经稳定的完整内容块，对活动块仍做完整解析。若假设每次解析开销随累计文本长度线性增长，等长小片段到达时，总扫描量是各次前缀长度之和，可能接近平方增长。这说明值得减少重复解析，但只是成本模型，不是本项目已测得的复杂度或性能结论。

**面试官：直接给每个块加 computed 不就有缓存了吗？**

> computed 能缓存依赖未变时的结果，但必须有合适的组件或数据边界。把整条消息的全部 HTML 放进一个 computed，活动块一变仍可能把所有块重新计算。
>
> 块组件或按稳定身份建立的缓存，才能更精确地复用未变化内容。缓存不能只依赖 contentIndex，也不能永久记住每个流式前缀；否则不同消息可能串结果，长对话还会积累大量无用项。还需处理流式实例转为历史实例时的身份衔接。

源码：[MessageItem](../../app/components/MessageItem.vue)、[Markdown 渲染](../../app/utils/markdown.ts)、[事件裁剪](../../shared/lib/agent-event-wire.ts)。

## 6 自动滚动：用户意图与布局变化

### 6.1 当前实现

`useAutoScroll` 计算距底部是否小于 80px。滚动事件更新位置，依赖变化后使用 `flush: "post"` 和 rAF 调度，再测量是否需要滚到底部。离开底部时显示“回到最新消息”按钮。

`ChatPanel` 传入的依赖是消息数量、运行标记和内容块数量。虽然没有直接读取文本长度，但 reducer 替换了 `streamingMessage`，会使 getter 重新执行；getter 返回新数组，也会触发 watcher。

既有最小响应式验证记录显示：内容块数量仍为 1，替换消息并增加文本后，watcher 执行；同一 tick 连续两次替换合并为一次回调。该结果解释依赖为何触发，具体滚动位置仍需要浏览器验证。

### 6.2 从实现追问到反例

**面试官：用户本来就在底部，为什么突然不再跟随？**

> 先检查跟随意图在哪个时点判断。当前实现是在新内容渲染后重新测距底部距离。假设用户原来距底部为 0，一次更新让内容增高 120px，新距离就超过 80px，于是代码不再跟随，即使用户没有主动上翻。这是根据当前判断式得到的反例，实际触发还需要浏览器验证。

**面试官：那把阈值改成 200px 呢？**

> 只能改变触发范围，不能区分主动阅读与内容增长。阈值大了，还可能在用户确实上翻时把人拉回去。更合适的是单独保存“是否跟随最新消息”的意图，在用户滚动离开时关闭，回到底部或点击按钮时开启，再在布局变化后按这个意图滚动。
>
> 程序触发的滚动也会产生事件，需要避免它意外改变意图。还应在图片加载、工具卡片展开等高度变化时触发测量；当前只监听业务依赖，没有用内容尺寸观察完整覆盖这些变化。

**面试官：用 ResizeObserver 不就解决了吗？**

> 它能补充“内容尺寸变了”的信号，但不能代替跟随意图。只要高度一变就滚到底部，仍会打断用户阅读。应该让尺寸变化进入合并调度，再根据跟随状态决定是否滚动，清理时断开 observer 和未执行回调。
>
> 持续输出通常采用即时跟随，用户主动点击返回按钮才考虑平滑滚动，并尊重减少动效偏好。当前按钮调用显式 smooth，不能仅凭 CSS 有减少动效规则就认定这条 JS 路径也已处理。

源码：[useAutoScroll](../../app/composables/useAutoScroll.ts)、[ChatPanel](../../app/components/ChatPanel.vue)。

## 7 Markdown 交互与列表身份

**面试官：v-html 生成的复制按钮怎么绑定事件？每次重新绑定吗？**

> 当前在消息容器做点击委托，使用 data-code-copy 和 data-md-file 找到目标。新生成节点会经过同一个父级处理函数，不需要对每次解析出来的按钮逐个绑定。
>
> 但委托只解决事件接入，不保留被替换节点的局部状态。例如复制后的提示文字直接改在按钮 DOM 上，后续 v-html 更新替换了按钮，这个提示也可能丢失。若要让反馈稳定，需要把必要交互状态放到 Vue 可管理的位置或减少无意义的 HTML 替换。

**面试官：列表已经有 key，还会丢组件状态吗？**

> 当前历史 key 优先使用 entry ID，没有时使用 local 加索引；历史重载拿到真实 ID 后，key 可能变化。流式消息也作为独立实例存在，定稿后进入历史列表并不保证沿用原组件。折叠或局部交互状态是否保留，需要结合这些身份变化检查。
>
> 改进时可以维护稳定 UI 消息身份，或把需要保留的交互状态放到按消息身份索引的位置。不要直接给数组索引加个字符串就认为身份稳定，也不必把每个临时 hover 都搬到全局 store。

**面试官：模型生成的 Markdown 放进 v-html 是否安全？**

> 当前 markdown-it 关闭原始 HTML，代码高亮失败会回到转义路径，外链也设置了相关属性。这些是已有措施。v-html 本身不提供安全保证，添加自定义渲染规则、插件或新链接协议时，仍需逐项检查转义和允许的行为。不能因为关闭 html 就忽略后续规则生成的 HTML。

源码：[交互委托](../../app/utils/markdown-interaction.ts)、[Markdown](../../app/utils/markdown.ts)、[消息 key](../../app/components/ChatPanel.vue)。

## 8 这个实现有什么不同

### 8.1 相对只展示文本的聊天页

这里用“用户输入后追加一段流式文本”的简化实现作为对照，不表示其他产品都没有这些能力。

| 对比维度 | 本项目的具体做法 | 面试中值得解释的取舍 |
| --- | --- | --- |
| 运行单位 | 一次任务可以包含多条助手消息、工具执行和压缩 | 文本暂时停止不等于任务完成，状态拆分更多 |
| 输出结构 | 文本、思考和工具参数按内容块组装，结果按调用 ID 配对 | 不能只追加一个字符串，也不能依赖结果紧邻调用 |
| 文件协作 | 消息文件链接打开 Inspector，侧栏文件可引用到输入框 | 对话与本地项目操作形成关联，需要路径解析和服务端访问边界 |
| 用量展示 | 文件累计消耗与当前上下文占用分开 | 让用户区分已花费的 token 与窗口剩余，不把压缩解释成历史删除 |

用量展示一行的来源是 [session-stats.ts](../../shared/lib/session-stats.ts)：`computeSessionStats` 遍历完整 entry 列表累计 token 与成本，`getContextUsage()` 返回的是运行态上下文占用，**这是两个不同口径**。压缩只追加摘要 entry，被汇总的历史仍留在文件里，所以压缩后累计值不会减少 —— 变化的是上下文占用，不是历史记录被删除。相关测试见 [session-stats.test.ts](../../tests/shared/lib/session-stats.test.ts) 与 [usage-format.test.ts](../../tests/app/utils/usage-format.test.ts)。

这些差异说明项目为什么比纯文本演示需要更复杂的前端状态；它们是工程能力，不自动构成算法创新或个人原创成果。

文件协作一行也要补一句安全边界：文件预览的路径校验约束的是**预览这条读路径**，它**不是执行沙箱**，接口没有鉴权，Agent 工具仍在 Node 进程权限下运行。这一边界在 [02 核心模块与工程取舍](02-核心模块与工程取舍.md) 的文件权限一节有完整展开。

### 8.2 相对 pi-web 参考实现

参考实现一列沿用此前的本地 pi-web 对照记录，本项目一列按当前工作区更新。这里用于理解框架适配的差异，参考实现的最新变化需另行核验。

| 维度 | 参考实现 | 本项目 | 判断 |
| --- | --- | --- | --- |
| 状态接入 | React hook 中的 useReducer、state 和 ref | Pinia 组织领域状态，reducer 结果写回 reactive 对象，连接实例放在闭包 | 是框架适配；需要重新检查代理身份和组件清理，不能只翻译语法 |
| Markdown | React Markdown 组件与插件链，消息渲染含大内容保护 | markdown-it + Highlight.js，HTML 注入后使用事件委托 | 渲染与交互路线不同；当前不能据此宣称解析更快或功能等价 |
| 发送失败 | 既有版本对照记录为区分明确拒绝与传输不确定 | 当前区分提示并在传输不确定时重读历史，但仍清理本地运行态 | 有局部补强，仍缺命令身份及完整接受状态对账；不是幂等保证 |
| 滚动跟随 | 流事件处理读取已有的近底部标记，再调度滚动 | 独立 composable，在 DOM 更新后测距底部再决定跟随 | 抽出了 Vue 行为，但判断时机改变，应验证大块增长场景 |

reducer、连接管理、事件裁剪和快照流等已有明确移植来源。**“项目采用了这一机制”与“这个机制由我原创”是两种说法。** 具体来源见 [THIRD_PARTY_NOTICES.md](../../THIRD_PARTY_NOTICES.md)。

**面试官：所以你做得不一样的地方，主要就是换了 Vue？**

> Vue 是技术栈变化，真正需要说明的是接入后哪些约束变了。纯 reducer 可以复用，但结果要写入 Vue 的响应式状态；原本基于普通对象的引用判断，进入代理数组后就需要重新验证。连接实例也没有直接放进 reactive，而是由 store 闭包管理，通过路由生命周期决定关闭。
>
> 渲染同样发生了变化：当前采用 markdown-it 生成 HTML，并在容器做交互委托，所以复制反馈、HTML 替换和稳定消息身份要按这条路线处理。它不是只把 JSX 改成模板，但也不能把适配描述成已经比参考实现更快、更可靠。

**面试官：哪些差异值得保留，哪些能力需要补齐？**

> 可以保留清楚的 Pinia 领域分工，以及连接逻辑和纯 reducer 的分离；Markdown 路线是否继续使用，要看实际功能需求和测量结果。提交后结果不确定的对账、按用户意图滚动这类保护，则应该优先补齐，而不是为了显得不同继续简化。
>
> 判断标准是这个变化是否让当前产品更易维护、行为更正确，并有证据支持。如果只是代码行数少了，却丢掉失败路径，就不能叫优化。个人面试表达应落在自己实际完成并验证的那部分。

## 9 验证方案与面试表达边界

| 层级 | 核心验证 | 当前证据 |
| --- | --- | --- |
| reducer | 文本、思考、工具块组装，快照替换与结束清理 | 有相关单元测试 |
| store | 会话响应顺序、代理回滚、附件快照、草稿合并、终态重连和队列交错 | 有对应测试；真实网络、所有刷新窗口及完整恢复协议不在这些断言范围内 |
| 渲染 | 固定文本下解析调用次数、最终 HTML 与交互一致性 | 本次未做浏览器性能采样 |
| 滚动 | 底部大块增长、主动上翻、图片迟加载、工具展开 | 已分析源码与响应式触发，浏览器行为待验收 |
| 优化队列 | 最后一帧、切会话、快照和结束事件后的旧回调 | 合并方案尚未实现，需随实现补测 |

性能比较使用固定输入与 delta 时间表，分别记录解析耗时、长任务、更新次数和最终输出。不能把网络或模型时间都算到渲染优化上，也不能只凭主观“顺滑”填写提升百分比。

可以作为当前项目回答的主线是：**结构化流式状态、事件与命令分工、工具配对、已有交互和恢复机制**。块缓存、帧级合并、Worker、虚拟列表和改进滚动属于可讨论方案。实际经历应补充本人做过的改动与验证，不把本文中的反例直接改成“我当时遇到并解决了”。

参考测试：[streaming-message.test.ts](../../tests/shared/lib/streaming-message.test.ts)、[chat.test.ts](../../tests/app/stores/chat.test.ts)、[markdown.test.ts](../../tests/app/utils/markdown.test.ts)。

### 如果要产品化，前端这边先做什么

下面几条是从前端视角出发的**候选改进**，与 [01 项目介绍与架构表达](01-项目介绍与架构表达.md) 第 7 节的 P0-P4 方向一致，但**当前都没有实现**。写进面试回答时可以讲思路和判据，不能讲成已经完成的工作。

1. **先建性能基线，再谈优化。** 固定回复内容与固定 delta 时间表，分别记录事件处理与 reducer、Markdown 解析、DOM 提交与布局、滚动四段的耗时，能指出占比最大的一段。这也是 5.2 节判据表能落地的前提；没有基线就只剩主观感受。
2. **给流式块加稳定的块级渲染缓存。** 按消息身份加内容版本建立缓存，命中未变化块，活动块仍做完整解析，并在消息定稿和流实例转历史实例时正确回收。当前 `MessageItem` 里 `v-html="renderMarkdown(block.text)"` 是普通函数调用，没有这层缓存。
3. **等事件序号落地后，用游标做前端对账。** 服务端返回带游标的历史与当前消息，前端记录最后应用的序号；重连或切回会话时按游标比对，缺口显式补拉或提示，而不是靠握手状态和页面活跃标记这两个间接条件推断。
4. **把临时消息身份替换为稳定客户端 ID。** 现在乐观消息靠文本与时间戳做局部匹配，列表 key 还会从临时索引变成 entry ID；稳定 ID 能让去重、失败撤回和交互状态保留各少一类边界。
5. **给滚动换成显式的跟随意图。** 在用户滚动离开时关闭意图，回到底部或点击按钮时开启，再在布局变化后按意图滚动，并把内容尺寸变化纳入合并调度。当前是渲染后测距底部距离再决定是否跟随。
