# 核心模块与工程取舍

本文承接 [项目介绍与架构表达](01-项目介绍与架构表达.md)，围绕核心模块展开技术回答。回答中的改进方案使用将来或条件表述，不替代真实开发经历。

每个主题先讲现有机制，再通过追问说明它的边界。源码说明与口头回答不同：口头先交代数据关系和取舍，面试官要求实现时再展开函数。对应的系统原理集中在 learning 中，避免为了答题把各模块理解成互不关联的知识点。

## 1 工具调用在前端如何组织

> 我的理解是，工具调用同时涉及消息内容和执行状态。消息里保存工具名称、参数和调用 ID，执行事件表示工具何时开始、是否有部分输出以及何时结束。前端需要把两者关联起来，不能只收到工具名就把它当成一次已经完成的操作。
>
> 当前项目在助手消息里渲染工具调用卡片，用运行事件维护活跃工具，再用调用 ID 将最终工具结果配到卡片中。这样既能展示当前正在做什么，也能在任务完成后保留参数和结果。工具结果不再额外显示成一段重复正文。
>
> 还要检查标签与证据是否一致。当前卡片在没有错误、也不处于执行中时默认显示“完成”，这意味着恢复后缺失结果的调用也可能显示完成。因此面试时应说明调用与结果的配对机制，但不能把界面标签直接当成执行成功的证明。

**追问：工具显示耗时，能否当成精确性能指标？**

> 不能直接这样使用。当前消息组件中的部分耗时根据消息时间戳计算，是展示口径，不是完整的工具 tracing。模型输出、工具排队和记录落盘可能处于不同时间点。如果要分析工具性能，需要明确开始结束事件对应的时间，给调用建立稳定标识，再记录真正的执行区间。界面上的一个秒数只能在理解来源后解释，不能直接当作优化前后的性能证据。

**面试官：同名 read 调用两次，结果会不会配错？**

> 工具名表示能力类型，调用 ID 才表示这一次执行。前端用 toolCallId 建立结果索引，不是按工具名查找。实际卡片查询形如 `toolResultsByCallId.get(block.toolCallId)`。如果调用 ID 本身缺失或重复，就要回到事件适配和数据校验检查，不能靠 UI 的显示顺序补救。

源码：[工具卡片](../../app/components/ToolCallCard.vue)、[消息组件](../../app/components/MessageItem.vue)、[进度摘要](../../app/utils/tool-progress.ts)。

## 2 会话记录为什么采用树状关系

> 从数据用途看，对话历史不仅有消息，还可能有模型变化、压缩和分支。每条记录保存 ID 与父记录关系，可以表达某次后续操作基于哪个上下文发生。界面需要展示当前分支时，沿叶节点向上回溯，再转成顺序消息即可。
>
> 当前项目由 SDK 管理这种存储结构，应用层负责读取和转换。这里我会重点说明消息和记录的区别：不是每条记录都应变成气泡，但配置变化记录仍影响当前模型；消息 ID 与记录 ID 也不能随意用数组下标替代。
>
> 这种组织方式为分支提供基础，但基础数据能力和完整功能不是一回事。当前代码能读取活跃历史链，也有服务端导航命令，前端的分支切换和编辑重发流程尚未闭环。因此项目介绍应强调历史恢复，而不是宣称已经完成所有分支交互。

**追问：如果实现编辑历史后重发，关键是什么？**

> 我会先确认编辑对应哪个记录节点，以及新输入应该接到哪个父节点。然后处理界面草稿、服务端当前叶节点和历史展示之间的一致性：操作失败时要保留输入，切换过程中要防止旧请求覆盖新分支。还需要明确运行中是否允许切分支。当前规划选择先限制在稳定状态操作，可以减少与正在执行工具的冲突。单独增加一个编辑按钮并不能完成这项能力。

源码：[历史构建](../../server/utils/session-reader.ts)、[详情接口](../../server/api/sessions/[id].get.ts)。

## 3 上下文压缩与历史记录如何区分

> 我会把模型要消费的上下文和用户要查阅的历史分开。历史用于追溯发生过什么，模型上下文则受窗口限制，需要在持续对话中控制体积。压缩由 SDK 负责，应用提供手动入口、取消动作和状态展示。
>
> 当前压缩结束后，前端重新读取历史并刷新运行时上下文用量。原先的历史记录仍可保存在文件里，所以累计用量不会因为压缩就自动清零；屏幕上还能看到较长对话，也不代表下一次模型请求会原样携带全部历史。
>
> 我认为界面要把这两个概念表达清楚，否则用户可能误以为压缩删除了文件，或者把累计 token 当作窗口占用。当前实现展示压缩开始和结束，没有连续百分比进度；模型摘要质量本身也需要通过任务验证，不能仅凭压缩成功事件推断信息完全保留。

**追问：压缩会不会影响任务质量？**

> 存在信息被省略或表达变化的可能，因此我会用带有明确约束的长任务验证，比如文件路径、已经确认的决策和剩余步骤是否仍能被正确使用。验证应比较压缩前后相同追问的回答与操作，而不是只看 token 减少多少。当前应用主要集成 SDK 的压缩能力，没有独立实现摘要算法或完成质量评测；若要声称“压缩不影响准确率”，必须先定义评估任务和判定标准。

源码：[统计逻辑](../../shared/lib/session-stats.ts)、[压缩与运行状态](../../app/stores/chat.ts)。

## 4 会话实例为什么需要注册表和启动合并

> 命令和事件连接需要操作同一个会话实例。如果每次请求都重新创建 Agent，状态和订阅就可能分散，也会增加配置加载开销。因此当前服务端按 session ID 保存 wrapper，并复用存活对象。
>
> 仅有注册表还不够。两个请求同时发现实例不存在时，可能同时启动，所以又保存进行中的启动 Promise，后续请求等待同一次初始化。新建会话则使用独立临时 key，避免把两个独立创建请求误合并。
>
> 我的判断是，这里要区分实例复用、启动合并和业务幂等。启动合并只保证同一次恢复过程复用对象，不会自动防止同一 prompt 被执行两次。也因为 Map 在内存里，这套实现只在单进程中成立，未来多实例部署需要重新处理会话路由。

**追问：实例缓存能否一直保留？**

> 长期保留可以减少恢复成本，但会占用内存和 SDK 资源。当前包装器用 10 分钟定时器，收到事件会重置，有订阅者时推迟回收。不过回调没有检查 isRunning，所以无订阅者且长时间没有事件的任务也可能被回收。要改进，应先保证执行中的任务不被误清理，再根据空闲实例数量与内存占用设置淘汰策略，不能把现有定时器直接当作完善的空闲检测。

源码：[实例管理](../../server/utils/rpc-manager.ts)、[服务关闭钩子](../../server/plugins/cleanup.ts)。

## 5 本地文件接口的权限如何处理

> 浏览器提供路径时，服务端不能直接按这个路径读取。当前项目先取得允许访问的根目录，再检查规范化后的路径是否在根内，并对现存文件解析真实路径，检查符号链接是否指向范围之外。
>
> 我会把词法校验和真实路径校验分别说明。词法校验处理相对跳转、路径分隔符和同前缀目录；真实路径校验补上符号链接这一层。Windows 下还需要考虑盘符和大小写，不能用一个简单的字符串前缀比较覆盖所有场景。
>
> 同时这只是文件预览 API 的访问规则。项目没有多用户鉴权，允许根也可能包含多个已知会话目录；Agent 的本地命令执行不受同一预览函数约束。因此可以说做了文件接口访问边界，不能说已经实现一个完整安全沙箱。

**追问：如果要开放远程访问，需要补什么？**

> 我会先补身份认证、会话与目录的用户归属，再考虑命令执行隔离和资源限制。只加一个登录页不能解决不同用户共享本地进程、配置和文件的问题。执行环境需要明确权限、可访问目录以及超时等约束，敏感配置接口也要重新审查。这会改变当前本机单用户假设，应该作为运行架构调整来做，而不是简单修改服务监听地址。

源码：[允许根](../../server/utils/file-access.ts)、[路径校验](../../server/utils/path-security.ts)、[文件接口](../../server/api/files/[...path].get.ts)。

## 6 模型配置如何管理草稿和保存

> 当前模型管理把表单草稿放在 Pinia 中，记录 dirty、保存中和错误状态，保存时整份提交给服务端。服务端会清理无效条目、规范化费用字段，再通过临时文件和替换操作写入正式配置。连通性测试使用临时配置，不要求先污染正式文件。
>
> 这套设计分别处理编辑体验、文件完整性和测试隔离。用户可以先修改和测试，再决定保存；写入时避免让其他读取者拿到半截 JSON。但原子替换不等于并发版本控制，两个窗口保存仍可能后写覆盖前写。源码能确认当前没有版本冲突检测，不能仅凭本机使用场景推断这是经过验证后主动接受的取舍。
>
> 我还会区分保存成功和运行时生效。保存后清理模型列表缓存，不代表每个已存在 Agent 实例都已重建。默认模型、当前会话模型和配置里的可用模型也分别对应不同操作。

**追问：要避免多个窗口互相覆盖怎么做？**

> 我会考虑在读取配置时返回版本或内容摘要，保存时携带原版本，服务端只有在版本未变化时才接受覆盖。冲突后让用户重新加载或比较差异。自动字段合并也需要明确语义，例如同一模型被一边删除、另一边修改时不能静默猜测。版本校验解决逻辑冲突，原子替换解决文件写入完整性，两者需要配合，而不是互相替代。

**面试官：比较版本以后再写文件，中间又有别人保存呢？**

> 检查和写入还需要放在同一个串行临界区或具备条件更新语义的存储操作中。否则两个请求都看到旧版本有效，再各自写入，仍会覆盖。对本机文件方案可以在服务层串行化相关写入，但其他进程也写同一文件时还需协作锁或另行约定。这是增强方案，当前的临时文件替换没有提供这层版本事务。

源码：[配置 store](../../app/stores/models-config.ts)、[配置持久化](../../server/utils/models-config-store.ts)、[原子替换](../../server/utils/atomic-file.ts)。

## 7 Skills、Extensions 与 Plugins 如何区分

> 我会从资源形态而不是面板名称来区分。Skill 是指令资源，Extension 是可以参与运行的代码扩展，Plugin 管理的是承载资源的包。一个包可能带来多种资源，所以安装了包不意味着某个工具已经在当前会话完成注册。
>
> 当前应用通过 SDK 加载技能信息，通过静态扫描展示扩展来源和信任状态，通过包管理器执行安装、启停、更新等操作。管理界面需要展示来源和作用域，避免用户不知道一次变更影响的是全局还是项目。
>
> 项目信任是重要的执行边界。查看扩展列表不应直接执行陌生代码；涉及项目包的变更应检查信任。当前源码有这些管理机制，但没有那两个具体自定义工具的实现，所以我会把资源管理作为已完成能力，把新增业务工具作为后续扩展。

**追问：自定义工具接入后如何判断好不好用？**

> 我会同时看输入契约、输出结构和失败反馈。工具参数要能被明确校验，结果要便于模型继续处理，失败要能区分参数错误、无结果和外部服务异常。还需要准备固定任务，观察模型是否在合适时机调用工具，返回结果是否改善后续操作。能注册成功只证明接入路径通了，不能直接证明工具选择质量或任务收益；这些需要另外的实际执行记录。

源码：[技能接口](../../server/api/skills.get.ts)、[扩展读取](../../server/utils/extensions.ts)、[插件管理](../../server/utils/plugins.ts)。

## 8 事件裁剪有哪些收益和代价

> 当前 SDK 增量事件可能携带一份完整 partial 消息。如果每个增量都重复传输不断增长的全文，就会产生额外序列化和网络数据。项目在服务端去掉这部分，同时提前提取工具 ID 和名称，让浏览器仍能定位对应工具块。
>
> 我会将收益表述为减少重复字段和降低前端对 SDK 内部快照结构的依赖。具体降低多少字节、CPU 或耗时，需要对同一组事件测量，不能用直觉填百分比。
>
> 代价是协议适配层承担了更多责任。删除字段前需要确认消费者是否依赖它，SDK 升级后也要检查事件形状是否变化。当前对部分事件做明确转换，其余事件仍可能透传，所以也不能把它描述为全面稳定的自研协议。

**追问：SDK 升级时怎么防止协议适配失效？**

> 我会保留典型文本、思考、工具与错误事件的输入样例，检查裁剪后的字段和 reducer 输出，再用实际 SDK 进行一轮集成验证。尤其要检查工具元数据位置和快照结构，避免类型断言让变化在编译阶段被掩盖。版本锁定能够限制变化频率，但不能替代升级验证。必要时在适配层增加运行时校验和明确错误，而不是让未知结构默默进入组件。

源码：[事件裁剪](../../shared/lib/agent-event-wire.ts)、[裁剪测试](../../tests/shared/lib/agent-event-wire.test.ts)。
