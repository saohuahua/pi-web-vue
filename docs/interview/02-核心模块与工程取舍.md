# 核心模块与工程取舍：从工具卡片到文件和配置

用户看到的每个功能，都对应一组数据关系与失败条件。本篇从工具卡片、历史分支、上下文压缩、文件预览和配置保存出发，解释实现与技术取舍。

每节先看具体场景，再理解状态关系与处理顺序。发送与断线恢复的主链路见 [01 项目介绍](01-项目介绍与架构表达.md)。

## 1 工具调用在前端如何组织

用户要求“检查接口为什么失败”，Agent 先读取路由文件，再读取配置文件，最后执行测试。页面上有两次同名 `read`，但参数和结果不同，测试还可能持续输出。卡片需要回答三件事：模型准备调用什么、当前执行到哪里、最终返回什么。

### 核心处理：调用内容、实时状态、最终结果分别保存

| 数据 | 来自哪里 | 页面用途 |
| --- | --- | --- |
| 工具名称、调用 ID、参数 | 助手消息中的工具调用块 | 显示这次调用的目标和参数 |
| 开始、进度、结束 | 工具执行事件 | 显示当前活跃工具和实时摘要 |
| 最终结果或错误 | `toolResult` 消息 | 保留执行结果并配回调用卡片 |

store 将最终结果组织成以调用 ID 为键的索引：

遍历当前完整消息，挑出工具结果，用每次调用的唯一 ID 建立查询索引。工具卡片拿自己的调用 ID 查结果，而不是按工具名或数组中的相邻位置查找。这样两次同名工具调用即使结果到达顺序变化，也有各自的对应关系。

消息组件根据 `block.toolCallId` 取结果。两次 `read` 可以有相同工具名，但只要调用 ID 不同，结果就能正确关联。这个 Map 是基于消息列表计算出的索引，并非一份独立持久数据；消息变化时会重新计算，不能直接称为增量缓存。

实时执行另外放在 `activeTools`。开始时按 ID 插入，进度事件更新已有项，结束时删除。最终工具消息仍留在历史里，因此“从活跃工具删除”表示不再执行，不表示结果消失。

### 面试官：为什么不把工具事件直接拼成一条消息

> 工具调用同时涉及消息内容和执行状态。消息里保存工具名称、参数和调用 ID，执行事件表示工具何时开始、是否有部分输出以及何时结束。前端需要把两者关联起来，不能只收到工具名就把它当成一次已经完成的操作。
>
> 当前项目在助手消息里渲染工具调用卡片，用运行事件维护活跃工具，再用调用 ID 将最终工具结果配到卡片中。这样既能展示当前正在做什么，也能在任务完成后保留参数和结果。工具结果不再额外显示成一段重复正文。
>
> 还要检查标签与证据是否一致。当前卡片在没有错误、也不处于执行中时默认显示“完成”，这意味着恢复后缺失结果的调用也可能显示完成。因此面试时应说明调用与结果的配对机制，但不能把界面标签直接当成执行成功的证明。

**追问：工具显示耗时，能否当成精确性能指标？**

> 不能直接这样使用。当前消息组件中的部分耗时根据消息时间戳计算，是展示口径，不是完整的工具 tracing。模型输出、工具排队和记录落盘可能处于不同时间点。如果要分析工具性能，需要明确开始结束事件对应的时间，给调用建立稳定标识，再记录真正的执行区间。界面上的一个秒数只能在理解来源后解释，不能直接当作优化前后的性能证据。

**面试官：同名 read 调用两次，结果会不会配错？**

> 工具名表示能力类型，调用 ID 才表示这一次执行。前端用 toolCallId 建立结果索引，不是按工具名查找。实际卡片查询形如 `toolResultsByCallId.get(block.toolCallId)`。如果调用 ID 本身缺失或重复，就要回到事件适配和数据校验检查，不能靠 UI 的显示顺序补救。

## 2 会话记录为什么采用树状关系

用户修改上一轮的问题后，希望保留旧回答，又从修改后的问题生成新回答。数组只能表达当前展示顺序，父记录关系才能表达“这个回答基于哪个上下文产生”。同一父节点可以接出不同后续分支，界面选择当前叶节点后，沿父链回溯出当前路径，再映射成消息列表。

### 面试官：为什么要区分消息与会话记录

> 从数据用途看，对话历史不仅有消息，还可能有模型变化、压缩和分支。每条记录保存 ID 与父记录关系，可以表达某次后续操作基于哪个上下文发生。界面需要展示当前分支时，沿叶节点向上回溯，再转成顺序消息即可。
>
> 当前项目由 SDK 管理这种存储结构，应用层负责读取和转换。消息和记录的区别在于：不是每条记录都应变成气泡，但配置变化记录仍影响当前模型；消息 ID 与记录 ID 也不能随意用数组下标替代。
>
> 当前已接入分支切换和编辑重发：找到旧问题的父记录，预览目标，导航并重读权威详情，确认叶节点后再提交新文本。导航失败尝试对账和回退，位置无法确认时禁止发送。这个范围有代码和 store 测试支持，但不等于任意多窗口并发编辑都有事务保证。

**追问：为什么不直接改消息数组，然后重新发送？**

> 先区分屏幕上的消息和模型下一次真正消费的上下文。直接改数组只改变显示，服务端仍可能位于旧回答之后，新请求会携带错误历史。当前通过记录 ID 找旧问题的父节点，再改变服务端位置并读取确认；运行中、压缩中、导航中或位置未确认时禁止启动这类操作。失败后还要保留输入并确认回退结果，不能仅恢复前端选中态。这样虽然比替换数组多了请求，但每一步对应一个具体风险：目标无效、位置改变未确认、旧响应覆盖或者新输入丢失。

**追问：为什么沿用 JSONL 记录树，不直接换数据库？**

> 这是 SDK 已有的会话存储形态，应用在其上读取和导航。当前本机工作台需要恢复会话和追溯分支，沿用记录 ID、父子关系和文件结构能够避免同时维护两份权威历史。数据库可以提供更强的查询、索引和事务能力，但引入以后还要决定 SDK 文件与数据库谁说了算，是否双写、怎样处理失败与迁移。若需求变成跨用户检索、大量会话统计或多实例协作，可以重新评估持久化接口；现在没有基准证明文件读取是瓶颈，不会仅因数据库听起来更完整就替换存储。

源码：[历史构建](../../server/utils/session-reader.ts)、[详情接口](../../server/api/sessions/[id].get.ts)、[导航流程](../../app/composables/useSessionNavigation.ts)。分步案例见 [03 项目亮点与贡献说明](03-项目亮点与贡献说明.md)。

## 3 上下文压缩与历史记录如何区分

会话持续很久，用户看到完整历史，但模型窗口快满了。点击压缩后，界面仍应能查到发生过的事情，同时下一次模型请求使用压缩后的上下文。这个场景里有三个不同的量：文件里存了多少记录、下一次模型要读取多少上下文、历史模型调用累计消耗多少 token。

### 面试官：压缩会删除聊天历史吗

> 把模型要消费的上下文和用户要查阅的历史分开。历史用于追溯发生过什么，模型上下文则受窗口限制，需要在持续对话中控制体积。压缩由 SDK 负责，应用提供手动入口、取消动作和状态展示。
>
> 当前压缩结束后，前端重新读取历史并刷新运行时上下文用量。原先的历史记录仍可保存在文件里，所以累计用量不会因为压缩就自动清零；屏幕上还能看到较长对话，也不代表下一次模型请求会原样携带全部历史。
>
> 界面需要把这两个概念表达清楚，否则用户可能误以为压缩删除了文件，或者把累计 token 当作窗口占用。当前实现展示压缩开始和结束，没有连续百分比进度；模型摘要质量本身也需要通过任务验证，不能仅凭压缩成功事件推断信息完全保留。

**追问：压缩会不会影响任务质量？**

> 存在信息被省略或表达变化的可能，因此需要用带有明确约束的长任务验证，比如文件路径、已经确认的决策和剩余步骤是否仍能被正确使用。验证应比较压缩前后相同追问的回答与操作，而不是只看 token 减少多少。当前应用主要集成 SDK 的压缩能力，没有独立实现摘要算法或完成质量评测；若要声称“压缩不影响准确率”，必须先定义评估任务和判定标准。

源码：[统计逻辑](../../shared/lib/session-stats.ts)、[压缩与运行状态](../../app/stores/chat.ts)。

## 4 会话实例为什么需要注册表和启动合并

打开一个历史会话时，事件订阅和运行状态查询可能几乎同时到达服务端。如果两个接口各自恢复 SDK，会出现两个实例：命令发给一个，浏览器监听另一个。注册表确保同一会话复用实例，启动中的 Promise 则处理实例还没创建完的并发窗口。

```text
请求一检查实例不存在 → 保存启动中的 Promise → 开始恢复
请求二检查实例不存在 → 找到同一个 Promise → 等待
恢复完成             → 两个请求取得同一个实例
```

只缓存成功后的实例，挡不住恢复期间的重复创建。反过来，如果创建失败后不清理启动中的失败 Promise，后续重试会不断拿到同一个失败结果。因此需要同时考虑已完成实例与正在进行的初始化。

### 面试官：缓存实例与合并启动有什么区别

> 命令和事件连接需要操作同一个会话实例。如果每次请求都重新创建 Agent，状态和订阅就可能分散，也会增加配置加载开销。因此当前服务端按 session ID 保存 wrapper，并复用存活对象。
>
> 仅有注册表还不够。两个请求同时发现实例不存在时，可能同时启动，所以又保存进行中的启动 Promise，后续请求等待同一次初始化。新建会话则使用独立临时 key，避免把两个独立创建请求误合并。
>
> 这里要区分实例复用、启动合并和业务幂等。启动合并只保证同一次恢复过程复用对象，不会自动防止同一 prompt 被执行两次。也因为 Map 在内存里，这套实现只在单进程中成立，未来多实例部署需要重新处理会话路由。

**追问：实例缓存能否一直保留？**

> 长期保留可以减少恢复成本，但会占用内存和 SDK 资源。当前包装器用 10 分钟定时器，收到事件会重置，有订阅者时推迟回收。不过回调没有检查 isRunning，所以无订阅者且长时间没有事件的任务也可能被回收。要改进，应先保证执行中的任务不被误清理，再根据空闲实例数量与内存占用设置淘汰策略，不能把现有定时器直接当作完善的空闲检测。

源码：[实例管理](../../server/utils/rpc-manager.ts)、[服务关闭钩子](../../server/plugins/cleanup.ts)。

## 5 本地文件接口的权限如何处理

用户点击回答里的 `src/api.ts`，Inspector 请求本地文件。这个路径来自浏览器输入，服务端需要判断它是否属于允许目录。以允许根 `D:\work\demo` 为例：

| 请求路径 | 直接字符串前缀的问题 | 正确处理需要检查什么 |
| --- | --- | --- |
| `D:\work\demo\src\api.ts` | 正常子路径 | 规范化后位于根内 |
| `D:\work\demo-backup\secret.txt` | 裸前缀也会匹配 demo | 根后必须有目录分隔边界 |
| `D:\work\demo\..\secret.txt` | 原始文本看起来以根开头 | resolve 后的实际层级 |
| 根内链接指向根外文件 | 词法路径仍在根内 | realpath 后的真实目标 |

### 核心处理：先规范化，再比较目录边界

词法检查需要先把路径转成统一形式，再按目录边界判断包含关系：

判断允许访问有两种情况：目标就是允许根本身，或者目标以“允许根加目录分隔符”为开头。补上分隔符，是为了拒绝名称相似的兄弟目录。比较前还要解析相对跳转，并按平台统一路径分隔符和大小写规则。

现存文件再用 `realpathSync` 解析目标和允许根，把真实路径交给同一词法检查。目标不存在直接拒绝，已失效的根不参与允许集合。这样分别处理路径文本逃逸和符号链接逃逸。

### 面试官：为什么前端限制只能点击项目内文件还不够

> 浏览器提供路径时，服务端不能直接按这个路径读取。当前项目先取得允许访问的根目录，再检查规范化后的路径是否在根内，并对现存文件解析真实路径，检查符号链接是否指向范围之外。
>
> 把词法校验和真实路径校验分别说明。词法校验处理相对跳转、路径分隔符和同前缀目录；真实路径校验补上符号链接这一层。Windows 下还需要考虑盘符和大小写，不能用一个简单的字符串前缀比较覆盖所有场景。
>
> 同时这只是文件预览 API 的访问规则。项目没有多用户鉴权，允许根也可能包含多个已知会话目录；Agent 的本地命令执行不受同一预览函数约束。因此可以说做了文件接口访问边界，不能说已经实现一个完整安全沙箱。

**追问：如果要开放远程访问，需要补什么？**

> 先补身份认证、会话与目录的用户归属，再考虑命令执行隔离和资源限制。只加一个登录页不能解决不同用户共享本地进程、配置和文件的问题。执行环境需要明确权限、可访问目录以及超时等约束，敏感配置接口也要重新审查。这会改变当前本机单用户假设，应该作为运行架构调整来做，而不是简单修改服务监听地址。

## 6 模型配置如何管理草稿和保存

用户修改模型地址，点击测试，确认可连通后再保存。测试失败时仍应保留正在编辑的内容，正式配置也不应提前变成不可用地址。因此编辑草稿、临时测试和正式保存是三个动作，不能把每次输入都立即写入正式文件。

```text
读取正式配置 → 创建可编辑草稿 → 用户修改
                                ├→ 临时连通性测试 → 显示结果
                                └→ 保存 → 服务端规范化 → 临时文件 → 替换正式文件
```

测试回答“这份待保存配置能否连通”，保存回答“正式配置是否已落盘”，运行实例是否使用新配置还取决于其刷新和重建逻辑。三个成功状态不能互相代替。

### 面试官：保存配置为什么还要写临时文件

> 当前模型管理把表单草稿放在 Pinia 中，记录 dirty、保存中和错误状态，保存时整份提交给服务端。服务端会清理无效条目、规范化费用字段，再通过临时文件和替换操作写入正式配置。连通性测试使用临时配置，不要求先污染正式文件。
>
> 这套设计分别处理编辑体验、文件完整性和测试隔离。用户可以先修改和测试，再决定保存；写入时避免让其他读取者拿到半截 JSON。但原子替换不等于并发版本控制，两个窗口保存仍可能后写覆盖前写。源码能确认当前没有版本冲突检测，不能仅凭本机使用场景推断这是经过验证后主动接受的取舍。
>
> 我还会区分保存成功和运行时生效。保存后清理模型列表缓存，不代表每个已存在 Agent 实例都已重建。默认模型、当前会话模型和配置里的可用模型也分别对应不同操作。

**追问：要避免多个窗口互相覆盖怎么做？**

> 可以考虑在读取配置时返回版本或内容摘要，保存时携带原版本，服务端只有在版本未变化时才接受覆盖。冲突后让用户重新加载或比较差异。自动字段合并也需要明确语义，例如同一模型被一边删除、另一边修改时不能静默猜测。版本校验解决逻辑冲突，原子替换解决文件写入完整性，两者需要配合，而不是互相替代。

**面试官：比较版本以后再写文件，中间又有别人保存呢？**

> 检查和写入还需要放在同一个串行临界区或具备条件更新语义的存储操作中。否则两个请求都看到旧版本有效，再各自写入，仍会覆盖。对本机文件方案可以在服务层串行化相关写入，但其他进程也写同一文件时还需协作锁或另行约定。这是增强方案，当前的临时文件替换没有提供这层版本事务。

## 7 Skills、Extensions 与 Plugins 如何区分

用户在能力中心看到一个安装包，包里可能同时包含指令资源和可执行扩展。查看包已安装，只能说明资源已经取得；当前会话是否加载、是否信任项目代码、是否注册工具，还要看各自的运行流程。

### 面试官：安装了一个 Skill 就等于新增工具吗

> 资源的区别在于它提供指令、代码还是安装载体。Skill 是指令资源，Extension 是可以参与运行的代码扩展，Plugin 管理的是承载资源的包。一个包可能带来多种资源，所以安装了包不意味着某个工具已经在当前会话完成注册。
>
> 当前应用通过 SDK 加载技能信息，通过静态扫描展示扩展来源和信任状态，通过包管理器执行安装、启停、更新等操作。管理界面需要展示来源和作用域，避免用户不知道一次变更影响的是全局还是项目。
>
> 项目信任是重要的执行边界。查看扩展列表不应直接执行陌生代码；涉及项目包的变更应检查信任。当前源码有这些管理机制，但自定义业务工具仍需另外实现输入校验、执行逻辑和输出契约。

**追问：自定义工具接入后如何判断好不好用？**

> 需要同时检查输入契约、输出结构和失败反馈。工具参数要能被明确校验，结果要便于模型继续处理，失败要能区分参数错误、无结果和外部服务异常。还需要准备固定任务，观察模型是否在合适时机调用工具，返回结果是否改善后续操作。能注册成功只证明接入路径通了，不能直接证明工具选择质量或任务收益；这些需要另外的实际执行记录。

源码：[技能接口](../../server/api/skills.get.ts)、[扩展读取](../../server/utils/extensions.ts)、[插件管理](../../server/utils/plugins.ts)。

## 8 事件裁剪有哪些收益和代价

模型不断返回文本片段，每个片段如果还附带当前完整消息，那么第十次会重复带前九次内容，第一百次又带前九十九次内容。页面只需用 delta 更新状态，重复全文会增加序列化和传输工作。

### 核心处理：先提取仍需的工具身份，再删除全文

处理一个增量事件时，先从它携带的全文快照中找到对应工具块，取出调用 ID 和工具名称；再删除重复全文，把工具身份和原有增量字段一起发送给浏览器。文本事件不需要额外工具身份，就只保留原有增量字段。

不能直接删 `partial` 就结束，因为部分工具开始与参数增量的 ID、名称位于全文快照对应块里。先读取它们并提升到客户端事件，reducer 才能知道正在拼哪一次工具调用。

如果简化假设每次新增一个等长片段，连续发送累计全文的字符量近似为 `1 + 2 + ... + n` 个片段；只传增量约为 `n` 个片段，再加必要快照和结束消息。这解释了减少重复传输的原因，实际字节和耗时仍需对具体事件样本测量。

### 面试官：裁剪之后怎么保证前端还能还原

> 当前 SDK 增量事件可能携带一份完整 partial 消息。如果每个增量都重复传输不断增长的全文，就会产生额外序列化和网络数据。项目在服务端去掉这部分，同时提前提取工具 ID 和名称，让浏览器仍能定位对应工具块。
>
> 直接收益是减少重复字段和降低前端对 SDK 内部快照结构的依赖。具体降低多少字节、CPU 或耗时，需要对同一组事件测量，不能用直觉填百分比。
>
> 代价是协议适配层承担了更多责任。删除字段前需要确认消费者是否依赖它，SDK 升级后也要检查事件形状是否变化。当前对部分事件做明确转换，其余事件仍可能透传，所以也不能把它描述为全面稳定的自研协议。

**追问：SDK 升级时怎么防止协议适配失效？**

> 可以保留典型文本、思考、工具与错误事件的输入样例，检查裁剪后的字段和 reducer 输出，再用实际 SDK 进行一轮集成验证。尤其要检查工具元数据位置和快照结构，避免类型断言让变化在编译阶段被掩盖。版本锁定能够限制变化频率，但不能替代升级验证。必要时在适配层增加运行时校验和明确错误，而不是让未知结构默默进入组件。

源码：[事件裁剪](../../shared/lib/agent-event-wire.ts)、[裁剪测试](../../tests/shared/lib/agent-event-wire.test.ts)。

## 9 为什么 reducer 和 Pinia 同时存在

页面同时收到文本、工具参数和运行状态。文本拼接需要确定性的数据变换；发送请求、保存草稿和关闭连接则有副作用。把两类工作拆开，才能在不建立网络连接时验证内容组装，也能单独控制网络时序测试 store。

**面试官：都用 Pinia 了，直接修改状态不是更简单吗？**

> 两者分别负责数据变换和业务副作用。文本、思考、工具参数按块组装，输入是旧状态和事件，输出是新状态，这部分适合纯 reducer，能用固定序列反复演算；请求何时发送、连接何时关闭、错误怎样提示以及切会话后结果还能否提交，则属于 store 的业务时序。直接在 store 修改也能做，但会把内容拼接和网络生命周期混在一起，测试一个参数分片都可能要准备连接。当前分层的代价是多一次状态适配，且仍有数组复制和字符串追加成本，所以我讲可测试性和职责清晰，不把纯函数说成天然更快。

**追问：为啥不直接一个文本字符串，要设计内容块？**

> 一条实际输出可能是：先有思考，再有正文，然后出现工具调用参数，工具完成后模型继续回答。这里存在不同类型、不同结束时点和调用身份，仅靠一个字符串无法知道哪部分是待解析参数、哪个结果属于哪次工具执行。当前按内容索引更新块，用调用 ID 关联工具结果，参数未完整时保存原始片段，最终再使用结构化参数。代价是事件模型更复杂，需要测试缺少块、快照替换和结束清理；但这些复杂度来自业务内容本身。只展示纯文本的演示可以更简单，不需要提前照搬整套结构。

## 10 为什么 Markdown 选择 HTML 渲染，而不是组件树

回答里出现标题、代码块和本地文件链接。当前渲染器输出 HTML，消息容器统一监听点击，识别代码复制或文件打开操作。这让不断生成的新节点共用一个交互入口，同时带来 HTML 替换后的局部状态维护问题。

**面试官：markdown-it 加 v-html 有什么取舍？**

> 当前走的是 Markdown 转 HTML，再通过容器事件委托处理代码复制和本地文件链接。这种方式把文本解析集中在渲染器，组件不用为每个语法节点创建专门的 Vue 组件；但代价是 HTML 子树不由普通 Vue 模板逐项管理，复制反馈和折叠状态可能在替换时丢失，安全也要检查转义和自定义链接规则。如果改成语法树到 Vue 组件，可以更自然地绑定节点交互，但要增加映射、身份维护和组件复杂度。两者没有现成的性能胜负证据。可以根据交互需求和实际采样决定，当前先保证最终渲染一致，再评估缓存与组件化。

**追问：既然整段解析可能慢，为什么不一开始就上 Worker 和虚拟列表？**

> 先判断慢在哪一层。Worker 针对可搬离主线程的解析计算，虚拟列表针对大量 DOM，两者解决的问题不同。如果瓶颈是短时间重复解析活动代码块，先减少重复工作可能比跨线程传文本更直接；如果卡在布局，搬走解析未必有用。虚拟列表还会增加可变高度、代码折叠、查找和滚动锚点的维护成本。当前没有性能基线支撑这些投入，所以先用固定内容与固定事件节奏测解析、渲染和布局，再选最小有效方案。把它们作为条件成立时的备选，而不是把所有优化名词都列成项目已完成能力。
