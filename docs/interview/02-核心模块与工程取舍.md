# 核心模块与工程取舍：从工具卡片到文件和配置

用户看到的每个功能，都对应一组数据关系与失败条件。本篇从工具卡片、历史分支、上下文压缩、文件预览和配置保存出发，解释实现与技术取舍。

## 1 工具调用在前端如何组织 [P1]

用户要求“检查接口为什么失败”，Agent 先读取路由文件，再读取配置文件，最后执行测试。页面上有两次同名 `read`，但参数和结果不同，测试还可能持续输出。卡片需要回答三件事：模型准备调用什么、当前执行到哪里、最终返回什么。

**核心结论：** 工具调用是三层数据——调用身份与参数在助手消息的工具调用块里，实时执行状态在 `activeTools`，最终结果在 `toolResult` 消息里。三层只用 `toolCallId` 配对，不按工具名、也不按数组中的相邻位置查找。

### 核心处理：调用内容、实时状态、最终结果分别保存

| 数据 | 来自哪里 | 页面用途 |
| --- | --- | --- |
| 工具名称、调用 ID、参数 | 助手消息中的工具调用块 | 显示这次调用的目标和参数 |
| 开始、进度、结束 | 工具执行事件 | 显示当前活跃工具和实时摘要 |
| 最终结果或错误 | `toolResult` 消息 | 保留执行结果并配回调用卡片 |

store 将最终结果组织成以调用 ID 为键的索引：遍历当前完整消息，挑出工具结果，用每次调用的唯一 ID 建立查询索引。工具卡片拿自己的调用 ID 查结果，而不是按工具名或数组中的相邻位置查找，所以两次同名工具调用即使结果到达顺序变化，也各有自己的对应关系。

消息组件按 `block.toolCallId` 取结果，两次 `read` 工具名相同、调用 ID 不同就能正确关联。这个 Map 是基于消息列表计算出的索引，不是一份独立持久数据：消息变化时会重新计算，不能称为增量缓存。

实时执行另外放在 `activeTools`：开始时按 ID 插入，进度事件更新已有项，结束时删除。最终工具消息仍留在历史里，所以「从活跃工具删除」表示不再执行，不表示结果消失。

### 追问：三个容易混淆的工具调用边界

- **不要把工具事件直接拼成一条消息。** 工具调用同时涉及消息内容和执行状态：消息里保存工具名称、参数和调用 ID，执行事件表示工具何时开始、是否有部分输出以及何时结束，前端必须把两者关联起来，不能只收到工具名就把它当成一次已经完成的操作。当前项目在助手消息里渲染工具卡片，用运行事件维护活跃工具，再用调用 ID 把最终结果配回卡片，这样既能展示当前正在做什么，也能在任务完成后保留参数和结果，工具结果不再额外显示成一段重复正文。**但界面标签不能当作执行成功的证明**：卡片在没有错误、也不处于执行中时默认显示「完成」，恢复后缺失结果的调用也会显示完成。
- **耗时不能当作精确性能指标。** 消息组件里的部分耗时按消息时间戳计算，是展示口径，不是完整的工具 tracing；模型输出、工具排队和记录落盘可能处于不同时间点。要分析工具性能，需要明确开始结束事件对应的时间、给调用建立稳定标识、再记录真正的执行区间。
- **同名 `read` 不会配错结果。** 工具名表示能力类型，调用 ID 才表示这一次执行，卡片查询形如 `toolResultsByCallId.get(block.toolCallId)`。如果调用 ID 本身缺失或重复，就要回到事件适配和数据校验检查，不能靠 UI 的显示顺序补救。

## 2 会话记录为什么采用树状关系 [P1]

用户修改上一轮的问题后，希望保留旧回答，又从修改后的问题生成新回答。数组只能表达当前展示顺序，父记录关系才能表达“这个回答基于哪个上下文产生”。同一父节点可以接出不同后续分支，界面选择当前叶节点后，沿父链回溯出当前路径，再映射成消息列表。

**核心结论：** 历史不是数组而是带父记录的树：父链决定「这次回答基于哪个上下文」，叶节点决定界面显示哪条分支。SDK 管理记录树，应用层只负责沿父链回溯、映射成消息列表，再按记录 ID 做导航。

### 面试官：为什么要区分消息与会话记录

> 从数据用途看，对话历史不仅有消息，还可能有模型变化、压缩和分支。每条记录保存 ID 与父记录关系，可以表达某次后续操作基于哪个上下文发生。界面需要展示当前分支时，沿叶节点向上回溯，再转成顺序消息即可。
>
> 当前项目由 SDK 管理这种存储结构，应用层负责读取和转换。消息和记录的区别在于：不是每条记录都应变成气泡，但配置变化记录仍影响当前模型；消息 ID 与记录 ID 也不能随意用数组下标替代。
>
> 当前已接入分支切换和编辑重发：找到旧问题的父记录，预览目标，导航并重读权威详情，确认叶节点后再提交新文本。导航失败尝试对账和回退，位置无法确认时禁止发送。这个范围有代码和 store 测试支持，但不等于任意多窗口并发编辑都有事务保证。

**追问：为什么不直接改消息数组，然后重新发送？**

> 先区分屏幕上的消息和模型下一次真正消费的上下文。直接改数组只改变显示，服务端仍可能位于旧回答之后，新请求会携带错误历史。当前通过记录 ID 找旧问题的父节点，再改变服务端位置并读取确认；运行中、压缩中、导航中或位置未确认时禁止启动这类操作。失败后还要保留输入并确认回退结果，不能仅恢复前端选中态。这样虽然比替换数组多了请求，但每一步对应一个具体风险：目标无效、位置改变未确认、旧响应覆盖或者新输入丢失。

## 3 上下文压缩与历史记录如何区分 [P1]

会话持续很久，用户看到完整历史，但模型窗口快满了。点击压缩后，界面仍应能查到发生过的事情，同时下一次模型请求使用压缩后的上下文。

**核心结论：** 压缩改的是模型下一次要消费的上下文，不改文件里的聊天历史：压缩只追加一条摘要记录，被汇总的旧记录仍在文件里。所以「历史还在」与「下次请求不再原样携带全部历史」同时成立，累计用量不会因为压缩清零。

### 面试官：压缩会删除聊天历史吗

> 把模型要消费的上下文和用户要查阅的历史分开。历史用于追溯发生过什么，模型上下文则受窗口限制，需要在持续对话中控制体积。压缩由 SDK 负责，应用提供手动入口、取消动作和状态展示。
>
> 当前压缩结束后，前端重新读取历史并刷新运行时上下文用量。原先的历史记录仍可保存在文件里，所以累计用量不会因为压缩就自动清零；屏幕上还能看到较长对话，也不代表下一次模型请求会原样携带全部历史。
>
> 界面需要把这两个概念表达清楚，否则用户可能误以为压缩删除了文件，或者把累计 token 当作窗口占用。当前实现展示压缩开始和结束，没有连续百分比进度；模型摘要质量本身也需要通过任务验证，不能仅凭压缩成功事件推断信息完全保留。

**追问：压缩会不会影响任务质量？**

> 存在信息被省略或表达变化的可能，因此需要用带有明确约束的长任务验证，比如文件路径、已经确认的决策和剩余步骤是否仍能被正确使用。验证应比较压缩前后相同追问的回答与操作，而不是只看 token 减少多少。当前应用主要集成 SDK 的压缩能力，没有独立实现摘要算法或完成质量评测；若要声称“压缩不影响准确率”，必须先定义评估任务和判定标准。

### 追问：点一次压缩，前端怎么知道结束了

> 前端只发一条 `compact` 命令，本地先把 isCompacting 置为 true 做按钮反馈。命令的 HTTP 返回不代表压缩完成，真正的结束信号是 `compaction_end` 或 `auto_compaction_end` 事件；收到结束事件后重新读历史、再拉一次运行态，于是累计值和上下文占用一起刷新。
>
> 取消压缩走的是另一条命令 `abort_compaction`，服务端调到 `abortCompaction()`。它和「停止本次回答」的 `abort` 是两个动作，源码注释里也写明前端必须分开调用。

前端（`app/composables/useSessionRuntime.ts`）：

```ts
// 压缩结果由事件落定 HTTP 接纳不代表压缩结束
const compact = async () => {
  const id = dependencies.sessionId.value;
  if (!id || dependencies.isCompacting.value) return;
  const generation = dependencies.generation();
  dependencies.isCompacting.value = true;
  try {
    await sendAgentCommand(id, { type: "compact" });
  } catch (error) {
    if (dependencies.sessionId.value !== id || generation !== dependencies.generation()) return;
    dependencies.isCompacting.value = false;
    dependencies.notice(error instanceof Error ? error.message : String(error));
  }
};
```

服务端分发（`server/utils/rpc-manager.ts`）：

```ts
case "compact":
  try {
    return await this.inner.compact(command.customInstructions as string | undefined);
  } finally {
    invalidateSessionListCache();
  }

case "abort_compaction":
  // 压缩中止与 agent 停止是两个动作 前端必须分开调用
  this.inner.abortCompaction();
  return null;
```

压缩开始与结束的状态在前端只改一个 `isCompacting`：`compaction_start` 与 `auto_compaction_start` 置 true，`compaction_end` 与 `auto_compaction_end` 置 false 并同时触发重新读历史和刷新运行态。

> 界面上还有几个 token 数字，口径完全不同不能相加。三种口径、各自的数据来源与刷新时机见篇末「深入参考（P2）」。

## 4 会话实例为什么需要注册表和启动合并 [P1]

打开一个历史会话时，事件订阅和运行状态查询可能几乎同时到达服务端。如果两个接口各自恢复 SDK，会出现两个实例：命令发给一个，浏览器监听另一个。注册表确保同一会话复用实例，启动中的 Promise 则处理实例还没创建完的并发窗口。

```text
请求一检查实例不存在 → 保存启动中的 Promise → 开始恢复
请求二检查实例不存在 → 找到同一个 Promise → 等待
恢复完成             → 两个请求取得同一个实例
```

只缓存成功后的实例，挡不住恢复期间的重复创建。反过来，如果创建失败后不清理启动中的失败 Promise，后续重试会不断拿到同一个失败结果。因此需要同时考虑已完成实例与正在进行的初始化。

**核心结论：** 服务端按 session ID 保存 `AgentSessionWrapper`，并用「已完成实例注册表 + 进行中的启动 Promise」两级复用，保证同一会话只有一个执行对象；新建会话用一次性临时 key，避免两个独立创建请求被误合并。这套结构在内存里，只在单进程成立。

### 面试官：缓存实例与合并启动有什么区别

> 命令和事件连接需要操作同一个会话实例。如果每次请求都重新创建 Agent，状态和订阅就可能分散，也会增加配置加载开销。因此当前服务端按 session ID 保存 wrapper，并复用存活对象。
>
> 仅有注册表还不够。两个请求同时发现实例不存在时，可能同时启动，所以又保存进行中的启动 Promise，后续请求等待同一次初始化。新建会话则使用独立临时 key，避免把两个独立创建请求误合并。
>
> 这里要区分实例复用、启动合并和业务幂等。启动合并只保证同一次恢复过程复用对象，不会自动防止同一 prompt 被执行两次。也因为 Map 在内存里，这套实现只在单进程中成立，未来多实例部署需要重新处理会话路由。

**代价与边界：**

- **空闲回收的判据是「没人监听」，不是「没在跑」。** 长期保留实例可以减少恢复成本，但会占用内存和 SDK 资源。包装器用 10 分钟定时器，收到事件会重置，有订阅者时推迟回收。但回收回调只检查 `listeners.size`，没有检查 `isRunning()`，所以无订阅者且长时间没有事件的任务也可能被回收。要改进，应先保证执行中的任务不被误清理，再根据空闲实例数量与内存占用设置淘汰策略，不能把现有定时器直接当作完善的空闲检测。
- **接纳串行不是幂等。** `promptAdmissionTail` 把每次 prompt 排进一条串行链，保证接纳判断按顺序执行，`clear_queue` 也要等这条链，才能拿到 SDK 尚未消费的队列。它约束的是同一个 wrapper 内的接纳顺序，既不跨进程，也不阻止同一条 prompt 被提交两次。

## 5 本地文件接口的权限如何处理 [P1]

用户点击回答里的 `src/api.ts`，Inspector 请求本地文件。这个路径来自浏览器输入，服务端需要判断它是否属于允许目录。以允许根 `D:\work\demo` 为例：

| 请求路径 | 直接字符串前缀的问题 | 正确处理需要检查什么 |
| --- | --- | --- |
| `D:\work\demo\src\api.ts` | 正常子路径 | 规范化后位于根内 |
| `D:\work\demo-backup\secret.txt` | 裸前缀也会匹配 demo | 根后必须有目录分隔边界 |
| `D:\work\demo\..\secret.txt` | 原始文本看起来以根开头 | resolve 后的实际层级 |
| 根内链接指向根外文件 | 词法路径仍在根内 | realpath 后的真实目标 |

**核心结论：** 文件接口的边界是「路径必须落在允许根内」，分两层校验：规范化后的词法比较负责相对跳转、分隔符和同前缀目录，`realpathSync` 负责符号链接。它只约束文件预览这条读路径，**不等于执行沙箱**。

### 核心处理：先规范化，再比较目录边界

词法检查需要先把路径转成统一形式，再按目录边界判断包含关系：

判断允许访问有两种情况：目标就是允许根本身，或者目标以“允许根加目录分隔符”为开头。补上分隔符，是为了拒绝名称相似的兄弟目录。比较前还要解析相对跳转，并按平台统一路径分隔符和大小写规则。

现存文件再用 `realpathSync` 解析目标和允许根，把真实路径交给同一词法检查。目标不存在直接拒绝，已失效的根不参与允许集合。这样分别处理路径文本逃逸和符号链接逃逸。

### 面试官：为什么前端限制只能点击项目内文件还不够

> 浏览器提供路径时，服务端不能直接按这个路径读取。当前项目先取得允许访问的根目录，再检查规范化后的路径是否在根内，并对现存文件解析真实路径，检查符号链接是否指向范围之外。
>
> 把词法校验和真实路径校验分别说明。词法校验处理相对跳转、路径分隔符和同前缀目录；真实路径校验补上符号链接这一层。Windows 下还需要考虑盘符和大小写，不能用一个简单的字符串前缀比较覆盖所有场景。
>
> 同时这只是文件预览 API 的访问规则。项目没有多用户鉴权，允许根也可能包含多个已知会话目录；Agent 的本地命令执行不受同一预览函数约束。因此可以说做了文件接口访问边界，不能说已经实现一个完整安全沙箱。

### 面试官：项目信任（project trust）是不是一个工具沙箱

> 不是。它回答的是「要不要信任这个仓库带来的资源」，不是「Agent 允许做什么」。

用一句话记住边界：**trust 决定 `.pi/` 下的项目级扩展、技能、插件能不能加载和修改；命令执行不在这套判定里。**

| 问题 | project trust 回答吗 | 真正的约束在哪 |
| --- | --- | --- |
| 这个仓库的项目级扩展、技能、插件能不能加载 | 是 | `readTrustDecision` 读 `<agentDir>/trust.json`，沿父目录向上找最近的决定 |
| 项目作用域的插件能不能安装、卸载、更新 | 是 | `runPluginAction` 在未信任时直接抛 403 |
| Agent 能不能执行命令 | 否 | 与信任无关，命令在 Node 进程权限下运行 |
| 能不能读某个目录的文件 | 否 | 文件接口另有允许根与 realpath 校验 |
| 命令能跑多久、占多少资源 | 否 | 现有超时都在外围操作上，Agent 命令没有对应限制 |

信任决定本身的读法很短，也值得背下来：

```ts
// 沿父目录向上找最近的信任决定 插件包管理等其他能力也依赖它判断 project 作用域是否可写
export function readTrustDecision(agentDir: string, cwd: string): boolean {
  const trustPath = join(agentDir, "trust.json");
  if (!existsSync(trustPath)) return false;
  try {
    const data = JSON.parse(readFileSync(trustPath, "utf8")) as Record<string, unknown>;
    let current = normalizeTrustPath(cwd);
    while (true) {
      const value = Object.entries(data).find(([key]) => normalizeTrustPath(key) === current)?.[1];
      if (value === true || value === false) return value;
      const parent = dirname(current);
      if (parent === current) return false;
      current = parent;
    }
  } catch {
    return false;
  }
}
```

几个要点：

- **查表有三条分支，函数最终只返回布尔值。** 沿父目录向上找最近的一条记录：显式 true 直接信任，显式 false 直接拒绝，一直找到盘符根都没有记录也返回 false。也就是说「没有记录」和「明确拒绝」在返回值上一样，但这是两种不同的事实，讲的时候要分开。
- **读信任状态不执行项目代码。** `listExtensions` 用它给项目扩展标 `needs-trust` 或 `ready`，`statusFor` 只在「项目作用域且未信任」时降级。测试还断言读一次 trust.json 不会顺手创建 SDK 的锁目录（`trust.json.lock` 不存在）。
- **写信任只有一条路径。** `PATCH /api/capabilities/project-trust` 要求 cwd 在允许根内，再经 `ProjectTrustStore(getAgentDir()).set(cwd, true)` 写入 `<agentDir>/trust.json`，源码注释写明「信任决定只写入 Pi 自己的 trust.json 不会执行项目扩展」。
- **查看和授予是两件事。** `server/utils/skills.ts` 为了能把项目技能列全，显式传 `projectTrusted: true`，同时注释说明「静态查看项目技能不授予扩展执行或安装权限」。这正好说明 trust 管的是加载与写入许可，不是运行权限。
- **插件包的那条 403 是最硬的一处。** `runPluginAction` 里，project 作用域的 install / remove 直接拒绝；不带 source 的全量 update 在存在 project 包时也拒绝，而不是静默跳过——源码注释写明「全量更新会触及 project 包 未信任时拒绝而不是静默跳过」。

> 照读答案：project trust 是资源授权，不是沙箱。它决定 `.pi/` 下的项目级扩展、技能、插件能不能加载、能不能改，回答的是「要不要信任这个仓库带来的代码」；它不决定 Agent 能执行什么命令、能读哪些目录、能跑多久。所以信任之后，扩展代码和 Agent 执行的命令跑在同一个 Node 进程权限下，没有容器、没有目录白名单、也没有单独的执行超时。这部分边界与 [01 的安全边界](01-项目介绍与架构表达.md) 是同一件事，我只是在资源加载这一侧再确认一次。

## 6 模型配置如何管理草稿和保存 [P1]

用户修改模型地址，点击测试，确认可连通后再保存。测试失败时仍应保留正在编辑的内容，正式配置也不应提前变成不可用地址。因此编辑草稿、临时测试和正式保存是三个动作，不能把每次输入都立即写入正式文件。

```text
读取正式配置 → 创建可编辑草稿 → 用户修改
                                ├→ 临时连通性测试 → 显示结果
                                └→ 保存 → 服务端规范化 → 临时文件 → 替换正式文件
```

**核心结论：** 编辑草稿留在 Pinia，连通性测试写临时目录，保存时服务端先清理无效条目、规范化费用字段，再通过临时文件和替换写正式文件。测试回答「这份待保存配置能否连通」，保存回答「正式配置是否已落盘」，运行实例是否使用新配置还取决于它的刷新和重建逻辑：三个成功状态不能互相代替。

### 面试官：保存配置为什么还要写临时文件

> 当前模型管理把表单草稿放在 Pinia 中，记录 dirty、保存中和错误状态，保存时整份提交给服务端。服务端会清理无效条目、规范化费用字段，再通过临时文件和替换操作写入正式配置。连通性测试使用临时配置，不要求先污染正式文件。
>
> 这套设计分别处理编辑体验、文件完整性和测试隔离。用户可以先修改和测试，再决定保存；写入时避免让其他读取者拿到半截 JSON。但原子替换不等于并发版本控制，两个窗口保存仍可能后写覆盖前写。源码能确认当前没有版本冲突检测，不能仅凭本机使用场景推断这是经过验证后主动接受的取舍。
>
> 我还会区分保存成功和运行时生效。保存后清理模型列表缓存，不代表每个已存在 Agent 实例都已重建。默认模型、当前会话模型和配置里的可用模型也分别对应不同操作。

**源码：** [配置 store](../../app/stores/models-config.ts)、[配置持久化](../../server/utils/models-config-store.ts)、[原子替换](../../server/utils/atomic-file.ts)。多窗口并发的两种追问合并放在篇末「深入参考（P2）」。

## 7 Skills、Extensions 与 Plugins 如何区分 [P1]

用户在能力中心看到一个安装包，包里可能同时包含指令资源和可执行扩展。查看包已安装，只能说明资源已经取得；当前会话是否加载、是否信任项目代码、是否注册工具，还要看各自的运行流程。

**核心结论：** 三者的交付物不同：**Extension 交付代码，Skill 交付指令，插件包只是安装载体。** 当前项目做到的是资源发现与管理界面；**本仓库里没有任何工具注册代码，自定义业务工具没有实现**。

### 面试官：安装了一个 Skill 就等于新增工具吗

> 资源的区别在于它提供指令、代码还是安装载体。Skill 是指令资源，Extension 是可以参与运行的代码扩展，Plugin 管理的是承载资源的包。一个包可能带来多种资源，所以安装了包不意味着某个工具已经在当前会话完成注册。
>
> 当前应用通过 SDK 加载技能信息，通过静态扫描展示扩展来源和信任状态，通过包管理器执行安装、启停、更新等操作。管理界面需要展示来源和作用域，避免用户不知道一次变更影响的是全局还是项目。
>
> 项目信任是重要的执行边界。查看扩展列表不应直接执行陌生代码；涉及项目包的变更应检查信任。当前源码有这些管理机制，但自定义业务工具仍需另外实现输入校验、执行逻辑和输出契约。

**追问：自定义工具接入后如何判断好不好用？**

> 需要同时检查输入契约、输出结构和失败反馈。工具参数要能被明确校验，结果要便于模型继续处理，失败要能区分参数错误、无结果和外部服务异常。还需要准备固定任务，观察模型是否在合适时机调用工具，返回结果是否改善后续操作。能注册成功只证明接入路径通了，不能直接证明工具选择质量或任务收益；这些需要另外的实际执行记录。

### 面试官：扩展、插件包、技能这三种机制到底差在哪

> 一句话区分：**Extension 交付代码，Skill 交付指令，插件包只是安装载体。** 三者不是一套东西的三个名字，一个插件包里可以同时带扩展、技能、提示词和主题。

| 机制 | 是什么 | 当前项目做到哪一步 |
| --- | --- | --- |
| Extension（扩展） | Pi 的扩展 API。扩展文件被加载后能注册工具、钩子、命令，交付物是可执行代码 | 只做**静态目录扫描并列出**，标记 `needs-trust` 或 `ready`；不执行、不注册 |
| 插件包（package / plugin） | SDK 包管理器管理的安装单元。一个包可以同时贡献 extensions、skills、prompts、themes 四类资源 | 静态解析资源计数与包状态，并且真的执行安装、卸载、更新、启停 |
| Skill（技能） | Markdown 描述的能力包，交付的是给模型看的指令，不是工具 | 经 SDK 的 `loadSkills` 列出，可切换 `disable-model-invocation`，会话内以 `skill:` 前缀出现在斜杠命令里 |
| MCP | 外部工具服务的接入协议 | **完全未接入**，能力中心是空状态 |

三条链路各自的落地情况：

- **Extension 是代码，当前只被列出。** `server/utils/extensions.ts` 扫两个目录：全局 `~/.pi/agent/extensions` 和项目 `<cwd>/.pi/extensions`。识别规则是后缀为 `.ts/.js/.mjs/.cjs` 的单文件，或者带 `package.json` 且声明了 `pi.extensions`（退一步有 `index.ts`）的目录。全局条目恒为 `ready`，项目条目在未信任时标 `needs-trust`。
- **插件包是载体，管理动作是真的。** `server/utils/plugins.ts` 用 SDK 的 `DefaultPackageManager` 解析 settings 里配置的包，按四类资源分别计数。注意 disable 的实现是把四类资源数组同时清空，所以四个数组都为空就等于禁用；资源计数只统计 `enabled` 且 `origin === "package"` 的条目，顶层目录里的散装资源不算任何包。
- **Skill 是指令。** `/api/skills` 走 `listSkills`：先用包管理器解析已安装资源，再用 `loadSkills` 读 frontmatter 和正文。`PATCH /api/skills` 只改 frontmatter 里的 `disable-model-invocation`，而且必须先确认这个文件是已发现的技能——测试专门断言授权根里的普通文件不能冒充技能被写。
- **MCP 未接入。** `app/components/capabilities/McpPanel.vue` 只有一个 `PiEmptyState`，标题就是「尚未接入 MCP Bridge」，说明里写明 Pi 不提供原生 MCP 服务注册表。

扫描函数本身就是「不执行」这条约束的证据：

```ts
// 只做静态目录扫描 不能为了列出扩展而执行项目代码
export function listExtensions(cwd: string, options: ScanOptions = {}): ExtensionsResponse {
  const agentDir = options.agentDir ?? getAgentDir();
  const trust = options.projectTrusted ?? readTrustDecision(agentDir, cwd);
  const extensions = [
    ...scanRoot(join(agentDir, "extensions"), "global", true),
    ...scanRoot(join(cwd, ".pi", "extensions"), "project", trust),
  ].sort((a, b) => collator.compare(a.name, b.name) || collator.compare(a.filePath, b.filePath));
```

测试是用「会抛错的扩展文件」来验证这一点的：fixture 里的 `audit.ts` 内容就是 `throw new Error('must not run')`，扫描照常返回结果。

**重点结论：本仓库里没有任何工具注册代码。** `server/utils/extensions.ts` 通篇只有扫描与状态判断，没有工具定义、没有参数 schema、没有执行逻辑；整个 `server/` 下也搜不到 `registerTool`、`defineTool`、`customTools` 这类调用，会话创建只是 `createAgentSessionFromServices({ services, sessionManager })`，没有传自定义工具。所以**「自定义业务工具」在当前仓库里没有实现，已经实现的是资源发现与安装这条链路**。谁加载扩展文件由 SDK 的资源加载器在会话创建时决定，而本仓库既不提供扩展文件（仓库根下没有 `.pi/` 目录），也不为扩展注册出来的工具写任何校验和测试。这是简历上最容易被说过头的一句话。

> 照读答案：这三种机制的差别在于交付物是什么。Skill 交付指令，进的是提示词和斜杠命令；Extension 交付参与运行的代码，加载后可以注册工具和钩子；插件包只是安装载体，一个包里可能同时带指令和代码，所以「包已安装」既不代表技能已被加载，也不代表某个工具已经注册。当前项目做到的是资源管理：技能走 SDK 的 `loadSkills` 列出来，扩展走静态目录扫描列出来，插件走包管理器读列表并执行安装、卸载、启停。这里有一个必须说清的边界——本仓库里没有任何工具注册代码，没有工具定义、参数 schema 和执行逻辑，所以自定义业务工具在当前仓库里没有实现，我做过的是资源发现和管理界面。

**追问：那这个项目到底有没有可用工具？**

> 有，但都是 SDK 自带的。`get_tools` 命令返回的就是会话当前的工具列表和每一项的激活状态，应用层只做展示，不定义工具，也不改工具的输入输出。斜杠命令面板同理：`get_commands` 只把提示词模板和技能拼成命令列表，源码注释写明「pi-web 还有扩展注册命令 本项目不启用扩展 只有模板与技能」。

## 8 事件裁剪有哪些收益和代价 [P1]

模型不断返回文本片段，每个片段如果还附带当前完整消息，那么第十次会重复带前九次内容，第一百次又带前九十九次内容。页面只需用 delta 更新状态，重复全文会增加序列化和传输工作。

**核心结论：** 服务端在推送前删掉增量事件里那份不断增长的完整快照，同时先把工具 id 与名称提升到事件顶层，让浏览器仍能定位工具块。收益是去掉重复序列化与传输，代价是协议适配层要自己承担字段契约的维护。

### 核心处理：先提取仍需的工具身份，再删除全文

处理一个增量事件时，先从它携带的全文快照中找到对应工具块，取出调用 ID 和工具名称；再删除重复全文，把工具身份和原有增量字段一起发送给浏览器。文本事件不需要额外工具身份，就只保留原有增量字段。

不能直接删 `partial` 就结束，因为部分工具开始与参数增量的 ID、名称位于全文快照对应块里。先读取它们并提升到客户端事件，reducer 才能知道正在拼哪一次工具调用。

如果简化假设每次新增一个等长片段，连续发送累计全文的字符量近似为 `1 + 2 + ... + n` 个片段；只传增量约为 `n` 个片段，再加必要快照和结束消息。这解释了减少重复传输的原因，实际字节和耗时仍需对具体事件样本测量。

### 面试官：裁剪之后怎么保证前端还能还原

> 当前 SDK 增量事件可能携带一份完整 partial 消息。如果每个增量都重复传输不断增长的全文，就会产生额外序列化和网络数据。项目在服务端去掉这部分，同时提前提取工具 ID 和名称，让浏览器仍能定位对应工具块。
>
> 直接收益是减少重复字段和降低前端对 SDK 内部快照结构的依赖。具体降低多少字节、CPU 或耗时，需要对同一组事件测量，不能用直觉填百分比。
>
> 代价是协议适配层承担了更多责任。删除字段前需要确认消费者是否依赖它，SDK 升级后也要检查事件形状是否变化。当前对部分事件做明确转换，其余事件仍可能透传，所以也不能把它描述为全面稳定的自研协议。

**追问：SDK 升级时怎么防止协议适配失效？**

> 可以保留典型文本、思考、工具与错误事件的输入样例，检查裁剪后的字段和 reducer 输出，再用实际 SDK 进行一轮集成验证。尤其要检查工具元数据位置和快照结构，避免类型断言让变化在编译阶段被掩盖。版本锁定能够限制变化频率，但不能替代升级验证。必要时在适配层增加运行时校验和明确错误，而不是让未知结构默默进入组件。

## 9 为什么 reducer 和 Pinia 同时存在 [P1]

页面同时收到文本、工具参数和运行状态。文本拼接需要确定性的数据变换；发送请求、保存草稿和关闭连接则有副作用。把两类工作拆开，才能在不建立网络连接时验证内容组装，也能单独控制网络时序测试 store。

**核心结论：** 内容归并是确定性的数据变换，交给纯函数 reducer，不建连接就能用固定事件序列反复演算；请求时机、连接生命周期、错误提示和切会话守卫是业务副作用，留在 Pinia。讲的是职责分离和可测试性，不是纯函数天然更快。

### 面试官：都用 Pinia 了，直接修改状态不是更简单吗？

> 两者分别负责数据变换和业务副作用。文本、思考、工具参数按块组装，输入是旧状态和事件，输出是新状态，这部分适合纯 reducer，能用固定序列反复演算；请求何时发送、连接何时关闭、错误怎样提示以及切会话后结果还能否提交，则属于 store 的业务时序。直接在 store 修改也能做，但会把内容拼接和网络生命周期混在一起，测试一个参数分片都可能要准备连接。当前分层的代价是多一次状态适配，且仍有数组复制和字符串追加成本，所以我讲可测试性和职责清晰，不把纯函数说成天然更快。

**追问：为啥不直接一个文本字符串，要设计内容块？**

> 一条实际输出可能是：先有思考，再有正文，然后出现工具调用参数，工具完成后模型继续回答。这里存在不同类型、不同结束时点和调用身份，仅靠一个字符串无法知道哪部分是待解析参数、哪个结果属于哪次工具执行。当前按内容索引更新块，用调用 ID 关联工具结果，参数未完整时保存原始片段，最终再使用结构化参数。代价是事件模型更复杂，需要测试缺少块、快照替换和结束清理；但这些复杂度来自业务内容本身。只展示纯文本的演示可以更简单，不需要提前照搬整套结构。

源码：[消息 reducer](../../shared/lib/streaming-message.ts)、[消息组件](../../app/components/MessageItem.vue)。

## 10 Nuxt 全栈工程怎样分层 [P1]

打开一个历史会话会同时发生好几件事：浏览器渲染消息、Nitro 收下 SSE 连接、Node 里恢复 SDK 会话、本地文件被读出来。先分清谁在哪里跑，再谈为什么这么切。

| 目录 | 跑在哪里 | 什么时候执行 | 能 import 什么 |
| --- | --- | --- | --- |
| `app/` | 浏览器 | 用户操作与事件到达时 | Vue、Pinia、`#shared/lib`；不能 import Pi SDK |
| `server/api/` | Nitro（Node 进程） | HTTP 请求或 SSE 连接到达时 | `#shared/lib`、`server/utils` |
| `server/utils/` | Nitro（Node 进程） | 被路由或 SSE 流调用时 | Pi SDK、`node:*` |
| `shared/lib/` | 两边各打包一份 | 谁 import 谁执行 | 纯函数与类型；不允许 import Pi 包 |

**核心结论：** 浏览器只跑 `app/`，`server/api/**` 与 `server/utils/**` 都在同一个 Node 进程里由 Nitro 执行，`shared/lib/**` 是一份被两端各打包一次的源码。所以关掉 SSR 只是不给页面做服务端渲染，服务端能力仍然在同一个工程里，不需要再补一个独立 Express 服务。

要点：

- **`shared/` 不是第三个进程，也不是一个服务。** 它只是一份同时被两端 import 的源码：`app/stores/chat.ts` 用它归并事件，`server/utils/session-reader.ts` 用它算统计。同一份代码在浏览器产物里就是普通前端模块，在 Node 里就是普通服务端模块。
- **这条约束的来由是打包位置。** 共享层一旦 import 了 Pi 包，浏览器那一份就会把 SDK 拖进前端产物，所以 `shared/lib/**` 只放纯函数与类型——`shared/lib/types.ts` 里的 `SessionStatsInfo` 就是两端同源的类型定义。
- **别名是 Nuxt 给的。** `~` 指 `app/`，`#shared/lib/...` 指 `shared/lib/...`（映射写在 Nuxt 生成的 tsconfig 里）。写代码时不需要相对路径跳来跳去。
- **Nitro 还提供进程级生命周期钩子。** `server/plugins/cleanup.ts` 挂在 Nitro 的 `close` 钩子上销毁全部会话实例，让 SDK 有机会落盘清理。这类钩子是「服务端是一段常驻 Node 进程」的直接证据。

### 面试官：关了 SSR，为什么还需要 Nuxt，不另起一个 Express 服务

> 关掉的是「页面 HTML 由谁渲染」，不是服务端能力。`ssr: false` 之后页面在浏览器渲染，但 `server/api/**` 仍然由 Nitro 在 Node 里执行：HTTP 命令、SSE 事件流、读写本地文件、创建 SDK 会话都在这一侧。既然服务端能力已经在同一个工程里，就不需要再补一个独立 Express 服务，也不用维护两套启动、路由和接口约定。
>
> 收益是省掉水合相关的麻烦：`EventSource` 和 `localStorage` 都只存在于浏览器，开着 SSR 就要额外处理它们的初始化时序，而这个工作台没有 SEO 与首屏需求。代价也要说清：没有服务端渲染与 SEO；前端初始化时序要自己管（例如打开会话必须先等 SSE 握手完成再发 prompt，见 [01 的发送链路](01-项目介绍与架构表达.md)）；`devServer` 固定绑 `127.0.0.1`，只服务本机。

| 决定 | 收益 | 代价 |
| --- | --- | --- |
| `ssr: false` | 不用处理 EventSource 与 localStorage 的水合麻烦，也没有为零收益的 SSR 付复杂度 | 没有 SSR 与 SEO，前端初始化顺序要自己保证 |
| `devServer` 绑 `127.0.0.1` | Windows 上 `localhost` 只解析到 `::1` 时 `curl 127.0.0.1` 仍能连上 | 只服务本机，与「无鉴权因此不要暴露」的边界一致 |

### 面试官：Pi SDK 的打包配置为什么值得单独说

> 因为 SDK 是纯 ESM 的重包，还内嵌 WASM。如果让它进 Nitro 的打包流程，构建期就要处理它内部的原生资源与模块格式。当前在 `nuxt.config.ts` 里把四个 `@earendil-works/*` 包和 `undici` 排除出 Nitro 打包，运行时从 node_modules 原样加载，等价于 pi-web 在 next.config.ts 里的 serverExternalPackages。

```ts
nitro: {
  // pi SDK 是纯 ESM 且内嵌 WASM photon 的重包
  // 必须排除出 Nitro 打包 运行时从 node_modules 原样加载
  // 等价于 pi-web next.config.ts 的 serverExternalPackages
  externals: {
    external: [
      "@earendil-works/pi-coding-agent",
      "@earendil-works/pi-agent-core",
      "@earendil-works/pi-ai",
      "@earendil-works/pi-tui",
      "undici",
    ],
  },
},
```

配套约束一共四条，面试时按被问到的方向展开：

1. **四个 Pi 包版本锁在一起**，都是 `0.85.1`，升级要一起升。
2. **Node 版本要求 `>= 22.19.0`**，写在 `package.json` 的 `engines` 里。
3. **SDK 服务创建有一层重试**：`server/utils/agent-services.ts` 只对 `~/.pi/agent` 锁文件相关的瞬时错误重试，其他错误原样抛出，避免掩盖真实故障。
4. **运行时仍需要这几个包存在**：排除出打包意味着由 Node 按 ESM 自己解析它们，所以本机开发流程是 `npm run dev` 直接跑，而不是产出一个自包含的单文件服务。

这一节只讲本项目真正用到的部分，不展开 Nuxt 与 Nitro 的完整机制。想深入看 [C01 Nuxt 工程与 Nitro 服务端](../learning/后端基础/C01-Nuxt工程与Nitro服务端.md)；为什么选 Nuxt 而不是 Vite 加独立 Node 服务，见 [01 第 5 节](01-项目介绍与架构表达.md)。

**源码：** [Nuxt 配置](../../nuxt.config.ts)、[依赖与 Node 版本](../../package.json)、[SDK 服务创建与重试](../../server/utils/agent-services.ts)、[共享类型](../../shared/lib/types.ts)、[进程关闭钩子](../../server/plugins/cleanup.ts)。

## 深入参考（P2）

以下条目是低频 API 比较、逐分支的假设推演和源码级细节。**技术结论与正文同等有效，只是查到即可，不作为默认复习任务。** 原第 10 节「Markdown 选择 HTML 渲染」整体移入本区，正文编号保持不变。

**① Token 的三种口径**

至少三个口径，回答三个不同的问题，不能互相换算，更不能相加：

| 口径 | 数据来源 | 谁刷新它 | 压缩之后会怎样 |
| --- | --- | --- | --- |
| 文件里的累计消耗 | `computeSessionStats(entries)` 遍历完整 entry 列表，把消息与压缩摘要的 usage 相加 | 刷新会话详情 `reload()`，也就是 `agent_settled`、`compaction_end` 这类事件之后 | 不会减少，只增不减 |
| 当前上下文窗口占用 | 运行中 agent 的 `getContextUsage()`，经 `get_state` 命令返回 `{ percent, contextWindow, tokens }` | 运行态快照 `refreshRuntimeState()` | 会下降，压缩要解决的就是它 |
| 历史记录条数 | 同一份 entry 列表里的 `userMessages`、`assistantMessages`、`toolCalls`、`toolResults`、`totalMessages` | 与文件累计来自同一份统计 | 不会减少，摘要 entry 只追加不删除 |

三个口径分别回答：**这次会话一共花了多少**、**下一次请求还能塞进多少**、**历史上发生过多少条消息**。

还有第四个容易混的量是屏幕上显示的消息条数：它只算当前分支，未激活分支的消息会进文件累计但不显示。`buildSessionContext` 按叶节点切出消息列表，统计却按完整 entries 计算，这两个口径本来就不该相等。

代码把这条边界写死了：

```ts
const stats = ref<SessionStatsInfo | null>(null); // 文件累计 usage 与运行态 context 是两项指标

// 会话使用量的文件累计
// compaction 只追加摘要 entry 被汇总的历史仍留在文件里 因此累计值单调增长
// 与运行态的 context usage 是两项独立指标 前端不得相加
export interface SessionStatsInfo {
```

界面上的写法也是分开的：使用量弹层里「会话累计」一组列出输入、输出、缓存读、缓存写和成本，「当前上下文」单独一项，就是为了避免用户把它们加起来。

`tests/shared/lib/session-stats.test.ts` 把「压缩后累计不减」这条口径钉住了：

- 压缩摘要 entry 的 usage 会计进 `tokens` 与 `cost`，但不计进消息数。
- 未激活分支的消息同样计进合计。
- 缺 usage 的旧会话不抛错也不累计。

> 照读答案：这套界面里有三个不同的量。文件里的累计消耗来自完整 entry 列表，压缩只是追加一条摘要记录，旧记录还在文件里，所以它只增不减；当前上下文占用来自运行中 agent 的 `getContextUsage()`，压缩之后确实会下降；历史记录条数说的是发生过多少条记录，不代表下一次请求要读多少条。前端分别用会话详情接口和运行态快照刷新这两项，源码注释里明确写了它们不能相加。

源码：[统计逻辑](../../shared/lib/session-stats.ts)、[共享类型](../../shared/lib/types.ts)、[累计统计测试](../../tests/shared/lib/session-stats.test.ts)、[压缩与运行状态](../../app/stores/chat.ts)、[运行态与命令封装](../../app/composables/useSessionRuntime.ts)。

**② 模型配置的多窗口并发写入（两个追问合并）**

- **要避免多个窗口互相覆盖**：可以在读取配置时返回版本或内容摘要，保存时携带原版本，服务端只有在版本未变化时才接受覆盖。冲突后让用户重新加载或比较差异。自动字段合并也需要明确语义，例如同一模型被一边删除、另一边修改时不能静默猜测。版本校验解决逻辑冲突，原子替换解决文件写入完整性，两者需要配合，而不是互相替代。
- **比较版本以后再写文件，中间又有别人保存**：检查和写入还需要放在同一个串行临界区，或者使用具备条件更新语义的存储操作。否则两个请求都看到旧版本有效，再各自写入，仍会覆盖。对本机文件方案可以在服务层串行化相关写入，但其他进程也写同一文件时还需协作锁或另行约定。这是增强方案，当前的临时文件替换没有提供这层版本事务。

源码：[配置持久化](../../server/utils/models-config-store.ts)、[原子替换](../../server/utils/atomic-file.ts)、[配置 store](../../app/stores/models-config.ts)。

**③ Project trust 的源码级推演**

**需要作者核实的一点：** 会话创建路径里 `SettingsManager.create(sessionCwd, agentDir)` 没有传 `projectTrusted`（[实例管理](../../server/utils/rpc-manager.ts)），而 SDK 0.85.1 里这个默认值是 `true`（`node_modules/@earendil-works/pi-coding-agent/dist/core/settings-manager.js` 的 `fromStorageWithPaths` 里写着 `options.projectTrusted ?? true`）。同时 `listExtensions` 与 `plugins.ts` 都是显式传信任决定的。也就是说能力中心显示的 `needs-trust`，与会话内实际加载哪些项目资源，可能不是同一套判定。这里只有源码阅读，没有实测加载结果，面试前需要作者核实；如果确实不一致，那更说明 trust 不是安全边界。

源码：[信任判定与扫描](../../server/utils/extensions.ts)、[插件包信任分支](../../server/utils/plugins.ts)。

**④ 会话记录为什么沿用 JSONL 记录树，不直接换数据库**

这是 SDK 已有的会话存储形态，应用在其上读取和导航。当前本机工作台需要恢复会话和追溯分支，沿用记录 ID、父子关系和文件结构能够避免同时维护两份权威历史。数据库可以提供更强的查询、索引和事务能力，但引入以后还要决定 SDK 文件与数据库谁说了算，是否双写、怎样处理失败与迁移。若需求变成跨用户检索、大量会话统计或多实例协作，可以重新评估持久化接口；现在没有基准证明文件读取是瓶颈，不会仅因数据库听起来更完整就替换存储。

源码：[历史构建](../../server/utils/session-reader.ts)、[详情接口](../../server/api/sessions/[id].get.ts)。

**⑤ 如果开放远程访问，需要补什么**

先补身份认证、会话与目录的用户归属，再考虑命令执行隔离和资源限制。只加一个登录页不能解决不同用户共享本地进程、配置和文件的问题。执行环境需要明确权限、可访问目录以及超时等约束，敏感配置接口也要重新审查。这会改变当前本机单用户假设，应该作为运行架构调整来做，而不是简单修改服务监听地址。这一条与正文第 5 节是同一层安全边界的不同侧面。

源码：[允许根](../../server/utils/file-access.ts)、[路径校验](../../server/utils/path-security.ts)、[文件接口](../../server/api/files/[...path].get.ts)。

**⑥ Markdown 为什么输出 HTML，而不是组件树**

- **当前做法**：`markdown-it` 以 `html: false` 把 Markdown 转成 HTML，消息容器用 `v-html` 挂进 `.markdown-body`。代码复制按钮和本地文件链接都在 HTML 里，只能靠容器上的事件委托 `handleMarkdownClick` 处理。
- **收益**：文本解析集中在渲染器，组件不用为每个语法节点创建专门的 Vue 组件，不断生成的新节点共用一个交互入口。
- **代价**：HTML 子树不由普通 Vue 模板逐项管理，替换时复制反馈和折叠状态可能丢失；安全上要自己检查转义和自定义链接规则。
- **备选方案**：改成语法树到 Vue 组件，可以更自然地绑定节点交互，但要增加映射、节点身份维护和组件复杂度。两者没有现成的性能胜负证据，可以按交互需求和实际采样决定。
- **Worker 与虚拟列表是条件成立的备选，不是已完成能力**：Worker 针对可搬离主线程的解析计算，虚拟列表针对大量 DOM，两者解决的问题不同。当前没有性能基线支撑这些投入，先测解析、渲染和布局，再选最小有效方案。

源码：[Markdown 渲染器](../../app/utils/markdown.ts)、[消息组件](../../app/components/MessageItem.vue)、[交互委托](../../app/utils/markdown-interaction.ts)。

**⑦ 前端真的卡了，按什么顺序定位**

先拿数据再决定改什么，顺序固定四步：

1. **分段计时**，别只测总时长：等待握手、事件处理与 reducer、Markdown 解析与高亮、组件提交与布局、滚动，各记一段。
2. **固定复现条件**：固定回复内容与固定 delta 节奏，避免把模型自己变慢误判成前端卡顿。
3. **按占比选最小改动**：解析重复为主就先减少重复解析，历史 DOM 规模为主才谈虚拟化，解析本身占满主线程才谈 Worker。
4. **改完复测同一组条件**，不要拿界面手感当验收。

每一步的判据、条件成立时的备选方案以及各自的代价，见 [05 前端流式对话实现与优化](05-前端流式对话实现与优化.md) 的第 5 节与篇末「深入参考（P2）」的候选优化表，这里只留顺序，不重复细节。更细的分层观察表见 [04 第 9 节](04-验证方案与源码索引.md)。进一步的前端专题见 [05 前端专题](05-前端流式对话实现与优化.md)。
