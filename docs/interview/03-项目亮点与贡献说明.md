## 1 带图发送：为什么提交时要保存快照 [P1]

**核心结论：** 发送要回答的不是“请求有没有发出去”，而是**本次任务拥有哪一份输入**。所以文本与附件在点击发送时固化成提交快照，成功后只清理属于这一批的附件，失败只撤回仍属于这一批的乐观气泡，晚到的结果按会话身份与代次丢弃。代价是这份快照只是浅拷贝，临时消息也还没有稳定 ID。

### 问题：先把反馈做出来，回滚就成了三处坑

用户输入“分析这张报错截图”，附上图片 A，点击发送。冷启动时握手可能需要等待，界面先展示用户气泡能让操作立即有反馈。等待过程中，用户还可能添加图片 B，或者切到另一个会话。这时问题已经不只是“把请求发出去”，还包括本次请求究竟拥有哪份输入。

早期先追加气泡、失败再回滚的方案改善了反馈，但后续逐步补上了三个问题：

| 初始处理 | 可构造的反例 | 后续改动 |
| --- | --- | --- |
| 用数组末尾对象与原始乐观对象比较 | Vue 从响应式数组读出代理，引用比较不相等，气泡撤不掉 | 用 `toRaw` 比较 |
| Composer 清空图片，store 再读图片 | store 读到空数组，带图输入变成仅文字 | 显式传入附件快照，成功后只移除本批附件 |
| 异步完成后继续写共享状态 | A 提交后切 B 再回 A，旧失败清除新任务状态 | 保存会话 ID 与代次，在关键 await 后检查 |

### 最终方案：提交快照、定向清理、有归属的撤回

1. **点击发送时固定本批输入。** 把这一批文字与附件列表交给提交逻辑，后续请求使用这份提交快照，不重新读取已经可能被用户修改的附件列表。这里是浅拷贝数组：只固定本次包含哪些附件对象，不复制整份图片数据，因此它不提供任意对象字段修改后的深度隔离。
2. **成功后只清理这一批。** 把当前附件列表与本批快照比较，只移除属于这次提交的附件；比较对象身份前先用 `toRaw` 还原 Vue 代理，避免同一个附件因代理包装而无法匹配。等待期间新加的附件不属于本批，继续留在输入区。如果提交时列表是 `[A]`，等待期间变成 `[A, B]`，成功后过滤掉 A、留下 B —— 直接把整个列表设成空数组会误删 B，等到真正发请求时再读列表，又可能把 B 错发进本次任务。
3. **失败只撤回仍属于本次的乐观气泡。** 查看消息列表末尾，确认它仍是本次乐观插入的对象，再同时移除这条消息和它的临时记录 ID；末尾已经变成别的消息时就不删除，避免误伤后来新增的权威内容。消息列表与记录 ID 列表平行，插入临时消息时放一个空记录 ID，撤回也要一起删除，否则后续编辑可能把消息与记录配错。

三处判据都依赖对象身份而不是“输入框当前是什么”：**快照解决“发送范围”，定向清理解决“清理范围”，末尾身份比较解决“撤回的对象还是不是本次这一条”。**

**验证：** [发送测试](../../tests/app/stores/chat.test.ts) 覆盖三条对应用例 —— “发送握手启动失败仅提示一次且撤回乐观消息”“只发送本批附件 成功后保留发送期间新增附件”“切走再回到同一会话时旧失败不能清除新一轮运行状态”；[会话交错测试](../../tests/app/stores/chat-races.test.ts) 用可控 Promise 让旧响应晚于会话切换返回。

**剩余边界：** 局部回滚依赖对象身份，还没有客户端消息 ID；接受状态未确认时只能提示用户核对历史，**没有请求幂等**。

### 面试官：讲一次有实质变化的项目迭代

> 发送链路经历了几次具体调整。最初为了让冷启动有反馈，先把用户消息追加到页面，再等连接就绪后提交。但立即反馈只是第一步，失败时还要准确撤回本次操作。后续代码修正了 Vue 代理导致的引用比较问题，把附件改成提交时的快照，同时用会话身份和操作代次判断异步结果是否仍有效。这样既保留即时反馈，也不会因旧请求失败去清掉另一个会话的新状态。可以用握手失败、发送期间新增图片、切走再回同一会话三个测试解释效果；已有测试能证明这些具体行为，不能据此说所有网络失败都已解决。

### 追问：为什么不用深拷贝，或者取消旧请求就结束了

> 对象身份和数据内容是两件事。这里的局部回滚需要判断末尾是不是本次插入的对象，深拷贝会创造新身份，不能直接修复这个判断。还原代理可以解决目前的引用比较，但如果以后列表会排序、替换或并发插入，就应给临时消息一个稳定 ID。取消请求解决资源浪费，代次守卫解决结果有没有资格写回，两者也不同。请求可能已经到达服务端，取消浏览器等待不等于撤销任务；即使无法取消，只要返回时检查归属，仍能避免旧结果污染当前页面。所以先保住提交归属，再按实际需要补取消和稳定消息身份。

### 追问：服务端执行了，但响应没回来，回滚是不是错的

> 这个结果属于接受状态未确认。当前普通发送在传输异常后保留输入、提示先核对会话并重读历史，这是工作区已有的补强；但它仍会清理本地乐观运行态，而且没有可查询的命令 ID。因此它降低了误操作概率，并没有实现请求幂等。下一步应由客户端生成一次提交的稳定 ID，服务端记录接受状态，同 ID 重试返回原状态而不重复执行。还要定义记录过期和进程重启后的行为。去重依据应是命令身份，因为用户可能确实想连续提交两次相同指令。

**证据：** [chat store](../../app/stores/chat.ts) 的 `sendPrompt`、`submitPrompt`；[输入组件](../../app/components/ChatComposer.vue) 的 `submit`；[发送测试](../../tests/app/stores/chat.test.ts)。

## 2 会话切换：同名会话为什么还需要代次 [P1]

**核心结论：** 异步结果归谁，不是一个会话名能表达的。会话 ID 说明属于哪个会话，代次说明属于这个会话的第几次打开，查询序号说明属于同一生命周期里的哪一次历史查询；三项都相同，结果才有资格写回共享状态。

### 问题：只比较会话名，同名会话会通过检查

用户在会话 A 发出“检查接口”，切到 B 查看旧记录，再回 A 开始新的任务。第一条请求此时才返回错误。若只检查当前会话是否仍叫 A，检查仍会通过，旧错误可能清掉新任务的运行态。

### 最终方案：两层身份加一层查询序号

一项异步操作开始时，同时保存当前会话 ID 和当前生命周期代次。前者说明操作属于哪个会话，后者说明它属于这个会话的哪一次打开。

关闭会话时递增代次：`close()` 里同时递增 `sessionGeneration` 与 `reloadSequence`。等待结束后，把保存的两项信息与当前值比较。会话变了，或者同名会话已经重新打开，就结束旧操作，不再清理附件、不回填输入，也不修改新任务的运行状态。

| 值 | 表达的含义 | 能识别的变化 |
| --- | --- | --- |
| session ID | 当前是哪一个会话 | A 切到 B |
| generation | 当前属于哪一轮会话生命周期 | A 切 B 再回 A |
| reload sequence | 同一生命周期里的哪一次历史查询 | 查询二先返回、查询一后返回 |

返回值还区分三种结果：`true` 是提交已确认，`false` 是当前操作失败，`null` 是操作归属已失效。失效不是当前页面的一次失败，不能触发向当前输入框回填旧文字或显示旧错误。

历史查询另外维护序号：发出查询时递增并保存序号，返回时同时比较会话 ID、代次和序号。这避免同一个会话里较早发出的历史查询覆盖较晚查询。

**验证：** [store 测试](../../tests/app/stores/chat.test.ts) 覆盖“快速连续打开两个会话 慢的旧响应被丢弃”“切换会话后旧提交不修改新会话状态”“切走再回到同一会话时旧失败不能清除新一轮运行状态”“同名会话重入时旧握手等待者不能提交旧消息”；[会话交错测试](../../tests/app/stores/chat-races.test.ts) 用可控 Promise 覆盖同名会话重入后旧撤回结果、旧提交与新会话的交错。

**剩余边界：** 查询序号不代表事件版本，历史列表与流式事件的衔接仍需另外处理；打开会话的部分收尾只检查 ID，是继续审查的具体位置；跨窗口与进程重启见 §6.9。

### 面试官：每个 await 后都检查，会不会太繁琐

> 检查应放在异步结果准备影响共享状态的位置。比如握手完成后准备发送旧输入，命令返回后准备清附件，异常时准备回滚气泡，finally 准备释放提交锁，都可能发生在用户切会话之后。成功分支保护了、finally 没保护，旧操作仍可能把新一轮的锁释放。当前把部分逻辑拆进 composable 后，通过依赖传入统一的代次读取函数，各操作使用同一判断依据。这比只保护消息数组更完整，因为 loading、错误提示和草稿保护也属于当前会话状态。打开会话的部分收尾仍只检查 ID，是继续审查的具体位置。

### 追问：AbortController 能不能替代代次

> 取消等待和禁止写回分别解决两个问题。取消能减少无用请求，但请求可能已到服务端，服务端任务也可能继续执行，某些异步来源还不支持取消。代次守卫不依赖底层能否中止，只要结果到达后发现已经过期，就不再修改当前状态。两者可以配合：切走时尽量取消读请求，返回后仍检查归属；对于已接受的 Agent 任务，则允许后台继续，通过关闭订阅停止当前页面接收。只有用户点击停止时才表达终止任务的意图。

**证据：** [chat store](../../app/stores/chat.ts)、[会话交错测试](../../tests/app/stores/chat-races.test.ts)。

## 3 草稿恢复：发送失败时保留旧文字，也保留新输入 [P1]

**核心结论：** 输入框清空不等于用户意图消失。所以提交时另存一份“待确认提交”，持久化时把它与新输入一起保存，成功才释放、失败则合并，并以会话 ID 为键 —— 保存的是文字与编辑目标，不保存图片，也不把浏览器草稿当成服务端执行记录。

### 问题：把文字放回去，仍然会丢东西

用户提交“检查接口” → 等待期间输入“顺便检查测试” → 原提交失败。直接赋回旧输入会覆盖新输入；只在输入框为空时恢复，会让旧输入在新输入存在时丢失；只保存在组件内存里，刷新又会丢。

### 最终方案：待确认提交、失败合并、存储降级

1. **清空输入框之前先留一份待确认记录。** 提交前把文字、会话身份和编辑目标放进一份待确认记录，再清空可编辑输入框。持久化逻辑同时考虑待确认记录与当前新输入，因此清空输入框只改变页面编辑状态，不立即删除仍未确认的原文字。
2. **持久化时把待确认文字和新输入一起存。** 如果这个会话存在待确认提交，就把待确认文字和用户当前输入合并保存。输入框虽然清空，存储里仍有“检查接口”；用户继续输入“顺便检查测试”后，存储里包含两段。确认成功才释放待确认部分。
3. **失败时按三种情况合并，两份输入都留下。** 原提交为空就保留当前输入；当前输入为空就恢复原提交；两份都有文字，就把原提交放在前面，隔一行再接上当前输入（`mergeDraftText` 用 `\n\n` 连接）。这样用户能同时找回失败内容和等待期间的新内容。它保留文字但不自动推断两段语义是否重复，用户可以在重新提交前编辑；把“失败文字”只放进一条 toast 会让恢复成本变高，直接覆盖则会丢新内容。
4. **打开会话先恢复文字，再等待详情。** `openSession` 先写回草稿再发详情请求，否则晚到的详情会覆盖加载期间用户已经输入的内容。
5. **存储出问题时不阻断编辑。** 草稿只保存文字、更新时间和可选的编辑目标记录 ID，以会话 ID 为键。读取时验证数据形状并过滤超过 30 天的条目；JSON 损坏时清理损坏数据并提示；浏览器存储不可用时改存内存并只提示一次。这个降级让当前页面继续编辑，但刷新后的恢复依赖持久化成功。图片数据不写进这份文字草稿，所以“恢复输入”具体指文字及有效编辑目标。

**验证：** [草稿测试](../../tests/shared/lib/draft-store.test.ts) 覆盖“隔离会话并只保存文字与编辑目标”“清理过期草稿并从损坏数据恢复”“存储不可用时保留页面内草稿”“失败内容放在新输入之前”；[store 测试](../../tests/app/stores/chat.test.ts) 覆盖切换会话恢复各自文字、提交拒绝后合并期间输入并保留图片、连接结果不明时提示先核对且保留文字。

**剩余边界：** 存储不可用时的降级只保证当前页面还能继续编辑，无法保证刷新恢复；多窗口也没有完整的冲突合并。

### 面试官：为什么不直接 watch 输入框写 localStorage

> 关键在于清空输入和确认接受的先后顺序。发送一开始会清空输入框，但这时服务端还没有确认接受；如果只监听可见输入，空字符串会把原草稿从存储删掉，刷新就丢失待确认内容。所以当前方案还保存本次提交中的文本，持久化时把它与新输入一起考虑，确认接受后才释放。失败则合并旧文本和新输入，避免覆盖用户后来写的内容。草稿以会话为键，是因为不同会话的编辑上下文不同。这里保存的是文字和编辑目标，不保存图片，也不把浏览器草稿当成服务端执行记录。

### 追问：既然能恢复，刷新后为什么不自动重发

> 因为恢复文字只说明用户曾经准备或提交过这些内容，不能说明服务器没有执行。尤其是发送成功但确认丢失时，刷新后的草稿和服务端运行任务可能同时存在。先恢复可编辑文字，再让用户核对历史与运行状态，不能用自动重发替代确认。另外，存储不可用时的降级只保证当前页面还能继续编辑，无法保证刷新恢复；多窗口也没有完整的冲突合并。若以后需要跨设备草稿或大附件恢复，再考虑服务端草稿或 IndexedDB，并补版本、配额和清理机制，现在不把这些能力混入已有结果。

**证据：** [草稿存储](../../shared/lib/draft-store.ts)、[草稿测试](../../tests/shared/lib/draft-store.test.ts)、[store 测试](../../tests/app/stores/chat.test.ts)。

## 4 编辑旧问题：页面变了，模型上下文也必须改变 [P1]

**核心结论：** 编辑重发本质上是一次上下文切换。用户改的是旧问题，而 Agent 下一次从哪个节点继续取决于服务端会话位置，所以流程必须是定位父记录 → 预览 → 导航 → 权威回读，确认位置正确后才提交新文本；位置无法确认时宁可不发送。

### 问题：只改界面，不改模型看到的上下文

这个功能先具备分支读取，再加入编辑重发。两步的差别是从“读取已有结构”进入“改变下一轮任务的上下文”。

原记录链为 `问题一 → 回答一 → 问题二 → 回答二`。修改问题二再发送，应回到问题二的父节点回答一，再追加新问题。直接替换页面上的问题二，只改了显示，服务端可能仍带着原回答二继续执行。

### 最终方案：父记录定位、导航后的权威回读、未知位置锁发送

当前流程为：稳定状态才能编辑 → 确定记录父节点 → 预览目标 → 服务端导航 → 重读详情确认叶节点 → 发送新文本。

1. **先定位旧问题的父记录。** 根据用户点击的消息位置取得真实记录 ID，再到会话树中查找它的父记录。找不到父记录就不启动编辑流程；找到后分别保存“正在编辑哪条消息”和“新输入应该接在哪个节点之后”。消息记录 ID 表示正在编辑哪条记录，父记录 ID 表示新问题应该从哪里继续，两者不能混用：如果导航到原问题本身，再追加改写后的问题，模型可能同时看到旧问题和新问题。记录 ID 也不能用数组下标替代，因为不同分支、过滤后的消息列表与原始记录树并非同一序列。
2. **改变服务端位置后必须读回确认。** 导航的主体顺序是预览 → 发导航命令 → reload → 比较实际叶节点与目标。只有这几步都确认完成，新的文本才能继续提交。HTTP 确认只表示命令返回，`reload` 才确认页面拿到的实际分支。
3. **异常路径先查再退，最后锁住发送。** 异常路径保存原叶节点，先读取实际位置，再决定是否发回退命令；回退后仍读不到或叶节点不正确，就设置 `positionUnknown`。发送入口和导航入口都检查这个状态，避免在未知位置上继续执行。源码在各等待点插入会话代次检查，防止操作途中切会话后继续修改新页面。

**验证：** [导航互斥测试](../../tests/server/utils/rpc-manager.test.ts) 的“分支导航等待扩展期间拒绝 prompt 与第二次导航 完成后释放互斥”“导航失败后释放互斥不阻止下一条消息”；[store 测试](../../tests/app/stores/chat.test.ts) 的“先预览再导航 最后加载权威分支”“导航拒绝后仍停留原分支”“回退后仍无法读取权威状态则锁住发送”；[会话交错测试](../../tests/app/stores/chat-races.test.ts) 的“导航恢复读取期间切换会话不会回退旧会话或锁住新会话”。

**剩余边界：** 服务端互斥是单实例内的操作互斥，不是数据库事务，也不是跨进程锁；位置确认依赖一次额外的 `reload` 对账。

### 面试官：编辑历史消息，为什么做得这么复杂

> 编辑重发本质上是一次上下文切换。用户改的是旧问题，但 Agent 下一次从哪个节点继续，取决于服务端会话位置。所以当前实现先找到旧问题的父记录，验证目标可用，再导航和读取权威详情，确认位置正确后才提交新文本。如果网络在服务端导航之后断开，浏览器看到失败也不能认为仍在原分支，因此还需要查询和回退。无法确认位置时先禁止发送，是为了避免把新问题接到错误上下文。实现增加了等待和状态，但换来的是失败时有明确处理路径。

### 追问：前端禁用按钮了，为什么后端还要互斥

> 前端按钮只能约束当前页面，另一个窗口或直接接口调用仍可能进入。导航还可能等待扩展钩子，若此时另一条 prompt 改变了消息链，原操作结束时就可能指向错误位置。工作区服务端在导航期间设置互斥状态，在 finally 释放，并拒绝冲突的 prompt 或第二次导航。它解决的是单实例内操作互斥，不是数据库事务，也不是跨进程锁。可以用可控 Promise 暂停导航，在暂停期间发第二个命令，检查被拒绝，再让导航失败并确认锁能释放；这样验证的不是按钮外观，而是服务端约束。

**证据：** [导航流程](../../app/composables/useSessionNavigation.ts)、[父节点选择](../../shared/lib/session-branches.ts)、[服务端包装器](../../server/utils/rpc-manager.ts)、[导航互斥测试](../../tests/server/utils/rpc-manager.test.ts)。

## 5 运行中补充指令：停止时要把队列一起处理 [P1]

**核心结论：** 加入队列后，“停止”不再只是停掉当前输出，还要处理“未来还准备执行什么”。所以停止流程先撤回队列、把可撤回文字合并回草稿，再发 abort，并在整个阶段禁止本页继续追加；队列快照用版本号判断是否已被更新的事件取代。

### 问题：abort 之后，队列仍可能继续触发执行

Agent 正在修改接口，用户补充“先不要改数据库”，或者要求“这一轮结束后补测试”。页面分别提供调整当前执行方向和安排后续输入的模式。具体消费时点由 SDK 处理，前端把模式随命令传递，并通过队列事件展示 SDK 实际接受的内容。

加入队列后，即使当前任务 abort，剩余队列仍可能继续触发执行。停止流程必须同时考虑“未来还准备执行什么”。当前工作区进一步保护了这些交错：

| 操作交错 | 当前保护 | 为什么需要 |
| --- | --- | --- |
| 两个 prompt 几乎同时进入 | 服务端串行化接纳阶段 | 避免接纳判断交叉，不等待整轮任务完成 |
| 接纳尚未完成就撤回 | 撤回等待接纳链，再读取 SDK 队列 | 不能用旧页面列表猜实际撤回内容 |
| 清队列后等待 abort | 整个停止阶段禁止本页继续追加 | 避免刚清空又从本页塞入下一条 |
| 快照请求未回，先收到新队列事件 | 队列版本变化后拒绝旧快照覆盖 | 同一会话也有新旧响应竞争 |

### 最终方案：不假造队列状态、按版本安装快照、只串行接纳阶段

1. **页面不提前假造已入队状态。** 运行中提交将 `streamingBehavior` 与文字、图片一起交给服务端，队列展示由 `queue_update` 或运行态快照更新。这样前端不根据点击前的运行标记推断最终结果：请求到达 SDK 时，上一轮可能恰好结束，SDK 才掌握当时应入队还是开启新轮。
2. **旧快照不能覆盖新队列。** 发出队列查询时记住本地队列版本，响应返回时再次比较，版本相同才允许安装这份快照。队列每次更新都会递增版本：发查询时版本是 3，返回前收到新事件后版本变成 4，旧快照就不能覆盖。会话 ID 解决跨会话污染，队列版本解决同一会话内的查询与事件交错，两层都需要。
3. **接纳串行与完整执行分开。** 服务端用 Promise 链（`promptAdmissionTail`）组织接纳顺序，相当于只为短暂的接纳阶段排队：每次接纳请求先记住前一个请求的等待对象，再创建自己的等待对象并接到队尾；等前一项释放后，自己才能进入接纳判断；本次接纳无论成功还是失败，都在收尾时释放后一个请求。如果把等待范围扩大到整轮生成，第二个请求就无法在运行中进入 SDK，运行中追加也会失去意义。
4. **停止按撤回 → 合并草稿 → abort 的顺序执行。** 撤回队列先等待接纳链，再让 SDK 返回尚未消费的内容；停止流程先撤回、把实际返回文字合并进草稿，再发 abort；本页从撤回开始到 abort 返回期间用 `isStopping` 阻止新增。

**验证：** [队列测试](../../tests/app/stores/chat-queue.test.ts) 覆盖“仅在 SDK 确认后由队列事件展示追加内容”“停止前撤回全部队列并只恢复实际返回文本”“清队列失败时不误称任务已停止”；[会话交错测试](../../tests/app/stores/chat-races.test.ts) 覆盖“从撤回到 abort 返回的整个停止阶段拒绝追加指令”“撤回响应不能覆盖期间更晚的队列事件”；[服务端测试](../../tests/server/utils/rpc-manager.test.ts) 覆盖“第二条 prompt 等第一条接纳后再进入 SDK”“撤回队列等待正在接纳的 prompt”。

**剩余边界：** 撤回只恢复 SDK 返回的文字，已经消费的内容不能假装撤回，图片也没有完整的队列恢复契约；多窗口仍可能在两个请求之间插入操作，要获得更强保证，需要服务端提供原子的清队列并停止命令；接纳阶段本身如果一直不结束，后续接纳和撤回也会被阻塞，还缺明确的超时与监测策略。

### 面试官：停止为什么要先撤回队列，再 abort

> 点击停止通常希望当前工作收住，而不是当前输出停一下、下一条任务立即开始。项目加入队列后，仅 abort 不足以表达这个意图，所以现在先让 SDK 返回实际尚未消费的队列，把可撤回文字合并回草稿，再发送 abort。清队列失败时不继续宣称停止成功；从撤回开始到 abort 返回，本页也禁止继续追加。撤回只恢复 SDK 返回的文字，已经消费的内容不能假装撤回，图片也没有完整的队列恢复契约。多窗口仍可能在两个请求之间插入命令，若要更强保证，需要服务端原子的清队列并停止操作。

### 追问：为什么串行的是接纳，不是整个 Agent 运行

> 用户需要在 Agent 正在运行时追加调整或后续任务。如果互斥一直持有到完整生成结束，第二条命令只能等第一轮结束，就失去了运行中追加的意义。当前服务端等待前一条命令完成接纳判断，然后允许后一条进入 SDK，由 SDK 根据当时的运行状态决定入队或开启新轮。这能减少用过期状态做决定的问题。代价是接纳阶段本身如果一直不结束，后续接纳和撤回也会被阻塞，所以还需要明确的超时与监测策略；已有串行化不等于所有命令都有截止时间。

**证据：** [队列逻辑](../../app/composables/usePromptQueue.ts)、[运行态快照](../../app/composables/useSessionRuntime.ts)、[队列测试](../../tests/app/stores/chat-queue.test.ts)、[交错测试](../../tests/app/stores/chat-races.test.ts)。

## 6 最难的问题：旧异步结果怎样污染新会话 [P0]

**本节是 P0：如果只剩很少准备时间，先读这一节。**

前面五节各讲一个功能的处理顺序。这一节把它们串成**一条完整的问题主线**，用来回答“你遇到过最难的问题是什么、怎么定位、怎么解决、还剩什么”。

### 6.1 业务现象：一次切换就能让页面显示错的内容

用户的操作只有三步：在会话 A 发出“检查接口”，切到会话 B 看一条旧记录，再切回 A 开始新任务。

出问题的是**第一步的响应回来得太晚**。等它返回时，用户早已经不在原来的上下文里了。此时如果代码无条件把结果写进共享状态，就会发生下面这些现象：

| 用户看到的现象 | 被写坏的状态 | 为什么用户会觉得莫名其妙 |
| --- | --- | --- |
| A 里冒出 B 的错误提示 | 错误信息 | 错误来自一次已经无关的请求 |
| 刚发的新消息一直转圈 | 运行标记 | 旧请求的 `finally` 把新一轮的锁释放了 |
| 发消息时提示“正在发送” | 提交锁 | 上一轮的锁没被正确归属就释放或占用 |
| 带图发送时图片消失 | 附件列表 | 旧失败清掉了当前这一批附件 |
| 历史列表跳回旧内容 | 消息列表 | 较早发出的历史查询后返回 |

### 6.2 为什么它比“一个 bug”难

因为它不是一处写法错误，而是一类问题的统称：

> **任何一次 `await` 之后要写共享状态的代码，都可能在用户已经离开原上下文之后才执行。**

这类代码在这个项目里到处都是：等待 SSE 握手、等待 HTTP 提交、等待历史查询、等待队列快照、等待导航确认、`finally` 里释放锁。所以逐处打补丁的做法会一直漏 —— 每加一个异步入口，就多一个可能的污染点。

**构造场景：** 下面这张时间线是为了说明失败时序而构造的，用来解释“为什么只检查会话名不够”，不是真实发生过的线上事故。

```text
t0  在会话 A 点击发送            保存 sessionId=A, generation=7
t1  等待握手 / 等待 HTTP 返回    （异步窗口开始）
t2  用户切到 B                    closeSession() → generation=8
t3  用户切回 A                    openSession()  → generation=9
t4  t1 的请求返回错误             此时 sessionId 又是 A
```

在 `t4` 这一刻，如果判断条件只是 `sessionId === "A"`，检查会**通过**，于是旧错误照样清掉了 `t3` 之后新任务的运行状态。

### 6.3 定位过程：先把“哪一层被写坏”分开

定位顺序是自下而上的，每一步都问“这个状态归谁管、凭什么判断它还该写”：

1. **先看服务端。** 服务端的会话实例是按 `sessionId` 注册的，同一个会话拿到的是同一个 wrapper，跨会话本身不会串。所以问题在前端写回，不在实例归属。
2. **再看前端有几种状态。** 把 store 里的状态按“谁拥有它”分组：属于当前会话的（消息、运行标记、附件、错误、锁），属于一次查询的（历史列表），属于一次拉取的（队列快照）。
3. **然后找所有写这些状态的位置。** 逐个标记它前面有没有 `await`。有 `await` 就是候选污染点。
4. **最后判断“需要什么信息才知道它还该不该写”。** 结论是需要三层：这是哪个会话（session ID）、是这个会话的第几次打开（generation）、是同一生命周期里的第几次查询（reload sequence）。

第 4 步是整个问题的关键。前面几层信息都不够用：

- 只知道“有请求在飞” → 无法区分它属于哪个会话。
- 只知道会话 ID → `A → B → A` 时同名会话通过检查。
- 加上代次 → 能挡住跨生命周期，但挡不住同一生命周期里两次历史查询乱序返回。
- 队列还要再加一层 → 队列快照与 `queue_update` 事件之间是另一种交错，版本号解决的是“这份快照是不是比我现在手里的旧”。

### 6.4 对比过的候选方案

| 方案 | 能解决什么 | 为什么没有单独采用 |
| --- | --- | --- |
| `AbortController` 取消请求 | 减少无用请求与等待 | 请求可能已经到达服务端；已接受的 Agent 任务本来就要继续跑。取消是省资源，不是防污染 |
| 全局请求序号 | 区分新旧响应 | 不带会话语义，跨会话无法判断 |
| 只比较会话 ID | 挡住跨会话污染 | `A → B → A` 同名会话通过检查，保护不到 |
| 加会话代次 | 挡住跨生命周期污染 | 挡不住同一生命周期内的查询乱序 |
| 服务端串行化一切 | 服务端状态一致 | 前端写回仍会交错；而且会失去“运行中追加”的能力 |
| 前端禁止并发操作 | 从根上不会交错 | 用户不能在等待期间切会话或继续输入，体验不可接受 |

结论是**分层组合**：不同层解决不同类型的交错，没有哪一个能单独收口。

### 6.5 最终方案：四层归属判断

| 判断层 | 表达什么 | 在哪一层生效 | 保护的状态 |
| --- | --- | --- | --- |
| `sessionId` | 这是哪个会话 | 所有异步写回 | 跨会话污染 |
| `sessionGeneration` | 是这个会话的第几次打开 | 所有异步写回与 `finally` | `A → B → A` 后的旧结果 |
| `reloadSequence` | 同一生命周期里的第几次历史查询 | 历史列表写入 | 查询乱序覆盖 |
| 队列 `version` | 这份队列快照是否已经过期 | 队列快照安装 | 快照与事件交错 |

配套的一条实现约定：**检查点放在“即将写共享状态”的位置，而不是机械地放在每个 `await` 后面。** 成功分支要检查，`finally` 里释放锁也要检查 —— 只保护成功路径的话，旧操作照样能把新一轮的锁释放掉。

下面是 `stop()` 的**节选**（省掉了 3 秒兜底定时器的函数体），它把上面几条约定集中体现了一遍。**注意每个 `await` 之后都有一道归属判断，连 `finally` 也有。**

```ts
async function stop() {
  // 操作开始先把身份固定下来 之后每一步都用它判断还该不该继续
  const id = sessionId.value;
  const generation = sessionGeneration;
  if (!id || isStopping.value) return;
  isStopping.value = true;

  try {
    // Pi 在 abort 后可能继续尚存的队列 因此必须先撤回再停止
    const recalled = await recallQueue();
    if (sessionId.value !== id || generation !== sessionGeneration) return;
    if (!recalled) {
      addNotice("error", "队列未确认 当前任务仍在运行");
      return;
    }

    try {
      await sendAgentCommand(id, { type: "abort" });
    } catch (error) {
      if (sessionId.value !== id || generation !== sessionGeneration) return;
      addNotice("error", error instanceof Error ? error.message : String(error));
      return;
    }

    if (sessionId.value !== id || generation !== sessionGeneration) return;

    // 此处省略 3 秒兜底定时器 它在回调里同样比对 id 与 generation 再落定运行态
  } finally {
    // 只保护成功路径不够 旧操作仍会在 finally 里释放新一轮的停止锁
    if (sessionId.value === id && generation === sessionGeneration) isStopping.value = false;
  }
}
```

被省略的兜底定时器同样体现这条约定：`abort` 的 POST resolve 与 `agent_settled` 可能乱序或丢失，所以 3 秒后在回调里再次比对 `id` 与 `generation`，才强制落定运行态并 `reload` 一次对账；`settled` 先到则取消。

被追问“为什么要写这么多重复判断”时，回答的落点是：**这些判断不是防御性编程，而是每一条都对应一个能复现的失败时序**；把它们收在一处、共用同一个判据，比分散在各处写不同的检查更容易维护。

### 6.7 被保护住的不变量

修完之后，下面三句话在代码里成立。面试时可以直接讲这三条，比讲具体 diff 更容易记住：

1. **任何异步结果写共享状态前，先确认“这次操作仍然属于当前会话的当前生命周期”。**
2. **失败清理只处理自己造成的状态**，不删除后来新增的消息、附件或任务状态。
3. **服务端只对改变消息链的操作互斥**（导航、压缩），不对整轮执行互斥 —— 否则运行中追加就失去意义。

### 6.8 怎么验证

验证手段是**可控异步**：把测试里的异步操作换成手动 resolve 的 Promise，从而精确控制返回顺序。

| 测试 | 控制什么顺序 | 断言什么 |
| --- | --- | --- |
| [chat-races.test.ts](../../tests/app/stores/chat-races.test.ts) | 让旧请求晚于会话切换返回 | 新会话的运行态、附件和错误不被旧结果改写 |
| [chat-queue.test.ts](../../tests/app/stores/chat-queue.test.ts) | 让快照晚于 `queue_update` 返回 | 旧快照不覆盖新队列 |

**验证到了什么、没验证到什么：** 这些测试证明了守卫在**受控的返回顺序**下生效，不能证明真实网络抖动、浏览器标签休眠、多窗口操作或服务端进程重启下的表现。后者属于未做端到端验收的部分。

### 6.9 还剩哪些边界

- **跨窗口。** 两个标签页同时改一个会话时，代次只在各自的页面内存里，互相不可见。要解决需要服务端提供原子操作或版本对账。
- **服务端进程重启。** 内存里的代次、队列与快照全部消失，只能从 JSONL 恢复历史。
- **命令幂等。** 现在的守卫保证“不乱写”，但不保证“不重复执行”；接受状态未知时只能提示用户核对历史。
- **停止请求超时。** 停止流程本身没有超时闭环。

### 6.10 一段可以照读的口述版本

> 这个项目里最难的不是某个功能，而是一类问题：异步结果回来的时候，用户已经不在原来的上下文里了。它出现在等待握手、等待提交、等待历史查询、`finally` 释放锁这些位置，逐处打补丁会一直漏。
>
> 我的处理是先把前端状态按“谁拥有它”分组，再给每组找到需要的归属信息：会话 ID 管跨会话，代次管同名会话重新打开，请求序号管同一生命周期里的查询乱序，队列版本管快照和事件的交错。检查点放在即将写共享状态的位置，成功分支和 `finally` 都要检查。
>
> 验证用的是可控异步测试，故意让旧请求晚于切换返回，断言新状态不被改写。这样能证明守卫在受控顺序下生效，但跨窗口和服务端重启还没有覆盖，命令幂等也还是下一步。

### 8.3 第 2 条：流式消息增量渲染

这一条的落点是**渲染**而不是状态设计，所以措辞要往“更新粒度、引用复用、渲染成本”上靠，别写成“分离数据流”。

| 表述要点 | 源码与测试证据 | 当前边界 | 状态 |
| --- | --- | --- | --- |
| 承接高频增量事件，按 `contentIndex` 把文本、思考与工具调用归并为内容块 | [streaming-message.ts](../../shared/lib/streaming-message.ts) 的 `streamReducer`、`applyDelta`、`updateContentBlock`：逐块处理 start / delta / end。[streaming-message.test.ts](../../tests/shared/lib/streaming-message.test.ts) | 模块清单与来源标注见 [THIRD_PARTY_NOTICES.md](../../THIRD_PARTY_NOTICES.md)；`shared/lib` 下的纯函数按该文件的清单管理 | 🟢 |

> **面试钩子与答案要配套。** “保持其余块引用不变”会引出“那渲染层做缓存了吗”，答案是**没有**，并补上原因：块级缓存要先解决“哪些块已经稳定”的判定（`text_end` 之后才稳定），而稳定块与活动块混在同一条消息里。这样回答比被问出来强。

| 表述要点 | 源码与测试证据 | 当前边界 | 状态 |

### 8.6 简历亮点定稿（三条）

以下是定稿版本。**第 2 条刻意把落点放在「渲染」而不是「状态管理」**，因为它要引出的是前端渲染与性能追问，而不是数据流设计。个人动词按真实职责补充。

- **Agent 全链路接入：** 基于 Pi Agent SDK 构建服务端 Agent 执行链路，封装会话管理与任务触发逻辑；在服务端适配 Agent 执行事件，将模型文本增量、工具调用及执行状态转换为前端可识别的事件，通过 SSE 持续推送至浏览器，实现 Agent 执行过程的实时可视化，并降低前端对 SDK 内部事件结构的直接依赖。
- **流式消息增量渲染：** 承接高频增量事件，以纯函数 reducer 按 `contentIndex` 将文本、思考与工具调用归并为内容块，更新时只替换目标块并保持其余块引用不变，再整体写回 Vue 响应式容器；工具调用与结果按 `toolCallId` 配对，支撑文本逐步输出与工具执行状态切换。
- **异步任务与消息恢复：** 将「命令被接纳」与「整轮执行完成」拆成两个独立时点，HTTP 只等待接纳确认，执行进度经事件通道持续反馈；针对刷新后进行中消息丢失的问题，以服务端当前消息快照配合前端状态恢复逻辑重建展示，并对旧异步结果的写回施加会话身份与代次守卫。

三条的分工是：**第 1 条服务端接入层、第 2 条前端渲染层、第 3 条异步一致性层**。写的时候避免互相覆盖 —— 尤其第 3 条不要再重复 SSE 的推送机制（那是第 1 条的内容）。

关于收益句：第 1 条那句“降低前端对 SDK 内部事件结构的直接依赖”是可验证的，保留；第 2、3 条的“提升可维护性”“改善交互连续性”属于效果描述，建议删掉，把字数留给具体机制。

**这条会引出哪些前端追问，提前备好：**

| 简历里的措辞 | 会被追问 | 回答落点 |
| --- | --- | --- |
| 高频增量事件 | 每个 delta 都触发一次渲染吗，要不要按帧合并 | 当前逐事件处理；按帧合并属候选优化，要先测出瓶颈再决定 |
| 只替换目标块、保持其余块引用不变 | Vue 怎么知道该更新；引用不变有什么用 | 不可变返回整体写回 reactive；引用不变是**块级渲染缓存的前提**，而缓存当前没做 |
| 长回复的渲染成本 | 你测过吗，瓶颈在哪一层 | 有分层定位顺序（事件处理 → Markdown 解析与高亮 → DOM 提交与布局 → 滚动跟随），但**没有可复现的基线数据**，所以不写任何百分比 |
| 长列表 | 用虚拟列表吗 | 当前没用；虚拟化的测量成本与流式增长的消息高度冲突，先确认瓶颈在解析还是 DOM 数量 |

### 如果还要写第四条（原 §8.5）

只写三条时这一节可以跳过。但要补第四条时，**推荐换成「异步竞态防护」，而不是原来的「Agent 扩展与上下文管理」**。

原因很直接：原来的第四条只能用“探索”措辞，因为仓库里没有自定义工具的实现；而异步竞态这条线的证据最硬。两者对比：

**建议的第四条写法：**

> **异步竞态防护：** 针对“切走后旧请求晚返回、覆盖新状态”这一整类问题，以会话 ID、会话代次、历史请求序号与队列版本四层判据守卫全部异步写回（含 `finally` 释放路径），并用可控异步测试构造旧响应晚于会话切换到达的反例。

**如果仍想保留“扩展与上下文管理”**，把“自定义工具接入”换成真实存在的部分：

> **能力资源与上下文可见性：** 接入扩展、技能与插件包的资源发现与管理，区分“文件累计用量”与“运行时上下文占用”两个统计口径，并明确项目级资源的信任判定不等同于执行沙箱。

### 其他可用的项目级摘要（原 §8.8）

如果简历篇幅还够，或者面试时想主动展开别的模块，可以用下面这几条：

- **异步状态隔离：** 针对发送与切会话交错，通过输入快照、会话代次和响应写回守卫，保护当前会话状态与新增附件，并用延迟返回测试验证典型反例。
- **输入恢复：** 从失败回填扩展为按会话保存文字草稿，覆盖待确认提交、失败合并及存储不可用降级，明确图片不跨刷新恢复。
- **上下文一致性：** 将历史编辑实现为父节点定位、预览、导航和权威回读，失败时回退或阻止继续发送，避免仅修改界面而与服务端上下文脱节。
- **任务交互治理：** 接入运行中追加与队列撤回，通过接纳串行化、队列版本和停止互斥处理命令交错，明确本地互斥与服务端原子操作的区别。

### 逐分支异常推演（原 §1、§2）

**构造场景：** 下面几条由代码路径推导，用来解释失败时序，不代表真实发生过的线上事故。

- **局部回滚遇到历史整体替换（原 §1）。** 如果消息列表已被历史回读整体替换，原乐观对象身份可能不存在，这条局部回滚就不会随意删数据。以后需要在任意位置可靠定位临时消息，可以引入客户端消息 ID；它与服务端用于请求去重的命令 ID 是两层身份。
- **查询期间有新 SSE 消息进入（原 §2）。** 历史查询序号能挡住同一会话里的查询乱序，但查询序号本身不代表事件版本；如果查询期间有新 SSE 消息进入，历史列表与流式事件的衔接还需要另外处理。
- **等待期间附件列表增长（自 §1 的定向清理推导）。** 等待期间新增的附件只影响“本批范围”的判断，不影响清理判据：快照加上按身份过滤，已经把这种情况挡住，不需要额外守卫。
