# 编程 Agent 架构与选型对比

同样输入“读取这个项目，修复一个问题，并运行相关测试”，为什么有的方案适合直接使用，有的适合嵌进自己的应用，还有的更适合拿来学习？这个专题从完整任务路径出发，逐个理解 Pi、OpenCode、DeepSeek Harness 和 learn-claude-code，再讨论本项目的选择。

读完应能画出各方案的执行边界，解释工具结果如何回到模型，并回答：换一个 Agent 底座，哪些工作可以省掉，哪些责任仍属于 Web 应用。

## 先建立四个概念

| 概念    | 在“改代码并测试”中负责什么                        | 不应混淆的地方                                     |
| ------- | ------------------------------------------------- | -------------------------------------------------- |
| 模型    | 根据输入和工具结果，提出修改与下一步动作          | 模型输出工具调用，不等于文件已经被修改             |
| Harness | 提供工具、执行循环、上下文、会话和执行约束        | 不只是一次模型 API 请求，也不只是一段提示词        |
| 产品    | 把上述能力组织成终端、编辑器或 Web 中可用的工作流 | SDK 有某能力，不等于产品已做好对应交互             |
| SDK     | 给应用开发者提供调用接口                          | 可能是进程内库，也可能是 HTTP 客户端或子进程客户端 |

“都有 SDK”和“都有插件”只能说明存在入口。真正需要比较的是：入口后面运行着什么，状态归谁持有，扩展能改变到哪一层。

## 怎样读表格和图

- **原生支持**：该基线的库或产品明确提供；是否默认启用仍看配置。
- **扩展实现**：需要额外插件、包或应用代码，不算当前工作台已经接入。
- **教学示例**：用于讲清机制，不等于成熟的生产契约。
- **未核实**：本次材料不足，不能转换成“不支持”。

五张图分别采用会话嵌入、客户端服务端、插件组合、机制演进和接入边界结构。实线表示调用或数据返回，虚线表示配置或机制挂载；图内颜色只是辅助，文字标注给出具体含义。

本专题没有安装运行外部 Agent，没有请求付费模型，也没有进行效果、速度或成本基准测试。场景选型是基于已核验架构的工程判断；示例面试回答不代替真实的个人选型经历。
