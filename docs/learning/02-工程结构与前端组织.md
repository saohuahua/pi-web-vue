# 工程结构与前端组织

对应业务流程：[页面对象与职责](业务流程与前后端协作/B01-业务对象与职责分工.md)。本篇解释这些职责为什么分别放在组件、store、composable 和纯函数，而不是集中进一个聊天组件。

> 本篇接在 [核心链路](00-从最小Agent到Web工作台.md) 后面。已经知道一句话怎样往返，现在看怎样把输入、连接、状态和展示放进合适的模块。

## 实现思路 让代码的归属跟随状态生命周期

### 先确定拆分的依据

同一个任务会同时影响输入框、消息区、运行状态条和侧栏。组件需要共享会话事实，但文件标签、模型草稿与局部展开状态又不应随着一次消息刷新一起重置。拆分模块前，要先判断谁拥有数据、谁使用数据，以及数据应该活多久。

### 四个设计决定

1. **页面负责进入和离开，store 负责业务过程。** 路由将会话 ID 交给 chat store，由它协调历史、连接和运行状态。这样组件可以围绕同一会话协作，旧页面卸载时也有明确的关闭入口与身份检查。
2. **将确定性规则从网络和 UI 中提取。** 消息 reducer 只计算旧状态如何变成新状态，不负责 fetch、弹提示或滚动。store 决定何时调用它，再提交到 reactive 容器，便于直接验证事件序列的结果。
3. **按业务领域拆共享状态。** 侧栏列表刷新只更新 sessions，文件切换只更新 file-viewer，模型编辑保留在 models-config。共享并不意味着必须共用一个可以被整体替换的大对象。
4. **分别控制首次加载与后续保留。** 异步组件决定代码何时需要加载，everOpened 决定首次何时挂载。打开后保留外壳组件，避免仅因暂时关闭就丢掉全部局部阅读状态；真正的内部面板状态仍遵循各自挂载条件。

这些决定落实后，读一个函数时就能先判断它应当管什么。例如 reducer 不应决定是否重连，文件标签 store 也不应接管 Agent 停止。

## 一 从一个聊天组件开始拆分

最小聊天页可以在一个 Vue 组件里完成：

1. 读取输入框。
2. 发送请求并建立事件连接。
3. 累计回答。
4. 显示结果。

加入会话切换、文件引用和工具状态后，同一个组件就同时管理页面、网络与消息规则。项目按责任拆分，让不同生命周期的内容有自己的归属。

## 二 一个工程 两个运行环境

| 位置 | 运行环境 | 主要能力 |
| --- | --- | --- |
| `app/` | 浏览器 | DOM 用户输入 EventSource 与 localStorage |
| `server/` | Node | SDK 文件系统 命令执行和配置读写 |
| `shared/lib/` | 由导入方决定 | 共享类型 协议适配 路径函数和消息变换 |

Nuxt 把前后端代码放在同一工程。当前配置 `ssr: false` 表示页面采用客户端渲染，Node API 仍然存在。

> `shared` 是代码归属，不是第三个进程。放在那里也不意味着代码同时在两端执行。

## 三 先搭页面骨架 再放业务状态

页面关系可以简化为下面的结构，省略布局与操作按钮：

```vue
<SessionSidebar />
<NuxtPage />
<FileViewer v-if="viewer.everOpened" />
<CapabilityCenterModal v-if="center.everOpened" />
```

- **外壳 `app.vue`**：组织侧栏、中央路由区、文件 Inspector 和能力中心。
- **首页**：提供选择目录与新建会话入口。
- **会话路由页**：读取 URL 中的 ID，打开对应会话。
- **`ChatPanel`**：组织消息、运行状态和输入区。

路由页保持较薄。会话加载和消息处理由 chat store 协调，便于多个组件读取同一业务事实。

## 四 为什么要拆成多个 store

先看一个跨区域操作：用户在侧栏引用文件，中央输入框获得文件路径。侧栏和输入框不是简单父子关系，共享 chat draft 比穿过多层组件转发更直接。

但文件标签与模型表单没有必要一起塞进 chat store。

| Store | 保存什么 | 主要消费者 |
| --- | --- | --- |
| workspace | 当前项目和 worktree 选择 | 选择器 文件树和新会话入口 |
| sessions | 会话列表 | 侧栏 |
| chat | 当前会话 消息 输入和运行状态 | 对话区与输入框 |
| file-viewer | 文件标签与活动路径 | 文件树 消息链接和 Inspector |
| models-config | 模型表单草稿与保存状态 | 模型配置面板 |
| ui 与 settings | 布局状态与应用偏好 | 页面外壳与设置界面 |

状态是否共享和状态是否持久化是两个独立问题：

- 临时展开与测量值可以留在组件。
- 多个消费者使用的业务事实适合放 store。
- settings 显式写 localStorage。
- 模型配置提交服务端保存。
- chat 历史主要由服务端会话记录恢复。

> Pinia 提供状态组织，不会自动把所有状态写到磁盘。

## 五 组件 composable 和纯函数怎样配合

以消息更新为例：

```text
连接管理器收到事件
  → chat store 判断归属与阶段
  → reducer 计算下一份消息状态
  → store 写回 Vue 响应式对象
  → MessageItem 展示
```

三类代码按依赖区分：

1. **组件**：需要模板、用户操作和展示状态。
2. **composable**：需要 Vue 生命周期或 DOM，例如跟随滚动。
3. **纯函数**：根据输入计算输出，例如消息块组装。

实际状态提交代码为：

```ts
const stream = reactive<StreamingState>({ ...INITIAL_STREAMING_STATE });

function applyStream(action: Parameters<typeof streamReducer>[1]) {
  Object.assign(stream, streamReducer(stream, action));
}
```

- reducer 返回新数据，不依赖 Vue。
- `Object.assign` 写回已有代理容器，组件继续读取同一个响应式对象。
- `Parameters` 复用 reducer 动作参数类型，避免重复定义。

连接管理器则是持有连接与定时器的普通类，不能因为它不在组件里就称为纯函数。

## 六 前端实现亮点 延迟挂载与职责拆分

### 1 重面板等首次使用时再加载

源码中的加载入口是显式异步 import：

```ts
const FileViewer = defineAsyncComponent(() => import("~/components/FileViewer.vue"));
const CapabilityCenterModal = defineAsyncComponent(
  () => import("~/components/capabilities/CapabilityCenterModal.vue"),
);
```

这里定义的是异步组件包装器，真正进入挂载流程才需要取得组件实现。模板再用 `v-if="viewer.everOpened"` 控制首次挂载，两者分别控制代码获取与组件创建。若只是定义异步组件却立即在模板渲染，它仍会在首屏就开始加载。

项目用 `defineAsyncComponent` 定义文件预览和能力中心，再用 `everOpened` 控制首次挂载。

运行过程：

1. 初次进入应用，用户尚未打开面板。
2. `everOpened` 为 false，不触发该面板的首次挂载。
3. 首次打开时，加载异步组件并挂载。
4. 此后 `everOpened` 保持 true，外壳不因关闭操作立刻销毁组件。

**值得讲的点**：按功能使用时机决定加载与挂载，而不只是给组件换一个异步名称。

**边界**：

- 共享依赖可能已被其他组件使用，不能宣称全部 Markdown 或高亮代码都不进首屏。
- 子面板仍可能按当前标签重建。
- 没有测量首屏耗时与产物体积，不能给出量化收益。

### 2 业务规则可以脱离页面验证

前面的 `applyStream` 还有一个重要的引用关系：组件读取的是 reactive 创建的代理，reducer 返回的是普通的新对象。`Object.assign` 将新对象字段写入旧代理，让外层引用稳定而内部消息发生替换。

1. reducer 计算下一份 `streamingMessage`。
2. store 写入 `stream.streamingMessage`。
3. Vue 触发依赖该字段的更新。
4. 组件读取新消息，渲染仍由组件自己的依赖决定。

如果把局部变量直接换成 reducer 返回的普通对象，既有消费者仍可能持有旧代理。这里保留外壳、替换字段，明确了数据计算与响应式提交的交接位置。

- reducer 用事件输入与状态输出测试。
- store 用交错请求测试会话切换。
- DOM 滚动和真实布局留给浏览器验证。

这里的价值是依赖清楚、验证层次明确，拆文件本身不保证更快。

## 七 路由切换时 怎样清理旧页面

假设从会话 A 切到 B，B 已打开，A 的卸载回调才执行。无条件关闭 chat 会误关 B。

当前源码增加身份检查：

```ts
function closeIfCurrent(id: string | null | undefined) {
  if (id && sessionId.value !== id) return;
  close();
}
```

1. 旧页面带上自己负责的会话 ID。
2. store 比较当前 ID。
3. 已切到别的会话就跳过关闭。

> 页面清理关闭的是前端订阅。请求停止 Agent 是另一条命令。

这个检查处理旧页面误关新会话，不能代替所有请求代次控制。`A→B→A` 等问题在 [异步恢复](07-异步协作与恢复.md) 展开。
