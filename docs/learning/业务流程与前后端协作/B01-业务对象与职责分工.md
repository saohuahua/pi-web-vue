# B01 业务对象与职责分工

用户选择一个本地工程，输入“读取 README，告诉我怎么启动”。页面随后显示正在读取文件、文件内容和启动说明。继续问“帮我运行测试”，系统应当仍在同一个工程里工作，并知道前面讨论过什么。

要完成这些操作，系统必须同时确定三件事：在哪个目录执行、继续哪段对话、这一次请求现在进行到哪一步。工作区、会话和任务分别回答这些问题。

## 一 先把页面上的东西对应到业务对象

| 页面上的操作或内容 | 对应的对象 | 它保存或决定什么 |
| --- | --- | --- |
| 选择项目或 worktree | 工作区选择 | 新会话的执行目录，以及文件浏览的目录范围 |
| 点击侧栏的一段对话 | 会话 | 持续对话的身份、执行目录、历史与当前上下文位置 |
| 发送一次要求 | 一次提交及其后续执行 | 本次输入是否被接受，执行中产生了哪些消息和工具调用 |
| 一条用户或助手气泡 | 消息 | 用户输入、助手正文、思考或工具调用内容 |
| 一张工具卡片 | 一次工具调用 | 工具名称、参数、调用身份与对应结果 |
| 编辑旧问题后重发 | 会话分支 | 新问题基于哪段旧上下文继续 |
| 输入框里还没发出去的文字 | 用户草稿 | 尚未确认提交的内容及可能的编辑目标 |

会话可以包含很多次提交，一次提交又可以产生多条消息。比如用户要求“读文件并运行测试”，助手可能先说明计划，再调用读取工具、调用命令工具，最后总结结果。不能把一条助手消息的结束当成整次执行的结束。

“任务”在这里表示一段运行中的工作。当前应用主要通过会话实例、执行计数和 SDK 状态管理它，没有独立的持久任务表和完整命令状态查询接口。浏览器拿到会话 ID，不等于拿到了一个能跨进程恢复任意执行步骤的任务编号。

## 二 工作区与会话为什么要分开

假设先在工程 A 创建会话，再把顶部工作区选择切到工程 B。已有会话里的 Agent 不能悄悄改成读取 B，否则同一句“修改刚才的文件”会作用到另一份工程。

因此，工作区选择决定新建时使用的目录；会话创建后持有自己的执行目录。打开历史会话时，页面再根据该会话的目录同步工作区。两个同步方向不同：新建由工作区决定会话位置，恢复由会话决定页面应该显示哪个项目。

执行目录通常记作 cwd，可以理解为命令行当前所在目录。工具收到相对路径 README.md 时，需要在这个执行环境下解释。项目身份用于把同一仓库的会话归在一起，实际执行目录则可能是主目录，也可能是某个 worktree。

Git worktree 是另一份工作目录，会话分支是另一条对话上下文。切换会话分支不等于切换 Git 分支，也不会撤销此前工具已经写入磁盘的代码。后面编辑旧问题时，这个区别尤其重要。

工作区与会话的同步方向对应 [工作区专题的状态分工](../03-工作区与会话管理.md#五-前端实现亮点-列表与当前会话分开)；读到组件和 store 的拆分时，再对照 [前端状态归属](../02-工程结构与前端组织.md#四-为什么要拆成多个-store)，就能理解为什么侧栏刷新不应该重置中央区正在生成的消息。

## 三 浏览器、后端、SDK 和模型分别做什么

### 浏览器负责用户操作与展示

浏览器收集文字、图片和操作意图，通过接口交给服务端；接收文本和工具事件，将它们整理成消息、卡片和状态提示。它还保存用户草稿，处理切会话、文件预览和界面交互。

页面上的运行标记是一份展示状态。例如发送后先显示用户气泡，是为了及时反馈点击，不代表服务端已经接受。接口结果和运行事件到达后，页面还要继续校正这份状态。

### Node 后端负责接入执行环境

Node 是运行在本机上的 JavaScript 服务进程。它能访问工程文件，保存和查找 SDK 会话，并向浏览器提供接口。浏览器提交会话 ID 和本次命令，后端根据 ID 找到运行对象，再处理命令；浏览器不需要传递整个运行对象。

这里的运行对象可以理解为“服务端仍然活着的一段会话”：包含当前模型、上下文、生成状态及工具执行所需资源。它是内存中的对象，不是一个 HTTP 响应。请求返回以后，对象仍可以继续执行工作。

### SDK 负责推进 Agent 执行

SDK 是后端调用的库。它组织模型请求、接收工具调用、执行可用工具、把工具结果交回模型，并管理会话记录和运行事件。应用在 SDK 外面加了一层管理逻辑，处理实例复用、命令接纳、浏览器订阅和资源清理。

这层分工解释了为什么应用不需要在 Vue 组件里自己编写模型与工具循环，但仍然需要写大量状态处理：SDK 产生事件，不会直接替页面恢复输入、隔离旧请求或打开文件面板。

### 模型生成内容和下一步调用意图

模型收到上下文与工具说明后，可以生成文字，也可以提出“使用读取工具，参数是 README.md”。真正读磁盘的是服务端工具，模型服务并不是直接进入用户电脑寻找文件。

工具结果再次进入模型上下文，模型才能根据实际文件内容回答。一次工具调用失败，也可以作为结果交回模型，由后续执行决定是否换路径、补充信息或结束。

| 参与方 | 收到什么 | 做什么 | 输出什么 |
| --- | --- | --- | --- |
| 浏览器 | 用户文字、图片和点击 | 收集输入，发命令，展示状态 | 命令请求、页面画面 |
| 应用后端 | 会话 ID 与命令 | 找会话，检查命令，接入 SDK | 接受结果、查询结果、事件流 |
| SDK | 输入、模型配置、工具集合 | 组织上下文并推进执行 | 消息、工具调用、执行事件、会话记录 |
| 模型 | 上下文和工具说明 | 生成内容或提出工具调用 | 文本或结构化调用意图 |
| 工具实现 | 工具参数及执行环境 | 读取文件、执行命令等具体动作 | 数据、执行输出或错误 |

这里的 SDK 会话还包含“负责执行的对象”和“负责记录的对象”。[SDK 专题的两个对象](../01a-认识pi-SDK与Web工作台.md#两个对象分别做什么)会把这组职责对应到具体接口；理解这层关系，再读创建和恢复流程，就不容易把打开历史文件误认为恢复了正在执行的任务。

## 四 为什么同一会话有三条数据路径

前端常见的表单流程是“提交一次请求，拿到结果，更新页面”。Agent 执行可能持续较久，期间需要不断展示进度，而且用户刷新后仍要读取过去的内容。因此当前项目将数据分成三条路径。

**命令路径**处理发送、停止、切模型、压缩和导航等操作。响应表示该命令对应的确认或结果。发送命令主要确认接纳，不携带完整回答。

**事件路径**用 SSE 持续推送变化。SSE 可以理解为一条保持打开的 HTTP 响应，服务端不断写入事件，浏览器持续接收。文本追加、工具开始和任务结束都通过这条路径到达页面。

**历史查询路径**返回当前会话已有记录，包括消息及其真实记录 ID。页面刷新没有经历先前事件，就通过这条路径重建历史；正在生成的当前消息再通过运行快照补充。

事件回答“刚刚发生了什么”，历史和运行态查询回答“现在能读到什么”。二者结合才能恢复页面，单靠重新打开连接只能收到连接之后的变化。

## 五 四个关键时点决定不同页面行为

| 关键时点 | 已经发生什么 | 还不能推导什么 |
| --- | --- | --- |
| 用户点击发送 | 页面拿到了本次输入 | 服务端已接受 |
| 命令接受确认 | SDK 已接纳本次调用 | 回复已完成、工具已成功 |
| 一条消息结束 | 一个消息内容单元定稿 | 后续没有工具或其他消息 |
| 整体执行落定 | 当前执行阶段收敛，页面进入结束处理 | 此前所有工具都成功，或文件已恢复到执行前 |

例如工具已经读完 README，助手还在生成总结；工具调用结束了，但用户要求的解释尚未完整显示。又如用户点击停止，停止请求返回与后续结束事件可能先后交错，页面还要清理残留工具状态并核对历史。

失败也属于执行结果。一轮执行已经结束，可以同时存在“某个工具执行失败”的事实。运行中、已结束与成功、失败是两个维度。

## 六 状态保存在哪里，决定了能恢复到什么程度

| 数据 | 主要保存位置 | 页面刷新后的情况 |
| --- | --- | --- |
| 当前页面的运行标记和活跃工具 | 浏览器内存 | 需要重新查询或接收事件恢复 |
| 按会话保存的文字草稿 | 浏览器 localStorage，失败时降级内存 | 持久化成功时可恢复文字；降级内存后刷新会丢 |
| 待发送图片 | 当前页面状态 | 没有随文字草稿跨刷新持久化 |
| 正在执行的会话实例与当前消息 | Node 进程内存 | 服务端实例仍在时可以继续提供运行态 |
| 已保存的会话记录 | SDK 管理的本地会话文件 | 可重新读取历史与上下文位置 |
| 模型等正式配置 | 本地配置文件 | 可再次加载，但已有实例何时刷新需单独处理 |

关闭浏览器连接不会自动调用停止命令，因此任务可能继续。Node 进程退出则会丢失内存执行状态：能读回历史，不表示可以从工具执行到一半的位置自动续跑。

当前实例还有空闲回收机制，有浏览器订阅时会推迟回收。无订阅者的长时间静默任务仍需要关注回收条件，所以“离开页面不主动停止”也不等于“后台任务永远保活”。

这份存储位置表可以和 [架构图中的前后端与存储](../01-项目总体架构与核心功能.md#二-系统的三个参与方)对照：先标出数据在哪里，再沿箭头找读取或写入它的模块。涉及历史、页面消息和模型输入的差异，继续读 [三种消息集合](../08-会话存储与上下文.md#一-三种消息集合-为什么不能混在一起)。

## 七 从一个页面问题找到正确的数据来源

看到“消息显示运行中”，先分清是网页仍保留旧标记，还是服务端实例确实还在执行。看到“图片没有发送”，检查提交时保存的附件批次，而不是先怀疑模型。看到“切项目后读错文件”，确认正在继续哪个会话及其执行目录。

这三个问题分别属于展示状态、输入归属和执行环境。明确对象后，才能找到对应请求和状态；仅看界面上同一个加载动画，无法判断它们的原因。
