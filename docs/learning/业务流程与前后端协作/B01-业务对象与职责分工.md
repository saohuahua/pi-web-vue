# B01 业务对象与职责分工

用户选择一个本地工程，输入"读取 README，告诉我怎么启动"。页面随后显示正在读文件、文件内容和启动说明。继续问"帮我运行测试"，系统应当仍在同一个工程里工作，并记得前面讨论过什么。

要完成这些操作，系统必须同时确定三件事：

1. **在哪个目录执行** —— 由工作区回答
2. **继续哪段对话** —— 由会话回答
3. **这一次请求进行到哪一步** —— 由任务回答

## 一 先把页面上的东西对应到业务对象

| 页面上的操作或内容 | 对应的对象 | 它保存或决定什么 |
| --- | --- | --- |
| 选择项目或 worktree | 工作区选择 | 新会话的执行目录，以及文件浏览的目录范围 |
| 点击侧栏的一段对话 | 会话 | 持续对话的身份、执行目录、历史与当前上下文位置 |
| 发送一次要求 | 一次提交及其后续执行 | 本次输入是否被接受，执行中产生哪些消息和工具调用 |
| 一条用户或助手气泡 | 消息 | 用户输入、助手正文、思考或工具调用内容 |
| 一张工具卡片 | 一次工具调用 | 工具名称、参数、调用身份与对应结果 |
| 编辑旧问题后重发 | 会话分支 | 新问题基于哪段旧上下文继续 |
| 输入框里还没发出去的文字 | 用户草稿（`pendingDraft`） | 尚未确认提交的内容及可能的编辑目标 |

> **会话可以包含很多次提交，一次提交又可以产生多条消息**。不能把一条助手消息的结束当成整次执行的结束。

> "任务"表示一段运行中的工作。当前应用主要通过会话实例、执行计数和 SDK 状态管理它，**没有独立的持久任务表**。浏览器拿到会话 ID，不等于拿到一个能跨进程恢复任意执行步骤的任务编号。

## 二 工作区与会话为什么要分开

假设先在工程 A 创建会话，再把工作区切到工程 B。已有会话里的 Agent 不能悄悄改读 B，否则"修改刚才的文件"会作用到另一份工程。

- **新建**：工作区选择决定会话位置
- **恢复**：会话决定页面应该显示哪个项目

两个同步方向不同：

| 方向 | 谁决定谁 |
| --- | --- |
| 新建会话 | 工作区选择 → 会话的 cwd |
| 打开历史会话 | 会话的 cwd → 页面同步工作区 |

- 执行目录通常记作 **cwd**，可理解为命令行当前目录，工具收到相对路径 README.md 时在此环境下解释
- 项目身份用于把同一仓库的会话归组，实际执行目录可能是主目录或某个 worktree

> **Git worktree 是另一份工作目录，会话分支是另一条对话上下文**。切换会话分支 ≠ 切换 Git 分支，也不会撤销此前工具已写进磁盘的代码。

工作区与会话的同步方向对应 [工作区专题的状态分工](../03-工作区与会话管理.md#五-前端实现亮点-列表与当前会话分开)。

## 三 浏览器、后端、SDK 和模型分别做什么

**浏览器**：收集文字、图片和操作意图，通过接口交给服务端；接收文本和工具事件，整理成消息、卡片、状态提示。还保存用户草稿、处理切会话和文件预览。

**Node 后端**：运行在本机的 JS 服务进程，能访问工程文件，保存和查找 SDK 会话。浏览器提交会话 ID 和命令，后端按 ID 找到**运行对象**（`AgentSessionWrapper`）再处理命令。

> 运行对象是"服务端仍活着的一段会话"：含当前模型、上下文、生成状态、工具执行资源。它是**内存中的对象，不是 HTTP 响应**——请求返回后仍可继续执行。

**SDK**：后端调用的库，组织模型请求、接收工具调用、执行工具、把结果交回模型，管理会话记录和运行事件。应用在 SDK 外再加一层管理逻辑（实例复用、命令接纳、浏览器订阅、资源清理）。

**模型**：收到上下文与工具说明，生成文字或提出工具调用意图。真正读磁盘的是服务端工具，模型服务不直接进入用户电脑找文件。

| 参与方 | 收到什么 | 做什么 | 输出什么 |
| --- | --- | --- | --- |
| 浏览器 | 用户文字、图片、点击 | 收集输入、发命令、展示状态 | 命令请求、页面画面 |
| 应用后端 | 会话 ID 与命令 | 找会话、检查命令、接入 SDK | 接受结果、查询结果、事件流 |
| SDK | 输入、模型配置、工具集合 | 组织上下文并推进执行 | 消息、工具调用、执行事件、会话记录 |
| 模型 | 上下文和工具说明 | 生成内容或提出工具调用 | 文本或结构化调用意图 |
| 工具实现 | 工具参数及执行环境 | 读文件、执行命令等具体动作 | 数据、执行输出或错误 |

> SDK 会话还包含"负责执行的对象"和"负责记录的对象"两个职责，见 [SDK 专题的两个对象](../01a-认识pi-SDK与Web工作台.md#两个对象分别做什么)。理解这层关系，再读创建和恢复流程，就不容易把"打开历史文件"误认为"恢复正在执行的任务"。

## 四 为什么同一会话有三条数据路径

前端常见表单流程是"提交一次请求 → 拿结果 → 更新页面"。Agent 执行可能持续较久，期间需不断展示进度，且刷新后要能读回过去内容，所以数据分成三条路径：

| 路径 | 处理什么 | 响应含义 |
| --- | --- | --- |
| **命令路径**（`POST /api/agent/:id`） | 发送、停止、切模型、压缩、导航 | 对应命令的确认或结果，发送主要确认**接纳**，不携带完整回答 |
| **事件路径**（SSE，`events.get.ts`） | 持续推送变化 | 文本追加、工具开始、任务结束 |
| **历史查询路径**（`context.get.ts` 等） | 已有记录 + 真实记录 ID | 刷新后重建历史，正在生成的消息再靠快照补充 |

> SSE 是一条保持打开的 HTTP 响应，服务端不断写入事件、浏览器持续接收。

> **事件回答"刚刚发生了什么"，历史和运行态查询回答"现在能读到什么"**。二者结合才能恢复页面，单靠重开连接只能收到连接之后的变化。

## 五 四个关键时点决定不同页面行为

| 关键时点 | 已经发生什么 | 还不能推导什么 |
| --- | --- | --- |
| 用户点击发送 | 页面拿到了本次输入 | 服务端已接受 |
| 命令接受确认 | SDK 已接纳本次调用 | 回复已完成、工具已成功 |
| 一条消息结束 | 一个消息内容单元定稿 | 后续没有工具或其他消息 |
| 整体执行落定 | 当前执行阶段收敛，进入结束处理 | 此前所有工具都成功、文件已恢复 |

> 工具读完 README、助手还在生成总结——工具调用结束了，但用户要求的解释尚未完整显示。

> **失败也属于执行结果**：一轮执行结束，可同时存在"某工具执行失败"的事实。运行中/已结束 与 成功/失败 是两个维度。

## 六 状态保存在哪里，决定了能恢复到什么程度

| 数据 | 主要保存位置 | 页面刷新后的情况 |
| --- | --- | --- |
| 页面运行标记和活跃工具 | 浏览器内存 | 需重新查询或接收事件恢复 |
| 按会话保存的文字草稿 | localStorage，失败降级内存 | 持久化成功可恢复；降级内存刷新会丢 |
| 待发送图片 | 当前页面状态 | 不随文字草稿跨刷新持久化 |
| 会话实例与当前消息 | Node 进程内存 | 服务端实例仍在时继续提供运行态 |
| 已保存的会话记录 | SDK 管理的本地会话文件 | 可重新读历史与上下文位置 |
| 模型等正式配置 | 本地配置文件 | 可再次加载，但已有实例何时刷新需单独处理 |

- 关闭浏览器连接**不会**自动调用停止命令，任务可能继续
- Node 进程退出会丢内存执行状态：能读回历史，不表示能从工具执行到一半的位置自动续跑

> 实例有**空闲回收**（`IDLE_RECYCLE_MS`，10 分钟）：有浏览器订阅时推迟回收；无订阅者的长时间静默任务仍要关注回收条件。"离开页面不主动停止" ≠ "后台任务永远保活"。

这张表可对照 [架构图中的前后端与存储](../01-项目总体架构与核心功能.md#二-系统的三个参与方)。涉及历史、页面消息、模型输入的差异，继续读 [三种消息集合](../08-会话存储与上下文.md#一-三种消息集合-为什么不能混在一起)。

## 七 从一个页面问题找到正确的数据来源

| 看到的现象 | 先分清 | 属于哪类 |
| --- | --- | --- |
| "消息显示运行中" | 网页旧标记，还是服务端实例确在执行 | 展示状态 |
| "图片没有发送" | 提交时保存的附件批次 | 输入归属 |
| "切项目后读错文件" | 正在继续哪个会话及其 cwd | 执行环境 |

> 明确对象后，才能找到对应请求和状态；仅看界面上同一个加载动画，无法判断它们的原因。
