# B02 创建会话到完成一次任务

用户选中项目，发送“读取 README，告诉我怎么启动”。页面需要先确认工程位置，再找到可执行的会话，让模型获得文件内容，最后显示有依据的回答。下面按实际发生顺序拆开这次操作。

## 一 选择目录：先确定任务在哪里执行

浏览器里的路径字符串只是用户输入。服务端收到选择请求后，规范化路径，检查目标存在且是目录，再解析它属于哪个项目。普通目录也可以成为工作区；Git 仓库额外提供项目与 worktree 关系。

校验成功后，页面才更新工作区选择，并保存上次使用的目录。这样输入了一个不存在的路径，不会把原来可用的工作区直接替换成错误状态。

目录校验还会把该目录加入文件浏览的允许范围，供文件树和预览使用。这个授权针对应用的文件接口，SDK 工具执行使用的是自己的运行环境，两者的关系在 B05 展开。

浏览器保存的上次选择不是永久有效的事实。目录可能后来被删除、移动，或者所处磁盘没有挂载。重新使用时仍要以服务端能否访问为准。

## 二 创建会话：准备身份与运行环境

创建请求向后端提交执行目录。后端创建会话记录管理器，取得该会话的目录，再加载设置、模型运行资源和扩展资源，创建 SDK 会话对象。应用为对象安装事件监听并加入实例注册表，最后把真实会话 ID 返回页面。

实例注册表可以理解为一张进程内的索引：给定会话 ID，就能找到仍活着的运行对象。之后发送请求和事件订阅请求虽然是两次 HTTP 请求，都通过同一个 ID 取得同一个实例。

历史会话恢复时还需要处理并发初始化。假设页面同时发起事件订阅和状态查询，两条请求都发现实例尚未存在。如果各自创建，就会得到两个执行对象，出现命令进入一个对象、事件却监听另一个对象的问题。因此后端还记录正在进行的初始化，后来的请求等待同一次创建完成。

新建会话与恢复会话的语义不同：同一个历史会话的并发恢复应合并，两次独立点击新建则应产生两个会话。当前新建流程为每次创建分配独立临时身份，避免把两次新建误合并。

### 为什么创建后还要单独发送第一句话

创建接口只准备空会话，不同时提交首条输入。页面拿到 ID 后进入会话页，准备事件订阅，发送时再等待订阅就绪。

如果把创建与首条执行合在一起，服务端可能已经生成内容，浏览器还不知道会话 ID，更没有开始接收事件。短回答甚至可能在页面订阅前结束。先创建、后订阅、再发送，解决的是开始执行时就具备观察通道。

空会话也可能尚未生成磁盘文件。当前详情接口会优先读取存活实例里的会话管理器，因此“找不到历史文件”不能直接等同于“刚创建的会话不存在”。

同一会话的并发恢复为什么能合并，具体由 [服务端初始化等待机制](../04-Agent服务与生命周期.md#三-两个请求同时恢复-为什么需要第二张-map)解释。对照本节阅读时，重点看“已存在的实例”和“正在创建的实例”为什么需要分别记录。

## 三 点击发送：先固定输入，再等待网络

本次输入包括文字和可选图片。页面在点击时保存这批输入，等待期间用户新增的附件不应混进本次请求，成功后也只能清除本批附件。

同时，提交逻辑保留待确认文字，清空可编辑输入，立即显示用户气泡和运行反馈。保留待确认文字是为了处理握手失败、请求失败和刷新：输入框清空不代表服务端已经接受，原内容此时仍要能够找回。

这段等待可能跨越会话切换。因此提交还记住会话 ID 与生命周期代次。代次是每次关闭、重新进入后变化的编号，用来区分“同一个会话 ID 对应的不同次打开”。握手或命令返回后，只有身份和代次都仍匹配，旧操作才能继续影响当前页面。

按钮禁用只能阻止当前页面的一部分误操作。服务端仍检查消息类型、图片和运行模式等输入，并在导航或压缩等不适合接纳的状态下拒绝发送。其他窗口或直接请求不会经过当前按钮，服务端判断仍然必要。

## 四 业务握手：连接建立不等于已经能接收任务事件

浏览器先连接 SSE。服务端可以立即打开 HTTP 响应，但取得会话实例和安装业务监听还需要时间。此时网络通道存在，不代表即将发生的 SDK 事件已经有人转发。

服务端在实例就绪、监听安装后，发送业务握手。前端等到这条消息才提交 prompt，也就是用户要求。当前握手还携带是否正在流式执行的信息，用于已有会话的运行恢复。

两种信号要分开理解：HTTP 连接打开说明传输可用，业务握手说明这个会话的事件接入已准备好。发送等待后者，避免快速输出早于监听。

若初始化失败，事件通道发送启动错误，等待发送的逻辑撤回本地临时气泡并保留输入。这个阶段尚未通过该发送路径提交 prompt，和“prompt 已发出但没收到响应”有不同含义。

业务握手在 [协议专题的连接就绪处理](../05-HTTP与SSE协议.md#四-先完成业务握手-再发-prompt)中展开。这里规定发送前必须有人监听，技术篇说明连接对象怎样把收到握手这件事转成发送流程可以等待的结果。

## 五 服务端接纳：为什么响应可以早于最终回答

命令接口根据会话 ID 查找存活实例；没有实例时，先定位已有会话文件并恢复。取得实例后，应用检查命令，交给 SDK 执行。

一次 prompt 有两个需要观察的时点。第一个是 SDK 预检通过，表示调用被接纳；第二个是完整执行结束，可能已经经历多次模型请求和工具调用。应用分别等待这两个结果：HTTP 可以在成功预检后返回，后台继续观察完整执行，后续进度走事件通道。

预检可以理解为正式执行前的检查关口，涉及 SDK 与扩展的处理。应用不是收到 HTTP 请求就无条件确认成功，而是等待成功接纳信号；预检前失败通过 HTTP 错误返回，接受后的异步失败通过事件报告。

服务端还维护未完成调用计数。它避免“HTTP 已经返回，所以会话已经空闲”的误判；同步抛错和异步结束都需要正确减少计数，否则可能永久显示运行中。

| 时点 | HTTP 侧 | 事件侧 | 页面应表达什么 |
| --- | --- | --- | --- |
| 等待业务握手 | 尚未提交 prompt | 等待订阅就绪 | 输入已提交到页面，正在准备 |
| prompt 预检失败 | 返回错误 | 不应把它当成已接受任务 | 显示原因，保留输入 |
| prompt 被接受 | 可以返回确认 | 执行继续 | 保持运行展示 |
| 接受后执行出错 | 原确认不能被撤回 | 报告后续错误 | 显示执行失败及已有内容 |
| 执行结束 | 请求可能早已结束 | 消息与结束相关事件到达 | 整理结果，刷新历史和统计 |

HTTP 与 SSE 是独立通道，事件也可能比接受响应更早到达。页面按各自含义处理，不能假设所有事件一定发生在 POST 返回之后。

这两个完成时点对应 [接受确认与完整执行的两个 Promise](../04-Agent服务与生命周期.md#五-接受任务和完成任务-为什么是两个-promise)。需要验证它们确实分开时，接着读 [保持执行未完成的测试](../11-测试体系与验证边界.md#三-异步测试-先控制时间顺序)：先让预检成功，故意不结束执行，检查 HTTP 确认与运行标记。

## 六 模型怎样真正取得 README

SDK 把当前上下文、用户要求和可用工具说明发给模型。上下文就是本次请求中模型能够看到的材料，包含历史对话、指令和必要的工具结果，不是浏览器页面上所有数据的自动集合。

模型若决定读取 README，会提出工具调用，说明工具名称和参数。参数里的路径告诉工具读哪个文件。SDK 调用服务端的读取实现，取得文件内容，再把结果送回后续模型请求。

模型随后根据真实内容回答启动方式；如果还缺依赖脚本信息，也可能继续读取 package.json。工具提供真实外部信息，模型负责利用信息生成下一步内容。

启用工具并不意味着每个问题都必定触发调用。模型可能根据已有上下文直接回答，具体调用也受指令、工具集合和 SDK 执行影响。页面能可靠展示的是实际发生的调用和返回结果。

### 文件不存在时谁处理

读取失败会形成工具错误或执行错误，具体取决于失败位置。工具层已经返回可处理错误时，模型可以看到这个结果，继续尝试其他路径或解释问题；若模型请求本身失败，则还涉及 SDK 的错误与重试机制。

因此“工具卡片显示错误”不一定意味着后续整轮任务立即停止。前端分别展示这次工具结果和整体运行状态，而不是把任意局部错误统一解释为整段会话不可用。

## 七 过程怎样变成页面上的消息和工具卡片

服务端监听 SDK 事件，再适配成浏览器使用的数据。文本增量只需要新增片段，重复携带的完整消息会被裁剪；工具 ID 和名称若原本藏在完整快照里，则先提取出来，避免裁剪后无法关联调用。

浏览器把正在生成的助手消息与已完成消息分开保存。正文片段进入对应文本块，工具参数片段进入工具块；参数未生成完整时先保存原始片段，结束时再采用完整结构化参数。这样不会把半截参数当成可执行对象。

工具还同时有实时执行状态和最终结果。执行开始后进入活跃工具集合，进度事件更新摘要，执行结束后从活跃集合移除；最终工具结果保存在消息里，按调用 ID 配回卡片。两次同名读取靠不同调用 ID 区分，不能按名字或相邻位置匹配。

一条完整消息结束时，它进入历史展示列表，当前流式气泡清理。完整执行落定时，再清理活跃工具、重试等运行状态，重读会话详情和运行信息。详情补回真实记录 ID、分支位置和统计，避免只靠前端临时身份长期维持历史。

从事件到页面的细节见 [文本组装演算](../06-消息状态与工具渲染.md#四-先手算一遍文本组装)和 [工具参数与结果配对](../06-消息状态与工具渲染.md#六-工具参数和结果怎样接到卡片)。沿同一条读取任务看，前者解释文字如何增长，后者解释工具卡片为什么不能只按名称匹配。

## 八 请求报错以后，是否可以重新发送

先看错误发生在接纳之前还是接纳结果未知。

握手失败时，本次 prompt 尚未通过发送流程发出，可以保留输入供再次尝试。明确的业务拒绝应根据原因修正。请求已经发出，但 HTTP 响应丢失时，任务可能已在服务端运行，直接重发可能产生第二次工具执行。

当前普通发送会提示提交结果未确认、保留文字并重读历史，但没有完整的命令 ID 查询与服务端去重。这个处理帮助用户核对结果，不能证明同一请求绝不重复执行。重新提交前应先确认原会话是否已有本次任务及结果。

同样，看到助手写“测试通过”时，可以继续查看实际工具输出。模型正文是总结，工具返回的退出结果和输出才是核对执行情况的材料。任务结束与结论正确仍需分别判断。
