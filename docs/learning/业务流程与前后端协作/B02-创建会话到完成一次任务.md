# B02 创建会话到完成一次任务

用户选中项目，发送"读取 README，告诉我怎么启动"。这次操作依次经过四个阶段：

1. **选择目录** —— 确定任务在哪里执行
2. **创建会话** —— 准备身份与运行环境
3. **业务握手 + 接纳** —— 建立事件通道，让服务端接受任务
4. **执行与展示** —— 模型读文件，结果变成页面上的消息和工具卡片

下面按这个顺序拆开，每一步都标注了对应的代码符号。

## 一 选择目录：先确定任务在哪里执行

浏览器传来的路径只是字符串，服务端收到后按顺序校验：

1. 规范化路径（`normalizeCwd`，展开 `~` 和相对路径）
2. 检查目标存在且是目录
3. 解析它属于哪个项目（`resolveProject`，识别 Git 仓库与 worktree 关系）

- 普通目录也能成为工作区；Git 仓库额外提供项目身份
- 校验通过后，页面才更新工作区选择并保存上次使用目录——输入了不存在的路径，不会把原来的工作区替换成错误状态

> 目录校验通过还会调用 `allowFileRoot`，把该目录加入**文件浏览允许范围**。这个授权针对应用的文件接口；SDK 工具执行用自己的运行环境，两者关系在 B05 展开。

> 浏览器保存的上次选择不是永久有效：目录可能已被删除、移动，或磁盘未挂载。重新使用时仍以服务端能否访问为准。

## 二 创建会话：准备身份与运行环境

创建会话按顺序发生 6 步（入口 `sessions/index.post.ts`）：

1. 前端提交执行目录（cwd）
2. 后端创建**会话记录管理器**（`SessionManager.create`），取得真实 cwd
3. 加载设置、模型运行资源、扩展资源（`createAgentServicesWithRetry`）
4. 创建 SDK 会话对象（`createAgentSessionFromServices`）
5. 包装成 `AgentSessionWrapper`，安装事件监听，加入**实例注册表**（`registry`）
6. 返回真实会话 ID

> **实例注册表**（`registry`）= 一张进程内索引：给定会话 ID → 找到存活对象。之后的发送请求和事件订阅虽是两次 HTTP 请求，都靠同一个 ID 拿到同一个实例。

**历史会话恢复要处理并发初始化**：

- 页面可能同时发起「事件订阅」「状态查询」两条请求
- 两条都发现实例未创建 → 各自创建 → 得到**两个执行对象**（命令进 A、事件监听 B）
- 解法：用第二张 Map（`locks`）记录**正在进行的初始化**，后来的请求等同一次创建完成

> **新建 ≠ 恢复**：同一历史会话的并发恢复要合并；两次独立点击新建要产生两个会话。新建流程用临时 key（`newSessionTempKey`）防误合并——真实 ID 要等 SDK 创建后才产生。

### 为什么创建后还要单独发送第一句话

- 创建接口只建空会话，**不同时提交首条输入**
- 页面拿到 ID → 进入会话页 → 订阅就绪 → 才发送

> 若创建与首条执行合并：服务端可能已生成内容，浏览器还不知道 ID、也没开始收事件，短回答可能早于订阅结束。**先创建、后订阅、再发送**，保证开始执行时就有观察通道。

- 空会话可能还没生成磁盘文件；详情接口优先读存活实例的会话管理器，所以"找不到历史文件" ≠ "会话不存在"

并发恢复为什么能合并，具体由 [服务端初始化等待机制](../04-Agent服务与生命周期.md#三-两个请求同时恢复-为什么需要第二张-map) 解释。

## 三 点击发送：先固定输入，再等待网络

本次输入 = 文字 + 可选图片。点击时页面做两件事：

1. **固定这批输入**——等待期间用户新增的附件不混进本次请求，成功后只清本批附件
2. **保留待确认文字**（`pendingDraft`）——清空输入框，但把原文存起来，处理握手失败、请求失败和刷新

> 输入框清空 ≠ 服务端已接受。原内容要能找回，靠的就是 `pendingDraft`。

**生命周期代次**（`sessionGeneration`，对外通过 `generation()` 访问）：

- 每次关闭、重新进入会话后变化的编号
- 用于区分"同一个会话 ID 对应的不同次打开"
- 握手或命令返回后，只有**身份 + 代次都仍匹配**，旧操作才能继续影响当前页面

> 按钮禁用只挡住当前页面的部分误操作。服务端仍会检查消息类型、图片、运行模式，并在导航或压缩等状态下拒绝发送——其他窗口或直接请求不经过按钮，服务端判断仍然必要。

## 四 业务握手：连接建立不等于已经能接收任务事件

浏览器先连接 SSE（`GET /api/agent/:id/events`），服务端可以立即打开 HTTP 响应，但**取得会话实例、安装业务监听还需要时间**。

- 网络通道存在 ≠ 即将发生的 SDK 事件已有人转发
- 服务端在实例就绪、监听装好后，发送**业务握手**（`connected` 事件）
- 前端等到 `connected` 才提交 prompt

> 两种信号要分开：**HTTP 连接打开** = 传输可用；**业务握手** = 事件接入已准备好。发送等后者，避免快速输出早于监听。

- 初始化失败时，事件通道发**启动错误**（`startup_error`），前端撤回本地临时气泡并保留输入
- 这个阶段尚未发出 prompt，和"prompt 已发出但没收到响应"含义不同

业务握手在 [协议专题的连接就绪处理](../05-HTTP与SSE协议.md#四-先完成业务握手-再发-prompt) 展开。

## 五 服务端接纳：为什么响应可以早于最终回答

命令接口（`agent/[id]/index.post.ts`）按顺序：

1. 按会话 ID 查存活实例（`registry`）
2. 没有实例 → 定位会话文件并恢复（`startRpcSession`）
3. 检查命令，交给 SDK 执行

**一次 prompt 有两个时点**：

| 时点 | 含义 | 应用怎么处理 |
| --- | --- | --- |
| SDK 预检通过（`preflightResult`） | 调用被**接纳** | HTTP 可以返回确认 |
| 完整执行结束 | 可能已历经多次模型请求和工具调用 | 后台继续观察，进度走事件通道 |

> **预检** = 正式执行前的检查关口（涉及 SDK 与扩展）。应用不是收到 HTTP 请求就无条件成功，而是等接纳信号；预检前失败走 HTTP 错误，接受后失败走事件报告。

**未完成调用计数**（`pendingPromptCount`）：

- 防止"HTTP 已返回 → 会话已空闲"的误判
- 同步抛错和异步结束都必须正确减少计数，否则会永久显示运行中

| 时点 | HTTP 侧 | 事件侧 | 页面应表达什么 |
| --- | --- | --- | --- |
| 等待业务握手 | 尚未提交 prompt | 等待订阅就绪 | 输入已提交到页面，正在准备 |
| prompt 预检失败 | 返回错误 | 不应当成已接受 | 显示原因，保留输入 |
| prompt 被接受 | 可以返回确认 | 执行继续 | 保持运行展示 |
| 接受后执行出错 | 原确认不能撤回 | 报告后续错误 | 显示执行失败及已有内容 |
| 执行结束 | 请求可能早已结束 | 消息与结束事件到达 | 整理结果，刷新历史和统计 |

> HTTP 与 SSE 是独立通道，事件可能比接受响应**更早**到达。页面按各自含义处理，不能假设事件一定发生在 POST 返回之后。

这两个时点对应 [接受确认与完整执行的两个 Promise](../04-Agent服务与生命周期.md#五-接受任务和完成任务-为什么是两个-promise)。验证方法见 [保持执行未完成的测试](../11-测试体系与验证边界.md#三-异步测试-先控制时间顺序)。

## 六 模型怎样真正取得 README

- SDK 把**上下文 + 用户要求 + 可用工具说明**发给模型
- 上下文 = 本次请求模型能看到的材料（历史对话、指令、必要工具结果），不是页面上所有数据的自动集合

模型决定读 README 时的流程：

1. 模型提出**工具调用**（工具名 + 参数，参数里的路径告诉工具读哪个文件）
2. SDK 调用服务端的读取实现，取得文件内容
3. 结果送回后续模型请求
4. 模型根据真实内容回答；缺依赖信息时可能继续读 package.json

> 启用工具 ≠ 每个问题都触发调用。模型可能根据已有上下文直接回答。页面能可靠展示的，是**实际发生的**调用和返回结果。

### 文件不存在时谁处理

- 读取失败形成**工具错误**还是**执行错误**，取决于失败位置
- 工具层已返回可处理错误时，模型能看到结果，继续尝试其他路径或解释问题
- 模型请求本身失败时，涉及 SDK 的错误与重试机制

> "工具卡片显示错误" ≠ 整轮任务立即停止。前端分别展示「这次工具结果」和「整体运行状态」，不把局部错误统一解释为整段会话不可用。

## 七 过程怎样变成页面上的消息和工具卡片

**事件裁剪**（`agent-event-wire.ts` 的 `toClientAgentEvent`）：

- 文本增量只保留新增片段，重复携带的完整消息被裁剪
- 工具 ID 和名称若藏在完整快照里，先提取到事件顶层，避免裁剪后无法关联调用

**流式消息 vs 已完成消息**：

- 正在生成的助手消息与已完成消息分开保存
- 正文片段进文本块，工具参数片段进工具块
- 参数未生成完整时先存原始片段，结束时才用完整结构化参数——不把半截参数当可执行对象

**工具的实时状态与最终结果**：

- 执行开始 → 进**活跃工具集合**（`activeTools`），进度事件更新摘要
- 执行结束 → 从活跃集合移除；最终结果存在消息里，按**调用 ID** 配回卡片
- 两次同名读取靠不同调用 ID 区分，不能按名字或相邻位置匹配

**两个"结束"要分清**：

| 结束类型 | 发生什么 |
| --- | --- |
| 一条消息结束 | 进入历史展示列表，当前流式气泡清理 |
| 完整执行落定 | 清理活跃工具、重试等运行状态，重读会话详情和运行信息 |

> 详情补回真实记录 ID、分支位置和统计，避免只靠前端临时身份长期维持历史。

从事件到页面的细节见 [文本组装演算](../06-消息状态与工具渲染.md#四-先手算一遍文本组装) 和 [工具参数与结果配对](../06-消息状态与工具渲染.md#六-工具参数和结果怎样接到卡片)。

## 八 请求报错以后，是否可以重新发送

先判断错误发生在**接纳之前**还是**接纳结果未知**：

- **握手失败**：prompt 尚未发出，可保留输入再试
- **明确的业务拒绝**：按原因修正
- **请求已发出但 HTTP 响应丢失**：任务可能已在服务端运行，直接重发可能产生**第二次工具执行**

> 当前普通发送会提示"提交结果未确认"、保留文字并重读历史，但**没有命令 ID 查询与服务端去重**——能帮助核对结果，不能证明同一请求绝不重复执行。重发前应先确认原会话是否已有本次任务。

- 看到助手写"测试通过"时，还要看实际**工具输出**：模型正文是总结，工具返回的退出结果和输出才是核对执行情况的材料
- 任务结束 ≠ 结论正确，两者要分别判断
