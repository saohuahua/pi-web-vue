# B05 文件浏览与执行目录

用户在回答里看到一个文件路径，点击后希望在右侧预览；也可以从文件树把文件引用插入输入框，让 Agent 检查。两种操作都涉及文件，但一个是浏览器查看，一个是让执行系统使用，读取入口和责任不同。

## 一 文件相关操作分别做了什么

| 用户操作 | 实际发生的事情 | 是否自动把全文交给模型 |
| --- | --- | --- |
| 展开文件树 | 请求某个目录的子项 | 否 |
| 搜索文件或使用 @ 补全 | 查询文件路径索引 | 否 |
| 打开文件预览 | 浏览器通过文件接口读取内容 | 否 |
| 把文件引用插入输入框 | 在草稿里插入相对路径文字 | 否 |
| Agent 调用读取工具 | SDK 工具访问文件并返回结果 | 工具结果会参与后续执行上下文 |

文件预览是给用户看的，工具读取是给任务执行使用的。用户刚在 Inspector 看过一个文件，不等于模型已经获得该文件内容。当前文件引用也只是路径提示，实际内容仍需要 Agent 根据任务读取。

## 二 点击文件链接后怎样打开预览

Markdown 渲染器先判断链接能否解释为本地文件。可识别的绝对路径、文件 URL，以及具备基准目录的相对路径，会转换为应用内文件目标。用户点击后，由消息或预览容器统一处理，把路径交给文件查看器。

文件查看器按路径维护标签。已经打开的文件切换为当前标签，新文件加入标签列表。具体内容通过后端文件接口读取，文本返回文字和类型信息，图片则由浏览器读取对应二进制响应。

### 相对路径必须知道相对于哪里

预览 docs/README.md 时，其中的 ./guide.md 应相对于 docs 目录解释，而不是相对于网页路由或进程启动目录。当前文件预览向 Markdown 渲染器传入所在文件路径，因而能为内部链接和图片建立这个基准。

会话正文当前没有向同一渲染器传入文件路径上下文，因此不能把预览里的相对链接能力直接推广到所有助手回答。绝对文件链接与相对文件链接要分开检查；相对链接无法正确打开时，先看是否具备基准目录，而不是只看链接文字像不像文件名。

链接尾部的行号标记会从文件路径中剥离，避免把行号当作文件名的一部分。路径能解析，只说明知道请求哪个文件；文件是否存在、是否允许读取，仍由后端判断。

本地链接进入查看器后，涉及 [动态 Markdown 的事件委托](../09-文件访问与预览.md#六-前端实现亮点-让动态-markdown-仍可交互)。它与 [Agent 真正读取文件](B02-创建会话到完成一次任务.md#六-模型怎样真正取得-readme)共用文件这个对象，却是两条独立的数据路径：一条给用户预览，一条把工具结果交给执行循环。

## 三 后端怎样判断一个路径能否读取

浏览器可发出任意请求，不能只因为界面文件树没有显示某个路径，就认为用户无法请求它。文件接口需要独立检查允许访问的根目录集合。

当前允许根来自已知会话的执行目录、项目根与 worktree 目录，以及通过工作区校验显式加入的目录。它不只包含当前页面选中的一个文件夹，也不是按不同登录用户划分的权限体系。显式加入的目录保存在服务端内存，服务重启后需要重新建立。

读取依次经过两个关键判断。

**第一层是规范化后的目录包含。** 先解析相对跳转，统一平台路径规则，再判断目标是否就是允许根，或者位于根目录之下。不能只检查原始字符串开头。

**第二层是真实路径包含。** 文件系统中的链接可能放在根内，却指向根外。后端解析目标与允许根的真实路径，再检查包含关系，处理这种跳转。

| 允许根为 D:/work/demo | 风险 | 需要的处理 |
| --- | --- | --- |
| D:/work/demo/src/api.ts | 正常子文件 | 检查存在且真实路径允许 |
| D:/work/demo-backup/secret.txt | 名称前缀相同，但属于兄弟目录 | 比较完整目录边界 |
| D:/work/demo/../secret.txt | 文本开头在根内，规范化后跑到根外 | 先解析上级跳转 |
| 根内链接指向其他目录 | 路径外观在根内，真实目标在根外 | 解析链接后的真实位置 |

Windows 还需要统一盘符大小写与分隔符。目标不存在、无权限和文件类型不符分别返回不同错误，前端才有依据显示“找不到”“不允许访问”或“不是可预览文件”。

路径包含与链接解析的具体判断见 [服务端文件访问检查](../09-文件访问与预览.md#七-前端传来路径-服务端怎样限制访问)。读到允许根时，回看 [工作区与会话的区别](B01-业务对象与职责分工.md#二-工作区与会话为什么要分开)：当前页面选择、会话执行目录和服务端允许集合并不是同一个范围。

## 四 文件很大或不是文本时怎样处理

Inspector 的目标是查看内容，不是把所有类型和任意体积的文件都完整加载进页面。当前文本预览返回最多 256 KiB，并标记是否截断；图片超过 10 MiB 时拒绝预览，非图片二进制文件也有不支持预览的处理。

文本响应同时返回文件大小和语言信息。页面据此进行代码高亮，遇到截断时提示用户当前只看到了部分内容。预览中的内容不完整，不代表磁盘文件被修改或删除。

当前后端对非图片文件先读入内容再做文本截断。因此 256 KiB 限制控制的是返回与展示范围，不能直接当成后端读取内存也严格限制在这个大小。大型文件读取策略是另一项实现问题。

Markdown 可以切换渲染预览与源码展示，渲染时还要处理图片路径、文件链接和代码复制。图片预览走二进制响应；SVG 具有文档能力，因此后端还设置限制脚本等行为的响应策略。

Agent 的读取工具有独立输出规则。页面显示“可让 Agent 读取”表示换用执行工具查看，不承诺工具一次会把任意大文件全部塞进模型上下文。

## 五 快速切换文件，为什么旧内容不能写回来

用户先打开 A，马上切到 B。A 的响应可能更晚回来，如果请求完成就直接赋值，B 标签下会显示 A 内容。再复杂一点，用户从 A 切 B 又切回 A，仅比较文件路径也不能区分第一次和第二次读取。

当前文本查看器为每次加载递增请求版本，返回时只允许当前版本更新内容。错误与加载完成也检查同一版本：旧请求失败不能把新文件显示成错误，旧请求结束不能提前关闭新请求的 loading。

标签选择与内容加载因此是两层状态。标签说明用户现在想看哪个文件，请求版本说明哪一次结果仍有资格影响这个选择。

这项保护覆盖文本加载的成功、失败和收尾路径，不等于所有浏览器图片加载或面板关闭情形都自动走同一套逻辑。

文本加载的版本检查在 [成功、错误与收尾的共同守卫](../09-文件访问与预览.md#3-为什么-catch-和-finally-也要检查)中展开。把文件 A→B→A 换成 [会话 A→B→A](B04-历史恢复与编辑重发.md#九-切走再回来为什么旧请求仍要作废)，能看出相同原则：对象名称相同，也可能属于不同次操作。

## 六 搜索为什么可能找不到磁盘上存在的文件

文件树、路径搜索和文件内容读取使用不同入口。文件树按目录列举；搜索与 @ 补全先取得受限的路径索引，再过滤结果；真正打开时才读取文件内容。

当前 Git 仓库索引使用 Git 已跟踪文件列表。刚创建但尚未加入跟踪的文件，可能存在于磁盘和目录树，却不出现在这份索引里。非 Git 目录改用遍历，并限制深度和文件总数，跳过依赖、构建产物等目录。

索引还有短时间缓存与返回数量上限：空查询最多返回五千个路径，带查询最多返回一百项。缓存可能让新增文件暂时不可见，数量限制也可能让结果不完整。搜索没命中时，应分别检查跟踪状态、目录过滤、缓存和截断，而不是立即判断文件不存在。

这些限制主要控制索引成本和页面补全数据量。它们与文件接口的读取权限不是同一种规则：没被索引到的路径，仍需要按真实路径和允许根独立判断是否可读。

## 七 工作区切换与文件引用可能怎样错位

已有会话的执行目录固定在其会话环境里，改变工作区选择不会自动迁移它。文件树的引用插入则根据当前选择目录生成相对路径。

如果页面选择了工程 B，但当前正在继续的会话仍属于工程 A，引用 B 的相对路径可能被任务按 A 的执行环境理解。当前机制不能仅凭字符串相同判断文件身份相同。遇到这种现象，要同时核对工作区选择、会话执行目录和引用的实际目标。

打开历史会话时同步工作区，有助于让文件浏览重新跟随会话，但这是异步同步，不是把所有目录概念合并成一个变量。需要在另一个工程执行时，应明确创建或打开那个工程的会话。

## 八 文件预览的权限不等于 Agent 沙箱

文件预览请求经过应用的允许根检查；Agent 工具则运行在 Node 与 SDK 提供的本地环境中，没有被自动套进同一个预览函数。

因此预览接口拒绝读取某个路径，不足以证明本地命令工具也无法访问该路径；反过来，工具能读取一个文件，也不意味着页面允许公开预览。两条入口需要分别理解权限与执行范围。

当前项目是本机工作台。若改成远程多用户服务，需要把会话、目录与用户身份绑定，并限制执行进程可访问的资源。页面隐藏按钮或文件树过滤目录，只改变界面入口，无法代替服务端身份校验与执行隔离。
