# B05 文件浏览与执行目录

用户在回答里看到一个文件路径，点击后希望右侧预览；也可以从文件树把文件引用插入输入框让 Agent 检查。两种操作都涉及文件，但一个是**浏览器查看**，一个是**让执行系统使用**——读取入口和责任不同。

## 一 文件相关操作分别做了什么

| 用户操作 | 实际发生的事情 | 是否自动把全文交给模型 |
| --- | --- | --- |
| 展开文件树 | 请求某个目录的子项 | 否 |
| 搜索文件或 @ 补全 | 查询文件路径索引 | 否 |
| 打开文件预览 | 浏览器通过文件接口读取内容 | 否 |
| 把文件引用插入输入框 | 在草稿里插入相对路径文字 | 否 |
| Agent 调用读取工具 | SDK 工具访问文件并返回结果 | 工具结果参与后续执行上下文 |

> **文件预览是给用户看的，工具读取是给任务执行用的**。用户在 Inspector 看过一个文件，不等于模型已获得其内容；文件引用也只是路径提示，实际内容仍需 Agent 根据任务读取。

## 二 点击文件链接后怎样打开预览

- Markdown 渲染器先判断链接能否解释为本地文件（`shouldOpenLocalFileInApp`）
- 可识别的绝对路径、文件 URL、带基准目录的相对路径 → 转为应用内文件目标
- 文件查看器按路径维护标签（`file-viewer.ts` 的 `tabs`）：已打开的切为当前，新文件加入列表
- 内容通过后端文件接口（`files/[...path].get.ts`）读取，文本返回文字和类型，图片读二进制响应

### 相对路径必须知道相对于哪里

- 预览 `docs/README.md` 时，其中的 `./guide.md` 应相对于 **docs 目录**解释，不是相对于网页路由或进程启动目录
- 预览向 Markdown 渲染器传入所在文件路径，为内部链接和图片建立基准（`resolveLocalFileHref` 的 `baseDir`）

> 会话正文当前没向同一渲染器传文件路径上下文，所以预览里的相对链接能力不能直接推广到所有助手回答。相对链接打不开时，先看是否具备基准目录，而不是只看链接文字像不像文件名。

- 链接尾部的行号标记会从路径中剥离，避免当成分名一部分
- 路径能解析 ≠ 文件存在、允许读取——这些仍由后端判断

本地链接进入查看器后，涉及 [动态 Markdown 的事件委托](../09-文件访问与预览.md#六-前端实现亮点-让动态-markdown-仍可交互)。它与 [Agent 真正读取文件](B02-创建会话到完成一次任务.md#六-模型怎样真正取得-readme) 共用"文件"这个对象，却是两条独立数据路径。

## 三 后端怎样判断一个路径能否读取

浏览器可发任意请求，不能因为文件树没显示某路径就认为用户无法请求。文件接口要**独立检查允许访问的根目录集合**。

**允许根**（`getAllowedFileRoots`）来自：

- 已知会话的执行目录（cwd）
- 项目根与 worktree 目录
- 通过工作区校验显式加入的目录（`allowFileRoot`）

> 允许根不是"当前页面的一个文件夹"，也不是按登录用户划分的权限体系。显式加入的目录存在服务端内存，服务重启后需重新建立。

**读取依次经过两层判断**：

1. **词法包含**（`isPathWithinRoots`）：解析相对跳转、统一平台路径规则，判断目标是否就是允许根或位于其下——不能只检查原始字符串开头
2. **真实路径包含**（`isExistingFilePathAllowed`）：用 `realpathSync` 消解符号链接后，再判断包含关系，拦截"链接在根内、指向根外"

| 允许根为 D:/work/demo | 风险 | 需要的处理 |
| --- | --- | --- |
| D:/work/demo/src/api.ts | 正常子文件 | 检查存在且真实路径允许 |
| D:/work/demo-backup/secret.txt | 名称前缀相同，属于兄弟目录 | 比较完整目录边界 |
| D:/work/demo/../secret.txt | 文本开头在根内，规范化后跑根外 | 先解析上级跳转 |
| 根内链接指向其他目录 | 外观在根内，真实目标在根外 | 解析链接后的真实位置 |

- Windows 还要统一盘符大小写与分隔符
- 目标不存在、无权限、类型不符分别返回不同错误，前端才有依据显示"找不到""不允许访问"或"不是可预览文件"

具体判断见 [服务端文件访问检查](../09-文件访问与预览.md#七-前端传来路径-服务端怎样限制访问)。回看 [工作区与会话的区别](B01-业务对象与职责分工.md#二-工作区与会话为什么要分开)：当前页面选择、会话执行目录、服务端允许集合**不是同一个范围**。

## 四 文件很大或不是文本时怎样处理

Inspector 目标是查看内容，不是把所有类型、任意体积都完整加载进页面。

- 文本预览最多返回 **256 KiB**（`TEXT_PREVIEW_MAX_BYTES`），标记是否截断
- 图片超 **10 MiB**（`IMAGE_PREVIEW_MAX_BYTES`）拒绝预览
- 非图片二进制文件不支持预览

- 文本响应同时返回文件大小和语言信息，页面据此代码高亮，截断时提示只看到部分
- 预览内容不完整 ≠ 磁盘文件被修改或删除

> 后端对非图片先读入内容再截断——256 KiB 限制的是**返回与展示范围**，不能当成后端读取内存也严格限制在这个大小。

- Markdown 可切换渲染预览与源码，处理图片路径、文件链接、代码复制
- SVG 有文档能力，后端设置 CSP 限制脚本

> Agent 的读取工具有独立输出规则。"可让 Agent 读取"表示换用执行工具查看，不承诺一次把任意大文件全部塞进模型上下文。

## 五 快速切换文件，为什么旧内容不能写回来

- 先打开 A 马上切 B，A 响应更晚回来，直接赋值会让 B 标签下显示 A 内容
- 更复杂：A→B→A，仅比较文件路径也区分不了第一次和第二次读取

- 文本查看器每次加载递增 **`loadVersion`**（`FileViewer.vue`），返回时只允许当前版本更新内容
- 错误与加载完成也检查同一版本：旧请求失败不能把新文件显示成错误，旧请求结束不能提前关新请求的 loading

> **标签选择与内容加载是两层状态**：标签说明用户现在想看哪个文件，`loadVersion` 说明哪一次结果仍有资格影响这个选择。

版本检查在 [成功、错误与收尾的共同守卫](../09-文件访问与预览.md#3-为什么-catch-和-finally-也要检查) 展开。把文件 A→B→A 换成 [会话 A→B→A](B04-历史恢复与编辑重发.md#九-切走再回来为什么旧请求仍要作废)，是同一原则：**对象名称相同，也可能属于不同次操作**。

## 六 搜索为什么可能找不到磁盘上存在的文件

文件树、路径搜索、内容读取用不同入口：

- 文件树按目录列举
- 搜索与 @ 补全先取受限的路径索引（`file-index.get.ts`），再过滤结果
- 真正打开时才读文件内容

- Git 仓库用**已跟踪文件列表**（`git ls-files`），刚创建未跟踪的文件存在于磁盘和目录树，却不在索引里
- 非 Git 目录改用遍历，限制深度和数量，跳过 node_modules 等目录

> 索引有短缓存与数量上限：空查询最多 5000 条，带查询最多 100 条。缓存让新增文件暂时不可见，数量限制让结果不完整。搜索没命中时，应分别检查跟踪状态、目录过滤、缓存、截断，而不是立即判断文件不存在。

> 这些限制控制索引成本，与文件接口的读取权限不是同一种规则：没被索引到的路径，仍按真实路径和允许根独立判断是否可读。

## 七 工作区切换与文件引用可能怎样错位

- 已有会话的执行目录固定在会话环境里，改变工作区选择不会自动迁移它
- 文件树引用按**当前选择目录**生成相对路径

> 若页面选了工程 B，但当前会话仍属工程 A，引用 B 的相对路径可能被任务按 A 的执行环境理解。当前机制不能仅凭字符串相同判断文件身份相同——要同时核对工作区选择、会话执行目录、引用的实际目标。

- 打开历史会话时同步工作区，让文件浏览跟随会话，但这是**异步同步**，不是把所有目录概念合并成一个变量

## 八 文件预览的权限不等于 Agent 沙箱

- 文件预览经过允许根检查；Agent 工具运行在 Node 与 SDK 提供的本地环境，**没有被自动套进同一套预览检查**

> 预览接口拒绝某路径，不足以证明命令工具也无法访问它；反过来工具能读一个文件，也不意味着页面允许公开预览。两条入口要分别理解权限与执行范围。

> 当前是本机工作台。若改成远程多用户服务，需把会话、目录与用户身份绑定，并限制执行进程可访问的资源——隐藏按钮或过滤目录只改界面入口，替代不了服务端身份校验与执行隔离。
