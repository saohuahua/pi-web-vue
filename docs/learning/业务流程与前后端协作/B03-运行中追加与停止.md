# B03 运行中追加与停止

Agent 正在排查接口错误，用户又输入"先别改数据库，只检查接口层"——这句话应参与当前执行；另一句"这轮结束后，再补测试"则适合成为后续任务。运行中输入必须表达这两种意图，否则同一个发送按钮无法说明新文字该何时被使用。

## 一 两种追加模式分别解决什么问题

运行中输入提供两种模式，通过 `streamingBehavior` 字段提交：

- **steer**（`"steer"`）：补充或调整**当前**执行方向
- **follow-up**（`"followUp"`）：安排**后续**输入，排队等待

前端把所选模式交给 SDK，由 SDK 在执行循环中决定具体消费时点。

| 用户要求 | 合适的意图 | 容易产生的误解 |
| --- | --- | --- |
| 先不要改数据库 | 调整当前方向（steer） | 以为点击后能立即撤销正在执行的命令 |
| 分析时也看看测试文件 | 补充当前任务信息（steer） | 以为只是输入框文字，没有真正提交 |
| 这轮结束后补测试 | 排队后续输入（follow-up） | 以为已入队就表示后续任务已完成 |
| 停下，我需要重新确认范围 | 停止执行 | 以为停止会恢复此前改动的文件 |

> **方向调整不是强制中断**：新输入被 SDK 接收后，要等执行循环在其支持的位置消费；已写入磁盘的修改不会因一句新要求自动消失。确实要停止时，走停止动作，再核对实际文件变化。

## 二 为什么前端不直接把文字加进队列列表

- 页面看到的"正在运行"是**稍早的状态**，请求到服务端时上一轮可能已结束
- 若前端直接断言"已排队"，可能与 SDK 实际开启新一轮的行为不一致

所以提交只携带文字、附件快照和运行模式，**队列显示来自 SDK 的队列事件或运行态查询**（`queuedMessages`），不在点击时伪造"已入队"项。

> 三个不同阶段要分清：**文字在输入框 → 提交等待确认 → SDK 已接纳**。等待期间保护原文字和本批附件，成功后释放本次输入，失败后合并回草稿（`pendingDraft`）。

- 队列显示的是**尚待消费**的内容
- 某项从队列消失 = 已被执行循环取走，**不代表**它要求的工作已完成，结果仍看后续消息和工具执行

## 三 服务端为什么只排队接纳，不等待整轮执行

假设两个追加请求几乎同时到达：第一个还在扩展预检，第二个也开始判断当前是否运行。若两个接纳过程交叉，就难以确定队列操作的先后顺序。

- 当前为接纳阶段建立**串行顺序**：后来的请求等前一个完成接纳判断，再进入 SDK
- 串行的只是"能否接收及怎样接收"，**不是等整轮回答结束**

> 若一直等完整执行结束才放行第二个请求，运行中追加就无法发生。**把接纳与执行拆开**，既能规定命令进入顺序，又允许长任务继续运行。这正是 [接受与完成分开的两个 Promise](../04-Agent服务与生命周期.md#五-接受任务和完成任务-为什么是两个-promise)。

**撤回为什么也要等这条链**（`promptAdmissionTail`）：

- 撤回要等前面已进入接纳链的请求完成判断，再问 SDK 还有哪些内容没消费
- 否则撤回先读到空队列，仍在预检的请求随后才入队，用户误以为已撤回

> 这只是**当前进程内**的顺序管理，没持久化成跨进程任务队列。若接纳阶段一直不返回，等待它的后续接纳或撤回也可能受阻，仍需单独考虑超时。

## 四 撤回队列：只能恢复真正还没消费的内容

用户点撤回时，页面列表可能已落后于 SDK（页面显示两条，第一条刚被取走）。若直接复制页面文字回输入框，会把已进入执行的内容也当成撤回成功。

- 服务端清空 SDK 待处理队列（`clear_queue`），返回**实际撤下来的文字**
- 浏览器只把返回内容合并进草稿：旧内容在前、用户后来输入的内容在后，不覆盖新输入

> 当前撤回是**清空全部**待处理队列，不是逐条撤回；返回契约主要是文字列表，不能还原原始附件。

| 服务端结果 | 页面该做什么 | 用户应如何理解 |
| --- | --- | --- |
| 返回一条文字 | 合并这一条到草稿 | 该文字尚未被消费，已撤下 |
| 返回空列表 | 不凭旧页面内容补文字 | 队列可能本来为空，也可能已被消费 |
| 返回错误 | 显示错误，保留现有状态 | 尚未确认撤回 |
| 请求没有返回 | 保持等待或进入超时处理 | 不能认定服务器没执行 |

## 五 为什么队列查询还要检查版本

- 页面恢复时请求一份完整队列，请求发出时队列为空
- 等待期间收到新事件 = 刚加入一条要求
- 若旧查询最后返回并直接覆盖，新内容会从界面消失

> 前端每次更新队列递增 `version`（`usePromptQueue` 的 `let version`），发查询时记住版本，结果回来只有版本仍相同才覆盖（`applySnapshot`）；版本已变就保留期间收到的新状态。撤回后的清空显示也遵循这一原则。

- 这个版本记录的是**当前页面看到的先后变化**，不是服务端持久事件序号
- 它能处理"已观察到的事件与旧查询竞争"，无法补回"根本没收到的事件"

队列版本与 [文件加载版本](../09-文件访问与预览.md#四-前端实现亮点-用加载版本拒绝旧结果) 都在判断"旧结果还能否写回"，但失效条件不同：文件切换启动新加载，队列收到新事件也改变版本。交错测试见 [倒序响应测试](../11-测试体系与验证边界.md#四-旧请求测试-要故意让结果倒序到达)。

## 六 停止为什么先撤回，再中止当前执行

点停止要处理两件事：**当前在做什么** + **之后还准备做什么**。只中止当前执行，待处理输入可能继续触发后续工作，用户会看到"刚停下又开始"。

停止顺序（`chat.ts` 的 `stop()`）：

1. 进入**停止中状态**（`isStopping`），阻止当前页面继续追加
2. 请求撤回尚未消费的队列，把返回文字保存回草稿
3. 撤回确认成功后，再向 SDK 发送**中止命令**（`abort`）
4. 结合结束事件清理运行状态，必要时延迟重读历史

> 撤回失败时不继续发送中止命令，并提示"队列未确认"——既然不知道后续输入是否已清除，就不能把停止流程展示成已完成。

- 从撤回开始到中止返回，`isStopping` 都要保留
- 只在清队列那一步禁用追加，会留下"清空完成但中止仍在等待"的窗口

> 这个保护目前约束当前页面。其他窗口仍可能在清队列与中止之间插入命令；要跨窗口严格实现"清队列并停止"，需要服务端提供一个整体操作和相应互斥。

## 七 停止返回、页面落定与文件回滚是三件事

- **中止命令返回** ≠ 页面已落定：界面还要消费结束事件、清理工具状态、读取历史
- 当前有中止确认后的**三秒兜底**，用于处理页面残留运行标记

> 三秒不是从点击开始计时——撤回或中止请求一直等待时，兜底尚未启动，所以没有"点击后最多三秒结束"的保证。本地定时器清掉运行标记，也替代不了对服务端实际执行状态的确认。

> **停止 ≠ 文件回滚**：工具已修改两个文件、第三个被中止，前两个修改仍留在磁盘。会话历史保存执行过程，不是代码仓库的自动事务。要通过文件内容或 Git 差异检查，再决定保留、修改还是恢复。

停止命令返回后，页面还要按 [消息结束与整体落定的分工](../07-异步协作与恢复.md#五-为什么结束事件要分层) 清理状态，结合 [恢复时的数据来源](B04-历史恢复与编辑重发.md#一-页面恢复需要找回三类内容) 一起看。

## 八 运行中出现错误时如何判断下一步

| 现象 | 先确认什么 | 后续处理 |
| --- | --- | --- |
| 追加按钮返回错误 | 是明确拒绝，还是没拿到接纳确认 | 明确拒绝后修正；未确认时先查队列和会话 |
| 队列项突然消失 | 是否已被 SDK 消费 | 查看后续消息，而不是直接重新入队 |
| 撤回后还有新队列项 | 撤回期间是否收到新队列事件 | 保留更新后的队列，不用旧响应覆盖 |
| 点击停止后仍等待 | 停在撤回、中止请求还是事件收尾 | 分别核对请求与运行态 |
| 页面已停止但文件变了 | 哪些工具动作此前已完成 | 检查实际变更，停止不自动恢复文件 |
