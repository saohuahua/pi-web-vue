# B04 历史恢复与编辑重发

用户刷新页面，希望继续看到刚才的回答；随后发现上一轮问题描述不准确，想修改后重新生成。前者要重建已有状态，后者要改变后续执行基于的上下文。两者都依赖会话记录，但不能用同一份前端消息数组完成。

## 一 页面恢复需要找回三类内容

| 内容 | 例子 | 从哪里恢复 |
| --- | --- | --- |
| 已经发生的历史 | 用户问题、完整助手回答、工具结果 | 服务端会话详情（`sessions/[id].get.ts`） |
| 仍在发生的执行 | 当前助手草稿、运行标记、队列 | SSE 握手 + 当前消息快照（`streamingMessage`）+ 运行态查询 |
| 用户尚未确认提交的内容 | 输入框文字、正在编辑的目标 | 浏览器按会话保存的草稿（`draft-store.ts`） |

> **历史属于服务端会话，草稿属于用户尚未完成的输入**。恢复文字不应自动重发——这份文字可能曾提交，只是接受响应丢失，服务端已经在执行。

- 正在生成的消息（来自 SDK 当前状态）≠ 输入草稿（来自浏览器保存）
- 两者都被叫"草稿"时容易混淆，判断恢复问题前要先分清是哪一份

## 二 重新打开会话时，先恢复什么

打开流程按顺序：

1. 保存并清理旧会话的页面状态，关闭旧订阅
2. 设置目标会话
3. 先从本地存储找回文字（避免把输入恢复放在较慢的历史请求之后——用户在加载期间输入了新内容，此时再赋回旧草稿会覆盖新输入）
4. 查询服务端详情，恢复历史消息、记录 ID、当前叶节点、会话树
5. 详情提供 cwd，页面据此同步工作区
6. 维护 SSE，查询模型、上下文使用、队列与可用命令

> 历史读取、工作区同步、运行信息查询**并不全部串行**，页面必须分别处理这些数据的归属。

- 历史读取优先用存活实例的会话管理器（`openSessionForRead`）；没有存活实例才打开会话文件
- 这样新建后尚未落盘的空会话仍能返回详情

## 三 历史为什么是树，页面为什么只展示一条链

原对话"问题一 → 回答一 → 问题二 → 回答二"，后来从回答一分出另一个问题——新旧两条后续都要保留。

- 每条记录保存自己的 `parentId`，表达它基于哪条记录继续
- 读取时从**当前叶节点**（`activeLeafId`）沿父记录向上找，直到起点，再反转顺序，得到页面展示的当前路径（`sliceActiveBranch`）
- 旁边分支仍保存在记录里，但不混进当前对话

> 持久记录不全是消息，还可能保存模型变化、压缩、会话信息。后端要把记录转换成展示消息（`entryToUiMessage`），同时返回每条消息对应的真实**记录 ID**（`entryIds`）。

> **记录 ID 用于编辑与导航，数组位置只用于列表展示**。分支变化后同一数组位置可能变成另一条消息；用下标当永久身份，编辑动作就可能指向错误节点。

记录树如何变成页面数组，见 [父链回溯与消息身份](../08-会话存储与上下文.md#三-为什么历史会成为一棵树)。

## 四 输出一半刷新，当前回答怎样继续

- 刷新前只显示"启动时需要"，服务端随后继续生成"先安装依赖"——浏览器内存已清空，无法靠下一小段文本推断前面内容
- 所以服务端建流时提供**当前助手消息快照**（`streamingMessage`）

恢复顺序：

1. 前端根据握手恢复运行标记
2. 用快照替换当前助手草稿
3. 继续追加新的增量

> **历史负责已完成记录，快照负责正在生成的这一条消息。**

- 服务端先装事件监听、再读快照，并暂存握手前到达的事件，接入期间的变化不丢
- 已包含在快照里的事件会被过滤，避免重复显示

> 当前没有保存每条传输事件及其可重放序号，所以快照恢复 ≠ 逐条补发断线期间的一切——断线期间已结束的其他消息，不一定包含在"当前正在生成的一条消息"里。

## 五 任务在断线期间结束，会出现什么差别

- **自动重连**：旧页面还保留运行标记。若服务端握手明确已不再流式、而页面之前确认过 Agent 活跃，当前实现清掉助手草稿、进入统一落定、清理活跃工具并重读历史
- **刷新**：建立全新页面状态。历史查询完成后、事件监听安装前，任务可能恰好结束——这段窗口没有统一恢复协议保证自动补齐

| 场景 | 当前已有处理 | 仍要注意什么 |
| --- | --- | --- |
| 刷新时仍有当前消息 | 历史加当前快照，继续接增量 | 快照不是所有断线事件的全集 |
| 自动重连发现已结束 | 有条件地落定并重读历史 | 条件依赖旧页面曾确认运行 |
| 历史查询与订阅之间结束 | 可能缺最终记录 | 需要订阅后的统一对账 |
| 服务进程也重启 | 可重新读取已保存历史 | 内存执行不能自动续接 |

> 查询发出后新消息已到达，旧查询再整体覆盖列表，会删掉刚显示的新内容。为快照与事件建立共同版本是解决这种交错的方案之一；当前只按请求序号判断查询先后，还不等于掌握事件版本。

快照与事件的衔接见 [断线后的快照机制](../05-HTTP与SSE协议.md#六-断线之后-为什么还需要快照)；页面响应归属见 [会话代次与查询顺序](../07-异步协作与恢复.md#三-切换会话-怎样挡住慢旧响应)。

## 六 编辑旧问题，为什么要回到它的父节点

原对话"问题一 → 回答一 → 问题二 → 回答二"。想把问题二改成新版本，新输入应接在**回答一**后面。若只替换页面文字，SDK 仍可能在回答二之后，下一次请求会继续带进旧问题和旧回答。

- 编辑先取得原问题的记录 ID（知道在编辑哪条），再找到**父记录**（知道新输入从哪里开始）
- 找不到有效父节点时，不能继续这条编辑路径
- 入口要求前面存在用户消息，不是所有历史消息都开放编辑
- 运行中、压缩中、导航中或位置未知时，也不允许改上下文位置

### 提交编辑后的完整顺序

1. 保留编辑后的输入，确定目标父节点
2. 请求**只读预览**（`context.get.ts`），确认该节点能构成有效上下文
3. 向服务端发**导航命令**（`navigate_tree`），改变 SDK 当前会话位置
4. 重新读详情，确认实际叶节点就是目标
5. 确认后发送新问题，由 SDK 在该上下文后继续执行

> **预览只读，导航才是写**。这个区分让目标无效时能在改变服务端之前发现问题，也避免用户只是看一眼其他分支就影响下一次提问。

## 七 导航失败为什么还要查询与回退

假设服务端已切到目标节点，但返回确认时网络断开——浏览器只看到错误，并不知道服务端是否已改变位置。

- 直接恢复前端选中状态到原分支，会造成"页面显示旧分支、SDK 从新位置继续"的分裂
- 当前保存原叶节点，导航异常后**先重读实际状态**，必要时发命令回退，再读一次确认
- 读不到、回退失败或位置不符 → 标记**位置未确认**，禁止发送，保留输入等待重载

> **回退只恢复会话上下文位置，不撤销文件写入**。成功切回旧分支，磁盘可能已含后来工具完成的修改；重新执行旧问题时，工具读的是此刻的文件内容，不是聊天历史时间点的快照。

- 前端禁用不够，服务端同样检查执行中、压缩中、导航中
- 导航可能等待扩展处理，期间通过互斥标记（`navigating`）阻止另一条 prompt 或导航改变消息链

## 八 草稿怎样避免"发送失败后丢文字"

用户提交"检查接口"，等待时又输入"顺便看看测试"。若失败时直接恢复旧文本，新文字会丢；若只有输入框为空才恢复，旧文本又可能找不回来。

- 提交单独保存**待确认文字**（`pendingDraft`），持久化时同时保存这段文字和当前输入
- 确认成功才释放待确认部分；失败时按"原提交在前、新输入在后"合并
- 切换会话后，旧操作必须通过会话身份 + 代次（`sessionGeneration`）检查，才有资格修改当前草稿

> 草稿按会话 ID 保存文字、更新时间和可选编辑目标，存在 `draft-store.ts`。读取时过滤超 30 天条目，损坏数据清理并提示，浏览器存储不可用时降级到内存——降级后只能保住当前页面，刷新恢复依赖持久化成功。

- 图片不随草稿持久化
- 编辑目标恢复时要重新确认对应记录及父节点仍有效，不能只凭存储里的旧 ID 直接导航

文字草稿与 [配置保存期间的新编辑](B06-模型配置与能力加载.md#保存期间又改了一个字段怎么办) 有共同点：**请求提交的内容与用户现在编辑的内容必须分开**。

## 九 切走再回来，为什么旧请求仍要作废

A 会话第一次查询较慢，用户切到 B 再回 A，当前会话 ID 又变成 A——只比较 ID，会让第一次打开时的旧结果误入这次页面。

- 发送与多条异步操作保存 `sessionGeneration`，结果回来同时比较 **ID + 代次**
- 历史查询额外比较**请求序号**（`reloadSequence`），避免同一代里较早查询覆盖较晚查询
- 成功、失败、清理分支都涉及状态写入，旧错误和旧 loading 收尾也要隔离

> 这些保护已有实现，但**不是所有异步入口自动继承**：打开会话的部分收尾仍只检查 ID，工作区同步又有独立请求。排查跨会话显示错误时，要沿实际写入点检查，不能只看到一个代次变量就认定全链路都受保护。
