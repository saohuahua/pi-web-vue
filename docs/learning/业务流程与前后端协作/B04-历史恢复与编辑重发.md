# B04 历史恢复与编辑重发

用户刷新页面，希望继续看到刚才的回答；随后发现上一轮问题描述不准确，想修改后重新生成。前一个操作要重建已有状态，后一个操作要改变后续执行基于的上下文。两者都依赖会话记录，但不能用同一份前端消息数组完成。

## 一 页面恢复需要找回三类内容

| 内容 | 例子 | 从哪里恢复 |
| --- | --- | --- |
| 已经发生的历史 | 用户问题、完整助手回答、工具结果 | 服务端会话详情 |
| 仍在发生的执行 | 当前助手草稿、运行标记、队列 | SSE 握手、当前消息快照与运行态查询 |
| 用户尚未确认提交的内容 | 输入框文字、正在编辑的目标 | 浏览器按会话保存的草稿 |

历史属于服务端会话，草稿属于用户尚未完成的输入。恢复文字不应自动再发一次；这份文字可能曾提交，但接受响应丢失，服务端已经在执行。

正在生成的消息又不同于输入草稿。前者来自 SDK 当前状态，后者来自浏览器保存。两者都被称为草稿时容易混淆，所以判断恢复问题时要明确是哪一份。

## 二 重新打开会话时，先恢复什么

当前打开流程先保存并清理旧会话的页面状态，关闭旧订阅，然后设置目标会话。浏览器先从本地存储找回文字，接着查询服务端详情，恢复历史消息、记录 ID、当前叶节点和会话树。

先恢复本地文字，是为了避免把输入恢复放在较慢的历史请求之后。用户可能已经在加载期间输入了新内容，若此时再把旧草稿整体赋回，就会覆盖新输入。

详情还提供会话执行目录，页面据此同步工作区。之后维护 SSE，并查询当前模型、上下文使用情况、队列与可用命令。历史读取、工作区同步和运行信息查询并不全部串行完成，因此页面必须分别处理这些数据的归属。

当前历史读取优先使用存活实例中的会话管理器；没有存活实例时，才根据会话文件打开记录。这样新建后尚未落盘的空会话仍能返回详情。

## 三 历史为什么是树，页面为什么只展示一条链

假设原对话是“问题一 → 回答一 → 问题二 → 回答二”。后来从回答一处分出另一个问题，新旧两条后续都需要保留。每条记录保存自己的身份与父记录关系，就能表达它基于哪一条记录继续。

当前叶节点是这次对话选择继续的位置。读取历史时，从叶节点沿父记录向上找，直到起点，再反转顺序，得到页面需要展示的当前路径。旁边分支虽然仍保存在记录里，却不会混进当前对话。

持久记录也不全是消息，还可能保存模型变化、压缩和会话信息。因此后端要把记录转换成展示消息，同时返回每条消息对应的真实记录 ID。

记录 ID 用于编辑与导航，数组位置只用于当前列表展示。分支变化后，同一数组位置可能变成另一条消息；如果用下标充当永久身份，编辑动作就可能指向错误的历史节点。

记录树如何变成页面数组，见 [父链回溯与消息身份](../08-会话存储与上下文.md#三-为什么历史会成为一棵树)。将其中的记录 ID 与本节的编辑目标对应起来，再看 [消息数据模型](../06-消息状态与工具渲染.md#二-先把数据模型讲清楚)，就能区分持久记录、展示消息和生成中的内容块。

## 四 输出一半刷新，当前回答怎样继续

假设页面刷新前只显示“启动时需要”，服务端随后继续生成“先安装依赖”。浏览器内存已经清空，无法靠下一小段文本推断前面内容，因此服务端在建立事件流时提供当前助手消息快照。

快照就是当前消息的完整状态。前端先根据握手恢复运行标记，再用快照替换当前助手草稿，之后继续追加新的增量。历史负责已完成记录，快照负责正在生成的这一条消息。

服务端先安装事件监听，再读取快照，并暂存握手前到达的事件。这样接入期间的变化进入可处理范围；部分已经包含在快照里的事件会被过滤，避免重复显示。

当前并没有保存每条传输事件及其可重放序号，所以快照恢复不等于逐条补发断线期间的一切。尤其是断线期间已经结束的其他消息，不一定包含在“当前正在生成的一条消息”里。

## 五 任务在断线期间结束，会出现什么差别

自动重连时，旧页面还保留之前的运行标记。若服务端握手明确已经不再流式运行，而页面之前确认过 Agent 活跃，当前实现会清掉助手草稿，进入统一落定处理，清理活跃工具并重读历史。

刷新则建立一份新页面状态。历史查询完成后、事件监听安装前，任务可能恰好结束：第一次历史查询没包含最终回答，订阅时又没有当前流式快照，旧页面的活跃标记也不存在。当前这段窗口没有统一的恢复协议保证自动补齐。

| 场景 | 当前已有处理 | 仍要注意什么 |
| --- | --- | --- |
| 刷新时仍有当前消息 | 历史加当前快照，继续接增量 | 快照不是所有断线事件的全集 |
| 自动重连发现已结束 | 有条件地落定并重读历史 | 条件依赖旧页面曾确认运行 |
| 历史查询与订阅之间结束 | 可能缺最终记录 | 需要订阅后的统一对账 |
| 服务进程也重启 | 可以重新读取已保存历史 | 内存执行不能自动续接 |

进一步改进时，需要协调恢复查询和实时事件。如果查询发出后新消息已经到达，旧查询再整体覆盖列表，反而会删掉刚显示的新内容。为快照与事件建立共同版本，是解决这个交错的一种方案；当前只按请求序号判断查询先后，还不等于掌握了事件版本。

快照与后续事件如何衔接，继续读 [断线后的快照机制](../05-HTTP与SSE协议.md#六-断线之后-为什么还需要快照)；页面响应归属则由 [会话代次与查询顺序](../07-异步协作与恢复.md#三-切换会话-怎样挡住慢旧响应)解释。前者处理漏了什么，后者处理回来的数据还能不能写，两个机制需要一起看。

## 六 编辑旧问题，为什么要回到它的父节点

原对话是“问题一 → 回答一 → 问题二 → 回答二”。用户想把问题二改成问题二的新版本，新输入应该接在回答一后面。若只替换页面文字，SDK 仍可能处在回答二之后；下一次请求就会把旧问题和旧回答继续带进上下文。

当前编辑先取得原问题的记录 ID，再找到父记录。保存原问题 ID，是为了知道正在编辑哪条消息；保存父记录，是为了知道新输入从哪里开始。找不到有效父节点时，不能继续这条编辑路径。

当前入口还要求前面存在用户消息，因此不是所有历史消息都开放相同的编辑方式。运行中、压缩中、导航中或位置未知时，也不允许随意修改上下文位置。

### 提交编辑后的完整顺序

1. 保留编辑后的输入，确定目标父节点。
2. 请求只读预览，确认该节点能构成有效上下文。
3. 向服务端发导航命令，改变 SDK 的当前会话位置。
4. 重新读取详情，确认实际叶节点就是目标。
5. 确认后发送新问题，由 SDK 在该上下文后继续执行。

预览只负责读取目标上下文，不改变当前分支。导航才是写操作。这个区分让目标无效时可以在改变服务端之前发现问题，也避免用户只是看一眼其他分支就影响下一次提问。

## 七 导航失败为什么还要查询与回退

假设服务端已经切到目标节点，但返回确认时网络断开。浏览器只看到错误，并不知道服务端是否已改变位置。直接把前端选中状态恢复到原分支，会造成页面显示旧分支、SDK 却从新位置继续的分裂。

当前流程保存原叶节点。导航出现异常后，先重新读取实际状态；必要时发命令回到原节点，再读一次确认。如果读不到状态、回退失败，或者返回位置不符合预期，就标记为位置未确认并禁止发送，保留输入等待重新加载。

这里的回退只是恢复会话上下文位置，不会撤销文件写入。即使成功切回旧分支，磁盘可能已经包含后来工具完成的修改。重新执行旧问题时，工具读取的是此刻的文件内容，不是聊天历史时间点的文件快照。

前端禁用操作还不够，服务端同样检查执行中、压缩中和导航中等状态。导航可能等待扩展处理，期间通过互斥标记阻止另一条 prompt 或导航改变消息链，完成或失败后释放。

## 八 草稿怎样避免“发送失败后丢文字”

用户提交“检查接口”，等待时又输入“顺便看看测试”。如果失败时直接恢复旧文本，新文字会丢；如果只有输入框为空才恢复，旧文本又可能找不回来。

当前提交单独保存待确认文字。持久化时同时保存这段文字和当前输入，确认成功才释放待确认部分，失败时按“原提交在前、新输入在后”合并。切换会话后，旧操作必须通过会话身份和代次检查，才有资格修改当前草稿。

草稿按会话 ID 保存文字、更新时间和可选编辑目标。读取时过滤超过三十天的条目；损坏的数据会清理并提示；浏览器存储不可用时退到页面内存并提示一次。降级内存后只能保住当前页面，刷新恢复依赖持久化成功。

图片没有随这份草稿持久保存。编辑目标恢复时也要重新确认对应记录及父节点仍有效，不能只凭存储里有一个旧 ID 就直接导航。

这里的文字草稿与 [配置保存期间的新编辑](B06-模型配置与能力加载.md#保存期间又改了一个字段怎么办)有共同点：一次请求提交的内容与用户现在编辑的内容必须分开。文字失败后合并，配置保存后比较基线，两者不能简单复用同一种覆盖规则。

## 九 切走再回来，为什么旧请求仍要作废

A 会话第一次查询较慢，用户切到 B 再回 A，当前会话 ID 又变成 A。只比较 ID，会让第一次打开时的旧结果误入这次页面。

当前发送与多条异步操作保存会话生命周期代次，结果回来时同时比较 ID 与代次。历史查询额外比较请求序号，避免同一代里较早查询覆盖较晚查询。成功、失败和清理分支都涉及状态写入，旧错误和旧 loading 收尾也需要隔离。

这些保护已有具体实现，但不是所有异步入口都自动继承。当前打开会话的部分收尾仍只检查 ID，工作区同步又有独立请求。因此排查跨会话显示错误时，要沿实际写入点检查，不能只看到一个代次变量就认定全链路都受保护。
