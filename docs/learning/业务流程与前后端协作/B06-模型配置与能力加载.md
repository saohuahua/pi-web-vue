# B06 模型配置与能力加载

用户新增一个模型地址，测试连通后保存，再切换当前会话的模型；随后启用一个 Skill，期待 Agent 按指定方式检查工程。这些操作都出现在能力相关界面，但改变的是不同层次：配置文件、当前运行实例、指令资源或可执行扩展。

## 一 先分清四个“模型状态”

| 状态 | 表示什么 | 由什么操作改变 |
| --- | --- | --- |
| 编辑中的配置草稿 | 用户准备提交的服务商和模型信息 | 修改表单 |
| 正式模型配置 | 服务端保存的模型连接定义 | 保存配置 |
| 默认模型设置 | 创建或初始化相关运行环境时使用的偏好 | 设置默认模型 |
| 当前会话模型 | 这个 SDK 会话实际选择的模型 | 对当前会话发送切换命令 |

保存一个新模型，只是让配置中有了它，不会自动把所有会话切到它。设置默认模型与修改当前会话模型也不是同一个接口。已经存在的实例持有运行资源，什么时候刷新、选择哪一个模型，要看具体命令流程。

服务商定义连接方式和认证等信息，模型定义具体模型标识及能力。把名字填进下拉框，不表示端点真实存在或支持图片、工具调用等全部能力。

## 二 为什么先编辑草稿，再测试和保存

用户把地址改了一半时，配置通常还不可用。如果每次输入都立刻覆盖正式文件，其他会话可能读到半成品。因此表单在浏览器维护草稿，另外保存最近一次成功读取或保存的版本，供放弃编辑时恢复。

点击测试，验证的是选定模型和当前草稿组合；点击保存，才把整份配置提交给服务端。这允许用户在正式文件仍可用时尝试新地址，测试失败也可以继续修改。

### 保存期间又改了一个字段怎么办

假设用户提交地址 A，等待保存时又将输入改成 B。请求成功仅证明 A 已保存，不能把当前 B 标成已保存，也不能用返回的 A 覆盖 B。

当前表单保存提交时的快照。响应回来后，将服务端返回的规范化配置记为新的保存基线；若用户草稿期间没变，可以更新为这份正式结果；若草稿已经变化，则保留用户新输入，并根据它与保存基线的差异继续显示未保存。

这解决同一页面的“保存期间继续编辑”，没有解决两个窗口同时修改同一配置。两个窗口各自保存整份内容，仍可能后写覆盖前写。

三份配置怎样比较，见 [提交快照与保存基线](../10-模型配置与能力中心.md#保存返回时-怎样保留请求期间的新编辑)。与 [文字草稿恢复](B04-历史恢复与编辑重发.md#八-草稿怎样避免发送失败后丢文字)对照，重点看为什么“请求成功”只能确认提交时的内容，不能替后来编辑的内容做决定。

## 三 连通性测试具体测试了什么

测试请求携带待测服务商与模型草稿。后端把这份内容写进临时配置目录，让模型运行组件加载，再解析认证信息，向模型发送一个很短的回答请求。

模型请求阶段有二十秒超时设置且不自动重试。测试结束后清理临时目录，正式模型配置文件保持原状。这样测试不会先污染真正配置，再尝试恢复。

成功结果说明这份配置能完成本次短文本请求，返回的数据还包括耗时、响应状态和短文本结果。它不能同时证明长上下文、图片、工具调用及完整 Agent 任务都可用，因为测试没有覆盖这些输入。

二十秒针对实际模型请求，不是从浏览器点击起覆盖所有临时初始化步骤的整体截止时间。判断“为什么测试还在等待”时，要区分配置加载、认证解析、模型请求和响应处理。

测试失败也要按阶段理解：模型不存在是配置定位问题，没有认证信息是认证问题，模型端返回错误是请求问题，等待超过设置时间则是超时。统一显示“模型不可用”会丢失用户下一步该改什么的信息。

## 四 保存为什么要经过规范化与文件替换

服务端先检查请求包含配置对象，再整理部分字段。例如移除没有有效模型 ID 的条目，补齐合法费用配置中缺失的字段，避免表单中的半成品直接影响 SDK 加载。

处理后的配置写入临时文件，再替换正式文件。这个过程主要避免读者在写入中途读到半截 JSON。保存成功后清理模型列表缓存，让后续查询能重新取得新增或删除后的模型。

这里有三层保证需要分开：

- 表单校验帮助用户及时发现输入问题。
- 服务端规范化决定正式保存的结构，保存结果可能与原草稿有差别。
- 临时文件替换改善文件完整性，不检测两个编辑者之间的逻辑冲突。

如果要防止多窗口覆盖，需要在读取时带版本，保存时检查原版本是否仍有效，并把版本检查和写入放在同一个受控操作中。当前整份配置保存没有这套冲突协议。

## 五 切换当前会话模型怎样确认成功

用户选择新模型后，前端向当前会话发切换命令。后端先在该实例的模型运行资源中查找；没有找到时，进行一次本地刷新再查找；仍不存在则返回错误，不调用模型切换。

找到后由 SDK 完成切换，前端收到成功结果才更新当前模型显示，并进一步刷新运行信息。失败时保留原选择，避免 UI 显示模型 B，实际会话还在使用模型 A。

等待期间用户可能已切到其他会话，因此返回结果还要检查会话身份和代次。A 的切换成功不能把正在查看的 B 的模型标签改掉，旧切换失败也不应在 B 弹错误。

切换模型不表示已经生成的回答会重新计算，也不表示正在进行的远程请求可以迁移到新模型。它改变的是会话的模型选择，具体执行约束由 SDK 与当前运行状态处理。

设置默认模型则写入 SDK 设置并刷新模型列表缓存，没有遍历全部存活会话替换运行对象。看到默认设置更新后，仍应查询当前会话实际模型。

配置更新后的列表与实例差异由 [缓存与运行生效](../10-模型配置与能力中心.md#六-保存后-为什么列表与运行实例不一定立即一致)展开；实例最初如何取得这些资源见 [SDK 会话创建](../01a-认识pi-SDK与Web工作台.md#三-本项目怎样创建-sdk-会话)。把创建、保存和切换连起来，才能定位新配置究竟在哪一步还没有被读取。

## 六 Skill、扩展和插件分别增加什么能力

假设希望 Agent 按团队规则审查接口：Skill 可以描述检查步骤和判断标准；若需要调用内部接口查询数据，则需要真正的工具实现；插件可以作为分发这些资源的包。

| 资源 | 提供什么 | 对任务的直接影响 |
| --- | --- | --- |
| Skill | 任务指令和相关资料 | 告诉 Agent 怎样处理某类工作 |
| 提示模板 | 可展开的输入内容 | 减少重复组织同类要求 |
| 扩展 | 运行时代码，可接入工具、命令或钩子等机制 | 增加或改变执行行为 |
| 插件包 | 一组可安装、启用或禁用的资源 | 管理资源从哪里来、以什么范围加载 |
| 工具 | 参数契约与具体执行实现 | 真正读取文件、调用服务或执行其他动作 |

“教模型使用某个接口”和“程序已具备访问该接口的工具”是两件事。Skill 可以要求调用某个工具，但工具不存在、未加载或没有有效认证时，仅靠文字指令无法完成实际调用。

模型是否使用某项能力，还受任务内容、资源加载情况与执行规则影响。能力中心显示资源存在，不能直接推出本轮一定使用过它；实际调用要看消息和工具结果。

## 七 技能启用、项目授权和插件安装怎样生效

### 技能列表与调用开关

技能列表根据执行目录查询全局与项目资源。当前开关修改技能文件里的模型调用限制字段。后端不仅检查文件路径允许，还确认它确实是这个目录下发现的技能，避免允许根中的普通文件被当成技能随意改写。

这个开关控制技能相关加载与调用配置，不是中止正在运行的任务。修改成功说明资源文件已更新；已有会话的资源加载器和前端缓存何时重新读取，仍要按实际刷新路径确认。当前命令列表还会按会话缓存，不能用“保存成功”推断所有旧列表和运行实例已经同步。

### 扩展列表与项目信任

扩展包含可执行代码。查看列表时，应用通过目录与包声明扫描展示来源、作用域和信任状态，不需要为了显示名称先执行项目扩展。

用户信任项目时，接口把决定写入 SDK 的信任存储。保存信任决定本身不执行扩展，也没有直接重建所有存活实例。后续加载环境会结合信任信息处理项目资源。

信任项目表示允许相关项目资源进入执行流程，不代表已经对其中每个工具行为做了隔离。执行权限与具体资源来源仍需要分别理解。

### 插件安装与启停

插件动作带有来源和全局或项目作用域。服务端通过包管理逻辑处理安装、更新、启停等操作，涉及项目范围的受限操作会检查项目信任。

当前禁用主要通过配置屏蔽包的资源选择，启用再恢复默认资源选择；它与卸载包不是同一动作。包仍在磁盘上，不代表其资源当前参与加载；显示启用，也不代表已有会话已热更新为最新资源。

安装或更新可能执行第三方代码，因此它是用户主动触发的变更操作。打开能力列表只应读取资源信息，不能自动变成安装、更新或执行。

## 八 长会话为什么还要压缩上下文

用户已经讨论很多轮，模型下一次请求能够携带的材料有限。模型用 token 计量文本等内容，token 是处理单位，不等于一个汉字或一个单词。上下文窗口表示单次处理的容量，输入还要结合模型规则为输出留出空间，长历史和工具结果会占用这部分容量。

压缩由 SDK 重新组织后续模型使用的上下文，通常涉及摘要等处理。应用提供手动触发、取消和状态展示，并在相关事件后重读历史与运行信息。当前应用没有自行实现摘要算法。

历史文件、页面消息和模型实际输入是三份不同用途的数据。压缩后，旧对话仍可能在页面可见，但模型下一次使用的是经过整理的材料。页面显示完整旧历史，不能据此判断模型仍逐字记得全部内容。

统计也要分开：累计消耗统计已经发生的模型调用，包含历史分支和压缩自身记录的用量；当前窗口占用来自 SDK 的运行查询。压缩后窗口占用下降，过去已经消耗的 token 和费用不会被抵消。

压缩需要占用会话状态。当前前端禁止在压缩期间普通发送或导航，服务端接纳也会检查压缩状态，避免同一上下文同时被重组和改写。取消压缩与中止普通 Agent 执行有各自入口。

上下文整理与用量统计分别见 [压缩接入](../08-会话存储与上下文.md#六-上下文压缩-怎样接入页面)和 [累计消耗与窗口占用](../08-会话存储与上下文.md#七-前端统计-为什么要分累计消耗和窗口占用)。再联系 [历史分支](B04-历史恢复与编辑重发.md#三-历史为什么是树页面为什么只展示一条链)：切换显示路径不会抹去另一分支已经发生的模型消耗。

## 九 从“配置好了却没生效”反查具体层次

| 页面问题 | 优先检查 | 不应直接推断 |
| --- | --- | --- |
| 连通测试成功，Agent 仍失败 | 实际选择模型、工具调用能力、长请求与认证使用情况 | 一次短文本测试覆盖全部任务 |
| 新模型保存后，旧会话仍显示原模型 | 当前会话是否发过切换命令 | 保存自动切换所有会话 |
| 保存成功后仍提示未保存 | 等待期间是否继续编辑 | 保存接口一定失败 |
| 技能文件已修改，命令列表还是旧的 | 会话资源与前端列表的刷新时机 | 文件写入没有发生 |
| 插件包存在，工具却不可用 | 启停配置、作用域、信任与实例加载 | 安装等于本轮工具已注册 |
| 压缩后累计费用没下降 | 显示的是累计消耗还是当前窗口 | 压缩没有生效 |
