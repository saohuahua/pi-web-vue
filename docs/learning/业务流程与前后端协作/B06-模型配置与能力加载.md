# B06 模型配置与能力加载

用户新增一个模型地址，测试连通后保存，再切换当前会话模型；随后启用一个 Skill 让 Agent 按指定方式检查工程。这些操作都在能力界面，但改变的是不同层次：**配置文件、当前运行实例、指令资源或可执行扩展**。

## 一 先分清四个"模型状态"

| 状态 | 表示什么 | 由什么操作改变 |
| --- | --- | --- |
| 编辑中的配置草稿 | 用户准备提交的提供商和模型信息 | 修改表单（`providers`） |
| 正式模型配置 | 服务端保存的模型连接定义 | 保存配置（`models.json`） |
| 默认模型设置 | 创建/初始化运行环境时使用的偏好 | 设置默认模型（`setDefaultModelAndProvider`） |
| 当前会话模型 | 这个 SDK 会话实际选择的模型 | 对当前会话发切换命令（`set_model`） |

> **保存一个模型 ≠ 自动切换所有会话**；设置默认模型与修改当前会话模型也不是同一个接口。已存在的实例持有运行资源，何时刷新、选哪个模型，看具体命令流程。

- 提供商定义连接方式和认证；模型定义具体标识和能力
- 把名字填进下拉框 ≠ 端点真实存在、支持图片或工具调用

## 二 为什么先编辑草稿，再测试和保存

- 地址改一半时配置通常不可用，若每次输入都立刻覆盖正式文件，其他会话会读到半成品
- 所以表单在浏览器维护草稿（`providers`），另存最近一次成功读取/保存的版本（`savedProviders`）供放弃编辑时恢复
- 点测试验证的是**草稿组合**；点保存才把整份配置提交服务端

### 保存期间又改了一个字段怎么办

用户提交地址 A，等待保存时又改成 B。请求成功只证明 **A 已保存**：

- 不能把当前的 B 标成已保存
- 也不能用返回的 A 覆盖 B

当前处理：

1. 保存时提交**快照**（`submittedProviders`）
2. 响应回来后，把服务端返回的规范化配置记为新的 `savedProviders`
3. 草稿期间没变 → 更新为正式结果
4. 草稿已变 → 保留用户新输入，据它与基线的差异继续显示未保存（`dirty`）

> 这解决同一页面的"保存期间继续编辑"，**没解决两个窗口同时修改**——两个窗口各自保存整份内容，仍可能后写覆盖前写。

三份配置怎样比较，见 [提交快照与保存基线](../10-模型配置与能力中心.md#保存返回时-怎样保留请求期间的新编辑)。对照 [文字草稿恢复](B04-历史恢复与编辑重发.md#八-草稿怎样避免发送失败后丢文字)：请求成功只能确认**提交时**的内容，不能替后来编辑的内容做决定。

## 三 连通性测试具体测试了什么

测试流程（`models-config/test.post.ts`）：

1. 携带待测提供商与模型草稿
2. 后端把内容写进**临时配置目录**，让模型运行组件加载
3. 解析认证信息，向模型发一个很短的回答请求
4. 结束后清理临时目录，正式配置保持原状

- 模型请求阶段 **20 秒超时**且不自动重试
- 成功 = 能完成本次短文本请求，返回耗时、响应状态和短文本结果
- **不能**同时证明长上下文、图片、工具调用及完整 Agent 任务可用（测试没覆盖这些）

> 20 秒针对**实际模型请求**，不是从点击起覆盖全部临时初始化的整体截止时间。判断"测试为什么还在等"时，要区分配置加载、认证解析、模型请求、响应处理。

> 失败按阶段理解：模型不存在 = 配置定位问题；没认证 = 认证问题；模型端返回错误 = 请求问题；超时 = 等待超限。统一显示"模型不可用"会丢失用户下一步该改什么的信息。

## 四 保存为什么要经过规范化与文件替换

服务端保存（`models-config-store.ts`）先检查配置对象，再整理字段：

- 移除没有有效 ID 的模型条目（`sanitizeModelsConfig`）
- 补齐合法费用配置缺失的字段（`normalizeModelsConfigCosts`）

然后写入临时文件、再替换正式文件（`writePrivateFileAtomicSync`），避免读者读到半截 JSON。保存成功后清模型缓存（`invalidateModelsCache`）。

**三层保证要分开**：

- 表单校验：帮用户及时发现输入问题
- 服务端规范化：决定正式保存的结构，结果可能与草稿有差别
- 临时文件替换：改善文件完整性，**不检测**两个编辑者间的逻辑冲突

> 要防多窗口覆盖，需读取时带版本、保存时检查原版本仍有效，并把版本检查和写入放在同一受控操作中。当前整份配置保存没有这套冲突协议。

## 五 切换当前会话模型怎样确认成功

切换命令（`set_model`）后端处理顺序：

1. 在该实例的模型运行资源中查找
2. 没找到 → 本地刷新一次再查
3. 仍不存在 → 返回错误，**不调用**模型切换

- 找到后 SDK 完成切换，前端收到成功结果才更新当前模型显示
- 失败保留原选择，避免 UI 显示模型 B、会话实际还在用模型 A

> 等待期间用户可能已切到其他会话，返回结果要检查**会话身份 + 代次**（`sessionGeneration`）——A 的切换成功不能改掉 B 的模型标签，旧切换失败也不应在 B 弹错误。

- 切换不重算已生成的回答，不迁移正在进行的远程请求
- 设置默认模型（`setDefaultModelAndProvider`）写入 SDK 设置并清模型缓存，**不遍历**存活会话替换运行对象——看到默认设置更新后，仍应查当前会话实际模型

配置更新后的列表与实例差异见 [缓存与运行生效](../10-模型配置与能力中心.md#六-保存后-为什么列表与运行实例不一定立即一致)。

## 六 Skill、扩展和插件分别增加什么能力

| 资源 | 提供什么 | 对任务的直接影响 |
| --- | --- | --- |
| Skill | 任务指令和相关资料 | 告诉 Agent 怎样处理某类工作 |
| 提示模板 | 可展开的输入内容 | 减少重复组织同类要求 |
| 扩展 | 运行时代码，可接入工具、命令、钩子 | 增加或改变执行行为 |
| 插件包 | 一组可安装、启用、禁用的资源 | 管理资源从哪来、以什么范围加载 |
| 工具 | 参数契约与具体执行实现 | 真正读文件、调服务或执行动作 |

> **"教模型用某接口"和"程序已具备该接口工具"是两件事**：Skill 可以要求调用某个工具，但工具不存在、未加载或没认证时，仅靠文字指令无法完成实际调用。

> 模型是否用某能力，还受任务内容、资源加载、执行规则影响。能力中心显示资源存在 ≠ 本轮一定用过它——实际调用要看消息和工具结果。

## 七 技能启用、项目授权和插件安装怎样生效

### 技能列表与调用开关

- 技能列表按执行目录查全局与项目资源（`skills.get.ts`）
- 开关修改技能文件里的模型调用限制字段（`setDisableModelInvocation`）
- 后端不仅检查文件路径允许，还确认它确实是这个目录下发现的技能，避免允许根中的普通文件被当技能改写

> 开关控制技能加载与调用配置，**不是中止正在运行的任务**。修改成功 = 资源文件已更新；已有会话的资源加载器和前端缓存何时重读，仍按实际刷新路径确认。

### 扩展列表与项目信任

- 扩展含可执行代码，列表扫描只展示来源、作用域、信任状态，**不为了显示名称先执行项目扩展**
- 信任项目时，接口把决定写入 SDK 信任存储（`ProjectTrustStore`），保存信任本身不执行扩展、不重建存活实例

> 信任项目 = 允许项目资源进入执行流程，**不代表对其中每个工具行为做了隔离**。

### 插件安装与启停

- 插件动作带来源和全局/项目作用域，服务端走包管理逻辑，项目范围的受限操作检查信任
- 禁用通过配置屏蔽包的资源选择（`setPackageDisabled`），启用恢复默认选择——**与卸载不是同一动作**

> 包仍在磁盘 ≠ 资源当前参与加载；显示启用 ≠ 已有会话已热更新为最新资源。安装/更新可能执行第三方代码，是用户主动触发的变更；打开能力列表只应读取资源信息，不能自动变成安装、更新或执行。

## 八 长会话为什么还要压缩上下文

- 模型用 token 计量文本，token 是处理单位，不等于一个汉字或单词
- **上下文窗口**表示单次处理容量，长历史和工具结果会占用它

- 压缩由 SDK 重新组织后续模型使用的上下文（摘要等），应用提供手动触发、取消和状态展示
- 应用没有自行实现摘要算法

> **历史文件、页面消息、模型实际输入是三份不同数据**：压缩后旧对话仍可在页面可见，但模型下一次用的是整理后的材料——页面显示完整旧历史，不能推断模型仍逐字记得全部。

- **累计消耗**统计已发生的模型调用（含历史分支和压缩自身用量）；**当前窗口占用**来自 SDK 运行查询
- 压缩后窗口占用下降，但过去已消耗的 token 和费用**不会被抵消**

- 前端在压缩期间禁止普通发送或导航，服务端接纳也检查压缩状态（`isCompacting`）
- 取消压缩（`abort_compaction`）与中止普通执行（`abort`）有各自入口

上下文整理与用量统计见 [压缩接入](../08-会话存储与上下文.md#六-上下文压缩-怎样接入页面) 和 [累计消耗与窗口占用](../08-会话存储与上下文.md#七-前端统计-为什么要分累计消耗和窗口占用)。

## 九 从"配置好了却没生效"反查具体层次

| 页面问题 | 优先检查 | 不应直接推断 |
| --- | --- | --- |
| 连通测试成功，Agent 仍失败 | 实际选择模型、工具调用、长请求与认证使用情况 | 一次短文本测试覆盖全部任务 |
| 新模型保存后，旧会话仍显示原模型 | 当前会话是否发过切换命令 | 保存自动切换所有会话 |
| 保存成功后仍提示未保存 | 等待期间是否继续编辑 | 保存接口一定失败 |
| 技能文件已修改，命令列表还是旧的 | 会话资源与前端列表的刷新时机 | 文件写入没发生 |
| 插件包存在，工具却不可用 | 启停配置、作用域、信任与实例加载 | 安装等于本轮工具已注册 |
| 压缩后累计费用没下降 | 显示的是累计消耗还是当前窗口 | 压缩没生效 |
