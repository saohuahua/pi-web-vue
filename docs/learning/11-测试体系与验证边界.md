# 测试体系与验证边界

对应业务流程：[一次任务的接纳与完成](业务流程与前后端协作/B02-创建会话到完成一次任务.md)。本篇把业务要求转成可控制的测试输入。队列撤回、刷新恢复和保存期间继续编辑，也分别对应[业务篇 B03](业务流程与前后端协作/B03-运行中追加与停止.md)、[B04](业务流程与前后端协作/B04-历史恢复与编辑重发.md)、[B06](业务流程与前后端协作/B06-模型配置与能力加载.md)。

> 前面的章节讲功能怎样实现，本篇接着讲怎样证明它按预期工作。从一个消息函数开始，再验证异步时序，最后检查真实页面。

## 实现思路 把设计保证转换为可控制的反例

### 先确定需要证明什么

真实模型返回一次正确答案，只说明这次输入走通了正常路径。它无法稳定证明两个请求倒序时谁应该写状态，也不能证明 HTTP 已返回时任务仍在执行。验证需要把时间顺序和外部结果变成可控制输入。

### 四个设计决定

1. **从每条设计保证反推断言。** “旧请求不能覆盖新页面”要检查最终消息和状态归属，“接受早于完成”要检查命令已返回但运行仍未结束。测试名称不替代这些断言。
2. **替换不确定的外部过程，保留被测机制。** 模型调用和网络可以用可控 Promise；验证 Vue 代理身份时保留真实响应式容器。否则测试可能因为把 reactive 换成普通数组而绕开真正的问题。
3. **用多个交错顺序检查同一个提交条件。** 旧请求先完成、后完成，以及失效后没有新请求，都可能暴露不同分支。缓存或代次测试应覆盖这些顺序，不能仅验证一条最顺利的时间线。
4. **把逻辑验证与实际展示分开记录。** 单元测试证明输入输出规则，浏览器证明事件、组件和 DOM 连通；性能测量另固定工作负载。最终结论写明覆盖哪层，便于读者知道哪些仍需现场验证。

> 本篇不仅给检查命令，还解释测试为什么这样安排。理解安排与断言的关系，才容易在面试中说明某项设计怎样被证实。

## 一 先把要证明的事情分层

“页面最后出现了答案”只能证明某次正常操作成功，不能证明旧响应、断线或失败时状态仍正确。

| 要验证的能力 | 合适层次 | 输入与输出 |
| --- | --- | --- |
| 事件组装消息 | 纯函数测试 | 事件序列 → 消息状态 |
| 会话切换隔离 | store 测试 | 请求顺序 → 最终会话数据 |
| 命令接受与完成 | wrapper 测试 | SDK 回调与 Promise → 响应和运行状态 |
| 路径访问规则 | 服务端函数测试 | 路径与允许根 → 允许或拒绝 |
| 用户可见流程 | 浏览器验收 | 点击 网络 DOM → 实际展示和操作反馈 |

项目使用 Vitest，测试主要在 `tests/`。配置了项目别名，但这不意味着普通单元测试自动运行在完整 Nuxt 浏览器环境。

> 用例数量不能代替覆盖范围。要看安排了什么输入，以及最终断言了什么。

## 二 最小测试 从事件输入得到确定状态

以正文“你好！”为例：

1. 建立助手快照。
2. 用 text_start 创建块。
3. 依次输入“你”和“好”。
4. 用 text_end 提供最终“你好！”。
5. 检查输出是否正确，原状态是否被意外改写。

这类规则不需要真实模型、网络或 DOM。reducer 独立于 Vue，能够直接运行输入输出测试。

随后再加入：

- 思考与正文同时存在。
- 工具参数分片到达。
- snapshot 替换当前消息。
- end 清理流式状态。

这些已有测试可在 [reducer 测试](../../tests/shared/lib/streaming-message.test.ts) 中查看。

## 三 异步测试 先控制时间顺序

真实模型耗时不可控，不适合用“等十几秒看结果”验证接受与完成的区别。

### 用一个可控 Promise 保持执行未完成

下面节选现有 wrapper 测试，`createWrapper` 是测试辅助函数：

```ts
let finishPrompt: () => void = () => {};
const completion = new Promise<void>((resolve) => {
  finishPrompt = resolve;
});
const wrapper = createWrapper((_text, options) => {
  options?.preflightResult?.(true);
  return completion;
});

await expect(wrapper.send({ type: "prompt", message: "hello" })).resolves.toBeNull();
expect(wrapper.isRunning()).toBe(true);
finishPrompt();
```

这段安排表达：

1. 预检已经成功。
2. 完整执行仍在等待。
3. wrapper 的命令必须能够返回。
4. 此时运行状态仍为 true。
5. 手动完成执行后，再检查结束事件和计数。

如果实现错误地等待完整 prompt，命令返回断言就不能按预期完成。

> mock 验证应用怎样处理约定。SDK 升级后，实际预检和事件契约仍需核对。

## 四 旧请求测试 要故意让结果倒序到达

先打开 A，再打开 B，却让 B 先完成：

```text
发 A → 发 B → B 返回 → A 返回
```

最后检查：

- 当前 ID 仍为 B。
- 消息、统计和相关归属没有变回 A。
- 旧页面清理没有关闭 B 连接。

现有 store 测试覆盖了部分慢旧响应、统计清理和模型切换失败。

在此基础上还应专门构造：

1. `A→B→A`，让第一次 A 最晚返回。
2. 同一会话的两个 reload 倒序完成。
3. 历史查询返回前，新 SSE 消息已经到达。
4. 旧文件请求失败时，新文件仍在 loading。

不同反例检验不同守卫，不能用 A→B 成功推导全部竞态正确。

## 五 前端测试亮点 让测试保留真实状态语义

### 用缓存测试看懂怎样安排交错

下面节选现有模型缓存测试中的一种返回顺序，result 是构造模型列表的辅助函数：

```ts
const old = Promise.withResolvers<ModelsResponse>();
const fresh = Promise.withResolvers<ModelsResponse>();
const oldRequest = loadModelsWithCache("workspace", () => old.promise);
invalidateModelsCache();
const freshLoader = vi.fn(() => fresh.promise);
const freshRequest = loadModelsWithCache("workspace", freshLoader);
fresh.resolve(result("fresh"));
await freshRequest;
old.resolve(result("old"));
await oldRequest;
expect(await loadModelsWithCache("workspace", freshLoader)).toEqual(result("fresh"));
expect(freshLoader).toHaveBeenCalledTimes(1);
```

这段测试的每个动作都服务于一个判断：

1. 两个 Promise 不自动完成，使测试拥有返回顺序的控制权。
2. invalidate 放在两次请求之间，模拟配置改变后旧请求失效。
3. 先完成 fresh，再完成 old，刻意制造旧结果最后到达。
4. 最后再读缓存，证明共享结果仍是 fresh，而不仅是某个调用者拿到了 fresh。
5. 检查 loader 次数，排除“其实又重新请求了一遍”造成的假通过。

完整用例还覆盖 old 先返回，以及失效后没有新请求的情况。三个时序共同检验 Promise 身份守卫，测试不需要真的等待缓存 TTL 或调用模型。

### 保留 Vue 代理行为

有些问题只有在真实 Vue 状态容器中才会暴露。

例如乐观消息回滚：

- 普通数组保存原对象，引用比较可能通过。
- 深响应式数组读取出的元素可能是代理。
- 如果测试把 reactive 换成普通数组，就可能漏掉真实问题。

因此测试替身应简化外部依赖，而保留被验证机制需要的语义。

具体做法：

1. 网络请求可替换为可控 Promise。
2. 模型调用可替换为事件与完成回调。
3. 若验证 Vue 引用和依赖行为，保留实际响应式容器。
4. 若验证滚动、布局或 EventSource 浏览器行为，进入真实页面。

这是选择测试边界的能力，不是把所有依赖都 mock 得越多越好。

| 已有测试方向 | 可以支持的结论 | 不能直接支持的结论 |

| 消息 reducer | 给定事件能按规则组装和清理 | 页面 Markdown 性能已优化 |

| event-stream | ReadableStream 握手和销毁时关闭 | 浏览器自动重连全链路已验证 |
| 路径规则 | 给定路径边界与部分符号链接情形 | 所有机器都执行了符号链接断言 |
| 配置持久化 | 配置规范化与保存逻辑 | 多窗口冲突已经解决 |
| 模型草稿 | 保存快照与继续编辑的 dirty 状态 | 多个独立窗口的版本冲突已经合并 |

两个需要特别准确表达的地方：

- 事件流测试名称提到前端重连，实际没有打开浏览器，它检查的是流握手与关闭。
- 符号链接测试在无法创建链接的环境可能跳过核心断言，测试进程成功不等于该场景实际执行。

当前已有发送回滚、附件快照和发送代次的测试；断线期间完成、停止请求挂起等场景，不能因邻近模块有测试就写成已解决。

## 七 真实页面沿用户流程验收

建议用同一任务走完整闭环：

1. 选择目录，创建会话。
2. 发送短文本，观察输入反馈与流式回答。
3. 发起读取文件的任务，核对参数、执行状态和结果配对。
4. 输出期间刷新或断线，检查已生成内容和最终状态。
5. 请求停止，区分点击反馈与实际终态。
6. 快速切换会话，检查消息与目录归属。
7. 从文件链接打开 Inspector，再切换文件标签。
8. 打开能力中心，编辑草稿、测试、保存或放弃，再关闭。

涉及可见 UI 变更时，还需覆盖：

- 桌面、平板和手机布局。
- 浅色、深色和减少动效状态。
- 键盘焦点、关闭与返回操作。

本轮文档整理没有代替这些运行验收，也不应把源码推导写成已实测结果。

## 八 性能怎么测 才能证明亮点

先固定输入，再比较同一环节：

| 机制 | 固定什么 | 测什么 |
| --- | --- | --- |
| 事件裁剪 | 相同原始 SDK 事件 | 序列化前后字节数 |
| Markdown 优化 | 相同长文本与 delta 节奏 | 解析次数和耗时 |
| 滚动合并 | 相同更新节奏和内容增长 | 测量与滚动调用次数 阅读行为 |
| 异步面板 | 相同入口与加载条件 | 首次加载请求 挂载时机和产物变化 |
| 文件预览 | 相同大小和类型的文件 | 读取 解析与高亮的分段开销 |

模型速度和网络抖动不应被算成前端优化收益。

优化后还要检查内容正确性：

- 按帧合并是否漏掉最后一次提交。
- 缓存是否在切换消息后返回旧数据。
- 滚动是否打断用户阅读历史。
- 大文本截断是否只减少显示，却没有减少读取内存。
