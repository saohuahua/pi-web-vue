## 用一条主线把二十多篇串起来

```text

    ↓

    ↓

    ↓ 等待业务握手（SSE 已装好监听）

    ↓

    ↓

    ↓

    ↓ 产出 SDK 事件
事件裁剪与协议转换              shared/lib/agent-event-wire.ts
    ↓

    ↓
```

## 术语统一表

同一件事在不同文档里出现过不同叫法。这一节是**权威口径**，读其他篇遇到歧义时回来查。

### 第一组：会话链路里的七个词

| 术语 | 在本项目里的准确含义 | 不要和什么混 |
| --- | --- | --- |
| **会话 session** | 一个持续存在的 Agent 会话，对应一个执行目录 + 一个 JSONL 文件 + 一个服务端运行实例 | 「界面上的对话区」只是展示区域，不是 session |
| **一次提交 / 一次 prompt** | 用户点一次发送产生的那一次输入 | 不是整轮执行 |
| **一次执行 / 一轮 run** | Agent 从开始到落定的一轮循环 | 一轮里可能包含多条消息和多次工具调用 |
| **消息 message** | 消息列表里的一项（用户、助手或工具结果） | 不是 JSONL 里的记录 |
| **记录 entry** | JSONL 文件里的一行，带自己的 `id` 与 `parentId` | 一个 entry 不一定对应界面上的一条消息；`entryIds` 与 `messages` 平行但来源不同 |
| **上下文 context** | 模型这一次请求实际收到的内容：当前分支上的消息 + 系统提示 + 工具说明 | 不是“全部历史”，也不是“界面上的消息列表” |
| **分支 branch** | 从某条记录继续展开形成的新路径，切换它等于改变下一轮从哪个节点继续 | **不是 Git 分支**，也不会撤销工具已经写进磁盘的改动 |

> 一句话记法：**会话装着多轮执行，一轮执行产生多条消息，消息在磁盘上表现为若干记录，记录决定模型的上下文，上下文决定下一轮从哪个分支继续。**

### 第二组：事件的三个层次

这三层在文档里经常被笼统地叫“事件”，但它们不是一回事。

| 层次 | 出现在哪 | 长什么样 | 谁负责 |
| --- | --- | --- | --- |
| **SDK 事件** | Pi SDK 通过 `subscribe` 回调推出 | SDK 自己的事件名，`message_update` 里可能带巨大的 `partial` 全量快照 | SDK |
| **wire 事件** | 服务端裁剪后发往浏览器 | 丢掉 `turn_start`/`turn_end`、剥掉 `partial`、把工具调用的 `id` 与 `toolName` 提到顶层 | `shared/lib/agent-event-wire.ts` 的 `toClientAgentEvent` |
| **前端状态** | chat store 里的 `messages`、`stream`、`activeTools` | 归并后的结果，不是事件的镜像 | `app/stores/chat.ts` 的 `applyEvent` |

完整的事件分发对照表见 [后端基础 README](后端基础/README.md) 的「SDK 事件 → 前端状态速查」。

### 第三组：能力与资源的五类

这五个词最容易被当成同一件事。**Pi 的扩展 API、界面上的插件包管理、MCP 是三种不同的机制。**

| 术语 | 是什么 | 当前项目做到哪一步 |
| --- | --- | --- |
| **工具 tool** | Agent 可以调用的函数，例如读文件、写文件、执行命令 | 由 SDK 提供；**项目没有注册任何自定义工具** |
| **扩展 extension** | 加载后会注册工具或钩子的模块，可以是一个文件，也可以是一个包 | 只做**静态目录扫描**与信任状态展示，不执行项目代码 |
| **技能 skill** | 用 markdown 描述的能力包，告诉 Agent 某类任务怎么做 | 提供读取与编辑 |
| **插件包 plugin / package** | 由包管理器安装的资源集合，一个包可以贡献扩展、技能、提示模板、主题四类资源 | 静态解析、安装、移除、检查更新 |
| **MCP** | 连接外部工具服务的协议 | **当前未接入**，能力中心里是空状态说明 |

> 一句容易说错的话：**“装了插件包”不等于“注册了新工具”**。包只是资源的容器，工具注册是另一条路径，而这条路当前项目没有走。

### 第四组：恢复相关的四个词

这四个词在面试里经常被混用，混用会让回答直接失真。

| 术语 | 指什么 | 当前项目 |
| --- | --- | --- |
| **重连 reconnect** | SSE 断开后浏览器自动重新建立连接 | 已实现 |
| **快照恢复 snapshot** | 建连时服务端补发当前**正在生成**的那一条消息 | 已实现，覆盖面仅限于这一条 |
| **历史回读 reload** | 从 JSONL 重新读取权威历史、分支与统计 | 已实现 |
| **事件重放 replay** | 按事件序号补发断线期间错过的事件 | **未实现**，需要服务端保存事件日志与游标 |

> 这四个词的区别决定了怎么回答“断线了会不会丢输出”：能重连、能靠快照接上当前这条、能重新读历史，**但不能补发断线期间已经结束的其他消息**。

## 六个最容易讲错的点

下面每一条都是“听起来合理、但与本项目实现不符”的说法。被追问时按右栏回答。

| 容易说成的样子 | 为什么不对 | 准确的说法 |
| --- | --- | --- |
| “断线后能完整回放事件，不会丢输出” | 服务端没有事件日志、事件序号，也没有按 `Last-Event-ID` 补发的协议 | 能重连、能用当前消息快照接上正在生成的那一条、能重读历史；**断线期间已经结束的其他消息补不回来** |
| “实现了自定义工具” | 仓库里没有工具定义、参数 schema 和执行逻辑，扩展侧只有静态扫描与包管理 | 接入了扩展与插件包的**发现和管理**，自定义工具的注册是下一步 |
| “关闭 SSR 就没有后端了” | SSR 与后端 API 是两件事；`server/api` 仍然由 Nitro 在 Node 里跑 | 页面改为浏览器渲染，**服务端接口照旧**，不需要另外起一个 Express 服务 |
| “切换会话分支就是 Git 分支” | 分支在这里指“下一轮从哪条记录继续” | 切换分支只改变模型后续看到的上下文，**不会撤销工具已经写进磁盘的改动** |
| “装了插件包就多了新工具” | 包只是资源容器，承载扩展、技能、提示模板和主题 | 安装包不等于注册工具，两条路径是分开的 |
| “请求返回成功就是任务完成了” | HTTP 返回只代表**已接受**，完整执行在后台继续 | 结束要等结束类事件；把“已接受”当成“已结束”会让运行态提前熄灭 |

## 如果没有它会怎样

每个机制都对应一类具体的坏结果。记住坏结果比记住机制名字更容易讲清楚“为什么要这么做”。

| 机制 | 去掉之后会怎样 |
| --- | --- |
| **业务握手 `connected`** | 先发 prompt 再装监听，极短回复可能在订阅建立前就生成完，前端整段丢失 |
| **提交时保存输入快照** | 等待期间新加的图片会被错发进本次任务，或者在失败清理时被误删 |
| **会话代次 `generation`** | `A → B → A` 之后，旧请求的失败会清掉新任务的运行状态和附件 |
| **历史查询序号** | 较早发出的历史查询后返回，把较新的历史整体覆盖掉 |
| **队列版本号** | 一份过期的队列快照覆盖刚收到的新队列事件 |
| **真实路径解析** | 允许 `D:/work/app` 时，`D:/work/app-secret` 因为前缀相同被误判为子目录 |
| **历史与上下文的区分** | 以为界面上能看到的消息就是模型这次收到的全部内容，忽略压缩与分支 |
| **结束事件分层** | 把“一条消息定稿”当成“整轮任务结束”，工具还在跑时就清掉了运行状态 |

> 面试里被问“为什么要加这个判断”时，先讲这张表里的坏结果，再讲实现 —— 顺序反了会显得像为了复杂而复杂。

## 读文档时的三个提醒

1. **图只表示逻辑关系**，不要把应用内的模块当成已经独立部署的服务。当前所有服务端逻辑都在同一个 Node 进程里。
2. **教学演进不代表真实开发历史。** 正文里“早期方案”“后续改动”这类叙述用于解释设计推导，真实的功能演进要看 Git 提交记录。
3. **改进建议不等于已实现功能。** 文中标注为候选改进、后续方案、尚未验证的内容，都不能当作已有成果讲。
