# C02 请求处理与后端分层

`server/api/` 下文件名就是 URL。本篇从一个最简单的健康检查开始，讲清 `defineEventHandler` 的输入输出工具，再说明本项目「薄转发层」和「业务层」的分工，最后看两种特殊响应——SSE 流和二进制文件——为什么也能从一个 handler 返回。

## 实现思路 让 API 层薄 把业务留在 utils

### 先确定需要保证什么

接口数量有二十多个，涉及会话、Agent、文件、配置。每个 handler 都塞满业务逻辑，改一处规则就要翻遍所有路由；所有逻辑都堆进一个「万能 service」，又会变成没人看得懂的大对象。所以需要一条规则：谁接请求、谁做业务、谁碰 SDK。

### 三个设计决定

1. **API 层只做「接住请求 → 校验参数 → 转给业务 → 返回结果」。** handler 负责协议层的事：取参数、设状态码、组错误体。真正的逻辑在 `server/utils/`。
2. **统一用 `{ error: string }` 表达错误，不抛框架异常。** 前端按这个结构解析，错误信息对用户可行动。这比每个接口各自定义错误格式更一致。
3. **SDK 只在业务层出现。** `server/api/` 的文件不直接 import pi SDK，SDK 的创建、复用、命令分发都在 `server/utils/rpc-manager.ts` 等业务模块里。

> 这条分层规则写在本项目 [server/api/README.md](../../../server/api/README.md) 的开头，是全仓库对后端结构的正式约定。

## 一 最小的接口 一个函数完成全部

[health.get.ts](../../../server/api/health.get.ts) 整个文件只有一行：

```ts
export default defineEventHandler(() => ({ ok: true, uptime: process.uptime() }));
```

- `defineEventHandler` 接收一个函数，函数返回的对象自动变成 JSON 响应。
- 这里不需要读参数、不需要设状态码，所以函数体最短。

> 返回一个普通对象，Nitro 会序列化成 JSON 并带上 `Content-Type: application/json`。这是 handler 最常见的返回方式。

## 二 请求里有什么 怎样取出来

真实接口需要读路径参数、查询参数和请求体。h3 提供对应工具，全部从 `event` 这个上下文对象取值。

### 1 路径参数 `getRouterParam`

动态段 `[id]` 的值：

```ts
export default defineEventHandler((event) => {
  const id = getRouterParam(event, "id")!;
  // URL /api/agent/abc123/events → id === "abc123"
});
```

### 2 查询参数 `getQuery`

`?cwd=D:/repo` 的值：

```ts
const cwd = getQuery(event).cwd;
// /api/worktrees?cwd=D:/repo → cwd === "D:/repo"
```

> `getQuery` 返回的值类型是 `unknown` 或 `string | string[]`，用前要校验。本项目 [worktrees.get.ts](../../../server/api/worktrees.get.ts) 就显式判断 `typeof cwd !== "string"` 再继续。

### 3 请求体 `readBody`

POST/PUT/PATCH 的 JSON 体：

```ts
const body = await readBody<{ cwd?: unknown }>(event);
```

> `readBody` 返回 Promise，需要 `await`。本项目对 body 字段一律先做运行时校验（`typeof body.cwd === "string"`），因为 TypeScript 的 `<T>` 只标注类型，不保证请求方真的传了合法值。

### 4 通配段 `[...path]`

`files/[...path].get.ts` 的剩余路径可能是字符串或数组，本项目收窄成段数组再处理：

```ts
function pathSegments(raw: unknown): string[] {
  const joined = Array.isArray(raw) ? raw.join("/") : String(raw ?? "");
  return joined.split("/").filter(Boolean).map((seg) => decodeURIComponent(seg));
}
```

## 三 错误怎样返回

本项目统一用 `{ error: string }` 加 HTTP 状态码，不抛框架异常。

```ts
if (!name) {
  setResponseStatus(event, 400);
  return { error: "name is required" };
}
```

| 动作 | 工具 | 含义 |
| --- | --- | --- |
| 设状态码 | `setResponseStatus(event, 404)` | 告诉浏览器这次失败的类型 |
| 组错误体 | 返回 `{ error: "..." }` | 告诉前端具体原因 |

前端封装按这个契约解析（[agent-client.ts](../../../shared/lib/agent-client.ts)）：

```ts
const body = await res.json() as { success?: boolean; data?: T; error?: string };
if (!res.ok || body.error) throw new AgentCommandError(body.error ?? `HTTP ${res.status}`, res.status);
```

> 错误体带的是「用户能据此行动」的信息。比如锁竞争映射成友好提示、文件不存在说清楚哪个路径，而不是把堆栈甩给用户。这条原则在本项目 [server/api/README.md](../../../server/api/README.md) 也有体现。

`createError` 在本项目只出现一次，绝大多数接口用上面这套手动状态码 + 错误体的方式，因为前端要的是统一结构，不是框架的默认错误页。

## 四 业务逻辑为什么不写在 handler 里

看 [sessions/[id].patch.ts](../../../server/api/sessions/[id].patch.ts)（重命名会话）的完整流程：

```ts
export default defineEventHandler(async (event) => {
  const id = getRouterParam(event, "id")!;
  const body = await readBody<{ name?: unknown }>(event);
  const name = typeof body?.name === "string" ? body.name.trim() : "";
  if (!name) { setResponseStatus(event, 400); return { error: "name is required" }; }

  const filePath = await resolveSessionPath(id);          // 业务：定位会话文件
  if (!filePath) { setResponseStatus(event, 404); return { error: "Session not found" }; }

  const wrapper = getRpcSession(id);                       // 业务：找存活实例
  if (wrapper?.isAlive()) {
    wrapper.inner.setSessionName(name);                    // 业务：内存实例改名
  } else {
    SessionManager.open(filePath).appendSessionInfo(name); // 业务：离线文件追加
  }
  invalidateSessionListCache();                            // 业务：失效列表缓存
  return { ok: true };
});
```

handler 自己做的只有三件协议层的事：取 `id`、读 body、校验 `name`。剩下的「定位文件、找实例、改名、失效缓存」全部调 `server/utils/` 的模块。

对应的业务模块分工：

| 业务模块 | 职责 |
| --- | --- |
| `rpc-manager.ts` | 会话实例的复用、命令分发、生命周期 |
| `session-reader.ts` | 会话文件扫描、路径反查、上下文构建 |
| `file-access.ts` + `path-security.ts` | 文件访问的允许根与路径校验 |
| `models-config-store.ts` | 模型配置的读写与原子替换 |
| `worktree.ts` | 项目身份与 worktree 解析 |

> 读一个 handler，先分清「协议层」和「业务层」。协议层三件事——取参数、设状态码、组错误体——几乎每个文件都一样；业务层才是这个接口真正在做什么。这个视角能让你快速理解任何新增接口。

## 五 handler 还能返回流和二进制

Nitro 的 handler 不只返回 JSON。本项目有两类特殊响应，返回的是原生 Web API 对象。

### 1 SSE 事件流

[agent/[id]/events.get.ts](../../../server/api/agent/[id]/events.get.ts) 返回 `text/event-stream`：

```ts
const stream = createAgentEventStream(abort.signal, id, sessionPromise);
return new Response(stream, {
  headers: {
    "Content-Type": "text/event-stream",
    "Cache-Control": "no-cache, no-transform",
    "Connection": "keep-alive",
    "X-Accel-Buffering": "no",
  },
});
```

- 返回 `Response` 而不是普通对象，手动指定 SSE 的响应头。
- `stream` 是一个 `ReadableStream`，服务端持续写入事件，浏览器持续接收。
- 这是「长连接」：响应不结束，连接保持打开。

> SSE 的完整语义——握手、快照、心跳——在 [05 HTTP 与 SSE](../05-HTTP与SSE协议.md) 展开。它同样是 `server/api` 下的一个普通 handler，只是返回类型特殊。

### 2 图片二进制

[files/[...path].get.ts](../../../server/api/files/[...path].get.ts) 读图片时返回二进制流：

```ts
return new Response(
  Readable.toWeb(createReadStream(filePath)) as ReadableStream<Uint8Array>,
  { headers: { "Content-Type": imageMime, /* ... */ } },
);
```

- Node 的 `createReadStream` 转成 Web `ReadableStream`，避免把大文件整个读进内存。
- 图片、SSE 流、JSON 都是同一个 handler 出口的不同返回类型。

> 判断一个接口返回什么，先看它 `return` 的是普通对象还是 `Response`。普通对象 → JSON；`Response` → 自定义响应（流、二进制、特殊头）。

## 六 一条请求的完整路径

把命令接口串起来看，从浏览器到 SDK 共三层：

```text
浏览器 fetch('/api/agent/123', { body: {type:'prompt', ...} })
   → server/api/agent/[id]/index.post.ts   薄转发：取 id、读 body
   → server/utils/rpc-manager.ts           业务：查 registry、分发命令
   → SDK AgentSession                       真正执行
```

`index.post.ts` 的存活实例分支（[节选](../../../server/api/agent/[id]/index.post.ts)）：

```ts
const existing = getRpcSession(id);
if (existing?.isAlive()) {
  return { success: true, data: await existing.send(command) };
}
```

- handler 不 import SDK，只调 `getRpcSession` 和 `send`。
- `send` 内部按 `command.type` 分发到 SDK 的 `prompt`、`abort`、`set_model` 等方法。
- 这个 `await` 等的是命令的「接受确认」，不是整轮执行结束——详细机制在 [04 Agent 服务](../04-Agent服务与生命周期.md)。
