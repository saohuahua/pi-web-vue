# C03 环境准备与首次跑通

前两篇讲清了工程和接口。这一篇把项目跑起来：先理解 `~/.pi/agent` 是什么，再配置模型，然后用一个最小程序和内置接口验证 SDK 能加载，最后从 `npm run dev` 走到第一次发送。

## 实现思路 先验证 SDK 再验证页面

### 先确定需要排除的风险

本项目最大的技术风险不是前端代码，而是 pi SDK 能不能在 Nitro 服务端正常加载——它是个纯 ESM 且内嵌 WASM 的包，打包配置不对就会报 `Cannot find module` 或 `wasm` 相关错误。

跑通顺序应该是：先让 SDK 在 Node 里能初始化，再让页面能调用它。反过来直接开页面，一旦黑屏就分不清是前端问题还是 SDK 问题。

### 三个设计决定

1. **先把模型配置和认证打通，再谈页面。** 没有可用模型，页面能打开也发不出第一条消息。配置失败是最常见的卡点。
2. **用项目自带的 `/api/sdk-check` 接口做第一道验证。** 它只验证 SDK 能加载和初始化，不涉及真实模型调用，能快速区分「加载失败」和「认证失败」。
3. **用最小 Node 程序做第二道验证。** 直接调用 SDK 发一句话，验证模型和认证真正可用，把「页面问题」和「SDK 问题」彻底分开。

> 配置内容依据 pi SDK `0.85.1` 的官方文档和本项目源码。

## 一 先认识 `~/.pi/agent`

pi 的 CLI、pi-web、以及本项目，共享同一份配置和会话文件。这个目录就是它们共同的家：

```text
~/.pi/agent/
  models.json    自定义模型提供商配置（本项目能力中心读写它）
  auth.json      通过 /login 保存的订阅或 API key 凭证
  settings.json  应用设置
  sessions/      会话文件（每个项目一个子目录，里面是 .jsonl）
  trust.json     项目信任决定
```

> 共享意味着：在 pi CLI 里配好的模型，本项目直接能用；在本项目能力中心配的模型，pi CLI 也能看到。这是本项目「生态同源」的根基，见 [PRODUCT.md](../../../PRODUCT.md)。

对首次跑通，只需要关心两件事：

1. **有没有可用的模型** —— 由 `models.json` 加认证决定。
2. **SDK 能不能加载** —— 由 Node 环境和打包配置决定。

## 二 配置一个可用模型

模型有两条来源，对应两种配置方式。

### 方式 A：内置提供商 + API key（推荐先试）

pi 内置了 Anthropic、OpenAI 等提供商。这类不需要写 `models.json`，只需提供凭证：

```bash
# 环境变量方式
export ANTHROPIC_API_KEY=sk-ant-...
```

或在 pi CLI 里用 `/login` 选择 API-key 提供商，凭证会存进 `~/.pi/agent/auth.json`。

> 哪种提供商内置、对应哪个环境变量，以官方 [providers.md](../../../node_modules/@earendil-works/pi-coding-agent/docs/providers.md) 为准。本项目的 [能力中心 Models 面板](../../../app/components/capabilities/ModelsPanel.vue) 也能在浏览器里完成同样的配置。

### 方式 B：自定义提供商（本地模型，写 models.json）

本地 Ollama、vLLM、LM Studio 之类，需要写 `~/.pi/agent/models.json`。最小示例：

```json
{
  "providers": {
    "ollama": {
      "baseUrl": "http://localhost:11434/v1",
      "api": "openai-completions",
      "apiKey": "ollama",
      "models": [
        { "id": "qwen2.5-coder:7b" }
      ]
    }
  }
}
```

- `apiKey` 对 Ollama 是占位值，但 pi 仍把它当作需要认证的模型，所以要给个假值（或用 `/login` 存一次 key）。
- 某些 OpenAI 兼容服务不支持 `developer` 角色，需要 `compat.supportsDeveloperRole: false`，细节见官方 [models.md](../../../node_modules/@earendil-works/pi-coding-agent/docs/models.md)。

本项目的能力中心提供这个文件的图形化编辑（[models-config.get.ts](../../../server/api/models-config.get.ts) 读、[models-config-store.ts](../../../server/utils/models-config-store.ts) 写），等价于手写 JSON：

- 读：`GET /api/models-config`
- 写：`PUT /api/models-config`
- 测试连通性：`POST /api/models-config/test`

> 这些接口和 pi CLI 读写的是**同一个文件**。保存时本项目会做校验、规范化并用原子替换防止写到半截 JSON，见 [10 模型配置与能力中心](../10-模型配置与能力中心.md)。

## 三 第一道验证 让 SDK 加载

启动开发服务器前，先验证 SDK 在服务端能初始化。项目自带一个专用接口 [sdk-check.get.ts](../../../server/api/sdk-check.get.ts)：

```ts
// ?cwd=<一个真实目录> 验证 pi SDK 能在 Nitro 服务端正常加载与初始化
export default defineEventHandler(async (event) => {
  const cwd = getQuery(event).cwd as string | undefined;
  const agentDir = getAgentDir();
  const settingsManager = SettingsManager.create(cwd, agentDir);
  await createAgentServicesWithRetry({ cwd, settingsManager });
  return { ok: true, agentDir };
});
```

它做的正是「初始化 SDK services」这一关键动作——创建设置管理器、加载模型运行资源。返回 `{ ok: true }` 就说明 SDK 加载成功。

操作步骤：

```bash
npm install
npm run dev
# 另开一个终端
curl "http://127.0.0.1:3000/api/sdk-check?cwd=D:/你的项目目录"
```

- 返回 `{ ok: true, agentDir: "..." }` → SDK 加载正常，进入下一道验证。
- 报错含 `wasm` / `photon` / `Cannot find module` → 检查 `nuxt.config.ts` 的 `nitro.externals.external` 里四个 pi 包名是否拼写正确。这正是 [C01](C01-Nuxt工程与Nitro服务端.md) 提过的那条 externals 配置。

> `sdk-check` 不调用模型，只验证加载。它通过不代表模型能用，但能让「SDK 加载」和「模型认证」两个问题分离。

## 四 第二道验证 发一句话

验证模型真正可用，用一个最小 Node 程序，避开页面和网络，直接调 SDK。保存为 `minimal-agent.mjs`：

```js
import {
  createAgentSession,
  SessionManager,
} from "@earendil-works/pi-coding-agent";

const cwd = process.cwd();
const { session } = await createAgentSession({
  cwd,
  tools: [],
  sessionManager: SessionManager.inMemory(cwd),
});

let answer = "";
const unsubscribe = session.subscribe((event) => {
  if (event.type !== "message_update") return;
  const update = event.assistantMessageEvent;
  if (update.type === "text_delta") answer += update.delta;
});

try {
  await session.prompt("用一句话解释什么是 Agent");
  console.log(answer);
} finally {
  unsubscribe();
  session.dispose();
}
```

运行：

```bash
node minimal-agent.mjs
```

- 打印出答案 → 模型和认证都通，可以放心进页面。
- 认证错误 → 回到第二步检查 API key 或 `/login` 是否完成。

> 这个程序用 `tools: []` 和内存会话，只验证「SDK + 模型」闭环，不写磁盘、不执行工具。它和本项目真实创建会话的区别——服务端用 `SessionManager.create` 持久化、加载真实工具——见 [00 从最小 Agent 到 Web 工作台](../00-从最小Agent到Web工作台.md#二-mvp-1-在-node-中发送一句话并取得回答)。

## 五 从页面走完第一次发送

两个验证都通过后，第一次完整操作：

1. 打开 `http://127.0.0.1:3000`。
2. 选择或输入一个项目目录，确认校验通过。
3. 新建会话，进入会话页。
4. 输入一句简单的话，比如「列出当前目录的文件」，发送。

如果这里卡住，按现象定位：

| 现象 | 先查什么 |
| --- | --- |
| 页面打不开 / 接口 404 | `npm run dev` 是否跑在 127.0.0.1:3000，`ssr: false` 下页面是否加载了 JS |
| 模型选择器是空的 | `curl "http://127.0.0.1:3000/api/models?cwd=..."` 看返回的 `modelList` 和 `modelError` |
| 发送后一直「正在思考」 | 打开浏览器开发者工具看 `/api/agent/:id/events` 的 SSE 是否收到 `connected`，再看 POST 是否返回错误 |
| 报 `Session not found` | 会话文件是否在 `~/.pi/agent/sessions/` 下，或实例是否已被回收 |

> 前两类现象对应「配置没通」，后两类对应「链路没通」。前者回第二步和第三道验证，后者进入 [05 HTTP 与 SSE](../05-HTTP与SSE协议.md) 和 [07 异步恢复](../07-异步协作与恢复.md) 排查。

## 六 一个安全提醒

本项目的接口**没有鉴权**，且 Agent 能执行任意命令。所以它只绑定 `127.0.0.1`，只供本机使用。

```ts
// nuxt.config.ts
devServer: { host: "127.0.0.1", port: 3000 },
```

> 不要把服务暴露到内网穿透或公网。对外展示用录屏或本机演示。这是不可协商的边界，见 [README](../../../README.md) 和 [PRODUCT.md](../../../PRODUCT.md)。
