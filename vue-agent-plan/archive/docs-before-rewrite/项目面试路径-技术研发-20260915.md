## 一条问题解决路径

`手动配置带来使用和观察门槛 → 将 SDK 事件接入浏览器 → 明确事件与状态契约 → 处理时序和恢复问题 → 手工验收关键流 → 补齐可复核的基线与端到端证据`

### 1. 发现问题

**已有事实**：项目目标本身就是将 pi coding agent 的会话和流式过程放入浏览器使用 E1。你确认，优先处理这个方向的信号来自手动编辑配置的痛点 E7。

**待验证推断**：手动配置之所以值得优先解决，可能是它增加了配置错误、上下文切换或观察执行过程的成本。这是合理假设，但仓库没有记录具体配置对象、用户任务或基线，不能当成已证影响。

**面试可讲**：

> 我没有把问题理解为单纯做一个聊天 UI，而是要让原本只暴露在 SDK 和本地配置中的 Agent 过程，在浏览器里可持续地观察和操作。痛点来自手动编辑配置，但我会明确说明当时没有统计耗时，所以不把它包装成效率提升指标。

**进入下一步的完成标准**：能写清一次典型任务的起点、手动动作、容易出错处和期望在网页中看到的状态。现在缺少这份记录。

### 2. 分析问题

**材料可证的技术判断**：

1. HTTP 连接已经建立不等于 SDK 会话已经可接收命令，因此前端不以 EventSource 的 `open` 作为就绪条件，而等待业务层的 `connected` 事件 E2、E4
2. 原始 `message_update` 会带较大的 `partial` 快照，直接传浏览器会造成重复数据和复杂的前端解析，因此在 shared 层把它裁为增量事件并统一工具元数据 E3
3. 刷新或重连时只等后续增量会丢失当前气泡，因此 SSE 服务在握手后发送流式快照，同时跳过快照已包含的事件以避免重复 E2、E6
4. 已完成消息和正在生成的消息不是同一种状态，前端以消息列表和流式 reducer 分离维护；停止、切换会话和 wrapper 销毁后需要重新对账 E4、E5、E6

**仍需本人确认**：这些判断中哪些由你提出，哪些来自对 pi-web 的参考实现学习。代码中的移植声明只能证明参考来源，不能证明个人技术决策的归属。

### 3. 方案取舍

| 备选 | 取舍 | 依据与边界 |
|---|---|---|
| 每次只用普通 HTTP 请求取完整结果 | 不采用 | 不能在生成期间显示文本、思考和工具进度，不满足 E1 的流式可视化目标 |
| 直接把 SDK 原始事件推给浏览器 | 不采用 | `partial` 会重复携带快照，工具元数据嵌套，前端渲染层被 SDK 内部形状绑定 E3 |
| WebSocket 承载命令和事件 | 当前未采用 | 现有实现以 HTTP POST 发命令、SSE 单向推事件 E2、E4。没有材料证明你做过 WebSocket 评估，面试中不要杜撰比较数据 |
| HTTP 命令 + 受控 SSE + 前端 reducer | 采用 | 命令和事件职责分开；通过业务握手、快照、重连和失败回滚补足 SSE 的生命周期边界 E2-E4 |

### 4. 推进解决

**用户自述可确认的行动**：你负责前端事件接入和 Vue 中的渲染落地，并完成验收 E7。

**材料可证的交付拆分**：执行计划和提交记录显示，后端会话与 SSE、前端流式聊天、工具和思考过程可视化按阶段进入项目 E5、E8。对个人项目而言，这就是可讲的推进方式，不应虚构跨团队评审或资源协调。

**已记录的阻碍**：

- 新旧路由组件的卸载和打开存在竞态，旧实例可能清空新会话状态，项目以条件关闭避免错误清理 E5
- wrapper 被空闲回收后，心跳会让前端误判连接健康，项目通过流关闭和前端重连形成双重恢复 E5、E6
- 在 SSE 就绪前提交短回复会丢首轮事件，前端调整为先握手、再发 prompt，并在失败时回滚乐观状态 E4、E5

**不可越界的表达**：如果上述问题不是你亲自定位，就说“项目后续出现并记录了这些时序问题，我负责理解并把前端状态处理接入修复”，不要说“我独立排查并主导修复”。

### 5. 验证结果

**已验证**：你确认完成了验收 E7；自动化测试覆盖事件裁剪、流式 reducer、快照和 wrapper 销毁后关闭流 E6。项目文档还记录核心闭环与阶段性验收 E8。

**归因限制**：本次未重新执行测试；仓库没有真实用户、性能基线或线上日志 E1。因此不能说“显著降低配置成本”“流式更快”或“修复了线上故障”。

**建议补齐的验收表**：在相同机器、Node 版本和模型配置下，录屏并保存结果。

| 场景 | 观察点 | 通过标准 |
|---|---|---|
| 创建会话后发送短回复 | 首个文本增量与运行态 | 消息不丢失，握手失败有错误提示且乐观消息回滚 |
| 生成中刷新或重开会话 | 当前流式气泡 | 快照恢复后不重复文本和工具调用 |
| 执行工具 | 工具名称、进度和结束态 | 执行中可见，结束后进入定稿消息 |
| 停止生成 | 运行态与活跃工具 | 收到 settled 时落定，事件缺失时 3 秒内对账恢复 |
| 切换会话 | 新旧会话消息 | 旧事件不写入新会话 |
| SDK 或配置锁竞争 | 错误可读性 | 短暂锁竞争重试，非锁错误明确暴露 |

### 6. 复盘沉淀

**材料可支持的沉淀**：

- 将 SDK 事件到浏览器事件的适配收敛到 `agent-event-wire`，避免组件直接理解 SDK 的原始事件 E3
- 将连接生命周期封装为 `AgentEventConnection`，将消息增量组装收敛到纯 reducer，分别建立单元测试 E4、E6
- 将“握手完成”“流式快照”“会话已落定”定义为业务状态，而不是误用底层网络状态 E2、E4

**适用边界**：当前产品只运行在本机，API 无鉴权且 Agent 可执行命令 E1。该模式不能直接迁移到多用户或公网场景，届时还需要认证、会话隔离、权限控制和更严格的审计。

## 面试讲述稿

> 这个项目是一个 Vue 和 Nuxt 实现的 pi coding agent 浏览器客户端。我主要负责把 pi-agent SDK 的能力通过 SSE 事件流接入前端，并做增量渲染。最初的痛点是有些 Agent 能力仍需要手动编辑配置，浏览器端缺少一个能连续观察会话、文本流、思考和工具执行的操作面。我没有把它当成普通聊天页面，因为 EventSource 连上不代表 SDK 会话已经可接收 prompt，而且刷新、切换会话和停止都会引入状态竞态。我的做法是让 HTTP POST 只负责命令，SSE 只负责事件；服务端在握手前缓冲事件、握手后发 `connected` 和当前流式快照，前端则分开维护已定稿消息和流式草稿。在发 prompt 前我等待业务握手，失败时回滚乐观消息；对 SDK 的原始事件先裁剪大快照，再把文本、思考和工具调用交给 reducer 组装。最后我按创建会话、流式回复、工具执行、停止、重连和切换会话做了手工验收，相关纯函数和流关闭行为也有测试。当前我不把结果说成效率提升，因为还没有记录手动配置的基线；下一步会用同一组任务补齐前后耗时和端到端回归证据。

## 面试官可能产生的 10 个疑问

**1. 手动编辑配置具体是什么问题，为什么值得做成浏览器端能力？**

- 为什么会问：目前只有“手动编辑配置痛点”的用户自述，缺少具体任务与影响
- 回答思路：如实说明它是立项信号 E7，不夸大为线上效率问题；再结合 E1 说明目标是把会话、流式回复和工具执行放入统一操作面
- 还需准备：写出一个真实配置对象、完成一次任务的原步骤、频率和最容易出错的环节

**2. 为什么不让前端直接调用 pi-agent SDK，而要经由服务端 SSE？**

- 为什么会问：检验边界划分和运行时约束，不是考 SSE 名词
- 回答思路：SDK 位于服务端，会话和本地文件能力不应进入浏览器产物；当前结构由服务端维护会话、HTTP 接收命令、SSE 推送事件 E2、E4。不要把“安全”扩展成已实现多用户授权
- 还需准备：确认你是否亲自做过该分层决定；准备浏览器运行环境不能直接复用 Node SDK 的具体原因

**3. 为什么 EventSource 打开后还要等待 `connected`？**

- 为什么会问：检验你是否理解网络连通与业务就绪的区别
- 回答思路：SSE 通道先立即打开，但 SDK 会话冷启动和监听器安装仍未完成；服务端在准备后发送 `connected`，前端 `ensureConnected` 后才发 prompt E2、E4
- 还需准备：能画出“打开 SSE → 收到 connected → POST prompt → message_start/update/end”的时序

**4. 刷新页面或断线重连时，为什么流式内容不会重复或丢失？**

- 为什么会问：流式系统最常见的错误是只关心新事件
- 回答思路：连接建立时发送 `streamingMessage` 快照；对已经包含在快照中的 `message_start` 和 `message_update` 去重 E2、E6。它解决的是当前流式状态恢复，不等同于全量消息历史恢复
- 还需准备：手动录一次生成中刷新并标记快照与增量的先后顺序

**5. 为什么要删除 `message_update` 中的 `partial` 字段，会不会影响前端渲染？**

- 为什么会问：检验你是否知道数据裁剪的正确性边界
- 回答思路：流式渲染只需要增量事件和工具调用元数据；`partial` 是重复的大快照，适配层提取必要字段后再传浏览器 E3。完整快照在重连场景通过独立 `message_start` 发送 E2
- 还需准备：说明 text、thinking、toolcall 三类增量各依赖哪些字段，并准备 E6 对应测试

**6. 已定稿消息和流式消息为什么要分开管理？**

- 为什么会问：检验状态模型是否能覆盖消息完成、停止和重连
- 回答思路：已定稿列表是历史事实，流式草稿是临时状态；`message_end` 到达后再定稿并清空 reducer，避免渲染重复 E4、E6
- 还需准备：准备一张状态转换图，包含 `start`、`snapshot`、`delta`、`end`、`agent_settled`

**7. 用户在握手失败或 prompt 提交失败时，界面如何恢复？**

- 为什么会问：乐观更新常造成“消息已显示但实际没发送”的假象
- 回答思路：前端先乐观追加以消除冷启动等待；握手或 POST 失败时只撤回仍在末尾的那条消息，复位运行态并显示错误 E4、提交 `edbbc5a`
- 还需准备：确认这段回滚是否由你实现；现场演示网络或服务端错误时的 UI 行为

**8. 你如何处理会话切换、wrapper 回收和 SSE 之间的竞态？**

- 为什么会问：这比“能连上 SSE”更能反映时序推理能力
- 回答思路：提交记录显示旧页面卸载可能清掉新会话，采用条件关闭 E5；wrapper 销毁时通知流关闭，使前端 onerror 触发重连，避免心跳掩盖失效连接 E5、E6。若根因不是你独立定位，要说明实际参与范围
- 还需准备：按真实经历补充首次复现、日志或断点位置，不能只背提交说明

**9. 为什么不直接使用 WebSocket，SSE 的局限是什么？**

- 为什么会问：检验方案取舍是否真实
- 回答思路：当前需求是服务端连续下推、客户端命令量小，HTTP POST + SSE 让职责更简单 E2、E4；局限是单向推送、认证和复杂双向协同能力有限。没有材料证明你做过 WebSocket 压测，不要杜撰数据
- 还需准备：说明若未来有协同编辑、高频双向控制或多用户会话，何时会重新评估 WebSocket

**10. 你如何证明这个改动真的解决了问题，而不是只是完成了功能？**

- 为什么会问：目前结果证据是手工验收和单测，尚无基线指标
- 回答思路：已完成验证包括手工验收 E7 和事件、reducer、流关闭测试 E6；坦诚目前没有用户或性能数据 E1。下一步会以固定配置任务记录原流程和网页流程的完成时长、错误次数及六类回归场景
- 还需准备：补一份脱敏验收记录或演示视频，标明环境、模型、会话状态和通过标准
